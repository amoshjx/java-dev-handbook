13 项目构建、打包与部署

围绕 Spring Boot 示例项目 fdc-webservice，从原始 javac 命令一路演进到 Maven 构建、Docker 镜像、Kubernetes 部署与 CI/CD 流水线。每一部分的产物都会被下一部分直接使用——跟着做完一遍，即掌握 Java 后端从源码到生产环境的完整链路。

默认基线：Java 21 LTS · Spring Boot 3.x · Maven 3.9+ · Docker 24+。Maven 安装见第 05 章；Spring Boot 探针与优雅停机见第 12 章；CI/CD 流水线实战见第 21 章。

本章概览

建议按顺序实操：手工构建 → Maven 打包 → 多环境与多模块 → 容器化 → JVM 容器调优 → K8s 部署 → CI/CD → 排障 → 上线清单。

预设环境：

  • JDK 21+（LTS，Spring Boot 3.x 基线）
  • Maven 3.9+ · Docker 24+
  • 可访问的 Kubernetes 集群（本地见第 05 章 WSL minikube，或 k3d/公司测试集群）
  • 镜像仓库（教程以 harbor-pro.com 为例）

从最原始的方式认识构建

在用 Maven 之前，先用最朴素的方式跑一个 Java 程序，理解构建工具到底替我们做了什么。

手工编译与运行

mkdir -p src/com/example
cat > src/com/example/Hello.java << 'EOF'
package com.example;

public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, Java build!");
    }
}
EOF

# 编译: 源码 .java -> 字节码 .class
javac -d build src/com/example/Hello.java

# 运行: 指定 classpath 和全限定类名
java -cp build com.example.Hello

手工打 JAR

cat > manifest.txt << 'EOF'
Main-Class: com.example.Hello
EOF

jar cfm hello.jar manifest.txt -C build .
java -jar hello.jar

这里要看明白几件事：

  1. Java 源码必须先编译成字节码才能运行，跨平台靠的是 JVM 而不是源码。
  2. classpath 告诉 JVM「去哪里找 class 文件」——所有依赖管理工具本质上都在解决这个问题。
  3. JAR 就是带元信息的 ZIP，MANIFEST.MF 里告诉 JVM 入口在哪。
  4. 一旦项目有几十个依赖，手工管 classpath 就不现实了——这就是 Maven 存在的原因。

Spring Boot 可执行 JAR 的结构

META-INF/MANIFEST.MF             <- 入口是 JarLauncher
org/springframework/boot/loader/ <- Spring Boot 自带的启动器
BOOT-INF/classes/                <- 你写的代码
BOOT-INF/lib/                    <- 所有依赖 jar
BOOT-INF/layers.idx              <- 分层信息 (Docker 优化用)

Spring Boot 不是把所有 class 平铺，而是用自己的 JarLauncher 在运行时加载 BOOT-INF/lib/ 下的 jar。这就是为什么不能用 java -cp 直接跑，只能用 java -jar。

依赖冲突排查

最常见的问题：NoSuchMethodError 或 ClassNotFoundException，几乎都是依赖冲突导致的。

mvn dependency:tree
mvn dependency:tree -Dverbose -Dincludes=com.fasterxml.jackson.core:jackson-databind

找到冲突后，在 pom 中排除：

<dependency>
    <groupId>some.group</groupId>
    <artifactId>some-artifact</artifactId>
    <exclusions>
        <exclusion>
            <groupId>com.fasterxml.jackson.core</groupId>
            <artifactId>jackson-databind</artifactId>
        </exclusion>
    </exclusions>
</dependency>

Maven 版本仲裁规则：

  1. 最短路径优先：依赖树中距离根节点近的版本胜出。
  2. 同距离时，先声明的胜出。
  3. 在 <dependencyManagement> 中显式锁版本，优先级最高。

多环境配置与多模块项目

配置外置化优先级

application.yml (打包在 jar 里)
  ↓
application-{profile}.yml
  ↓
外部 application.yml (jar 同目录)
  ↓
环境变量 SPRING_PROFILES_ACTIVE / SERVER_PORT
  ↓
JVM 参数 -Dspring.profiles.active=prod
  ↓
命令行参数 --spring.profiles.active=prod

实际生产环境推荐：配置文件放代码里，环境差异走环境变量。这是 11-Factor App 的核心思想，也是 K8s 时代的标准做法。Spring Boot 自动支持 SPRING_DATASOURCE_URL 这种命名映射到 spring.datasource.url。

export SPRING_PROFILES_ACTIVE=prod
export SERVER_PORT=9090
export APP_ENV=production
java -jar fdc-webservice-1.0.0.jar

多模块项目结构

fdc-platform/
├── pom.xml                   <- 父 pom (packaging=pom)
├── fdc-common/               <- 工具、DTO、常量
├── fdc-dao/                  <- 持久层
├── fdc-core/                 <- 业务逻辑
└── fdc-webservice/           <- 对外接口 (Spring Boot 启动模块，可部署)

父 pom 关键写法：

<project>
    <groupId>com.fdc</groupId>
    <artifactId>fdc-platform</artifactId>
    <version>1.0.0</version>
    <packaging>pom</packaging>

    <modules>
        <module>fdc-common</module>
        <module>fdc-dao</module>
        <module>fdc-core</module>
        <module>fdc-webservice</module>
    </modules>

    <dependencyManagement>
        <dependencies>
            <dependency>
                <groupId>com.fdc</groupId>
                <artifactId>fdc-common</artifactId>
                <version>${project.version}</version>
            </dependency>
        </dependencies>
    </dependencyManagement>
</project>

子模块（以 fdc-webservice 为例）只写 groupId 和 artifactId，版本从 dependencyManagement 取。常用命令：

mvn clean install
mvn clean install -pl fdc-webservice -am
mvn clean install -DskipTests -T 4

多模块拆分与架构分层见第 03 章、第 04 章排期。

容器化：从 Dockerfile 到镜像

反面教材

下面这份 Dockerfile 能跑，但有几个典型问题：

FROM openjdk:17
COPY target/fdc-webservice-1.0.0.jar app.jar
ENTRYPOINT ["java", "-jar", "/app.jar"]
  • openjdk:17 镜像已废弃，体积大（400MB+）。
  • 用了完整 JDK，运行时只需要 JRE。
  • 没有多阶段，镜像里残留构建过程。
  • 没考虑容器内存与 JVM 的关系；代码变化就要重打整层依赖。
  • 用 root 用户跑，安全风险。

生产级 Dockerfile（多阶段 + 分层）

# ============ 第一阶段: 构建 ============
FROM maven:3.9-eclipse-temurin-21 AS builder

WORKDIR /build
COPY pom.xml .
RUN mvn dependency:go-offline -B
COPY src ./src
RUN mvn clean package -DskipTests -B
RUN java -Djarmode=layertools -jar target/fdc-webservice-*.jar extract --destination target/extracted

# ============ 第二阶段: 运行 ============
FROM eclipse-temurin:21-jre-jammy

RUN groupadd -r app && useradd -r -g app -d /app app
WORKDIR /app

COPY --from=builder --chown=app:app /build/target/extracted/dependencies/          ./
COPY --from=builder --chown=app:app /build/target/extracted/spring-boot-loader/    ./
COPY --from=builder --chown=app:app /build/target/extracted/snapshot-dependencies/ ./
COPY --from=builder --chown=app:app /build/target/extracted/application/           ./

USER app
EXPOSE 8080

ENV JAVA_OPTS="-XX:MaxRAMPercentage=75.0 -XX:+UseG1GC -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/app/dumps/"

ENTRYPOINT ["sh", "-c", "exec java $JAVA_OPTS org.springframework.boot.loader.launch.JarLauncher"]

为什么要分层

Spring Boot 把 jar 拆成四层，Docker 镜像每一行 COPY 是一层——只要某层没变化就走缓存。把变化频率低的放前面，绝大多数 commit 只会推送 KB 级的 application 层，而不是几百 MB 的整包。

层内容变化频率
dependencies第三方稳定依赖（如 Spring Web）极低
spring-boot-loaderSpring Boot 加载器 class几乎不变
snapshot-dependenciesSNAPSHOT 版本依赖中
application业务代码和资源高

Java 镜像怎么选

镜像维护方特点
eclipse-temurinEclipse Adoptium社区主流，推荐
amazoncorrettoAWSAWS 环境首选，长期支持
bellsoft/libericaBellSoft性能优，体积小
gcr.io/distroless/java21Google极简，无 shell，安全性高

以 temurin 为例：21-jdk-jammy 是完整 JDK；21-jre-jammy 只有 JRE，适合运行环境；21-jre-alpine 体积最小但 musl libc 偶有兼容性问题。生产最稳妥的选择是 21-jre-jammy。

JVM 在容器中的考量

从传统部署转到云原生时最容易踩的坑。JVM 原理详见第 08 章。

容器感知

JDK 10 以前，JVM 看不到 cgroup 限制，会按宿主机内存算堆——容器限制 2G、宿主机 64G 时，JVM 仍可能按 16G 默认堆，直接 OOMKilled。JDK 10+ 默认开启 -XX:+UseContainerSupport，会正确读取 cgroup 限制，但默认堆只占容器内存的 25%，对 Java 应用来说太浪费。

堆大小配置

# 不推荐: 写死
java -Xmx1g -Xms1g -jar app.jar

# 推荐: 按容器内存的百分比
java -XX:InitialRAMPercentage=70.0 -XX:MaxRAMPercentage=75.0 -jar app.jar

为什么是 75% 而不是 100%？容器里除了堆，还有 Metaspace、Code Cache、Direct Buffer、线程栈、GC 开销与系统页缓存。经验值：堆占 70–80%，留 20–30% 给非堆和系统。

容器内存组成

容器 memory.usage_in_bytes (= K8s 看到的 working_set_bytes)
├── JVM 堆 (heap)          ← -Xmx 控制
├── JVM 非堆 (non-heap)
│   ├── Metaspace          ← 类元数据
│   ├── Code Cache         ← JIT 编译后代码
│   └── Direct Buffer      ← NIO 用
├── 线程栈                  ← 每个线程默认 1MB
├── GC overhead
└── Native memory

K8s 报 OOMKilled 但 Actuator 显示堆才用了 50%，八成是非堆爆了。用 jcmd <pid> VM.native_memory summary（需启动加 -XX:NativeMemoryTracking=summary）定位；持续监控 Actuator /actuator/metrics/jvm.memory.used 按 area 分组。

GC 与 Heap Dump

生产环境一定要预留 dump 能力。K8s 上配套要把 /app/dumps 挂载到 PVC，否则 Pod 重启 dump 就丢了。

JAVA_OPTS="
  -XX:+UseG1GC
  -XX:MaxGCPauseMillis=200
  -XX:MaxRAMPercentage=75.0
  -XX:+HeapDumpOnOutOfMemoryError
  -XX:HeapDumpPath=/app/dumps/
  -Xlog:gc*:/app/logs/gc.log:time,level,tags:filecount=10,filesize=10M
  -XX:NativeMemoryTracking=summary
"

信号处理与优雅停机

K8s 删 Pod 时发 SIGTERM。若 Dockerfile 写成 shell 形式的 ENTRYPOINT java -jar app.jar，实际跑的是 /bin/sh -c "java -jar app.jar"，sh 不会把 SIGTERM 转发给 java，最后变成强杀 SIGKILL。

# 写法一: exec 数组形式
ENTRYPOINT ["java", "-jar", "/app/app.jar"]

# 写法二: exec sh，让 java 替换 sh 进程
ENTRYPOINT ["sh", "-c", "exec java $JAVA_OPTS -jar /app/app.jar"]

配合 Spring Boot 的 server.shutdown=graceful，容器收到 SIGTERM 后会：停止接收新请求 → 等待进行中的请求完成（默认 30s 超时）→ 关闭线程池和连接池 → 退出。

Kubernetes 部署

下面是一份完整的 Java 应用（以 Spring Boot 为例）K8s 部署指南，结合 Harbor 镜像仓库与生产 namespace（fdc-prod）场景。建议将所有 YAML 放在 k8s/ 目录，按编号顺序 apply。

一、准备阶段

1. 构建可运行的 Jar 包

mvn clean package -DskipTests
# 产物: target/fdc-webservice-1.0.0.jar

2. 编写 Dockerfile

推荐多阶段构建 + 非 root 用户运行（此处为简化示例，单阶段直接复制 jar）：

# 使用精简基础镜像
FROM eclipse-temurin:17-jre-jammy

# 创建非 root 用户
RUN groupadd -r app && useradd -r -g app app
WORKDIR /app

# 复制 jar
COPY target/fdc-webservice-*.jar app.jar
RUN chown -R app:app /app
USER app

# 暴露端口
EXPOSE 8080

# JVM 参数通过环境变量传入，便于 K8s 调优
ENV JAVA_OPTS="-XX:+UseG1GC -XX:MaxRAMPercentage=75.0 -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/app/dumps"

ENTRYPOINT ["sh", "-c", "java $JAVA_OPTS -jar app.jar"]

关键点：用 MaxRAMPercentage 而不是 -Xmx，让 JVM 自适应 K8s 容器 memory limit。详见上文JVM 容器调优。

3. 构建并推送镜像到 Harbor

docker build -t harbor-pro.com/fdc/fdc-webservice:1.0.0 .
docker login harbor-pro.com
docker push harbor-pro.com/fdc/fdc-webservice:1.0.0

5. Deployment —— 核心部署

# 03-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: fdc-webservice
  namespace: fdc-prod
  labels:
    app: fdc-webservice
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0          # 保证滚动更新不掉容量
  selector:
    matchLabels:
      app: fdc-webservice
  template:
    metadata:
      labels:
        app: fdc-webservice
      annotations:
        prometheus.io/scrape: "true"
        prometheus.io/path: "/actuator/prometheus"
        prometheus.io/port: "8080"
    spec:
      imagePullSecrets:
        - name: harbor-cred
      containers:
        - name: fdc-webservice
          image: harbor-pro.com/fdc/fdc-webservice:1.0.0
          imagePullPolicy: IfNotPresent
          ports:
            - name: http
              containerPort: 8080
          # 环境变量：ConfigMap + Secret 注入
          envFrom:
            - configMapRef:
                name: fdc-webservice-config
            - secretRef:
                name: fdc-webservice-secret
          env:
            - name: JAVA_OPTS
              value: >-
                -XX:+UseG1GC
                -XX:MaxRAMPercentage=75.0
                -XX:InitialRAMPercentage=50.0
                -XX:+HeapDumpOnOutOfMemoryError
                -XX:HeapDumpPath=/app/dumps
                -XX:+PrintGCDetails
                -Xlog:gc*:/app/logs/gc.log:time,uptime:filecount=5,filesize=10M
            - name: POD_NAME
              valueFrom:
                fieldRef:
                  fieldPath: metadata.name
          # 资源限制 —— 关键!
          resources:
            requests:
              cpu: "500m"
              memory: "1Gi"
            limits:
              cpu: "2000m"
              memory: "2Gi"
          # 探针配置 —— Spring Boot Actuator
          startupProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            failureThreshold: 30       # JVM 启动慢，多给点时间
            periodSeconds: 10
          livenessProbe:
            httpGet:
              path: /actuator/health/liveness
              port: 8080
            initialDelaySeconds: 60
            periodSeconds: 30
            failureThreshold: 3
          readinessProbe:
            httpGet:
              path: /actuator/health/readiness
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 10
            failureThreshold: 3
          # 优雅停机
          lifecycle:
            preStop:
              exec:
                command: ["sh", "-c", "sleep 15"]   # 等流量摘除
          # 挂载 ConfigMap 中的 application.yml（可选）
          volumeMounts:
            - name: config-volume
              mountPath: /app/config
            - name: logs
              mountPath: /app/logs
            - name: dumps
              mountPath: /app/dumps
      terminationGracePeriodSeconds: 60   # 配合 preStop
      volumes:
        - name: config-volume
          configMap:
            name: fdc-webservice-config
            items:
              - key: application.yml
                path: application.yml
        - name: logs
          emptyDir: {}
        - name: dumps
          emptyDir: {}

几个 Java 部署的关键细节：

  • MaxRAMPercentage 配合 limits.memory：JVM 自动拿到 container memory 的 75%，留 25% 给 Metaspace / 直接内存 / 线程栈。
  • startupProbe：Spring Boot 冷启动可能 30s+，必须用 startupProbe，否则 liveness 会反复杀容器。
  • preStop + terminationGracePeriodSeconds：先 sleep 让 Service 摘除流量，再 SIGTERM，避免请求中断。
  • maxUnavailable: 0：滚动更新时不丢容量。

四、Java 应用在 K8s 上的避坑要点

坑解决方案
OOMKilled 频繁用 MaxRAMPercentage，memory limit 至少留 25% 给非堆
启动慢被 liveness 杀必加 startupProbe，failureThreshold 给够
滚动更新请求 502preStop sleep 15 + terminationGracePeriodSeconds: 60
GC 日志找不到挂 emptyDir 或 PVC 到 /app/logs
内存指标对不上区分 working_set_bytes (K8s) 和 JVM heap，详见JVM 容器调优
配置变更需重启ConfigMap 改完手动 rollout restart，或用 Reloader
单 Pod 节点故障全挂加 podAntiAffinity 把副本打散到不同节点

上线前自检清单

每次发版前逐项核对：

构建

  • mvn clean package 在干净环境能过
  • 单元测试覆盖率达标（团队约定值）
  • 没有 SNAPSHOT 依赖（生产版本）
  • 依赖漏洞扫描通过

镜像

  • 使用 jre 不是 jdk
  • 多阶段构建，体积 < 300MB
  • 用非 root 用户运行
  • tag 不是 latest，可追溯到 commit

JVM

  • 用 MaxRAMPercentage 而不是写死 -Xmx
  • 开启 HeapDumpOnOutOfMemoryError 并挂载到 PVC
  • GC 日志输出且滚动
  • 选定 GC 算法（G1 通常足够）

K8s

  • request == limit
  • 三种探针配齐
  • preStop sleep 配置
  • terminationGracePeriodSeconds 大于 graceful timeout + preStop
  • 副本数 ≥ 2 且配 PDB（PodDisruptionBudget）
  • 配置走 ConfigMap/Secret，不写死

可观测与发布

  • 日志输出到 stdout
  • Prometheus 抓取注解
  • 暴露 actuator 但限制访问（不要把 /env /heapdump 暴露到公网）
  • 有回滚预案
  • 灰度或金丝雀策略
  • 监控告警预设
