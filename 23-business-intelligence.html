LLM 业务引入总览

何时引入 LLM、与规则引擎/传统 ML 的边界

概要

LLM 适合：开放域语言理解/生成、非结构化文档问答、多步推理编排、自然语言接口（NL→API）。规则引擎（Drools、Easy Rules）适合确定性业务规则、可审计的 if-then、监管口径固定场景——成本低、可解释。传统 ML（分类、排序、风控模型）适合标注数据充足、指标可量化、延迟/成本需可控的预测任务。决策原则：① 能否用 SQL + 规则 + 检索解决？能则不上 LLM；② 错误代价是否可接受（客服草稿 vs 自动放款）？③ 是否有 Golden Set 可 Eval？无则先 PoC。架构师在需求基线后输出AI 可行性评估，避免“为 AI 而 AI”。

flowchart TD
    NEED[业务需求] --> Q1{规则可穷举?}
    Q1 -->|是| RULE[规则引擎/工作流]
    Q1 -->|否| Q2{有标注数据+固定指标?}
    Q2 -->|是| ML[传统 ML 模型]
    Q2 -->|否| Q3{开放语言+可容忍幻觉?}
    Q3 -->|是| LLM[LLM + RAG/Agent]
    Q3 -->|否| HYBRID[混合: 规则兜底 + LLM 辅助]

图：LLM vs 规则 vs ML 选型决策

阶段成果

  • AI 可行性评估：场景、风险等级、是否 Human-in-the-loop、替代方案对比
  • 场景清单：编号、业务域、输入输出、成功指标、数据敏感度

关键/技巧

  • 用「红队思维」问：LLM 说错话/泄露数据/被注入时业务会怎样？
  • 高合规场景默认「LLM 只产草稿，人确认后落库」。

易错点

  • 把 LLM 当搜索引擎——无 grounding 时幻觉率不可控。
  • 用 ChatGPT 演示效果直接写进 SLA，未做离线 Eval。

速记

「规则定边界，ML 算分数，LLM 补语言；先 Eval 再承诺。」

典型业务用例矩阵

客服、RAG、文档问答、抽取、Agent 工作流

概要

常见模式：
智能客服（意图识别 + 知识库 RAG + 工单升级）；
企业文档问答（制度/手册/合同）；
代码/运维助手（内部 Wiki + 日志，开发侧见第 21 章）；
结构化抽取（发票/简历/合同字段 → JSON Schema）；
Agent 工作流（查库存 → 算价 → 生成报价 → 发邮件）。
用价值 × 可行性 × 风险三维排优先级：MVP 选 1–2 个闭环场景，ROI 可度量（节省人力小时、转化率、首响时间）。

阶段成果

  • 用例矩阵：场景 × 用户 × 输入 × 输出 × 依赖数据 × 优先级 P0/P1/P2
  • 优先级路线图：PoC → 试点部门 → 全量

  • 未定义「答不上来」时的降级路径（转人工、固定话术）。

Agent 与工作流设计

单 Agent、多 Agent、Human-in-the-loop

概要

Agent（智能体）：“会思考 + 会行动 + 会反思”,能自主完成任务的 AI 执行体。 Agent核心结构：LLM + Skill/Tool + Planner + Memory + ReAct。 ReAct：Reason + Action，推理与行动。是一种让大语言模型在解决问题时边思考、边调用工具、边根据结果继续思考的框架。 单 Agent + ReAct：适合工具数 <10 的垂直场景。 多 Agent：Planner 分派专员 Agent，跨域但增延迟——架构上仅在上下文边界清晰时采用。 Human-in-the-loop：高风险动作（退款、权限变更）插入审批节点，与工作流引擎（Flowable/Camunda，见第 16 章工作流）结合：LLM 填表单 → 人审 → 执行 Tool。决策：能单不双，能审不自动；状态机记录每步 I/O 便于审计与 Eval。

  • 高风险 Tool 默认 dryRun=true 先展示计划。

「能单不双，能审不自动，状态可回放。」

规划器与控制器 (Planner)

编排 Agent 的推理与工具使用流程

规划器（Planner）与控制器（Controller）是 Agent Runtime 的「大脑调度层」：前者决定下一步做什么、调用哪个 Tool、何时结束；后者负责执行计划、校验边界、回收结果并驱动下一轮循环。LLM 本身只产出「意图」与「草案」，真正让 Agent 可落地、可审计的，是 Planner + Controller 对 ReAct 循环的编排。

1. Planner 的职责：从目标到可执行步骤

  • 任务分解：将用户自然语言目标拆成有序子步骤（如：查 Lot 状态 → 校验 Route → 预约设备 → 执行 start_step）。
  • Tool 选型：在已注册 Tool 目录中，按语义与前置条件挑选候选（见Agent Tool 设计）。
  • 停止条件：定义 maxSteps、超时、置信度阈值——防止无限推理烧 Token。
  • 多 Agent 分派：跨域场景由 Planner 将子任务路由给专员 Agent（客服 / 库存 / 审批），仅在上下文边界清晰时采用。

2. Controller 的职责：执行、校验与状态推进

  • 执行 Tool 调用：解析 LLM 的 tool_call，鉴权后调用 Java 业务 API，将结构化结果回灌模型。
  • 护栏校验：步数/预算/权限/高风险动作（Human-in-the-loop）在 Controller 层硬拦截，不依赖模型「自觉」。
  • 状态机推进：记录每步输入输出，支持回放、审计与 Eval（与Agent 工作流状态图一致）。
  • 异常与重试：Tool 失败 → 有限重试 → 降级（hold、转人工、固定话术），避免 Agent 在错误路径上死循环。
flowchart TD
    GOAL[用户目标] --> PLAN[Planner 分解与选 Tool]
    PLAN --> CTRL[Controller 校验护栏]
    CTRL -->|通过| ACT[执行 Tool / 调 LLM]
    CTRL -->|高风险| HITL[人工审批]
    HITL -->|通过| ACT
    ACT --> OBS[观察 tool_result]
    OBS --> DONE{目标达成?}
    DONE -->|否| PLAN
    DONE -->|是| RESP[生成最终响应]

图：Planner 规划、Controller 执行与 ReAct 闭环

3. 与 ReAct 的关系

ReAct（Reason + Act）是 Planner 常用的推理范式：模型先输出 Thought（为何这样做），再输出 Action（调用哪个 Tool），Controller 执行后把 Observation 写回上下文，Planner 据此决定下一轮。业务需求文档应明确：哪些步骤允许自动执行、哪些必须审批、最大循环次数。

阶段成果

  • Planner/Controller 规格：步数上限、超时、Tool 白名单、审批触发条件
  • 状态机与审计字段：每步 plan / action / observation / 耗时 / tokenUsage

关键/技巧

  • Planner 与 Tool 目录解耦——新增 Tool 只扩 schema，不改编排内核。
  • 高风险 Tool 默认 dryRun=true，先展示计划再执行。
  • 多 Agent 时由顶层 Planner 维护全局 sessionId，子 Agent 只接收裁剪后的子上下文。

延伸阅读：记忆与上下文（Planner 每轮依赖的历史）、Agent Tool 设计（Controller 调用的能力单元）。

记忆与上下文 (Memory)

维护会话历史，保障对话连贯性

记忆（Memory）负责在多次往返中保留「我们刚才聊了什么、做过哪些 Tool 调用、得到了什么结论」，让 Agent 在多轮对话里不丢线索、不重复提问、能引用前文决策。它与 RAG 不同：RAG 从企业知识库检索外部事实；Memory 维护当前会话的过程与状态。二者在 Prompt 组装时合并为 Context，但治理边界应分开设计。

1. 记忆分层

  • 工作记忆（Working Memory）：当前轮次送入模型的 messages 列表（system + 历史 user/assistant + tool 结果），受 Context Window 限制。
  • 会话记忆（Session Memory）：同一 conversationId 下的完整往返记录，持久化到 Redis/DB，支持刷新页面后续聊。
  • 长期记忆（Long-term Memory）：跨会话的用户偏好、历史工单摘要、实体画像（可选向量检索），需脱敏与 TTL 策略。
  • 程序记忆（Episodic / Tool Trace）：每步 ReAct 的 Thought-Action-Observation 链，供审计、调试与 Eval 回放。

2. 上下文窗口管理

模型 Context 有限，不能无界堆叠历史。常见策略：

  • 滑动窗口：保留最近 N 轮完整对话，更早的丢弃或摘要。
  • 摘要压缩：用较小模型将旧对话压成 session_summary，注入 System 或首条 User 消息。
  • 选择性保留：始终保留 System Prompt、最近 Tool 结果、用户明确约束（「不要换供应商」类指令）。
  • RAG 与 Memory 分工：事实查知识库；过程靠 Session Memory——避免把整段聊天塞进向量库。

3. 工程要点

  • 会话标识：conversationId 绑定 userId + tenantId，与 JWT 一致，防止串会话（见AI 与业务模块集成）。
  • 持久化与 TTL：客服场景 7–30 天；高敏场景更短或仅存摘要；合规要求下 Prompt 全文脱敏入库。
  • 并发与幂等：同一 messageId 重试返回缓存，避免重复写入 Memory。
  • Spring AI：ChatMemory / MessageChatMemoryAdvisor 抽象会话存储，可接 InMemory、Redis 或 JDBC 实现。

示例：会话记忆接口示意

// 概念示意 — 按 conversationId 读写会话
public interface SessionMemoryStore {
  List<Message> load(String conversationId, int maxTurns);
  void append(String conversationId, Message message);
  void summarizeIfNeeded(String conversationId, int tokenBudget);
}

// Planner 每轮组装 Context 时：
// system + sessionSummary + recentMessages + ragChunks + toolTrace

易错点

  • 把敏感 PII 写入长期记忆且未脱敏——违反数据治理要求。
  • 只存 user/assistant 文本，不存 tool_result——模型下一轮「忘记」已查过的订单状态。
  • 无窗口管理，长会话撑爆 Context 导致截断 System Prompt 或最新用户问题。

延伸阅读：RAG 架构（外部知识 grounding）、规划器与控制器（每轮读写 Memory 的编排方）。

RAG 架构设计

知识库、Embedding、向量库、检索与生成

概要

RAG（Retrieval-Augmented Generation，检索增强生成） 是目前大语言模型（LLM）落地企业级应用的核心技术。 简单来说，LLM 就像一个参加闭卷考试的学霸，虽然知识面广，但总有记错（幻觉）或者不知道最新消息的时候。而 RAG 就是给这个学霸一本开卷考试的参考书——先去资料库里查出相关的准确数据，再让大模型提炼、组织语言，给出回答。
RAG 链路：文档 ingest → 分块 → Embedding → 向量库 → 检索（+ rerank）→ Prompt Context → LLM 生成并强制引用来源。架构上 RAG 应作为独立能力层（RAG Platform / Knowledge Service），与业务域服务解耦：业务服务只调「问答 API」，不内嵌向量库逻辑。边界：ingest/索引归 RAG 平台；权限过滤在检索前按 tenant/role 过滤 metadata；生成层不直连业务 DB。Java 生态：Spring AI（VectorStore、DocumentReader、ChatClient）；LangChain4j。存储选型见第 03 章存储选型；与第 16 章 RBAC联动做知识库 ACL。

flowchart LR
    DOC[文档源] --> PARSE[解析分块]
    PARSE --> EMB[Embedding]
    EMB --> VDB[(向量库)]
    Q[用户问题] --> QEMB[Query Embedding]
    QEMB --> RET[Top-K 检索]
    VDB --> RET
    RET --> RERANK[可选 Rerank]
    RERANK --> CTX[Prompt Context]
    CTX --> LLM[LLM 生成]
    LLM --> ANS[答案+引用]

阶段成果

  • RAG 架构图：ingest/索引/检索/生成四层边界与数据流
  • 向量库选型 ADR：数据量、QPS、混合检索、运维成本对比
  • Chunk 策略说明：大小、重叠、metadata 规范、版本化 ingest 流程

Spring AI 示意

// 概念示意 — 检索增强问答
ChatResponse response = chatClient.prompt()
    .user(question)
    .advisors(new QuestionAnswerAdvisor(vectorStore, SearchRequest.defaults()))
    .call()
    .chatResponse();
// 返回答案时应附带 Document id / 片段供前端展示引用

关键/技巧

  • Hybrid 检索：向量 + BM25 关键词，提高专有名词命中率。
  • Chunk 带标题路径 metadata（如「财务制度/报销/第3节」）便于引用。

易错点

  • Chunk 过大塞满 Context，过小丢失语义——需 A/B chunk 策略。
  • 未做 ingest 版本化，文档更新后答案仍引用旧 chunk。

速记

「切好块、嵌好向量、检准了、答必带出处。」

业务 Prompt 设计

System Prompt、Few-shot、输出 Schema

概要

业务Prompt设计本质不是写提示词，而是在设计一套可执行的“业务控制语言 + 决策协议 + 工具使用规范”。它决定了 Agent 是“聊天模型”，还是“能跑业务的数字员工”。 业务 Prompt 的四大核心模块:[角色层] [目标层] [规则层] [工具层] 角色层：定义 Agent 在业务中的身份和职责。 目标层：明确 Agent 要达到的业务目标。 规则层：定义 Agent 在执行任务时应遵循的规则和约束。 工具层：定义 Agent 可以使用的工具和资源。 业务Prompt定义： System 定义角色、边界（如：「仅依据提供的 Context 回答，不知道则说不知道」）、语气与合规禁则；
User 传业务变量 + 用户问题；
Few-shot 示例对齐输出格式与拒答行为。结构化输出用JSON Mode / Response Schema（OpenAI structured outputs、Spring AI BeanOutputConverter）约束字段，便于 Java 反序列化进 DTO 落库。
Prompt版本化: 存 Git 或配置中心，与 Eval 集绑定——改 Prompt 必跑回归。开发侧 Prompt 技巧见第 22 章，本章强调业务语义与验收口径。

阶段成果

  • 业务 Prompt 规格：System/User 模板、Few-shot、拒答示例、版本号
  • 输出 Schema：JSON 字段定义与 Java DTO 映射表

JSON Schema 输出示例

System:
    你是一个 MES 执行 Agent，用于半导体制造系统中的 Lot / Step / Tool 操作执行。
    你的职责是：通过 MES 工具安全执行制造操作，确保所有操作符合工厂规则，不允许任何猜测或虚构数据。
    ---
    # 🎯 目标
    - 执行 Lot 的工艺流程操作（step start / hold 等）
    - 确保严格遵循 Route / Step / Tool / Recipe 规则
    - 所有事实数据必须来自工具查询
    - 防止任何非法或不合规操作
    ---
    # ⚠️ 基本规则（必须遵守）
    1. 不允许编造任何 MES 数据（Lot 状态、设备状态等）
    2. 所有关键决策必须先调用工具获取数据
    3. 未验证前禁止执行任何生产操作
    4. 必须严格按照 Route 顺序执行 Step
    5. 信息不足必须先查询工具或向用户确认
    6. 工具失败必须停止执行并报告错误
    ---
    # 🧩 核心业务对象
    - Lot：生产批次
    - Route：工艺路径（Step 顺序）
    - Step：工艺步骤（绑定设备和 Recipe）
    - Tool：设备
    - Recipe：工艺配方
    ---
    # 🔧 可用工具
    - get_lot_info(lot_id)：获取 Lot 信息
    - get_current_step(lot_id)：获取当前 Step
    - get_route(lot_id)：获取工艺路径
    - check_tool_availability(step_id)：检查设备可用性
    - validate_recipe(tool_id, recipe_id)：验证配方
    - reserve_tool(tool_id, lot_id)：预约设备
    - start_step(lot_id, step_id, tool_id, recipe_id)：开始工艺步骤
    - hold_lot(lot_id, reason)：Hold Lot
    ---
    # 🔄 执行模式（必须遵循）
    所有任务必须按以下循环执行：
    思考 → 调用工具 → 获取结果 → 再思考 → 再执行 → 最终输出
    ---
    # 🧠 决策规则
    - Lot 状态不是 READY → 不能执行
    - Step 不属于当前 Route → 停止
    - 设备不可用 → 等待或停止
    - Recipe 不匹配 → 禁止执行
    - 所有条件满足才允许 start_step
    ---
    # 🚨 异常处理
    如果工具调用失败：
    - 先重试一次
    - 仍失败 → hold lot 并报告原因
    ---
    # 📤 输出要求
    最终必须输出：
    - 当前状态总结
    - 执行了哪些工具调用
    - 最终结果（成功 / 失败原因）
输出 JSON: {"answer":"...","citations":["docId:chunkId"],"confidence":"high|medium|low","needHuman":boolean}

User CONTEXT:
    {{retrieved_chunks}}
    问题: {{user_question}}

关键/技巧

  • 拒答示例写进 Few-shot，减少「一本正经胡说」。
  • 长 System Prompt 拆「政策层 + 任务层」，便于 A/B 只改任务层。

易错点

  • Prompt 里写死今日促销——应参数化或由 Tool 查实时数据。
  • 未校验 JSON Schema，模型多字段/少字段导致解析异常。

Agent Tool 设计

与 Java 业务 API 对接、MCP 概念

概要

Agent Tool： Agent的“手脚”，是Agent可以调用的外部函数、API或脚本。 负责动作具体“怎么做”。可被模型安全调用的能力单元 Tool 分类： Retrieval Tools（检索类）只读
Action Tools（执行类）需要权限控制
Verification Tools（验证类）决策前必须调用
Planning Tools（规划类）辅助决策 Tool 结构： 1. Intent（语义）:Tool 必须“语义清晰”:Tool 名字必须表达业务意图： Tool = 动词 + 业务对象。
2. Input schema（输入结构）
3. Output schema（输出结构）
4. Preconditions（前置条件）
5. Side effects（副作用）
6. Failure modes（失败语义）

AI 数据治理

隐私、脱敏、出境与训练/推理边界

概要

数据分级：公开 / 内部 / 敏感 / 机密——决定是否可进 Prompt、是否需脱敏（手机号、身份证、薪资）。推理 vs 训练：企业 API 默认关闭「用对话改进模型」；私有化部署数据不出 VPC。出境：调用境外 API 需法务评估（个人信息保护法、行业监管）。日志：记录 Prompt/Response 摘要时脱敏，全量仅存加密审计库、短 TTL。与第 17 章安全开发联动：Prompt Injection 防护、输出过滤、租户隔离。RAG 知识库 ACL 与业务 RBAC 一致。

阶段成果

  • 数据流图：哪些字段进 LLM、留存多久、谁可访问
  • 合规检查清单：出境、PII、审计、用户告知与同意

易错点

  • 把生产全量 DB 导出做 Embedding，未做字段级过滤。
  • 在 Prompt 中粘贴客户完整合同未做权限校验。

成本、延迟与 SLO

Token 预算、缓存、流式与降级

概要

成本治理：Token 预算是第 03 章 FinOps TCO的子项，架构评审须纳入总成本表。按场景估算 QPS × 平均 Token × 单价；设 dev/staging/prod 配额与告警阈值（90% 预警、100% 熔断非 P0）。优化：意图路由（简单走 mini 模型）、Prompt 压缩、Embedding/语义缓存。延迟 SLO：流式 SSE 改善首 token 体验；同步 API 设 p99 上限。降级：模型超时 → 模板/转人工；向量库不可用 → BM25 兜底；预算熔断 → 限流。监控对接第 21 章可观测性。演进：PoC 不限预算 → 试点设软上限 → 生产硬配额 + FinOps 月报。

阶段成果

  • SLO 文档：p50/p99 延迟、可用性、首 token 时间、错误率
  • Token 预算表：场景 × 环境 × 月配额 × 告警阈值 × 负责人
  • 降级决策表：故障类型 → 降级动作 → 恢复条件（可演练）

成本治理决策表

| 场景           | 模型路由        | 预算动作              |
|----------------|-----------------|-----------------------|
| FAQ 简单意图   | mini 模型       | 占总额 ≤30%           |
| 合同抽取       | 标准模型+Schema | 按单计费，超 500/天告警|
| Agent 多步     | 标准+步数上限   | maxSteps=8 硬限制     |
| 月预算 100%    | —               | 非 P0 拒绝，P0 人工审批|

降级策略表

LLM 5xx/超时 → 重试1次 → 仍失败 → 固定话术 + 创建人工工单
向量检索空 → 扩大 K + BM25 → 仍空 → 「未找到相关规定，请联系 XX」
月 Token 达 90% 预算 → 告警；100% → 非 P0 场景拒绝服务

速记

「算清 Token 账，流式减焦虑，降级有预案。」

AI 效果评估

离线 Eval、Golden Set、幻觉检测、A/B

概要

Eval 体系是 AI 能力的质量门禁，架构上与 CI/CD 同级： Golden Set（50–200 条）+ 离线指标（Faithfulness、Citation 命中率）+ 业务 KPI（转人工率）构成三层评估。 架构产出：Eval 平台/流水线（Prompt 版本 tag → 自动跑分 → 门禁阈值 → 阻断发布）；与第 22 章 Harness Engineering衔接。无 Golden Set 不上生产；模型/Prompt/检索策略变更必跑回归。A/B 分桶看业务 KPI，非仅 ROUGE/BLEU。

阶段成果

  • Golden Set：问答对 + 期望要点 + 必含引用 + 拒答 case，版本化管理
  • Eval 门禁配置：Faithfulness ≥ 阈值、Citation 命中率、幻觉 case 零容忍
  • Eval 报告模板：版本对比、回归 diff、Go/No-Go 结论

关键/技巧

  • 从生产「转人工」会话挖掘 hard case 补进 Golden Set。
  • Eval 与 Prompt 同版本 tag，便于回滚对比。

易错点

  • 只用 BLEU/ROUGE 评 RAG——与业务正确性相关性弱。
  • Eval 集过拟合 demo 问题，上线后效果骤降。

Java 后端 LLM 集成

Spring AI、Ollama/OpenAI、异步与幂等

概要

Spring AI：统一 ChatModel、EmbeddingModel、VectorStore，配置 spring.ai.openai / spring.ai.ollama 切换供应商。Ollama：本地 dev/test；生产多选云 API 或私有化 vLLM。异步：长生成走 MQ（用户提交 → jobId → WebSocket/SSE 推送），避免阻塞 Tomcat 线程。幂等：同一 conversationId + messageId 重试返回缓存结果；写操作 Tool 带 idempotencyKey。超时、重试、熔断用 Resilience4j；密钥走第 21 章配置管理。

阶段成果

  • LLM 集成需求说明：同步/异步模式、幂等键、超时重试策略
  • 供应商选型约束：dev 本地 / prod 云 API、密钥管理要求

AI 与常见业务模块结合

RBAC、审计、日志、工作流

概要

AI 能力嵌入企业横切模块层，非孤岛：RBAC——Tool 与知识库按角色过滤；审计——model、prompt 版本、docId、tool 参数（脱敏）；日志——traceId 串联（见第 16 章日志体系）；工作流——AI 节点 + 人工节点；通知——完成发站内信。架构原则：优先在现有 BFF/领域服务加 AI Advisor，避免单独「AI 微服务」缺统一鉴权与数据权限。

AI 与业务模块集成架构（示意）

[前端] → [BFF/Gateway 鉴权]
              → [领域服务 + AI Advisor]
                   ├─ RBAC 过滤 Tool/知识库
                   ├─ 审计 AOP（model, tokenUsage）
                   ├─ 工作流（高风险 → 审批）
                   └─ 通知（完成 → 站内信）
              → [RAG Platform] / [LLM API]

关键/技巧

  • AI 会话 sessionId 关联 userId 与 tenantId，与 JWT 一致。
  • 操作审计 AOP 增加 aiModel、tokenUsage 字段。

速记

「AI 走同一套权、审、日志，别搞法外之地。」
