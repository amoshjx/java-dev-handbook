08 JVM

JVM 是 Java 工程的运行时操作系统：它把字节码装载、校验、执行、优化、分配、回收与诊断连成一条生产链路。下图按 HotSpot 五大子系统展开——类加载、运行时数据区、执行引擎、JNI 与 GC——帮助建立整体 mental model；学 JVM 不是背概念，而是能回答：对象在哪里、类为何冲突、GC 为什么停、CPU 为什么高、OOM 该拿什么证据。

图：JVM 整体架构——类加载、运行时数据区、执行引擎、JNI 与 GC

JVM 总体定位

JDK、JRE、JVM 与 Java 21 运行时口径

是什么

JVM 是执行 Java 字节码的虚拟机规范与实现，HotSpot 是主流实现；
JRE 是运行 Java 程序所需的运行时集合，包含 JVM 与标准类库；
JDK 在 JRE 基础上加入 javac、jcmd、jfr、jlink、jpackage 等开发与诊断工具。

Java 的跨平台来自“源码编译成平台无关字节码，JVM 在目标平台解释或编译成本地机器码”，不是同一个二进制机器码到处跑。

怎么用

# 确认版本、发行版、VM 与参数基线
java -version
java -XshowSettings:vm -version
jcmd <pid> VM.version
jcmd <pid> VM.flags
jcmd <pid> VM.system_properties

运行时数据区

程序计数器、栈、堆、元空间、常量池与直接内存

是什么

JVM 运行时数据区可以按线程隔离理解：程序计数器、虚拟机栈、本地方法栈是线程私有；堆、方法区、运行时常量池是线程共享。HotSpot 在 JDK 8 后用 Metaspace 作为方法区主要实现，使用本地内存而非 Java 堆。直接内存不是虚拟机规范内的数据区，但 NIO、Netty、压缩、加密和文件传输大量使用，线上内存问题必须纳入预算。

为什么

不同区域对应不同故障：栈深度导致 StackOverflowError，堆对象保活导致 Java heap space，类元数据和类加载器泄漏导致 Metaspace OOM，NIO 缓冲区导致 Direct buffer memory，线程过多可能是本地内存或 OS 线程限制耗尽。区域分清，证据才拿得准。

怎么用

# 堆与元空间摘要
jcmd <pid> GC.heap_info
jcmd <pid> VM.native_memory summary 
# 上述命令输出：Reserved（预留内存）：JVM 向操作系统申请的一张“空头支票”。表示准备占用这么多虚拟内存，但此时还没有真正分配物理内存。
            Committed（提交内存）：JVM 已经向操作系统真正“兑现”并正在占用的物理内存。排查内存泄漏和看内存大小，主要盯住 committed 的数值
            native_memory 包括： JVM运行时数据区 ， 直接内存空间
            

# NMT 需要启动时开启，生产建议预设为 summary
-XX:NativeMemoryTracking=summary
-XX:+UnlockDiagnosticVMOptions

怎么看问题

  • RSS 远大于 -Xmx：看 Direct Memory、Metaspace、线程栈、Code Cache、malloc、mmap 与 glibc arena。 RSS 是 Resident Set Size（常驻内存大小）。 为什么 Java 进程的 RSS 总是比 -Xmx 大很多？RSS 包含了整个 Java 进程的方方面面：
  • Metaspace 持续涨：看动态代理、脚本引擎、热部署、类加载器是否能被卸载。
  • 线程数异常涨：每个线程都有栈内存，-Xss 越大，可创建线程数越少。

对象在堆中的内存布局

是什么

HotSpot 对象通常由 对象头、实例数据、对齐填充组成。对象头包含 Mark Word（哈希、GC 年龄、锁状态等）和 Klass Pointer（指向类元数据）；数组对象还包含数组长度。实例数据是字段内容，字段会按布局规则重排以减少填充。对象大小通常按 8 字节对齐；启用压缩普通对象指针和压缩类指针时，64 位 JVM 可以用 4 字节引用降低内存占用。

类加载机制

加载、验证、准备、解析、初始化与双亲委派

是什么

类生命周期关键阶段是：加载（找到字节流并生成 Class 对象）、验证（保证字节码安全）、准备（为静态变量分配内存并设零值）、解析（符号引用转直接引用）、初始化（执行 <clinit>，包括静态字段赋值和 static 块）。类由“类加载器 + 类全限定名”共同确定身份，同名类被不同加载器加载，在 JVM 看来不是同一个类。

flowchart LR
    LOAD["加载"] --> VERIFY["验证"]
    VERIFY --> PREP["准备"]
    PREP --> RESOLVE["解析"]
    RESOLVE --> INIT["初始化"]
    REQ["加载请求"] --> APP["Application ClassLoader"]
    APP --> PLATFORM["Platform ClassLoader"]
    PLATFORM --> BOOT["Bootstrap ClassLoader"]
    APP -. "SPI/容器按需反向查找" .-> CHILD["线程上下文/自定义加载器"]

图：类加载阶段与双亲委派主线

为什么

双亲委派让子加载器先把请求交给父加载器，父加载不了再自己加载，保护 JDK 核心类并避免基础类重复。现实中也会“打破”或绕开委派：JDBC/JNDI 等 SPI 需要父加载器定义的接口反向发现应用实现；Tomcat 要隔离不同 WebApp；OSGi/插件系统需要模块边界；Spring Boot fat jar 需要从嵌套 jar 装载类。这些不是随意破坏规则，而是为了隔离、扩展和可部署性。

怎么用

// 查一个类来自哪个 jar、由谁加载
Class<?> type = com.example.Foo.class;
System.out.println(type.getClassLoader());
System.out.println(type.getProtectionDomain().getCodeSource().getLocation());

// 打印当前线程上下文加载器，SPI 常依赖它
ClassLoader cl = Thread.currentThread().getContextClassLoader();
while (cl != null) {
    System.out.println(cl);
    cl = cl.getParent();
}

怎么看问题

  • ClassCastException: X cannot be cast to X：优先怀疑同名类被不同 ClassLoader 加载。
  • NoSuchMethodError/NoClassDefFoundError：检查依赖冲突、运行时 classpath 与编译期不一致。
  • 热部署或插件卸载后 Metaspace 不降：看旧 ClassLoader 是否仍被线程、静态字段、ThreadLocal 或缓存引用。

字节码执行

解释执行、C1/C2、热点编译、内联、OSR 与 AOT/GraalVM

是什么

HotSpot 先解释执行字节码并收集 profile：方法调用次数、循环回边次数、分支概率、类型分布等。达到阈值后，JIT 将热点代码编译成本地机器码。C1 编译快、优化较轻，适合快速启动和分层编译前段；C2 编译慢但优化激进，适合长时间运行的热点路径。方法内联是核心优化入口，内联后才更容易做常量传播、逃逸分析、锁消除和循环优化。OSR 让正在运行的热点循环中途切入编译后的代码。

为什么

JVM 性能来自“运行时了解真实负载后再优化”。这也解释了预热、冷启动、流量切换、灰度重启、微基准测量为何重要。AOT 和 GraalVM Native Image 可以改善启动与内存占用，但会改变反射、动态代理、类加载和 profile 优化模型；GraalVM JIT 则是另一套高优化编译器路线，适合在明确收益和兼容性验证后引入。

怎么用

# 观察编译活动，预发/压测使用
-XX:+PrintCompilation
-XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining

# JFR 观察 Code Cache、Compilation、Execution Sample
jcmd <pid> JFR.start name=jit settings=profile duration=120s filename=/tmp/jit.jfr

怎么看问题

  • 刚启动延迟高：看冷代码解释执行、类加载、JIT warmup、连接池预热和缓存预热。
  • 代码改得“更抽象”后变慢：看调用层级、虚调用多态、内联失败和对象分配。
  • 微基准结果离谱：用 JMH，不要用手写 for 循环加 System.nanoTime() 当结论。

GC 基础、收集器与日志分析

从可达性与分代，到收集器选型，再到日志证据驱动调优

GC 工作原理

JVM 的 GC（垃圾回收）负责自动释放“已经没用的对象”占用的内存，避免内存泄漏和 OOM。

Java 对象主要存放在 Heap（堆）中，堆分为：

  • 新生代（Young）
  • 老年代（Old）

新创建对象先进入 Eden 区，大部分对象会很快死亡，因此 JVM 会频繁执行 Minor GC 回收新生代。存活多次 GC 的对象会晋升到 Old 区，老年代满了会触发 Major GC / Full GC。

JVM 通过可达性分析判断对象是否还能被引用：

  • 能从 GC Roots 找到 → 存活
  • 找不到 → 可回收

GC 常见算法：

  • 复制算法（新生代）
  • 标记清除
  • 标记整理（老年代）

GC 时会发生 STW（Stop The World）：

  • 所有业务线程暂停
  • Full GC 停顿时间通常最长

常见 GC 收集器：

  • Parallel GC：高吞吐
  • G1 GC：当前主流
  • ZGC：超低停顿

收集器选型对比（Java 21 视角）

收集器 典型堆 暂停目标 吞吐 适用场景 JDK 状态
Serial / SerialOld < 100 MB 单次几十~几百 ms 低 客户端、Sidecar、嵌入式、单核容器 长期可用
Parallel (PS+ParOld) ≤ 8 GB 不可控（吞吐优先） 最高 批处理、离线计算、对暂停不敏感的吞吐型服务 长期可用
G1（默认） 4 ~ 32 GB 100 ~ 200 ms（可配） 较高 绝大多数在线服务的默认选择 JDK 9+ 默认
ZGC >15 GB ~ 数 TB < 1 ms（亚毫秒） 中 大堆 + 严格尾延迟，金融撮合、低延迟交易、网关 JDK 15 GA
Generational ZGC >15 GB ~ 数 TB < 1 ms（且 CPU/内存开销显著降低） 中高 同上，分配速率高、对象朝生夕灭明显的场景 JDK 21 GA（-XX:+ZGenerational）
Shenandoah 4 GB ~ 数百 GB ~ 10 ms 量级 中 RedHat / OpenJDK 发行版的低停顿路线 JDK 12+（部分发行版）
Epsilon 任意 不回收 — 性能基线、压测、短生命任务，不能用于生产业务 JDK 11+

选型决策树（一句话版）：堆 < 8 GB 且对延迟无苛求 → G1；堆 ≥ 16 GB 或 P99 暂停要求 < 10 ms → ZGC（JDK 21 默认开启分代）；纯吞吐批处理 → Parallel；其它非默认选项必须有压测证据兜底。

常见 OOM 与排障

OOM 类型 现象 本质问题 常见原因 排查方向
Java heap space 堆内存溢出 Heap 被对象占满 大对象、内存泄漏、缓存无限增长、一次性加载数据 jmap dump + MAT、GC log 看 Full GC
GC overhead limit exceeded 系统卡顿 + OOM GC 大量运行但回收极少 内存严重不足、对象存活率高、Old Gen 压力大 看 Full GC 频率、Old Gen 是否持续高占用

JVM 参数调优

调优前的核心原则

进行调优时，应当遵循“无问题不调优”的原则，优先通过优化代码来解决性能瓶颈。
先测量，再调优：没有 GC 日志和性能指标做依据的调参都是玄学
业务场景决定策略：低延迟服务、高吞吐批处理、内存敏感应用的目标完全不同
一次只改一个参数：否则无法判断哪个参数起了作用

核心内存调优参数

内存大小的配置直接决定了 GC 的频率和耗时。
1. 堆内存（Heap）设置-Xms：设置堆的初始内存大小。-Xmx：设置堆的最大内存大小。
调优建议：必须将 -Xms 和 -Xmx 设置为相同的值（通常用内存占比参数，-XX:InitialRAMPercentage=70.0 -XX:MaxRAMPercentage=75.0）。这样可以防止 JVM 在运行过程中因为内存不足不断向操作系统申请内存、扩容或收缩，从而避免由此带来的系统性能震荡。

2. 新生代（Young Generation）设置-Xmn：直接设置新生代的大小。-XX:NewRatio：设置老年代与新生代的比例。例如 -XX:NewRatio=2 表示 老年代:新生代 = 2:1。-XX:SurvivorRatio：设置新生代中 Eden 区与单个 Survivor 区（S0/S1）的比例。默认是 8，即 Eden:S0:S1 = 8:1:1。
调优建议：高并发且对象生命周期短的业务（如 Web 接口），可适当调大新生代，让对象尽可能在 Minor GC 时被销毁，避免进入老年代。

3. 元空间（Metaspace，JDK 8 及以上）设置-XX:MetaspaceSize：触发元空间首次 Full GC 的初始阈值，而非初始大小。-XX:MaxMetaspaceSize：设置元空间的最大限制。
调优建议：默认情况下元空间上限是无限制的（受限于物理内存），生产环境务必显式设置 -XX:MaxMetaspaceSize，防止因动态类加载过多导致本地内存耗尽。通常建议设为 256M 或 512M。

4. 线程栈（Stack）设置-Xss：设置每个线程栈的字节大小。
调优建议：默认通常为 1M。若无深层递归或复杂调用，可调小至 256K 或 512K，从而在有限的物理内存中允许创建更多的并发线程。

垃圾收集器（GC）选择参数

垃圾收集器 启用参数 适用场景 调优特点
Parallel GC -XX:+UseParallelGC 后台批处理、科学计算、离线任务等场景。
  • 以高吞吐量为核心目标
  • 允许较长 STW（Stop-The-World）停顿
  • 多线程并行回收
  • 适合 CPU 资源较充足的环境
G1 GC -XX:+UseG1GC JDK 8 / 17 / 21 主流生产环境，大内存服务端应用。
  • 面向低停顿设计
  • 支持通过： -XX:MaxGCPauseMillis 控制停顿目标
  • Heap 划分为多个 Region
  • 同时兼顾吞吐量与响应时间
  • 目前企业应用最主流 GC
ZGC -XX:+UseZGC JDK 11+（JDK 15+ 正式商用），超大堆内存、低延迟系统。
  • 目标是极低延迟
  • GC 停顿通常控制在： < 10ms
  • 支持 TB 级大内存
  • 采用并发标记 / 并发转移
  • 适用于金融、实时交易、在线游戏等低延迟场景

异常诊断与故障排查参数

在生产环境中，必须配置自动捕获和定位 OOM（内存溢出）的参数。
-XX:+HeapDumpOnOutOfMemoryError ：当发生 OOM 异常时，自动生成堆转储（Heap Dump）快照文件。
-XX:HeapDumpPath=/path/to/dumps/ ：指定生成的 Dump 文件存放路径。
-XX:+PrintGCDetails（JDK 8）/ -Xlog:gc*（JDK 9+） ：开启并输出详细的 GC 日志，用于分析 GC 频次和停顿时间。

落地调优标准流程

JVM 调优不推荐盲目修改参数，通常需要遵循以下闭环流程：
            
监控数据 (jstat/Prometheus) ➔ 发现异常 (Full GC频繁/停顿长) ➔ 导出分析 (jstack/jmap/MAT) ➔ 针对性调整参数 ➔ 压测验证
            
1. 收集基准数据：通过压测工具（如 JMeter）模拟真实业务流量。
            
2. 观察监控指标：利用 jstat -gcutil  1000 观察各内存区的增长速度与 GC 耗时。
            
3. 定位核心矛盾：
| 现象            | 调优方向              |
| ------------- | ----------------- |
| Full GC 频繁    | 增大堆 / 检查内存泄漏 /如果由于大对象直接进入老年代导致，可调整年轻代晋升老年代的阈值 (-XX:PretenureSizeThreshold)     |
| Minor GC 频繁   | 增大 Young 区        |
| STW 停顿长       | 换 G1/ZGC          |
| OOM Heap      | 增大 `-Xmx`         |
| OOM Metaspace | 增大 MetaSpace      |
| CPU 高         | GC 线程过多 / Full GC |
            
4. 调整并对比：每次只调整 1~2 个参数，重新压测，对比吞吐率和接口响应时间（RT）的变化，直到达到性能最优平衡点。
            
5.生产灰度：先在一个 pod 上验证再全量

K8s 容器环境的特殊考虑

          JDK 8u191+ 和 JDK 10+ 已经能自动识别容器内存限制，但有几个点要注意：
          bash-XX:+UseContainerSupport                # JDK 10+ 默认开启
          -XX:MaxRAMPercentage=75.0               # JVM 最大占容器内存的 75%
          -XX:InitialRAMPercentage=75.0
          -XX:MinRAMPercentage=75.0

性能诊断工具

jps、jcmd、jstat、jmap、jstack、JFR、VisualVM、async-profiler 与 Arthas

是什么

jps：查看进程
jstat：动态监控 GC 情况（怎么判断 Full GC 是不是太频繁？）
jinfo：实时查看和修改 JVM 参数
jstack：打印线程堆栈（排查死锁与 CPU 飙高的利器）
jmap：生成内存快照（Dump 文件）
JFR：低开销事件采样
VisualVM：本地可视化
async-profiler：CPU、wall、alloc 火焰图
Arthas：线上动态观察方法调用、watch、trace

怎么用

jps -lv
jcmd <pid> VM.flags
jcmd <pid> Thread.print
jcmd <pid> GC.heap_info
jcmd <pid> GC.class_histogram
jstat -gcutil <pid> 1000 10
jcmd <pid> JFR.start name=debug settings=profile duration=300s filename=/tmp/app.jfr
./profiler.sh -d 60 -e cpu -f /tmp/cpu.html <pid>
./profiler.sh -d 60 -e alloc -f /tmp/alloc.html <pid>

为什么

排障不是工具秀，而是最小干扰地补齐证据链。CPU 高优先火焰图/JFR；延迟抖动看 GC、safepoint、线程阻塞、下游调用；内存泄漏看 histogram、heap dump、MAT dominator；死锁看线程栈；类冲突看 classpath 和 ClassLoader；线上临时观察才用 Arthas，且要控制命令影响面。

怎么看问题

  • jmap -dump、直方图和 Arthas watch 都可能增加停顿或开销，先在预发验证。
  • 容器内 attach 需要同用户、权限、PID namespace 和工具镜像支持。
  • 单次线程栈可能误导；CPU 高时连续取 3~5 次，或用 profiler 看时间占比。

线上排障流程

CPU 飙高、内存泄漏、频繁 Full GC、延迟抖动与死锁

是什么

线上 JVM 排障的目标是快速止血、保留证据、定位根因、验证修复。不要一上来重启或改参数；除非业务已不可用，否则先抓时间线：发布、流量、错误率、P95/P99、CPU、内存、GC、线程、下游依赖和容器事件。

怎么用

# CPU 飙高：找热点线程与方法
jcmd <pid> Thread.print > threads-1.txt
./profiler.sh -d 60 -e cpu -f cpu.html <pid>

# 内存泄漏：先轻后重
jcmd <pid> GC.class_histogram > histo.txt
jcmd <pid> GC.heap_dump /tmp/app.hprof

# 死锁/阻塞
jcmd <pid> Thread.print -l > deadlock.txt

# 延迟抖动
jcmd <pid> JFR.start name=latency settings=profile duration=180s filename=/tmp/latency.jfr

为什么

CPU 高不一定是业务代码，可能是 GC、锁自旋、序列化、正则、日志、加密或内核态；内存涨不一定是堆，可能是 Direct、Metaspace 或线程；Full GC 不一定靠加堆解决，可能是泄漏、Humongous 或元空间；接口抖动不一定在 JVM，可能是下游超时、连接池耗尽、DNS、磁盘或 safepoint。

怎么看问题

  • CPU：top -H 找线程 id，转十六进制对线程栈 nid，配合火焰图确认时间占比。
  • 内存：RSS、heap used、GC 后 used、direct、metaspace、thread count 分开看。
  • Full GC：看触发原因、GC 后是否下降、是否伴随 promotion/evacuation failure。
  • 延迟抖动：对齐请求 trace、GC/safepoint、线程池队列、连接池指标和下游耗时。
  • 死锁：线程栈若明确 deadlock，先止血隔离流量，再修复锁顺序或缩小锁范围。

生产配置建议

上线前 JVM baseline 与 checklist

是什么

  • 明确 JDK 发行版、Java 21 LTS 小版本、基础镜像和是否保留诊断工具。
  • 明确容器 request/limit、堆比例、Direct/Metaspace 上限、线程池上限和 dump 目录容量。
  • 默认开启 GC 滚动日志、OOM dump、hs_err、关键 JVM/Micrometer 指标。
  • 为每个服务记录 JVM 参数基线、压测报告、SLO、变更历史和回滚方式。

为什么

好的 JVM 配置不是“永不出问题”，而是资源边界可预测、故障时有证据、变更后能对比、超限时能被告警发现。配置要和应用画像绑定：CPU 密集、IO 密集、大堆低延迟、批处理、网关、消息消费者的参数基线不应相同。

怎么用

  • 压测门禁：记录 QPS、P95/P99、错误率、CPU、RSS、GC pause、GC CPU 占比、分配速率。
  • 告警门禁：堆使用率、GC 后老年代占用、Full GC 次数、线程数、Direct/Metaspace、容器 OOMKilled。
  • 变更门禁：JDK 升级、GC 切换、堆比例调整必须灰度，并保留至少一个高峰周期对比。

怎么看问题

  • 只设 -Xmx 不设非堆预算，是容器 OOM 的常见源头。
  • 只看平均延迟会掩盖 GC、锁和下游导致的尾延迟。
  • 没有 dump 目录容量和权限，OOM 自动留证会失败。

章末实战闭环

JVM 治理落地清单

输入

  • 服务画像：CPU/IO 类型、QPS、对象分配速率、堆大小、延迟 SLO、启动时间要求。
  • 部署画像：JDK 版本、容器 limit、实例规格、Pod 数、镜像是否带 JDK 工具。
  • 历史证据：GC 日志、JFR、heap dump、线程栈、故障复盘、发布变更记录。

输出

  • JVM 参数基线：堆比例、Metaspace、Direct、GC、GC 日志、OOM 留证、NMT 策略。
  • 可观测面板：GC pause、GC count、heap after GC、RSS、direct、metaspace、threads、class count。
  • 排障 Runbook：CPU、高延迟、OOM、Full GC、死锁、类冲突的取证命令和升级路径。
  • 压测报告：变更前后延迟分位、吞吐、GC、CPU、内存和错误率对比。

验收标准

  • 高峰压测下 GC 暂停、GC CPU 占比和 P99 延迟满足 SLO。
  • OOM、崩溃、Full GC、线程暴涨都有自动留证和告警。
  • JDK/GC/参数变更可灰度、可观测、可回滚。

失败信号

  • 参数来自复制粘贴，没有说明服务画像和压测依据。
  • 只看堆，不看 RSS、Direct、Metaspace、线程和容器事件。
  • 故障后只有重启动作，没有保留 GC 日志、dump、JFR 或线程栈。
