20 工程化·DevOps·CI/CD

本章回答两件事：为什么要搞（避免协作与上线的常见陷阱），以及怎么落地（从规范、CI、CD 到监控闭环）。示例项目 fdc-webservice（Java 21 · Spring Boot 3.x · Maven 3.9+）；构建与 K8s 细节见第 13 章，测试与质量见第 18 章、第 19 章。

本章概览

建议阅读顺序：为什么要搞 → 怎么落地（工程化 → 持续集成 → 持续交付/部署 → DevOps 与监控）→ 极简流水线总结。

一、为什么要搞这些？（Why）

工程化、DevOps、CI/CD 不是给团队「加流程负担」，而是用工具和约定，把重复、易错、难协作的事交给机器和统一标准。如果不搞，Java 项目很容易掉进下面四类典型困境。

四大地狱

1.「在我电脑上好好的」地狱

协作时，因为 JDK 版本、Maven 依赖、操作系统环境不一致，代码在你这里能跑，到别人那里就报错。根因是环境不可复现：有人用 JDK 17、有人用 21；有人本地 lib 里塞了 JAR，有人没同步；pom.xml 各写各的，依赖版本漂移。

对策方向：统一构建工具与 JDK（见第 05 章）、禁止手工拷 JAR、用 mvnw 或锁定 Maven 版本，让「能构建」这件事只依赖 Git 仓库，不依赖某台笔记本。

2. 手工部署地狱

每次上线都要手动打包、传 FTP、连服务器、改配置、重启。手一抖删错目录，或漏配一个环境变量，直接导致线上事故。发布窗口越长，人为失误概率越高。

对策方向：同一套制品（JAR / 镜像）由 CI 产出，CD 用脚本或 K8s 滚动更新部署，配置与代码分离（见下文配置中心化）。

3. 测试滞后地狱

代码写完了一直不测，直到上线前夕才交给 QA。测出一堆 Bug，开发只能熬夜修，越修越乱，主干长期处于「不可发布」状态。

对策方向：每次提交触发 mvn test，覆盖率不达标就熔断；测试左移见第 18 章。

4.「孤岛」地狱

开发（Dev）只管写代码，运维（Ops）只管看服务器。上线出了问题互相甩锅：「代码写得烂」「环境配得不对」。缺少共同语言和可观测数据，责任边界模糊。

对策方向：DevOps 要求共用流水线、共用监控与日志，用指标说话而不是用猜测吵架。

核心收益

维度说明
快自动化代替人工，代码从提交到可部署，从「几天」缩短到「几分钟」。
稳减少人为干预，机器执行流程不会「手抖」；门禁在合并前拦住坏代码。
爽开发专注业务逻辑，打包、部署、重复检查交给流水线。

二、怎么落地？（How）

在 Java 生态中，落地「工程化 · DevOps · CI/CD」通常分四个阶段递进：先规范，再集成，再交付，最后闭环监控。不必一步登天，小团队可从「Maven 规范 + Jenkins 自动打包」起步，再逐步引入 Docker、K8s 与完整观测链路。

1. 工程化（规范先行）

工程化解决的是代码如何组织、如何被一致地构建与审查的问题，是后续 CI/CD 的前提。

依赖与构建工具统一

  • 全面抛弃手动引入 JAR 包；新项目一律使用 Maven 或 Gradle（本手册示例以 Maven 为主，见第 13 章）。
  • 规范 pom.xml：父 POM 或 <dependencyManagement> 统一版本，避免传递依赖冲突。
  • 团队约定同一 JDK LTS（如 Java 21）、同一 Maven 版本，CI 与本地一致。

代码规范与静态检查

  • IDE 集成 Alibaba Java Coding Guidelines 或 SonarLint，提交前就能发现问题。
  • 构建阶段接入 SonarQube，强制处理 Blocker / Critical（空指针风险、未关闭的流等）。

分支管理策略（Git Flow 简化版）

  • main / master：永远是线上稳定版，禁止直接 Push。
  • develop：日常集成分支。
  • feature/*：新功能开发，通过 Pull Request（MR）合并，必须经过 Code Review 且 Pipeline 通过。

2. 持续集成（CI — Continuous Integration）

持续集成解决频繁合并代码并确保它不崩溃的问题：每次开发人员提交代码，自动触发构建和测试。

常用工具

Jenkins、GitLab CI、GitHub Actions 均可；选型时尽量让代码托管与 CI 同源，减少 Token 与权限对接。内网项目常见自建 GitLab CE；开源或 GitHub 托管可用 Actions。

典型流程（Java 视角）

  1. 触发：开发者 Push 或发起 MR。
  2. 拉取：CI 服务器（Runner / Agent）拉取最新代码。
  3. 编译与单元测试：执行 mvn clean test。Java 项目必须编写 JUnit / Mockito 单测；覆盖率未达团队标准（例如 70%）则 Pipeline 失败，禁止合并。
  4. 打包：测试通过后执行 mvn clean package -DskipTests，产出 JAR（或 WAR）。

可选阶段：SonarQube 静态扫描、依赖漏洞扫描（OWASP Dependency-Check），均应在合并前完成。测试写法与覆盖率门禁见第 18 章、第 19 章。

GitLab CI 示例（fdc-webservice）

# .gitlab-ci.yml（CI 阶段核心）
stages: [build, test, package]

variables:
  MAVEN_OPTS: "-Dmaven.repo.local=.m2/repository"

cache:
  key: "${CI_COMMIT_REF_SLUG}"
  paths: [.m2/repository/]

build:
  stage: build
  image: maven:3.9-eclipse-temurin-21
  script: [mvn -B compile -DskipTests]

test:
  stage: test
  image: maven:3.9-eclipse-temurin-21
  script: [mvn -B test]
  artifacts:
    reports:
      junit: [target/surefire-reports/TEST-*.xml]

package:
  stage: package
  image: maven:3.9-eclipse-temurin-21
  script: [mvn -B package -DskipTests]
  artifacts:
    paths: [target/*.jar]
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

3. 持续交付 / 部署（CD — Continuous Delivery / Deployment）

持续交付解决把打好的包安全、快速地部署到各环境的问题。现代 Java 架构中，CD 通常与容器化（Docker）绑定。

典型流程

  1. 容器化：CI 产出的 JAR 通过 Dockerfile 构建镜像。
  2. 推送到私服：镜像推送到 Harbor、阿里云 ACR、GitLab Registry 等。
  3. 部署到测试 / 生产：
    • 传统方式：Ansible 或 Jenkins 脚本分发 JAR，nohup java -jar ... & 启动（适合遗留系统过渡）。
    • 现代方式（云原生）：通知 Kubernetes 更新镜像，滚动更新（Rolling Update）、蓝绿或金丝雀 / 灰度发布，用户无感上线。K8s 清单见第 13 章。

Continuous Delivery：类生产自动部署，生产需人工审批。Continuous Deployment：测试全过后自动上生产，仅适合测试极厚、监管允许的场景。

Dockerfile 示例

# 多阶段构建更优；此处为最小示例
FROM eclipse-temurin:22-jre-alpine
WORKDIR /app
COPY target/fdc-webservice-*.jar app.jar
ENTRYPOINT ["java", "-jar", "/app/app.jar"]

生产环境建议多阶段构建 + Spring Boot 分层镜像，缩短推送与拉取时间，详见第 13 章 Docker 小节。

CD 阶段配置片段（GitLab）

build-image:
  stage: deploy
  image: docker:24
  services: [docker:24-dind]
  script:
    - docker build -t "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA" .
    - docker push "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA"
  needs: [package]
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

deploy-prod:
  stage: deploy
  image: bitnami/kubectl:latest
  script:
    - kubectl set image deployment/fdc-webservice \
        fdc-webservice="$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA" -n fdc-prod
    - kubectl rollout status deployment/fdc-webservice -n fdc-prod --timeout=180s
  when: manual
  needs: [build-image]

镜像 tag 使用 commit SHA，不用 latest；生产 Job 设 when: manual，同一镜像通过 ConfigMap / Secret 或 Spring Profile 区分环境，不要把环境差异写进镜像。

4. DevOps 文化与度量监控（闭环）

DevOps 不仅是工具链，更要求打破 Dev 与 Ops 的组织壁垒：共用流水线定义、共用监控与日志，用数据对齐责任。

配置中心化

数据库连接、密钥等不要写死在 application.yml 并打进 JAR。使用 Spring Cloud Config、Nacos 或 Apollo；环境变更时在配置中心修改，应用刷新即可，无需重新打包。

K8s 场景下也可用 ConfigMap / Secret 注入，与 Spring Profile 配合（见第 13 章多环境配置）。

全链路监控

线上 JVM 状态与业务指标必须可见，否则「快、稳」无法验证。

能力常见方案Java 侧接入
指标监控Prometheus + GrafanaSpring Boot Actuator（内存、CPU、GC、自定义业务指标）
日志收集ELK 或 Loki统一 JSON 日志格式，traceId 贯穿分布式调用
链路追踪Jaeger、Zipkin、SkyWalking微服务间调用耗时与异常定位

调优与 SLO 设计见第 20 章；安全扫描与密钥管理见第 17 章。

消息与异步集成（延伸阅读）

业务解耦、Outbox、MQ 选型与通知链路见第 03 章事件驱动、第 16 章消息通知；CI/CD 侧保证镜像与配置版本一致即可。

网关与流量（延伸阅读）

Ingress / API 网关、蓝绿与金丝雀流量切换见第 13 章 K8s 部署；与 CD 滚动更新配合验证无 502 尖刺（见第 12 章优雅停机）。

协作习惯

  • 开发者维护 .gitlab-ci.yml / Jenkinsfile，运维提供 Runner、集群与网络。
  • Pipeline 失败通知到企微 / 钉钉，@ 提交者；部署记录保留「谁、何时、哪版 SHA」。
  • 线上事故复盘同时看代码变更、配置变更与监控曲线，而不是单点甩锅。

三、总结：Java 极简 CI/CD 流水线

一条可落地的端到端链路如下：

flowchart LR
    GIT[代码提交 Git] --> MVN[编译/单测 Maven]
    MVN --> SONAR[质量扫描 SonarQube]
    SONAR --> DOCKER[构建镜像 Docker]
    DOCKER --> HARBOR[推送仓库 Harbor]
    HARBOR --> K8S[部署/滚动更新 K8s]
    K8S --> OBS[运行期监控 Grafana/ELK]

图：Java 极简 CI/CD 全链路

代码提交 (Git)
  → 自动化编译 / 单测 (Maven)
  → 代码质量扫描 (SonarQube)
  → 构建镜像 (Docker)
  → 推送仓库 (Harbor / GitLab Registry)
  → 自动化部署 / 滚动更新 (Kubernetes)
  → 运行期监控 (Grafana / ELK)

渐进式落地建议

刚开始不必一步登天。可按成熟度分阶段推进：

阶段目标典型动作
第 1 步能一致构建统一 Maven + JDK；main 保护；PR 必 Review
第 2 步能自动验证Jenkins / GitLab CI：mvn test + 覆盖率门禁
第 3 步能自动部署测试环境打 JAR 或 Docker 镜像，脚本部署 SIT
第 4 步生产可回滚、可观测K8s 滚动更新 + Prometheus + 集中日志

小团队建议从「统一 Maven 规范 + 一条 Jenkins / GitLab 脚本自动打包部署」开始，尝到「快、稳」的甜头后，再引入 Docker、K8s 与完整监控链路。
