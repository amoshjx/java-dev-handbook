07 面向对象

建模、封装与设计原则——决定代码能否在需求变化中存活。

封装、继承与多态

面向对象的三大核心是封装、继承和多态。它们一起解决“代码如何组织、如何复用、如何扩展”的问题：封装负责隐藏实现细节，继承提供层次化复用，多态让调用方依赖统一抽象而不是具体实现。

封装：先保护对象状态，再开放必要行为

封装的目标是让对象自己维护合法状态。实践中，优先使用 private 字段，通过方法暴露行为，而不是把内部数据完全暴露给外部随意修改。这样可以把校验逻辑放在对象内部，减少无效状态和隐蔽 Bug。

继承：表达 is-a 关系，避免为复用而继承

继承适合语义明确的父子关系，例如“信用卡支付是支付方式的一种”。如果只是想复用少量代码，通常应优先使用组合。继承层级过深会提升理解和维护成本，初中级开发中建议将继承控制在清晰、必要的场景。

多态：面向接口编程，减少分支判断

多态指同一接口在不同实现上表现出不同的行为。调用方只依赖抽象类型（接口或父类），运行时由具体对象决定执行逻辑。这样新增实现时通常不需要修改调用方代码，扩展性更好。

  • 封装关注“对象内部是否安全可控”。
  • 继承关注“类型关系是否真实且稳定”。
  • 多态关注“调用方是否依赖抽象而非细节”。

继承 vs 组合

继承表达稳定的 is-a 关系（子类可替换父类）；想复用行为或灵活切换实现时，优先用组合（has-a）委托，避免为复用代码而盲目继承。

// 继承：仅当类型关系真实且稳定时使用（信用卡支付 is-a 支付方式）
interface PaymentMethod {
    void pay(BigDecimal amount);
}

class CreditCardPayment implements PaymentMethod {
    @Override
    public void pay(BigDecimal amount) {
        // 调用信用卡网关
    }
}

// 组合：OrderService has-a PaymentMethod，运行时可切换实现，无需改 OrderService
class OrderService {
    private final PaymentMethod payment;

    OrderService(PaymentMethod payment) {
        this.payment = payment;
    }

    void checkout(BigDecimal total) {
        payment.pay(total);  // 委托给组合对象，而非继承父类
    }
}

// 反例：为复用 pay() 而让 OrderService extends CreditCardPayment
// 语义错误（订单服务不是信用卡），且切换支付宝/微信时要再造继承链

接口与抽象类

接口定义「能做什么」——只约定行为，不含实例字段；一个类可以 implements 多个接口。抽象类定义「一类事物共同的骨架」——可含共享字段和部分已实现的方法；一个类只能 extends 一个抽象类。

  • 只描述能力、需要多实现 → 用接口（如 Payable、Serializable）。
  • 子类共享状态或固定流程、只填差异 → 用抽象类（如模板方法：pay() 里校验 + 调抽象 doPay()）。
  • 拿不准时优先接口；Java 8 起接口可有 default 方法，向后兼容扩展更方便。
// 接口：定义能力，可实现多个
interface Payable {
    void pay(BigDecimal amount);
}

interface Refundable {
    void refund(BigDecimal amount);
}

// 抽象类：共享字段 + 骨架流程，子类只实现差异部分
abstract class BasePayment implements Payable {
    protected final String merchantId;

    BasePayment(String merchantId) {
        this.merchantId = merchantId;
    }

    @Override
    public void pay(BigDecimal amount) {
        if (amount.signum() <= 0) throw new IllegalArgumentException("金额须为正");
        doPay(amount);  // 模板方法：公共逻辑在此，具体支付交给子类
    }

    protected abstract void doPay(BigDecimal amount);
}

// 具体类：继承抽象类 + 按需实现多个接口
class AliPay extends BasePayment implements Refundable {
    AliPay(String merchantId) { super(merchantId); }

    @Override protected void doPay(BigDecimal amount) { /* 调支付宝 */ }

    @Override public void refund(BigDecimal amount) { /* 调退款 */ }
}

SOLID 原则

SOLID 是面向对象设计的五条基本原则，帮助代码在需求变化时保持可维护、可扩展。

  • S — 单一职责（SRP）：一个类只有一个变更理由。
  • O — 开闭原则（OCP）：对扩展开放，对修改关闭（策略、插件）。
  • L — 里氏替换（LSP）：子类可替换父类而不破坏行为。
  • I — 接口隔离（ISP）：客户端不依赖不需要的方法。
  • D — 依赖倒置（DIP）：高层依赖抽象，而非具体实现（Spring 构造器注入）。

速记：「单开里接依」。行为变化优先用策略/装饰器等设计模式，避免 if-else 膨胀。

常用设计模式

在 Java 开发中，设计模式（Design Patterns）是解决特定软件设计问题的经典方案。它们能让你的代码更具可复用性、可扩展性和可维护性。

GoF（Gang of Four）将设计模式分为三大类：创建型、结构型和行为型。下面为你精选每类中最常用、面试必问的几种设计模式进行深度讲解和代码演练。

一、创建型模式（Creational Patterns）

核心关注：对象的创建机制。它试图将对象的创建与使用分离，从而降低系统的耦合度。

1. 单例模式（Singleton Pattern）

核心思想：保证一个类在整个系统中有且仅有一个实例，并提供一个全局访问点。比如线程池、数据库连接池。

双重检查锁定（Double-Check Locking）实现：

public class Singleton {
    // volatile 关键字防止指令重排
    private static volatile Singleton instance;

    // 私有构造方法，防止外部 new
    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) { // 第一次检查：避免不必要的同步
            synchronized (Singleton.class) {
                if (instance == null) { // 第二次检查：确保线程安全
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}

2. 工厂方法模式（Factory Method Pattern）

核心思想：定义一个创建对象的接口，但让子类决定实例化哪一个类。工厂方法让类的实例化推迟到子类。

代码示例：汽车生产

// 1. 产品接口
interface Car { void drive(); }

// 2. 具体产品
class Tesla implements Car { public void drive() { System.out.println("开特斯拉，安静。"); } }
class BMW implements Car { public void drive() { System.out.println("开宝马，操控好。"); } }

// 3. 抽象工厂
interface CarFactory { Car createCar(); }

// 4. 具体工厂
class TeslaFactory implements CarFactory { public Car createCar() { return new Tesla(); } }
class BMWFactory implements CarFactory { public Car createCar() { return new BMW(); } }

3. 建造者模式（Builder Pattern）

核心思想：将一个复杂对象的构建与其表示分离，使得同样的构建过程可以创建不同的表示。

为什么不可错过：当一个类的构造方法参数超过 4 个，且有些参数是可选的时候，用传统构造方法会引发「构造方法爆炸」；而用 Setter 方法又会导致对象在构建过程中处于不完整状态（非线程安全）。Builder 模式是解决这个问题的终极方案。

💡 日常应用：在 Java 中，你最常用的 StringBuilder、Lombok 的 @Builder 注解、以及各种 HttpClient 的配置，全都是它。

代码示例：构建一个复杂的实体类

public class User {
    private final String firstName; // 必填
    private final String lastName;  // 必填
    private final int age;          // 可选
    private final String phone;     // 可选

    // 1. 私有构造方法，只接受 Builder 对象
    private User(UserBuilder builder) {
        this.firstName = builder.firstName;
        this.lastName = builder.lastName;
        this.age = builder.age;
        this.phone = builder.phone;
    }

    // 2. 内部 Builder 类
    public static class UserBuilder {
        private final String firstName;
        private final String lastName;
        private int age;
        private String phone;

        public UserBuilder(String firstName, String lastName) {
            this.firstName = firstName;
            this.lastName = lastName;
        }

        public UserBuilder age(int age) { this.age = age; return this; }
        public UserBuilder phone(String phone) { this.phone = phone; return this; }

        // 核心：build 方法返回最终的 User 对象
        public User build() { return new User(this); }
    }
}

// 优雅的链式调用方式：
User user = new User.UserBuilder("张", "三")
                .age(25)
                .phone("13800000000")
                .build();

二、结构型模式（Structural Patterns）

核心关注：对象的组合。如何组合类和对象以获得更大的结构。

1. 适配器模式（Adapter Pattern）

核心思想：作为两个不兼容接口之间的桥梁。它结合了两个独立接口的功能，让原本由于接口不兼容而不能一起工作的类可以一起工作。常见于新老系统对接或接入第三方 SDK。

代码示例：手机充电（将 220V 电压转换为 5V）

// 目标接口（手机需要的电压）
interface Target5V { int output5V(); }

// 已有的类（现有的 220V 电压）
class Adaptee220V {
    public int output220V() { return 220; }
}

// 适配器：将 220V 转换为 5V
class PowerAdapter extends Adaptee220V implements Target5V {
    @Override
    public int output5V() {
        int src = output220V();
        System.out.println("适配器：收到 " + src + "V 电压，正在转换...");
        return src / 44; // 转换成 5V
    }
}

2. 代理模式（Proxy Pattern）

核心思想：给某一个对象提供一个代理，并由代理对象控制对原对象的访问。Spring AOP（面向切面编程）的核心就是动态代理。

静态代理示例：

// 接口
interface Subject { void request(); }

// 真实对象
class RealSubject implements Subject {
    public void request() { System.out.println("执行核心业务逻辑..."); }
}

// 代理对象
class ProxySubject implements Subject {
    private RealSubject realSubject = new RealSubject();

    public void request() {
        System.out.println("预处理：记录日志/安全检查");
        realSubject.request(); // 调用真实对象的方法
        System.out.println("后处理：清理资源");
    }
}

3. 装饰器模式（Decorator Pattern）

核心思想：动态地给一个对象添加一些额外的职责。就增加功能来说，装饰器模式相比生成子类更为灵活。

为什么不可错过：它是类的继承的完美替代方案。如果你发现为了加功能，类的继承树已经变得无比庞大（比如：Text → BoldText → UnderlineBoldText），赶紧用装饰器。

💡 日常应用：Java 的 I/O 流是经典的装饰器模式。例如：new BufferedReader(new FileReader("test.txt"))，在没有改变文件读取基础类的情况下，动态为其增加了「缓存」功能。

代码示例：给纯咖啡加奶、加糖

// 1. 核心接口
interface Coffee { double getCost(); String getDescription(); }

// 2. 具体实现（原味咖啡）
class SimpleCoffee implements Coffee {
    public double getCost() { return 10.0; }
    public String getDescription() { return "纯咖啡"; }
}

// 3. 抽象装饰器（必须持有核心接口的引用）
abstract class CoffeeDecorator implements Coffee {
    protected final Coffee decoratedCoffee;
    public CoffeeDecorator(Coffee coffee) { this.decoratedCoffee = coffee; }
    public double getCost() { return decoratedCoffee.getCost(); }
    public String getDescription() { return decoratedCoffee.getDescription(); }
}

// 4. 具体装饰器（加奶）
class MilkDecorator extends CoffeeDecorator {
    public MilkDecorator(Coffee coffee) { super(coffee); }
    public double getCost() { return super.getCost() + 3.0; }
    public String getDescription() { return super.getDescription() + " + 加奶"; }
}

装饰器 vs 代理：如何区分？

两者结构相似（都持有同一接口的引用），但意图不同。面试高频考点如下：

维度装饰器模式（Decorator）代理模式（Proxy）
核心意图增强功能。动态地为对象添加新职责，是继承的替代方案。控制访问。为了限制、增强或延迟对真实对象的访问。
谁创建真实对象客户端（调用者）创建真实对象，并将其传入装饰器中。代理类自身创建或持有真实对象，客户端通常不知道真实对象的存在。
透明度客户端完全清楚自己正在「一层层叠加功能」。客户端甚至不知道自己用的是代理，它以为自己调用的就是真实对象。
关系基数通常是 1:N（一个对象可以被多层装饰器连续包装）。通常是 1:1（一个代理针对一个特定的真实对象进行控制）。

三、行为型模式（Behavioral Patterns）

核心关注：对象之间的通信。描述类或对象怎样交互以及怎样分配职责。

1. 策略模式（Strategy Pattern）

核心思想：定义一系列算法，把它们一个个封装起来，并且使它们可相互替换。本模式使得算法可独立于使用它的客户而变化。（告别成堆的 if-else 的利器！）

代码示例：电商根据不同会员等级计算价格

// 1. 策略接口
interface PriceStrategy { double calculate(double price); }

// 2. 具体策略
class NormalUser implements PriceStrategy { public double calculate(double p) { return p; } }
class VIPUser implements PriceStrategy { public double calculate(double p) { return p * 0.8; } }

// 3. 上下文环境
class PriceCalculator {
    private PriceStrategy strategy;
    public void setStrategy(PriceStrategy strategy) { this.strategy = strategy; }

    public double getFinalPrice(double price) {
        return strategy.calculate(price);
    }
}

2. 观察者模式（Observer Pattern）

核心思想：定义对象间的一种一对多的依赖关系，当一个对象的状态发生改变时，所有依赖于它的对象都得到通知并被自动更新。常用于事件驱动架构、消息队列。

代码示例：微信公众号推送

import java.util.ArrayList;
import java.util.List;

// 观察者（粉丝）
interface Observer { void update(String message); }
class User implements Observer {
    private String name;
    public User(String name) { this.name = name; }
    public void update(String msg) { System.out.println(name + " 收到推送: " + msg); }
}

// 被观察者（公众号）
class Subject {
    private List<Observer> observers = new ArrayList<>();
    public void attach(Observer o) { observers.add(o); }

    public void notifyAllObservers(String msg) {
        for (Observer o : observers) { o.update(msg); }
    }
}

总结与避坑指南

模式名称一句话核心常见应用场景
单例模式独一无二，全局共享线程池、配置读取类、Spring Bean（默认）
工厂方法别问我怎么装配的，去问工厂JDBC 获取连接、LoggerFactory.getLogger()
建造者模式分步组装，链式构建StringBuilder、Lombok @Builder、HttpClient 配置
适配器模式业务接口对不上，加个补丁凑一双旧系统重构、日志框架兼容（SLF4J）
代理模式无侵入式的功能增强Spring AOP、事务控制、RPC 调用
装饰器模式层层包装，动态叠加能力Java I/O 流（BufferedReader）、日志/缓存包装类
策略模式各种算法并列，谁合适谁上多支付方式选择、多促销活动计算
观察者模式牵一发而动全身事件监听器（Listener）、发布订阅模式

💡 架构师忠告：不要为了用设计模式而用设计模式。在项目初期，如果业务很简单，直接写朴素的代码往往是最好的选择。当系统迭代出现「频繁修改某处代码」、「扩展新功能引发连锁 Bug」时，才是重构引入设计模式的最佳时机。过度设计（Over-engineering）往往比没有设计更让人头疼。

equals / hashCode

对象相等契约

讲解

重写 equals 必须重写 hashCode，保证相等对象 hash 相同。契约：自反、对称、传递、一致；与 null 比较返回 false。实体 ID 相等通常按业务主键；值对象按所有字段。若字段存在多种等价表示（如 BigDecimal 的 scale），请在 equals/hashCode 中采用一致的归一化策略。放入 HashMap/HashSet 的 key 字段应保持不可变。

示例代码

@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Money money)) return false;
    return normalizedAmount().equals(money.normalizedAmount())
        && currency.equals(money.currency);
}

@Override
public int hashCode() {
    return Objects.hash(normalizedAmount(), currency);
}

private BigDecimal normalizedAmount() {
    return amount.stripTrailingZeros();
}

易错点

  • 只重写 equals 不重写 hashCode → HashMap 行为异常。
  • 可变对象作 HashMap key，hash 变化后找不到 entry。
  • 继承体系中 equals 违反对称性——考虑 getClass() 而非 instanceof。

不可变对象

线程安全与防御性拷贝

讲解

不可变对象天然线程安全、可安全共享、适合作为 Map key 和值对象。实现要点：final 字段、无 setter、可变组件防御性拷贝（List.copyOf）、不暴露内部可变引用。Java 17+ 值对象优先 record；需行为方法时用 final class + 私有构造。标准库典范：String、LocalDate、Instant。

flowchart LR
    A[不可变对象] --> B[final 字段]
    A --> C[无 setter]
    A --> D[防御性拷贝]
    A --> E[线程安全]
    A --> F[可作 Map Key]
    G[修改需求] --> H[返回新实例]
    H --> I[而非 mutate 原对象]

图：不可变对象设计要点与修改策略

示例代码

public final class OrderLine {
    private final String sku;
    private final int quantity;
    private final List<String> tags;

    public OrderLine(String sku, int quantity, List<String> tags) {
        this.sku = sku;
        this.quantity = quantity;
        this.tags = List.copyOf(tags); // 防御性拷贝
    }
    public List<String> tags() { return tags; } // 已是不可变
}

关键/技巧

  • 领域值对象（Money、Email）优先 record；需「修改」时 withXxx 返回新实例。
  • Collections.unmodifiableList 包装外部传入的 list 仍可变——构造时用 List.copyOf。
