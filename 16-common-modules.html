系统日志 — 分级、结构化与采集检索

Logback 分级、JSON 结构化、MDC traceId 与 ELK/Loki 采集

讲解

与操作审计分工：操作日志审计记「谁对谁做了什么」——业务动作、合规留痕、可检索的审计表；系统日志记应用运行态——启动、依赖调用、异常栈、慢查询线索，面向运维排障与可观测性，通常不落业务审计表而走日志管道。日志分级（SLF4J）：TRACE 极细调试（生产关闭）；DEBUG 开发/联调用；INFO 关键业务里程碑与启动信息；WARN 可恢复异常、降级、重试；ERROR 需介入的失败（附 stack，勿吞异常）。原则：生产默认 INFO，包级可对 com.yourcorp 临时开 DEBUG；禁止用 ERROR 打正常分支。

Spring Boot 日志：默认 Logback（spring-boot-starter-logging）；可换 Log4j2（排除 logging 依赖）。logback-spring.xml 支持 Profile：console 开发、`rolling-file` 生产（按天+大小滚动，保留 30 天）。application.yml 可覆盖级别与文件路径：logging.level.root、logging.file.name。

结构化日志：单行 JSON 便于 Filebeat/Vector 解析；logstash-logback-encoder 的 LogstashEncoder 统一字段：timestamp、level、logger、message、traceId、spanId、userId、service（应用名）。Kibana/Loki 按字段过滤，避免正则扒文本。

MDC / traceId：SLF4J MDC 存请求级上下文；网关或 Filter 写入 traceId，日志 pattern 加 %X{traceId}。与 Micrometer Tracing（原 Sleuth）集成后，traceId/spanId 自动注入 MDC；@Async、线程池需 TaskDecorator 或 ContextSnapshot 复制 MDC，否则子线程丢链路。排障时 audit 表 traceId ? 系统日志 ? 第 21 章 Trace 一键串联。

敏感信息：手机号、身份证、密码、Token、卡号不入日志或走脱敏 Converter；详见 第 17 章敏感数据与日志脱敏。SQL 参数、请求 Body 生产默认不打 DEBUG 明文。

日志采集：应用写本地滚动文件 → Filebeat 或 Vector tail → Elasticsearch + Kibana（ELK）或 Loki + Grafana（轻量、按 label 查询）。容器场景可 stdout + DaemonSet 采集；K8s 常 sidecar/节点 Agent。指标与链路见 第 21 章可观测性。

// Java：@Slf4j + MDC（Filter 或 Interceptor 入口设置）
@Slf4j
@Service
public class OrderService {
  public OrderDetail get(Long id) {
    MDC.put("userId", String.valueOf(SecurityUtils.userId()));
    try {
      log.info("fetch order id={}", id);
      return orderRepo.findById(id).orElseThrow();
    } catch (Exception e) {
      log.error("fetch order failed id={}", id, e);
      throw e;
    } finally {
      MDC.remove("userId");
    }
  }
}

// @Async 传递 MDC（TaskDecorator 示意）
@Bean
TaskDecorator mdcTaskDecorator() {
  return runnable -> {
    Map<String, String> ctx = MDC.getCopyOfContextMap();
    return () -> {
      if (ctx != null) MDC.setContextMap(ctx);
      try { runnable.run(); } finally { MDC.clear(); }
    };
  };
}

关键/技巧

  • 网关统一生成 traceId（W3C traceparent），Logback JSON 字段与 Micrometer Tracing 同源。
  • 生产禁止循环 INFO；热路径用 DEBUG 须带开关（logging.level 动态调整或 Actuator loggers）。
  • 异常必 log.error("orderId={}", id, e) 保留栈；业务可预期异常降级为 WARN。
  • 压测、大促前确认日志磁盘与 ES 索引生命周期，防 IO 打满。

易错点

  • 循环里打 INFO——流量放大拖垮磁盘与 ELK。
  • 多实例日志文件名冲突——路径含 ${HOSTNAME} 或只采集 stdout。
  • 线程池/异步丢 MDC——排障时 trace 断链，误以为单点故障。
  • 把操作审计写进 log 文件却不落库——合规检索与权限管控缺失。

速记

「审计记谁干了啥，系统日志记跑得咋样；分级 INFO 起步，JSON+traceId，采集走 ELK/Loki。」

操作日志审计

注解 + AOP 与变更前后快照

讲解

合规与排障需要「谁、何时、对什么、做了什么、结果如何」。实现：@AuditLog(module, action) + AOP 拦截 Controller 或 Service；记录 userId、IP、User-Agent、请求参数（脱敏）、耗时、成功/失败。数据变更：MyBatis 拦截器或 Envers 存 before/after JSON diff。存储：热数据 MySQL，冷数据 ES（第 21 章 ELK）；禁止记密码、Token、完整身份证号。查询：管理端分页检索，导出受 RBAC 与数据权限约束。

示例代码

@AuditLog(module = "ORDER", action = "EXPORT")
@GetMapping("/export")
public void export(OrderQuery q) { /* ... */ }

@Aspect
@Component
public class AuditAspect {
  @Around("@annotation(audit)")
  public Object around(ProceedingJoinPoint pjp, AuditLog audit) throws Throwable {
    var log = AuditRecord.builder()
        .userId(SecurityUtils.userId())
        .module(audit.module())
        .action(audit.action())
        .params(maskSensitive(args(pjp)))
        .build();
    try {
      Object ret = pjp.proceed();
      log.setSuccess(true);
      return ret;
    } catch (Throwable t) {
      log.setSuccess(false).setError(t.getMessage());
      throw t;
    } finally {
      auditRepo.saveAsync(log);
    }
  }
}

关键/技巧

  • 异步写日志（MQ 或 @Async），不拖慢主链路。
  • 敏感字段统一 MaskUtil：手机中间四位、身份证后六位。
  • 与 TraceId 关联（Micrometer），日志与链路一键跳转。

易错点

  • AOP 只记成功路径，异常未进 finally——漏审计。
  • 变更 diff 存全量大 JSON——字段级 diff + 压缩。

后端数据校验 — Bean Validation 与分层校验

Jakarta Bean Validation、分组校验与统一 400 响应

讲解

为何必须后端校验：前端/网关可被绕过，API 是唯一可信边界——格式、必填、长度、枚举范围必须在服务端兜底。Jakarta Bean Validation（Hibernate Validator）用声明式注解描述格式与简单约束：@NotNull、@Size、@Pattern、@Email、@Min/@Max；嵌套对象加 @Valid 级联校验。Controller 入参 @Valid @RequestBody CreateOrderCmd cmd；类级 @Validated 配合分组接口（如 Create.class / Update.class）区分新建与修改必填项。

分层分工：Controller/ DTO 层做格式校验（BV）；Service 层做业务规则（库存、状态、唯一性、跨字段逻辑）；多条件组合、可运营变更的复杂规则交给规则引擎——边界：「字段对不对」→ BV，「业务能不能做」→ Service/引擎。批量Excel 导入在监听器里复用同一套 DTO 校验 + 行号聚合错误；持久层用参数化查询/ORM，防 SQL 注入见第 17 章。

示例代码

// DTO + 分组
public interface Create {}
public interface Update {}

public record CreateOrderCmd(
    @NotNull(groups = Create.class) Long productId,
    @Min(1) @Max(9999) int quantity,
    @Pattern(regexp = "^1[3-9]\\d{9}$", message = "手机号格式错误")
    String mobile
) {}

@RestController
@Validated
public class OrderController {
  @PostMapping("/orders")
  public OrderVO create(@Validated(Create.class) @RequestBody CreateOrderCmd cmd) {
    return orderService.create(cmd);
  }
}

// 自定义约束
@Target(FIELD)
@Retention(RUNTIME)
@Constraint(validatedBy = IdCardValidator.class)
public @interface IdCard {
  String message() default "身份证号无效";
  Class<?>[] groups() default {};
  Class<? extends Payload>[] payload() default {};
}

public class IdCardValidator implements ConstraintValidator<IdCard, String> {
  public boolean isValid(String value, ConstraintValidatorContext ctx) {
    return value == null || IdCardUtils.isValid(value);
  }
}

// 统一 400 字段错误
@RestControllerAdvice
public class ValidationExceptionHandler {
  @ExceptionHandler(MethodArgumentNotValidException.class)
  public ResponseEntity<ApiError> handle(MethodArgumentNotValidException ex) {
    var fields = ex.getBindingResult().getFieldErrors().stream()
        .collect(Collectors.toMap(
            FieldError::getField,
            e -> e.getDefaultMessage() != null ? e.getDefaultMessage() : "invalid",
            (a, b) -> a));
    return ResponseEntity.badRequest().body(new ApiError("VALIDATION_FAILED", fields));
  }
}

// Service 业务校验（非 BV 职责）
public Order create(CreateOrderCmd cmd) {
  var product = productRepo.findById(cmd.productId()).orElseThrow();
  if (product.getStock() < cmd.quantity()) {
    throw new BusinessException("INSUFFICIENT_STOCK", "库存不足");
  }
  // ...
}

关键/技巧

  • DTO 与领域实体分离——Controller 只暴露 API 契约，实体内部不变式在聚合根方法里二次校验。
  • 分组 @Validated(Update.class) 与 PATCH 部分更新配合 @Null(groups = Update.class) 控制不可改字段。
  • 导入场景：Validator.validate(row) 收集 ConstraintViolation，按行号写入结果 Excel，与 HTTP 400 字段结构保持一致。
  • 校验异常与业务/系统异常合并进同一个 @RestControllerAdvice，见全局异常处理。

易错点

  • 只在前端做校验——抓包/API 直连直接写脏数据；安全与数据质量双失败。
  • Controller 没加 @Valid——注解写了也不生效，联调才发现。
  • 把复杂促销/风控规则全堆在 @AssertTrue——难测试、难热更新，应下沉规则引擎或 Service。
  • 校验失败返回 500 或裸 Exception 消息——客户端无法字段级修正；应固定 400 + 字段 map。
  • 批量导入「一行失败全回滚」未说明——用户期望部分成功时需分批事务 + 错误文件。

速记

「前端不可信，后端必校验；格式用 BV，业务在 Service，复杂规则上引擎；400 返字段，导入带行号。」

延伸阅读：Jakarta Bean Validation 3.0 规范、Hibernate Validator 参考手册、Spring MVC Validation 文档

全局异常处理

@RestControllerAdvice、Problem Details 与分层错误码

讲解

全局异常处理是 API 层的统一出口：Controller/Service 只抛领域化异常（如 BusinessException），由 @RestControllerAdvice（或 @ControllerAdvice）集中映射为稳定的 HTTP 状态码、业务错误码与用户可见文案——避免每个接口 try-catch、避免把堆栈或 SQL 细节泄漏给客户端。

异常分层：① 校验异常（MethodArgumentNotValidException、ConstraintViolationException）→ 400 + 字段级 errors，见后端数据校验；② 业务异常（库存不足、状态非法）→ 4xx + 稳定 code（如 order.stock.insufficient）；③ 鉴权/授权（Spring Security AccessDeniedException、自定义未登录）→ 401/403；④ 系统异常（未捕获 Exception）→ 500 + 通用 internal.error，详细栈只写系统日志。错误码命名与 HTTP 语义分工见第 03 章 API 设计；Spring 机制细节见第 12 章统一异常。

响应体约定：Spring Boot 3 推荐 RFC 9457 Problem Details（ProblemDetail），字段含 type、title、status、detail、扩展属性 code/errors；与 OpenAPI 中声明的 ApiError 模型保持一致，便于前端与网关统一解析。用户可见 detail 走 MessageSource + locale（见国际化），日志与对外文案分离。

组织方式：单应用一个 GlobalExceptionHandler 即可；模块多时可用 @Order 或按包拆多个 Advice，但同一异常类型只应有一处最终处理，避免映射冲突。Filter/网关层错误（如 JWT 过期）与 MVC Advice 分工：网关返回 401 JSON，业务服务 Advice 处理进入 Controller 之后的异常。

示例代码

// 业务异常：可预期，带 HTTP 状态与稳定 code
public class BusinessException extends RuntimeException {
  private final String code;
  private final HttpStatus status;

  public BusinessException(String code, HttpStatus status) {
    super(code);
    this.code = code;
    this.status = status;
  }
  public String getCode() { return code; }
  public HttpStatus getStatus() { return status; }
}

// 统一响应模型（也可直接用 ProblemDetail）
public record ApiError(String code, String message, Map<String, String> fields) {}

@RestControllerAdvice
@Slf4j
public class GlobalExceptionHandler {

  // 1) Bean Validation — @RequestBody
  @ExceptionHandler(MethodArgumentNotValidException.class)
  public ResponseEntity<ApiError> handleValid(MethodArgumentNotValidException ex) {
    var fields = ex.getBindingResult().getFieldErrors().stream()
        .collect(Collectors.toMap(
            FieldError::getField,
            e -> e.getDefaultMessage() != null ? e.getDefaultMessage() : "invalid",
            (a, b) -> a));
    return ResponseEntity.badRequest()
        .body(new ApiError("VALIDATION_FAILED", "参数校验失败", fields));
  }

  // 2) Bean Validation — @RequestParam / @PathVariable
  @ExceptionHandler(ConstraintViolationException.class)
  public ResponseEntity<ApiError> handleConstraint(ConstraintViolationException ex) {
    var fields = ex.getConstraintViolations().stream()
        .collect(Collectors.toMap(
            v -> v.getPropertyPath().toString(),
            ConstraintViolation::getMessage,
            (a, b) -> a));
    return ResponseEntity.badRequest()
        .body(new ApiError("VALIDATION_FAILED", "参数校验失败", fields));
  }

  // 3) 业务异常
  @ExceptionHandler(BusinessException.class)
  public ProblemDetail handleBusiness(BusinessException ex, Locale locale) {
    var pd = ProblemDetail.forStatusAndDetail(ex.getStatus(), ex.getCode());
    pd.setProperty("code", ex.getCode());
    // pd.setDetail(messageSource.getMessage(ex.getCode(), null, locale));
    return pd;
  }

  // 4) Spring Security（若未在 Security 入口统一写响应）
  @ExceptionHandler(AccessDeniedException.class)
  public ProblemDetail handleAccessDenied() {
    return ProblemDetail.forStatusAndDetail(HttpStatus.FORBIDDEN, "access.denied");
  }

  // 5) 兜底：系统异常
  @ExceptionHandler(Exception.class)
  public ProblemDetail handleSystem(Exception ex) {
    log.error("unexpected error", ex);
    return ProblemDetail.forStatusAndDetail(
        HttpStatus.INTERNAL_SERVER_ERROR, "internal.error");
  }
}

// Service 层：只抛业务异常，不拼 HTTP 响应
public Order get(Long id) {
  return orderRepo.findById(id)
      .orElseThrow(() -> new BusinessException("order.not_found", HttpStatus.NOT_FOUND));
}

关键/技巧

  • 校验、业务、系统异常合并进同一个 Advice，与OpenAPI 的 400/404/500 响应模型一一对应。
  • @ExceptionHandler 方法返回 ProblemDetail 或 ResponseEntity<?>；需要自定义 JSON 结构时用 @ResponseStatus + 统一 DTO。
  • 生产 500 响应禁止带回 ex.getMessage() 或堆栈；排障靠 traceId（ProblemDetail.setProperty("traceId", ...)）关联日志。
  • 微服务：BFF 可再包一层错误码翻译，各服务内部仍保持同一套 code 枚举。

易错点

  • Controller 里 catch 后返回 200 + 业务失败码——破坏 REST 语义，客户端与网关难以统一重试/告警。
  • 多个 Advice 重复处理 Exception.class——顺序不确定，行为漂移。
  • 只处理 MethodArgumentNotValidException，漏掉 ConstraintViolationException——Query 参数校验失败仍 500。
  • 业务异常与校验异常 JSON 结构不一致——前端要写两套解析逻辑。
  • 把校验逻辑写在 @ExceptionHandler 里——应在校验层失败时映射，而非用异常流做正常分支。

速记

「Controller 只抛，Advice 统一兜；400 带字段，4xx 有 code，500 藏细节；ProblemDetail 契约，日志靠 traceId。」

延伸阅读：第 12 章统一异常与错误码、RFC 9457 Problem Details、Spring MVC @ControllerAdvice 文档

Swagger / OpenAPI 接口文档

springdoc-openapi 集成、注解建模与调试入口

讲解

Swagger / OpenAPI 是什么：OpenAPI 是 HTTP API 的标准描述格式，Swagger 生态提供可视化与调试能力。对 Java 团队，它不是「好看文档」，而是接口契约中心：前后端联调、第三方对接、测试用例生成、网关/SDK 生成都依赖同一份契约。Spring Boot 3.x 主流方案是 springdoc-openapi（替代老版本 springfox），可自动扫描 Controller、参数、返回结构并输出 /v3/api-docs。

架构位置：OpenAPI 文档属于「接口治理与开发体验」能力，和后端校验、全局异常处理、RBAC、统一登录协同：文档告诉调用方「怎么调」，鉴权、校验与异常映射决定「能不能调、调错怎么报」。生产环境建议仅内网开放或按环境开关。

示例代码

<!-- pom.xml: Spring Boot 3.x 推荐 -->
<dependency>
  <groupId>org.springdoc</groupId>
  <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
</dependency>

// OpenAPI 基础信息配置
@Configuration
public class OpenApiConfig {
  @Bean
  public OpenAPI handbookOpenAPI() {
    return new OpenAPI()
        .info(new Info()
            .title("Java Dev Handbook API")
            .version("v1.0.0")
            .description("常见功能模块接口文档"));
  }
}

// 常用注解：@Tag / @Operation / @Parameter / @Schema
@RestController
@RequestMapping("/api/users")
@Tag(name = "用户模块", description = "注册、查询与资料维护")
public class UserController {
  @GetMapping("/{id}")
  @Operation(summary = "按 ID 查询用户", description = "返回脱敏后的用户信息")
  public UserVO getById(
      @Parameter(description = "用户 ID", required = true)
      @PathVariable Long id) {
    return userService.getById(id);
  }
}

@Schema(description = "用户视图对象")
public record UserVO(

统一登录验证

SSO / OAuth2 / JWT 与网关统一鉴权

讲解

架构：Spring Authorization Server / Keycloak / 企业 IdP 签发 Token；业务服务为 Resource Server，只验签不存 Session。网关（Spring Cloud Gateway）统一校验 JWT、透传 X-User-Id / Authorization。Access Token 短生命周期（15–30 min），Refresh Token 长周期存 HttpOnly Cookie 或 Redis 白名单。多端登录：同账号允许多端或「踢后者」——Redis 存 userId → latestTokenJti，校验时比对。单点登出：IdP 回调 + 各服务 Token 黑名单（Redis，TTL=剩余有效期）。

示例代码

    oauth2:

  if (!refreshStore.isValid(rt)) throw new UnauthorizedException();
  return tokenService.rotate(rt); // 旧 refresh 作废

// 多端互踢

  String latest = redis.get("login:jti:" + userId);

关键/技巧

  • JWT 载荷只放 userId、租户、角色摘要；敏感详情查库或 Redis 缓存。
  • 网关与下游时钟同步，避免 exp 边界误判。
  • 内部服务间用 mTLS 或 Service Account Token，不走用户 JWT 透传。

易错点

  • Refresh Token 放 localStorage——XSS 可窃取；优先 HttpOnly Cookie + CSRF 防护。
  • 只验签名不验 aud/iss——跨应用 Token 复用风险。
  • 登出只清前端 Token，服务端 Refresh 仍有效——必须服务端作废。

速记

「网关验 JWT，服务信网关；Access 短 Refresh 长，登出黑名单。」

数据权限

行级 / 部门 / 租户隔离

讲解

场景：同表不同人看到不同行——本人数据、本部门、本部门及下级、自定义、全部（管理员）。方案选型：① MyBatis 拦截器 / MyBatis-Plus DataPermissionInterceptor 自动拼 WHERE dept_id IN (...)；② JPA Specification 或 Hibernate Filter；③ 注解 + AOP 把数据范围写入 ThreadLocal，Repository 层读取拼接。多租户：共享库加 tenant_id 列 + 租户解析器（Header/子域）；独立库/schema 适合强隔离合规场景。与 RBAC 关系：功能权限决定「能不能调接口」，数据权限决定「接口返回哪些行」。

示例代码

// 注解声明数据范围
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface DataScope {
  String deptColumn() default "dept_id";
  DataScopeType type() default DataScopeType.DEPT_AND_CHILD;
}

// AOP：解析当前用户部门树，写入 DataScopeContext
@Around("@annotation(dataScope)")
public Object around(ProceedingJoinPoint pjp, DataScope dataScope) {
  var user = SecurityUtils.currentUser();
  DataScopeContext.set(buildScope(user, dataScope));
  try { return pjp.proceed(); }
  finally { DataScopeContext.clear(); }
}

// SELECT * FROM order WHERE status=1

关键/技巧

  • 数据权限 SQL 片段走索引列（dept_id、tenant_id），见第 17 章索引设计。
  • 导出、统计接口同样套数据权限，勿在 Service 里手写例外。
  • 单元测试覆盖「普通用户 vs 管理员」两种 Scope。

易错点

  • 子查询拼错导致全表泄露或空结果——用集成测试 + SQL 日志审计。

  • 租户 ID 只信前端传参——必须从 Token/网关 Header 解析。

列表及分页

PageHelper / Spring Data Pageable 与复杂查询

讲解

MyBatis 生态用 PageHelper：PageHelper.startPage(page, size) 后紧跟查询，自动 count + limit。Spring Data JPA 用 Pageable + Page<T>。统一响应：{ total, page, size, records }。排序：白名单字段防 SQL 注入（Sort.by(allowedFields)）。多条件：QueryDSL / JPA Specification / MyBatis 动态 SQL <if>；复杂报表可专用 Query Object。导出联动：列表与导出共用同一 Query Service，导出时 size=MAX 或游标分批（见 Excel 章节）。

示例代码

@GetMapping("/api/orders")
public PageResult<OrderVO> list(OrderQuery q,
    @RequestParam(defaultValue = "1") int page,
    @RequestParam(defaultValue = "20") int size) {
  PageHelper.startPage(page, size);
  var list = orderMapper.selectByQuery(q);
  var p = (Page<Order>) list;
  return PageResult.of(p.getTotal(), page, size, list.stream().map(mapper::toVo).toList());
}

// JPA
public Page<Order> search(OrderQuery q, Pageable pageable) {
  return orderRepo.findAll(buildSpec(q), pageable);
}

public record PageResult<T>(long total, int page, int size, List<T> records) {
  static <T> PageResult<T> of(long total, int page, int size, List<T> records) {
    return new PageResult<>(total, page, size, records);
  }
}

关键/技巧

  • 深分页（page>100）改游标/keyset：WHERE id > :lastId ORDER BY id LIMIT 20。
  • count 慢时：近似 total 或「超过 1 万条不精确 count」产品策略。
  • 列表字段用 VO/DTO，勿直接暴露 Entity 懒加载关联。

易错点

  • PageHelper 与后续多条 SQL 混用——分页套错语句。
  • 前端传 sort=;DROP TABLE——排序字段白名单校验。
  • 不分页全量 findAll() 接口被扫——强制 size 上限。

二维码生成

ZXing / Hutool 服务端生成、纠错级别与 Logo 叠加

讲解

典型场景：商品/资产追溯码、仓储拣货位、设备巡检点、活动签到、支付跳转 URL、小程序 scene 参数。架构上二维码生成属于轻量无状态能力——按业务主键或 URL 模板即时渲染 PNG/SVG，或预生成上传 OSS 供 CDN 缓存。

选型：ZXing（com.google.zxing:core + javase）生态成熟、可控纠错与编码；Hutool QrCodeUtil 封装 ZXing，一行生成适合内部工具；前端 qrcode.js 适合纯展示、减轻服务端压力。服务端统一生成便于审计、水印、Logo 叠加与权限校验（防任意 URL 二维码钓鱼）。

编码与纠错：内容超容量时自动升 Version；中文须指定 Charset.forName("UTF-8")。纠错级别 L/M/Q/H（约 7%～30% 可恢复）——带 Logo 或户外标签选 H；纯数字 URL 用 M 即可。边距（quiet zone）至少 4 模块宽，否则扫码枪难识别。

输出形态：① HTTP 接口直接 image/png 流式响应；② 生成 byte[] 上传 OSS 返回 URL；③ Base64 嵌入 PDF/标签模板（见标签设计及打印）。动态内容（含 Token、一次性核销码）禁止长期 CDN 缓存；静态物料码可缓存。

安全：二维码内容不编码明文密码、完整身份证；支付/登录类用短链 + 服务端校验。开放「任意内容生成」接口须鉴权 + 域名白名单，防钓鱼码批量生成。

// Maven：com.google.zxing:core + javase（或 cn.hutool:hutool-extra）
@Service
public class QrCodeService {

  public byte[] generatePng(String content, int sizePx, ErrorCorrectionLevel ecLevel) {
    var hints = Map.of(
        EncodeHintType.CHARACTER_SET, "UTF-8",
        EncodeHintType.ERROR_CORRECTION, ecLevel,
        EncodeHintType.MARGIN, 2);
    BitMatrix matrix = new MultiFormatWriter()
        .encode(content, BarcodeFormat.QR_CODE, sizePx, sizePx, hints);
    ByteArrayOutputStream out = new ByteArrayOutputStream();
    MatrixToImageWriter.writeToStream(matrix, "PNG", out);
    return out.toByteArray();
  }

  /** 中心 Logo：缩小码区后叠加，纠错须 ≥ H */
  public byte[] generateWithLogo(String content, int sizePx, BufferedImage logo) {
    BufferedImage qr = MatrixToImageWriter.toBufferedImage(
        new MultiFormatWriter().encode(content, BarcodeFormat.QR_CODE, sizePx, sizePx,
            Map.of(EncodeHintType.ERROR_CORRECTION, ErrorCorrectionLevel.H,
                   EncodeHintType.CHARACTER_SET, "UTF-8")));
    int logoSize = sizePx / 5;
    Graphics2D g = qr.createGraphics();
    g.drawImage(logo, (sizePx - logoSize) / 2, (sizePx - logoSize) / 2, logoSize, logoSize, null);
    g.dispose();
    ByteArrayOutputStream out = new ByteArrayOutputStream();
    ImageIO.write(qr, "PNG", out);
    return out.toByteArray();
  }
}

@RestController
@RequestMapping("/api/qrcode")
public class QrCodeController {
  @GetMapping(produces = MediaType.IMAGE_PNG_VALUE)
  public void png(@RequestParam String content,
                  @RequestParam(defaultValue = "256") int size,
                  HttpServletResponse resp) throws IOException {

标签设计及打印

从版面设计到出纸的完整链路

仓储面单、生产批次标、资产台账、实验室样品、零售价签等场景，都需要把业务数据变成可扫描、可粘贴、尺寸固定的物理标签。企业项目里这一能力常被拆成「设计」与「打印」两步，但落地时应视为一条链路：规格定义 → 模板设计 → 数据绑定 → 渲染 → 下发打印 → 补打审计。设计阶段决定条码能否扫、文字能否读；打印阶段决定能否静默出纸、批量是否稳定。

1. 先定规格，再画版式

标签设计的第一输入不是「长什么样」，而是物理约束：

  • 尺寸：常见 40×30mm、60×40mm、100×150mm；多规格各做独立模板，禁止同一 HTML/PDF 硬缩放适配所有纸型。
  • 打印机与 DPI：热敏常见 203/300 DPI；激光/喷墨按 A4 或自定义纸。像素与毫米换算：px ≈ mm × DPI / 25.4。例如 300 DPI 下 30mm 二维码边长约 354px。
  • 元素清单：一维码（拣货快扫）、二维码（追溯 URL/大容量）、文字（SKU、批次、日期、操作员）、Logo/警示图标。明确必填/选填与超长截断规则。
  • 留白与静区：条码/二维码四周须留 quiet zone（通常 ≥ 4 模块宽），否则工业扫码枪识别率骤降。

规格应写入 label_spec 表或配置中心（宽、高、DPI、打印机类型、模板版本），业务只引用 templateCode，避免页面里写死毫米数。

2. 模板设计：可视化 vs 代码化

  • 可视化设计器：BarTender、NiceLabel、LabelShop 等，适合运营/实施自助改版；导出 ZPL/TSPL 或 PDF 背景，后端只做字段替换。优点：所见即所得；缺点：版本管理、CI 回归需额外流程。
  • 代码化模板：Thymeleaf/Freemarker HTML、JasperReports JRXML、ZPL 字符串模板。适合 Java 团队全权掌控、字段与 API 同步演进。模板与数据解耦：存 DB/OSS + 版本号，运行时传入 DTO/Map。
  • 混合模式：设计器出「底图 + 坐标」，Java 按坐标填文字与条码——兼顾美观与动态数据。

无论哪种方式，模板变更必须升版本并保留历史，Print Agent 按版本拉取，避免旧客户端缺字段。

3. 渲染与输出格式

  • HTML + CSS 打印：@page { size: 60mm 40mm; margin: 2mm; }，浏览器预览后 window.print()。零客户端，适合办公室激光/A4 或不追求静默的场景。
  • 服务端 PDF：OpenPDF、iText、Flying Saucer 或 JasperReports，毫米级布局，可归档、可邮件、可下载。批量时合并 multipage PDF。
  • 指令式热敏：Zebra ZPL、TSC TSPL、Godex EPL，经网络 9100 或 USB 直写，工业现场主流。条码用 ^BC、二维码用 ^BQ，模块大小与打印机 DPI 对齐。
  • 国产静默打印：Lodop / C-Lodop，常见于政务、医疗 Win 客户端；新系统优先评估 Print Agent，减少浏览器插件依赖。

4. 打印下发：浏览器无法直连 USB

Web 应用受浏览器沙箱限制，不能直接操作本地 USB 打印机。常见路径：

  • A. 人工：预览 HTML 或下载 PDF，用户自行打印——实现最简单，不适合产线节拍。
  • B. Print Agent：内网部署小服务（Java / Electron），轮询 print_job 队列，拉取 ZPL/PDF 后调系统打印 API；适合仓库工位 PC。
  • C. 服务端代打：应用服务器向内网打印机 IP:9100 写 ZPL——须网络隔离、IP 白名单、任务鉴权，禁止暴露公网。
  • D. 云打印：部分厂商提供云端到设备的通道，按 SLA 与数据合规评估是否采用。

批量打印建议走 MQ + 幂等任务表：写入 print_job(status=PENDING) → Agent 消费 → 回写 PRINTED/FAILED；失败可重试，与定时任务配合做补打对账。

图表展示

后端聚合 API 与 ECharts 数据约定

讲解

图表数据由后端聚合，前端只负责渲染——避免把明细拉到浏览器再 groupBy。接口设计：按图表类型返回 ECharts 友好结构——折线/柱状 { categories: [], series: [{ name, data: [] }] }；饼图 [{ name, value }]。大屏：独立只读 API，Redis 缓存聚合结果（TTL 30s–5min），WebSocket 推送增量可选。报表 vs 实时：报表走 OLAP/预聚合表；实时监控走时序库或滑动窗口 SQL。权限：统计 API 同样套数据权限与 RBAC。

示例代码

  return new ChartVO(
      categories,
      List.of(

        new Series("已取消", cancelled)

  );
}

关键/技巧

  • 时间范围必填且设上限（如最多 90 天），防全表扫描。

HTTP 请求

RestClient / WebClient / OpenFeign 与第三方·微服务调用

讲解

HTTP 请求模块是企业项目的出站集成层：调用第三方支付、短信/OCR、地图、ERP，或内部微服务 REST API。与OpenAPI 文档（描述「别人怎么调我」）相对，本章聚焦「我怎么调别人」。架构原则：业务 Service 不直接散落 new HttpClient()，而是经统一 Client 封装 + 防腐层（ACL）隔离外部 DTO 与领域模型；超时、重试、熔断、日志 traceId 在基础设施层统一治理。

客户端选型（Spring Boot 3）：RestClient——同步阻塞，MVC + 虚拟线程场景首选，替代已废弃的 RestTemplate；WebClient——响应式/异步，WebFlux 或需并发聚合多下游时用；OpenFeign——声明式 HTTP，微服务间强契约、配合 Nacos/LoadBalancer；底层仍可走 JDK HttpClient（见第 10 章）。容错与 Resilience4j 集成见第 12 章；幂等与重试边界见第 03 章 API 设计。

关键/技巧

  • RestClient/WebClient 注册为 Spring Bean，全局单例复用连接池；禁止每次请求 new 客户端。
  • 连接超时（connect）与读超时（read/response）分开配置；下游 SLA 不同则分 Client Bean（如 smsRestClient、payRestClient）。
  • 重试仅用于幂等 GET 或带 Idempotency-Key 的 POST；支付/下单类写操作默认不重试，靠 MQ 补偿。
  • Feign 配合 @LoadBalancerClient + Nacos 服务名，URL 不写死 IP；本地开发可用 spring.cloud.openfeign.client.config.*.url 覆盖。
  • 敏感 Header（Authorization、签名密钥）走配置中心，日志脱敏；回调验签见支付模块。

易错点

  • 在 @Transactional 内同步调外部 HTTP——长事务占连接、外部慢拖垮 DB；外部调用放事务外或改异步。
  • 无超时配置，下游 hang 导致线程池耗尽——生产必配 connect + read 双超时。
  • 直接把第三方 JSON 当领域 Entity 用——字段变更/多余字段污染模型，必须防腐层映射。
  • Feign 默认重试 + 非幂等 POST → 重复下单；关闭 Feign 重试或仅对幂等接口开启。
  • SSL 证书校验被 trustAll 关掉——中间人攻击；测试环境用正规测试证书或 mTLS。

速记

「Bean 单例复连接，双超时防挂死；防腐层隔外部，幂等才重试。」

连接池 Druid

Druid 连接池治理、监控与生产调优

讲解

Druid 定位：阿里开源的 JDBC 连接池（Connection Pool），核心价值是连接管理 + SQL 监控 + Web 控制台一体化，适合对数据库访问可观测性要求较高的中大型业务系统。适用场景：你需要在线观察 SQL 执行统计、慢 SQL、连接活跃度，且希望在不引入额外 APM 组件时也有基础诊断能力。

与 HikariCP 简要对比：HikariCP（Spring Boot 默认）性能与延迟表现更极致，配置更精简；Druid在监控治理能力上更「开箱即用」。选型建议：极致吞吐优先 HikariCP；运维监控与 SQL 画像优先 Druid。二者都可用于生产，关键在于参数治理与容量规划。

核心配置思想：initialSize/minIdle/maxActive 控制池容量；maxWait 控制获取连接等待上限；timeBetweenEvictionRunsMillis + minEvictableIdleTimeMillis 做空闲连接回收与健康检测；泄漏治理关注长事务和未关闭连接（Connection Leak）。建议结合第 11 章 SQL 优化与第 20 章容量评估一起调参。

示例代码

# application.yml（Spring Boot 3.x + druid-spring-boot-starter）
spring:
  datasource:
    type: com.alibaba.druid.pool.DruidDataSource
    url: jdbc:mysql://127.0.0.1:3306/demo?useUnicode=true&characterEncoding=utf8&serverTimezone=Asia/Shanghai
    username: demo
    password: ${DB_PASSWORD}
    driver-class-name: com.mysql.cj.jdbc.Driver
    druid:
      # 池容量（Pool Sizing）
      initial-size: 5
      min-idle: 5
      max-active: 30
      max-wait: 3000

      # 连接检测与回收（Validation & Eviction）
      validation-query: SELECT 1
      test-while-idle: true
      test-on-borrow: false
      test-on-return: false
      time-between-eviction-runs-millis: 60000
      min-evictable-idle-time-millis: 300000

      # 监控与慢 SQL（Stat / Slow SQL）
      filter:
        stat:
          enabled: true
          merge-sql: true
          log-slow-sql: true
          slow-sql-millis: 200
        wall:
          enabled: true

      # 监控台（StatViewServlet）与 Web 统计（WebStatFilter）
      stat-view-servlet:
        enabled: true
        url-pattern: /druid/*
        login-username: admin
        login-password: ${DRUID_ADMIN_PASSWORD}
        allow: 127.0.0.1,10.0.0.0/8
        deny: 0.0.0.0/0
      web-stat-filter:
        enabled: true
        url-pattern: /*
        exclusions: "*.js,*.css,*.png,*.jpg,*.ico,/druid/*"

关键/技巧

  • 容量估算（Capacity Planning）：maxActive 不应超过数据库可承载并发连接，建议按「实例数 × 池上限」反推 DB max_connections。
  • 等待超时（Acquire Timeout）：maxWait 过大容易放大级联超时，建议 1s-5s，并在业务层做降级/快速失败。
  • 检测周期（Eviction Interval）：timeBetweenEvictionRunsMillis 常用 30s-60s；validationQuery 需轻量且可执行。
  • 监控统计（Observability）：开启 StatFilter 观察 SQL 次数、耗时、慢 SQL，结合链路追踪定位热点语句。
  • 安全治理（Security Hardening）：监控台必须鉴权 + IP 白名单，禁止公网裸露；密码放环境变量/密钥服务，不写死配置文件。

易错点

  • 连接泄漏（Connection Leak）：代码异常路径未关闭连接，连接数持续上涨；排查重点是长事务、手写 JDBC、流式查询未及时释放。
  • 连接耗尽（Pool Exhausted）：高峰期大量请求阻塞在取连接，表现为线程堆积 + RT 飙升；优先看慢 SQL、索引缺失和事务过长。
  • wait_timeout 不匹配：MySQL 已断开空闲连接，但连接池仍复用旧连接，出现 Communications link failure；需对齐连接存活时长与 DB 超时。
  • 监控全开但无采样策略，导致高并发下统计开销偏大；线上应按压测结果平衡可观测性与性能。

生产建议 checklist

  • 连接池参数已通过压测验证：峰值 QPS 下无大量等待、无连接耗尽。
  • 慢 SQL 阈值、告警规则、责任人闭环已建立（至少覆盖核心交易链路）。
  • /druid/* 仅内网可达，启用强口令/鉴权，禁止重置功能（resetEnable=false）。
  • 敏感信息（数据库口令、监控账号）走密钥管理，不落 Git 与日志。
  • 已核对 MySQL wait_timeout、应用事务超时、连接池回收参数的一致性。
  • 故障预案明确：连接泄漏、连接耗尽、数据库抖动时的限流/降级/熔断策略已演练。

速记

「Hikari 重性能，Druid 重治理；池参数看容量，慢 SQL 看根因，监控台先加锁再开放。」

后台定时任务

Spring @Scheduled、Quartz 与 XXL-JOB

讲解

选型：@Scheduled 适合单实例、简单 cron；Quartz 集群需 JDBC JobStore；XXL-JOB 国内常用，控制台调度、分片、失败告警、执行日志开箱即用。分布式防重复：Redis 分布式锁（Redisson tryLock）、数据库悲观锁、或 XXL-JOB 路由策略「第一个/分片」。任务要幂等：重复触发不产生脏数据。长任务：记录进度、支持中断；失败指数退避重试，最终进死信人工处理。

示例代码

@EnableScheduling
@SpringBootApplication
public class App { }

@Component
public class ReconcileJob {
  @Scheduled(cron = "0 0 2 * * ?")
  public void run() {

规则引擎 — 业务规则与决策表

Drools / Easy Rules / Aviator 与 Spring 集成

讲解

何时用规则引擎 vs 硬编码：规则少且稳定（如订单状态转移）→ 代码 + 枚举即可；规则多、变、需业务人员参与（定价档位、风控策略、促销叠加）→ 外置到引擎。硬编码 if-else 链在需求频繁变更时产生「改一行崩全局」——规则引擎把决策逻辑与执行代码解耦，支持版本、审计与热更新。

选型简述：Drools（Red Hat，国内金融/电商常用）——完整 RETE 引擎，支持 .drl 与 Excel 决策表；Easy Rules——轻量 POJO 规则，适合简单 if-then；Aviator（阿里）——高性能表达式引擎，适合动态公式/脚本化计算（定价表达式、 eligibility 表达式）。场景：定价、风控拦截、促销互斥、审批分支条件、会员 eligibility 判断。

Spring 集成：Drools 注入 KieContainer / KieSession，规则放 resources/rules/*.drl 或 .xlsx 决策表；执行前 insert(fact)，fireAllRules() 后读取 fact 上结论字段。与工作流分工：工作流管「谁在什么节点、任务怎么流转」；规则引擎管「这个节点/这个请求该不该通过、算多少钱」——BPMN 网关条件可调用规则服务，但不要把长流程编排写进 DRL。

热更新与版本：规则文件存 DB/OSS + 版本号，发布时重建 KieContainer 或 Drools KJAR 动态加载；灰度按租户/用户标签路由规则集；变更须留审计与回滚包。

flowchart TD
    REQ[业务请求/事实 Fact] --> LOAD[加载规则集 version=N]
    LOAD --> SESSION[KieSession / 表达式引擎]
    SESSION --> MATCH[模式匹配 / 表达式求值]
    MATCH --> FIRE[fireAllRules / eval]
    FIRE --> OUT[更新 Fact 结论字段]

  • Aviator 开放任意脚本无沙箱——限制可用函数与白名单，防注入。

讲解

  @Transactional
  public void handleNotify(PayNotify notify) {
    var order = payOrderRepo.findByOutTradeNoForUpdate(notify.outTradeNo())
        .orElseThrow();
    if (order.getStatus() == PayStatus.SUCCESS) return; // 幂等短路
    if (!order.getAmount().equals(notify.amount())) {
      throw new PayException("AMOUNT_MISMATCH"); // 金额篡改
    }
    order.markSuccess(notify.channelTradeNo());
    outboxRepo.save(OutboxEvent.paySuccess(order)); // 与订单同事务
  }
}

// 对账 Job（XXL-JOB，见 scheduled-jobs）
@XxlJob("reconcileWechat")
public void reconcile() {
  var bill = wechatClient.downloadBill(yesterday());
  reconcileService.diff(bill, payOrderRepo.findByDate(yesterday()));
}

关键/技巧

  • 回调 URL 只走 HTTPS 公网；内网服务用网关暴露 /pay/notify/*，IP 白名单可选。
  • 主动查单（关单/补单）：用户未付或回调丢失，定时 Job 调渠道「订单查询」，与回调双通道保障最终一致。
  • 渠道重复 notify 返回相同 SUCCESS 即可，但业务层必须幂等；应答体严格按渠道文档，勿改 Content-Type。
  • 金额用「分」long 或 BigDecimal 存库，禁止 double；对账差异 > 0 自动告警。

易错点

  • 未验签就改订单状态——伪造回调免费拿货。
  • 回调里同步调用发货/短信——超时导致渠道重试风暴；应 Outbox + MQ 异步。
  • 只信前端「支付成功」跳转——必须以服务端回调或查单为准。
  • 私钥提交 Git 或打日志——见第 19 章密钥管理；证书过期未监控。
  • 退款未幂等——重复请求导致多退；out_refund_no 业务唯一。

速记

「先验签再改态，幂等键防重放；Outbox 异步下游，T+1 对账兜底。」
