11 持久化

持久层是大多数性能事故与一致性 bug 的源头——SQL 要会写，更要会解释。

MyBatis vs JPA 选型

持久化框架决策矩阵

概要

| 场景                     | 推荐        | 理由                          |
|--------------------------|-------------|-------------------------------|
| 复杂报表/SQL 可控/遗留 SQL | MyBatis     | SQL 显式、优化透明            |
| 领域模型清晰/CRUD 为主     | JPA         | 对象映射、Specification 查询  |
| 混合项目                   | 分模块选型  | 核心域 JPA，报表 MyBatis      |

与第 12 章数据访问、RuoYi（MyBatis）对照：同一项目可共存，但同一聚合勿双栈。

SQL 优化

EXPLAIN 与慢查询治理

概要

优化流程：定位慢 SQL（慢日志/pg_stat_statements/AWR/APM）→ EXPLAIN 看 type/key/rows/Extra → 改索引或改写 SQL。避免 SELECT *、隐式类型转换、函数包裹索引列、大 offset 分页。深翻页优先 keyset（seek）分页；同时结合业务排序字段保证翻页稳定性。

示例代码

-- 反模式：offset 深分页
SELECT * FROM orders ORDER BY id LIMIT 1000000, 20;

-- 正模式：keyset 分页
SELECT * FROM orders
WHERE id > :lastId
ORDER BY id
LIMIT 20;

EXPLAIN ANALYZE
SELECT o.id, o.total FROM orders o
WHERE o.customer_id = ? AND o.status = 'PAID';

易错点

  • ORM 生成 N+1——开发环境开 spring.jpa.show-sql 或 p6spy；生产用 Micrometer hibernate.query 或 APM SQL 聚合，单请求 SQL 数 > 10 告警。
  • 在循环中单条 insert——改 JdbcTemplate.batchUpdate 或 MyBatis BATCH executor。

索引设计

联合索引与覆盖索引

概要

最左前缀：联合索引 (a,b,c) 通常可加速 a、ab、abc 条件；若缺失前导列，优化器可利用的索引能力会明显下降（个别数据库/版本存在特殊优化，不宜绝对化）。设计顺序一般遵循“等值匹配在前、范围条件靠后、排序分组字段随后”，并以实际 EXPLAIN ANALYZE 结果校验。覆盖索引命中后可减少回表（MySQL 常见 Using index）。软删除场景常用 (deleted, biz_key) 复合索引；大表加索引优先在线 DDL（MySQL 8 视语句可能为 INPLACE/INSTANT）。

graph TB
    ROOT[B+ 树根节点] --> IN1[内部节点]
    ROOT --> IN2[内部节点]
    IN1 --> LEAF1[叶子节点 有序键值+指针]
    IN2 --> LEAF2[叶子节点 双向链表]
    LEAF1 --- LEAF2
    LEAF1 --> ROW1[回表查数据行]
    COVER[覆盖索引] --> LEAF1

图：B+ 树索引结构概念——叶子链表与回表

示例代码

-- 查询：WHERE customer_id = ? AND status = ? ORDER BY created_at DESC
CREATE INDEX idx_orders_cust_status_created
    ON orders (customer_id, status, created_at DESC);

-- 覆盖索引
CREATE INDEX idx_orders_cover ON orders (customer_id, status)
    INCLUDE (total, created_at); -- PostgreSQL

速记

「等值在前，范围在后；高选择性优先；以 EXPLAIN ANALYZE 的实际代价与行数估算为准，不迷信单一指标。」

事务隔离

ACID 与 Spring @Transactional

概要

隔离级别：RU、RC（Oracle 默认）、RR（MySQL InnoDB 默认）、Serializable（PostgreSQL 默认是 RC）。典型问题：脏读、不可重复读、幻读。InnoDB 在 RR 下结合 MVCC 与 next-key lock，通常可避免常见幻读场景；但在“当前读/锁定读”与“快照读”混用时，仍需按语句语义逐条验证。Spring 默认传播 REQUIRED、隔离随数据库默认；跨库或读写分离时注意同一业务链路的事务上下文与连接一致性。readOnly=true 在 Spring 中主要是优化提示（如 Hibernate flush 策略、路由决策），不等同于数据库层面的强制只读。自调用不走代理——事务失效经典坑。

flowchart LR
    RU[READ UNCOMMITTED] -->|脏读| RC[READ COMMITTED]
    RC -->|不可重复读| RR[REPEATABLE READ]
    RR -->|幻读| SER[SERIALIZABLE]
    RR --> MVCC[InnoDB MVCC + Gap Lock]

图：事务隔离级别与典型并发问题

示例代码

@Service
public class TransferService {
    @Transactional(isolation = Isolation.READ_COMMITTED, rollbackFor = Exception.class)
    public void transfer(UUID from, UUID to, BigDecimal amount) {
        Account a = accountRepo.lockById(from); // SELECT FOR UPDATE
        Account b = accountRepo.lockById(to);
        if (a.balance().compareTo(amount) < 0) throw new InsufficientFundsException();
        a.debit(amount);
        b.credit(amount);
    }
}

易错点

  • 同类内部 this.method() 调用带 @Transactional 方法不生效——拆 Bean 或注入 self 接口。
  • 捕获异常后吞掉或转为正常返回会导致不回滚——应继续抛出异常，或显式标记 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()。
  • @Transactional 加在 private 方法无效（代理无法拦截）。
  • 长事务占连接、锁行——外部 HTTP/MQ 放事务外，事务内只做 DB。

连接池

HikariCP 配置与泄漏检测

概要

Spring Boot 3 默认 HikariCP。连接数并非越大越好：MySQL max_connections 有限，过多连接会放大数据库线程竞争与上下文切换。实践上以压测反推池大小：可先从每实例 10~30 的 maximum-pool-size 起步，再按吞吐、P99 延迟和数据库负载调优；K8s 多副本时各 Pod 池大小之和须控制在 DB max_connections 的安全水位（常见建议不超过 70%~80%）。max-lifetime 应小于 DB/防火墙连接超时（预留 30~60s 余量）。启用 leak-detection-threshold（如 60000）排查未归还连接。

flowchart LR
    APP[应用线程] -->|getConnection| POOL[HikariCP 连接池]
    POOL -->|借用| CONN[物理连接]
    CONN --> DB[(MySQL)]
    APP -->|close/try-with-resources| POOL
    LEAK[泄漏检测] -->|超时未归还| ALERT[告警堆栈]

图：HikariCP 连接池借还流程

示例代码

spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      minimum-idle: 5
      connection-timeout: 30000
      idle-timeout: 600000
      max-lifetime: 1800000
      leak-detection-threshold: 60000
      # 监控：Actuator metrics jdbc.connections.active / pending

关键/技巧

  • 连接池等待持续 > 0 → 先查慢 SQL 与事务过长，再考虑加大 pool（最后手段）。
  • 读写分离：RoutingDataSource + @Transactional(readOnly=true) 路由从库，写后立即读走主库防延迟。

JPA / Hibernate 生产陷阱

N+1 · 懒加载 · 二级缓存

概要

N+1：查 1 条主表 + N 次关联懒加载。诊断：开启 hibernate.statistics 或 p6spy，单请求 SQL 数异常。修复：@EntityGraph、JOIN FETCH、DTO 投影（@Query 直接 new DTO）。懒加载须在 Session 内访问——Controller 层触 LazyInitializationException 说明边界泄漏。二级缓存慎用，优先 Redis；实体缓存与业务缓存混用易不一致。

示例代码

@EntityGraph(attributePaths = {"lines", "customer"})
Optional<Order> findWithDetails(UUID id);

@Query("select new com.example.OrderSummary(o.id, o.total) from Order o where o.customerId = :cid")
List<OrderSummary> summarize(@Param("cid") String customerId);

分布式 ID

雪花 · ULID · 号段

概要

分库分表场景需全局唯一、趋势递增 ID。选型见第 03 章表设计：雪花（高性能，须处理时钟回拨）；ULID（字典序友好、无中心）；DB 号段（Leaf/Hi/Lo，依赖 DB 但简单）。Java 21 可用 UUID.randomUUID() 作非排序主键。

Flyway 迁移

版本化 Schema 变更

概要

Flyway 按 V{version}__{description}.sql 顺序执行，记录在 flyway_schema_history。变更原则：向前兼容（expand-contract）——先加列/表，双写，再删旧列。禁止修改已发布 migration 文件。

零停机大表 DDL

MySQL 大表加索引/改列：优先 Online DDL；不支持时用 gh-ost / pt-osc。流程：expand（加 nullable 列）→ 双写应用 → backfill → contract（删旧列）。与第 04 章上线窗口协调低峰执行。

示例代码

-- V1__create_orders.sql
CREATE TABLE orders (
    id          UUID PRIMARY KEY,
    customer_id VARCHAR(64) NOT NULL,
    status      VARCHAR(32) NOT NULL,
    total       NUMERIC(19,4) NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_orders_customer ON orders (customer_id);

-- V2__add_orders_version.sql
ALTER TABLE orders ADD COLUMN version BIGINT NOT NULL DEFAULT 0;

易错点

  • 大表 DDL（加列/改类型/加索引）要先评估是否可在线执行；MySQL 8 部分语句支持 INSTANT/INPLACE，无法在线时再考虑 gh-ost/pt-osc。
  • 多分支 migration 版本号冲突——团队统一版本号段。

数据库事务落地清单

输入

  • 事务边界与隔离级别要求
  • 慢 SQL 与索引现状报告

验收标准

  • 关键 SQL 有执行计划证据
  • 事务边界与幂等策略一致
  • 迁移变更可灰度并可回退

失败信号

  • 长事务跨远程调用未拆分
  • 索引策略无法覆盖核心查询
  • DDL 变更无演练直接上线
