18 测试·质量

测试是设计反馈环；质量门禁比事后救火便宜几个数量级。

JUnit 5

单元测试结构与参数化

讲解

JUnit 5 由 Jupiter（测试 API）、Platform（测试平台）、Vintage（JUnit 4 兼容层，可选）组成。测试命名应表达行为：shouldRejectWhenBalanceInsufficient。AAA 模式：Arrange-Act-Assert。参数化测试 @ParameterizedTest 用于覆盖边界与等价类组合。避免依赖测试执行顺序与共享可变状态。

springframework 测试依赖默认有带：
<dependency>
<groupId>org.springframework.boot</groupId>
<artifactId>spring-boot-starter-test</artifactId>
<scope>test</scope>
</dependency>

示例代码

@DisplayName("TransferService")
class TransferServiceTest {
    TransferService service = new TransferService(mockRepo(), mockGateway());

    @Test
    void shouldRejectWhenBalanceInsufficient() {
        var from = accountWithBalance("100.00");
        assertThrows(InsufficientFundsException.class,
            () -> service.transfer(from.id(), UUID.randomUUID(), new BigDecimal("200")));
    }

    @ParameterizedTest
    @CsvSource({ "0, false", "0.01, true", "999999.99, true" })
    void shouldValidateAmount(String amount, boolean valid) {
        assertEquals(valid, validator.isValid(new BigDecimal(amount)));
    }
}

关键/技巧

  • @Nested 按场景分组；@Tag("slow") 区分 CI 快/慢套件。
  • AssertJ 流式断言可读性优于 JUnit 原生 assertEquals。

Mockito

Mock、Spy 与验证交互

讲解

Mock 用于隔离被测单元的外部依赖；Spy 用于包装真实对象并按需替换部分行为。只 mock 跨边界协作者（Repository、HTTP Client），不 mock 值对象。验证行为 verify(mock, times(1)).save(...)；避免过度约束（over-specification，绑死实现细节）。

flowchart LR
    SUT[被测单元] --> MOCK[Mock 外部依赖]
    SUT --> REAL[真实值对象/纯逻辑]
    MOCK -->|verify 交互| BOUNDARY[跨边界协作者]
    AVOID[避免] --> IMPL[Mock 内部实现细节]

图：Mockito 边界——只隔离跨边界依赖

示例代码

@ExtendWith(MockitoExtension.class)
class CreateOrderHandlerTest {
    @Mock OrderRepository repo;
    @Mock PaymentGateway gateway;
    @InjectMocks CreateOrderHandler handler;

    @Test
    void shouldPersistAndCharge() {
        when(gateway.charge(any())).thenReturn(PaymentResult.ok("pay_1"));
        when(repo.save(any())).thenAnswer(inv -> inv.getArgument(0));

        var order = handler.handle(new CreateOrderCommand(...));

        assertThat(order.status()).isEqualTo(Status.PAID);
        verify(gateway).charge(argThat(c -> c.amount().signum() > 0));
    }
}

易错点

  • mock 过多导致测试与实现耦合，重构全红。
  • when(voidMethod()) 应用 doThrow().when() 语法。

Testcontainers

集成测试与真实依赖

讲解

Testcontainers 在 Docker 中启动 PostgreSQL、Redis、Kafka 等依赖，使集成测试更贴近生产。Spring Boot 3.1+ 原生支持 @ServiceConnection。测试数据可用 @Sql 或 fixture builder 管理；测试之间需保证数据隔离（事务回滚或显式清理）。容器复用适合本地提速，CI 通常应关闭复用以避免状态污染。

示例代码

@SpringBootTest
@Testcontainers
class OrderIntegrationTest {
    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:14-alpine");

    @DynamicPropertySource
    static void props(DynamicPropertyRegistry registry) {
        registry.add("spring.datasource.url", postgres::getJdbcUrl);
        registry.add("spring.datasource.username", postgres::getUsername);
        registry.add("spring.datasource.password", postgres::getPassword);
    }

    @Autowired TestRestTemplate rest;

    @Test
    void shouldCreateOrder() {
        var resp = rest.postForEntity("/api/v1/orders", request, OrderResponse.class);
        assertThat(resp.getStatusCode()).isEqualTo(HttpStatus.CREATED);
    }
}

UAT 环境搭建 — 预发布验收与数据策略

业务验收环境与上线前 Gate

讲解

UAT 定位：User Acceptance Testing 环境是上线前最后一道业务验收关——PO、业务方、QA 在接近生产的拓扑上验证需求是否「做对」。与 dev/test/staging/prod 分工：dev 本地联调；test（CI）跑自动化；staging 常作技术预发/性能；UAT 强调业务场景与签字；prod 承载真实流量。与第 18 章 TDD/测试金字塔分工：TDD 在开发环验证「写对代码」；Testcontainers 集成测试在 CI 验证组件协作；UAT 验证端到端业务价值与验收标准，不替代单元/集成自动化。

环境拓扑：UAT 须独立实例（不与 dev 共享 DB/Redis），Spring profile uat，中间件版本与 prod 对齐（PostgreSQL 16、Redis 7、Kafka 同 minor）。K8s 用独立 namespace（如 uat-order），ConfigMap/Secret 与 prod 结构同构、值不同。禁止 UAT 直连 prod 库——验收失败可 wipe 重建，不影响生产。

数据策略：① 脱敏生产副本（定时从 prod 快照 restore + 掩码手机号/身份证/卡号，见第 17 章日志脱敏）；② 合成数据（Faker/工厂类生成边界场景）；③ 刷新周期（每周或每迭代首日 reset，避免脏数据累积）。禁止真实 PII进入 UAT——违规即安全事件。

部署与晋级：CI 流水线 test 绿 → 晋级 UAT（同一不可变镜像 tag/digest，见第 21 章 CI/CD）；Flyway 随部署自动迁移；未完成特性用特性开关（LaunchDarkly/Unleash/@ConditionalOnProperty）在 UAT 打开、prod 关闭。

访问与权限：VPN 或 IP 白名单；专用测试账号（非员工真实账号）；RBAC 与 prod 隔离——UAT 角色可宽于 prod 便于验收，但须与 prod 权限模型同构（见第 16 章 RBAC），避免「UAT 能过、prod 403」。

验收流程：UAT checklist（需求 ID → 场景 → 期望 → 实际 → Pass/Fail）→ 缺陷流转 Jira/Linear（blocker 禁止晋级 prod）→ PO/业务签字 Gate → 才进入蓝绿/金丝雀发布（细节见第 21 章发布策略）。

flowchart LR
    DEV[dev 本地] --> TEST[test CI 自动化]
    TEST -->|镜像 tag 晋级| UAT[UAT 业务验收]
    UAT -->|签字 Gate| PROD[prod 蓝绿/金丝雀]
    UAT -.->|脱敏副本/合成数据| DATA[(UAT 独立 DB)]
    UAT -.->|VPN/白名单| PO[PO / QA / 业务]

图：dev → test → UAT → prod 晋级与 UAT 数据/访问隔离

示例代码

# application-uat.yml
spring:
  profiles: uat
  datasource:
    primary:
      url: jdbc:postgresql://uat-db.internal:5432/order_uat
      username: ${UAT_DB_USER}
      password: ${UAT_DB_PASSWORD}
    readonly:
      url: jdbc:postgresql://uat-db-replica.internal:5432/order_uat
      username: ${UAT_RO_USER}
      password: ${UAT_RO_PASSWORD}
  data:
    redis:
      host: uat-redis.internal
      port: 6379
  flyway:
    enabled: true
    locations: classpath:db/migration

app:
  feature:
    new-checkout: true   # UAT 开启，prod application-prod.yml 为 false

logging:
  level:
    root: INFO
  pattern:
    console: "%d{ISO8601} [%X{traceId}] %-5level %logger - %msg%n"

---
# k8s/uat/deployment.yaml（节选）
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-service
  namespace: uat-order
spec:
  replicas: 2
  template:
    spec:
      containers:
        - name: app
          image: registry.example.com/order:1.4.0-uat.42   # CI 晋级 tag
          env:
            - name: SPRING_PROFILES_ACTIVE
              value: uat
          readinessProbe:
            httpGet: { path: /actuator/health/readiness, port: 8080 }

# CI 晋级片段（GitHub Actions）
- name: Deploy UAT
  if: github.ref == 'refs/heads/release/1.4.0'
  run: |
    kubectl -n uat-order set image deploy/order-service \
      app=registry.example.com/order:${{ github.sha }}
    kubectl -n uat-order rollout status deploy/order-service

关键/技巧

  • UAT checklist 与需求/User Story ID 一一映射，便于追溯与签字。
  • 多数据源：主库读写验收流程，只读从库验证报表/导出——与 prod 只读分离同构。
  • 数据刷新脚本自动化（CronJob + pg_restore + 脱敏 SQL），减少手工操作。
  • 特性开关默认值 prod-off、uat-on，避免误开生产。

易错点

  • UAT 与 staging 混用同一 namespace/DB——验收脏数据互相污染。
  • 用 prod 真实 PII「方便测试」——合规与安全双重风险。
  • UAT 跳过 Flyway 手工改表——与 prod 迁移路径不一致，上线必炸。
  • 未设签字 Gate 直接推 prod——业务未验收的功能流入生产。

速记

「UAT = 独立实例 + 脱敏数据 + 业务签字；test 自动化，UAT 验价值，prod 才放量。」

延伸阅读：第 21 章 CI/CD、第 17 章数据脱敏、第 11 章 Flyway

静态分析

SpotBugs、PMD、Checkstyle 与 SonarQube

讲解

静态分析在编码与构建阶段发现空指针、资源泄漏、安全缺陷等问题。Checkstyle 管代码风格；SpotBugs/PMD 侧重缺陷模式；SonarQube 聚合覆盖率、重复率与安全热点。CI 中设置 Quality Gate（质量门禁）：例如新代码覆盖率 ≥ 80%、零 blocker issue（阻断问题）。

flowchart TD
    CODE[提交代码] --> CI[CI Pipeline]
    CI --> UNIT[单元测试]
    CI --> STATIC[SpotBugs/PMD/Checkstyle]
    CI --> SONAR[SonarQube 扫描]
    SONAR --> GATE{Quality Gate}
    GATE -->|通过| MERGE[允许合并]
    GATE -->|失败| FIX[修复后重跑]

图：质量门禁在 CI 流水线中的位置

示例代码

<!-- pom.xml 片段 -->
<plugin>
  <groupId>com.github.spotbugs</groupId>
  <artifactId>spotbugs-maven-plugin</artifactId>
  <configuration>
    <effort>Max</effort>
    <threshold>Low</threshold>
    <failOnError>true</failOnError>
  </configuration>
</plugin>

关键/技巧

  • 增量扫描：优先对 New Code（新增/变更代码）设置阻断阈值，避免历史债务一次性阻塞交付。
  • @SuppressWarnings 必须注释理由与 ticket 号。

契约测试

Pact · Spring Cloud Contract · CI 门禁

讲解

契约测试填补单元测试与 E2E 之间的鸿沟：独立验证服务双方对 API/消息的理解一致。架构层规范见第 03 章契约测试。Pact（Consumer-Driven）消费方发布期望，提供方验证；Spring Cloud Contract 适合 JVM 生态，契约即 Groovy/YAML，CI 生成 Stub。

Pact 消费者示例（JUnit 5）

@Pact(consumer = "order-service")
RequestResponsePact orderPact(PactDslWithProvider builder) {
  return builder
      .given("order exists")
      .uponReceiving("get order")
      .path("/api/v1/orders/1").method("GET")
      .willRespondWith().status(200)
      .body(new PactDslJsonBody().stringType("id", "1"))
      .toPact();
}

@ExtendWith(PactConsumerTestExt.class)
class OrderClientTest {
  @Test
  @PactTestFor(pactMethod = "orderPact")
  void fetch(MockServer mockServer) {
    var client = new OrderClient(mockServer.getUrl());
    assertThat(client.get("1").id()).isEqualTo("1");
  }
}

关键/技巧

  • 契约变更走 PR + Broker 版本化，与 OpenAPI lint 同级 CI 门禁。
  • Provider 验证失败阻断发布，避免「上游改字段下游全挂」。

ArchUnit 架构测试

分层依赖规则与架构腐化防护

讲解

ArchUnit 在测试中断言包依赖、命名、注解规则，防止 Domain 依赖 Infrastructure、Controller 绕过 Service 等架构违规。与第 12 章分层对齐，纳入 CI。

示例代码

@AnalyzeClasses(packages = "com.example.shop", importOptions = ImportOption.DoNotIncludeTests.class)
class ArchitectureTest {
  @ArchTest
  static final ArchRule domainIndependent = noClasses()
      .that().resideInAPackage("..domain..")
      .should().dependOnClassesThat().resideInAnyPackage("..infrastructure..", "..web..");

  @ArchTest
  static final ArchRule servicesTransactional = classes()
      .that().haveSimpleNameEndingWith("ApplicationService")
      .should().beAnnotatedWith(Service.class);
}

E2E 测试

Playwright · 数据工厂 · Flaky 治理

讲解

E2E 验证端到端业务价值，数量应少（测试金字塔顶层）。Playwright 支持多浏览器、自动等待、trace 回放。与第 18 章 TDD、UAT分工：E2E 在 CI 跑主路径 Smoke；UAT 由业务方签字。

Playwright 示例（TypeScript）

test('下单主路径', async ({ page }) => {
  await page.goto('/login');
  await page.fill('[name=username]', process.env.E2E_USER);
  await page.click('button[type=submit]');
  await page.click('text=新建订单');
  await expect(page.locator('.order-success')).toBeVisible({ timeout: 10000 });
});

Flaky 治理

  • 固定测试数据工厂 + Testcontainers 隔离，禁止依赖 prod 数据。
  • 失败自动 retry 最多 1 次；连续 flaky 记 tech debt 根因修复。

Code Review

Review 清单与可维护性

讲解

Review 关注：正确性（边界/并发/事务）、安全性（注入/鉴权/敏感数据）、可观测性（日志/traceId）、可测试性、性能（N+1/无界查询）。小 PR（<400 行）通常更快完成评审与合并。评论对事不对人，区分 nit / suggestion / blocker（阻断项）。与重构结合：发现重复/过长方法时，在 PR 内或跟进 PR 做「行为不变的小步重构」（重构 原则：测试绿灯 → 重构 → 再绿）。

速记 Checklist

维度问什么
正确性失败路径？幂等？
安全输入校验？权限？
性能热路径 IO？索引？
运维日志可搜？指标？
测试关键路径有测？

易错点

  • Review 只看风格不看语义——风格交给 linter。
  • 巨型 PR 没人认真看——拆分为可独立发布的增量。

延伸阅读：Clean Code、重构（Martin Fowler）

章末实战闭环

质量保障落地清单

输入

  • 质量目标与缺陷分级标准
  • 测试环境、数据与依赖准备
  • 静态分析与审查规则集
  • UAT 参与方与验收口径

输出

  • 单元/集成/UAT 全链路计划
  • 缺陷闭环与质量看板
  • 发布前质量门禁报告

验收标准

  • 关键路径具备自动化覆盖
  • 阻断级缺陷在发布前清零
  • 质量指标与业务结果联动

失败信号

  • 只看覆盖率不看用例价值
  • 测试环境与生产差异过大
  • 缺陷重复发生无根因改进
