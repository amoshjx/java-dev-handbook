19 性能调优

没有度量就没有优化——先定位瓶颈类型（CPU/IO/锁/GC/DB），再动刀。

指标体系

RED / USE 与 SLI/SLO

概要

服务层 RED：Rate（QPS）、Errors（错误率）、Duration（延迟分位）。资源层 USE：Utilization、Saturation、Errors。调优证据链：症状（告警/投诉）→ 指标确认（RED/USE）→ Profile（JFR/火焰图/堆 dump）→ 根因 → 修复 → 压测验证 SLO。无 Profile 不调 JVM 参数；无压测不宣称「已优化」。

flowchart TD
    SYM[性能症状] --> METRIC[RED/USE 指标]
    METRIC --> PROFILE[Profiler/火焰图/堆 dump]
    PROFILE --> ROOT[定位根因]
    ROOT --> FIX[代码/配置/架构修复]
    FIX --> VERIFY[压测验证 SLO]
    VERIFY -->|未达标| METRIC

图：性能调优证据链——从现象到验证闭环

示例代码

// Micrometer + Prometheus
Timer.builder("http.server.requests")
    .tag("uri", uri)
    .tag("status", String.valueOf(status))
    .publishPercentiles(0.5, 0.95, 0.99)
    .register(registry)
    .record(duration);

// SLO 告警：5 分钟窗口错误率 > 1%
ALERT ErrorBudgetBurn
  IF rate(http_errors[5m]) / rate(http_requests[5m]) > 0.01

速记

「服务看 RED，资源看 USE；优化对准 SLO，别追微基准幻觉。」

CPU/内存分析

火焰图与线程栈

概要

CPU 高：用 async-profiler 分别做 -e cpu 与 -e wall 采样，宽帧即热点。CPU 低但 QPS 上不去：查 BLOCKED/WAITING 线程（锁、连接池、DB）。内存高：Heap Dump + MAT Dominator Tree。分配速率异常：async-profiler -e alloc 或 JFR Object Allocation 事件。预发复现优先于生产 attach；生产侧更推荐短时 JFR（settings=profile），通常可控在低开销（常见约 1%~2%）。

flowchart LR
    CPU[CPU 高] --> FLAME[火焰图 CPU 采样]
    IO[CPU 低 QPS 低] --> BLOCK[线程 BLOCKED 分析]
    MEM[内存高] --> HEAP[Heap Dump Dominator]
    FLAME --> HOT[热点方法]
    BLOCK --> LOCK[锁/IO/DB 等待]
    HEAP --> LEAK[最大 Retained Set]

图：CPU/内存/阻塞三类症状诊断路径

示例 Shell

# CPU 火焰图（async-profiler，预发/短时生产）
./profiler.sh -d 60 -e cpu -f cpu.html <pid>
./profiler.sh -d 60 -e wall -f wall.html <pid>

# 分配热点
./profiler.sh -d 30 -e alloc -f alloc.html <pid>

# JFR（内置，JDK 11+）
jcmd <pid> JFR.start name=perf settings=profile duration=120s filename=/tmp/app.jfr

# 线程状态统计
jcmd <pid> Thread.print | grep "java.lang.Thread.State" | sort | uniq -c

# 与 Micrometer 指标对齐时间轴
curl localhost:8080/actuator/prometheus | grep jvm_threads_states

关键/技巧

  • 在预发复现优先；生产侧避免长时持续 profiling 干扰业务。
  • 对比正常与异常时间窗口的指标，找差异（delta）。

GC 调优

从 GC 日志到参数调整

概要

关注指标：GC 频率、单次 pause 时间、allocation rate、晋升失败/疏散失败（promotion failed / evacuation failure）。Young GC 频繁可能是堆太小或对象创建过快；Full GC 频繁可能与老年代压力、metaspace 增长异常或显式 GC 调用有关。调优顺序：先修复代码与对象生命周期问题 → 再调堆大小与代际比例 → 再选收集器 → 最后微调参数。

示例代码

# GC 日志（JDK 17+）
-Xlog:gc*,safepoint:file=gc.log:time,uptime,level,tags

# G1 常见微调
-XX:InitiatingHeapOccupancyPercent=45
-XX:G1ReservePercent=15

# 分析工具
# https://gceasy.io 或 GCViewer

易错点

  • 堆调到物理内存 100%，不留 OS page cache。
  • 忽略 allocation rate，只调 GC 参数治标不治本。

Long SQL 之 Mysql

慢 SQL 是 Java 后端 P99 恶化、连接池打满的常见根因。MySQL 调优闭环：查到 Long SQL → EXPLAIN 分析 → 改写 / 索引 → 压测验证。索引基础见第 11 章。

flowchart LR
    A[发现 Long SQL] --> B[EXPLAIN 分析]
    B --> C[改写 / 索引]
    C --> D[压测验证 SLO]

图：Long SQL 调优闭环（MySQL）

MySQL 8 通过 sys 库聚合 Performance Schema，从平均延迟与扫描行数两个维度定位 Top 慢语句。前提：performance_schema=ON，且 sys schema 已安装（官方发行版自带）。

查找 Long SQL

若视图无数据，先确认语句统计 consumer 已启用：

SHOW VARIABLES LIKE 'performance_schema';

UPDATE performance_schema.setup_consumers
SET ENABLED = 'YES' WHERE NAME LIKE 'events_statements%';

业务高峰或压测结束后执行：

-- TOP 慢 SQL（按平均延迟降序）
SELECT
    query,
    exec_count,
    avg_latency
FROM sys.statement_analysis
ORDER BY avg_latency DESC
LIMIT 20;

-- TOP 扫描行数 SQL（索引缺失 / 全表扫描常见信号）
SELECT
    query,
    rows_examined,
    exec_count
FROM sysstatement_analysis
ORDER BY rows_examined DESC
LIMIT 20;

avg_latency 高而 exec_count 低，多为偶发重查询；rows_examined 极大且 exec_count 高，多为高频扫表。数据为实例启动后累计；定位单次故障可先 TRUNCATE performance_schema.events_statements_summary_by_digest; 再复现。辅助：slow_query_log、Druid StatFilter（第 16 章）、APM。

针对性优化

拿到 query 后执行 EXPLAIN ANALYZE，关注 type、key、rows、Extra（filesort、临时表、回表）。

EXPLAIN ANALYZE
SELECT id, total FROM orders
WHERE tenant_id = ? AND status = 'PAID';
  • 索引：联合索引「等值在前、范围/排序在后」；覆盖索引减少回表（Using index）。
  • 分页：深翻页用 keyset 替代 LIMIT offset, n。
  • 反模式：SELECT *、函数包列、隐式类型转换、N+1（见第 11 章）。
  • 连接池等待时先治慢 SQL 与长事务，再调池大小（第 11 章）。

案例：订单列表深分页与索引缺失

预发 400 VU 压测，GET /api/v1/orders P99 从 140ms 升至 800ms+，Hikari pending 上升。按 rows_examined 查 sys.x$statement_analysis，该列表查询位居前列。EXPLAIN ANALYZE 显示全表扫描 + Using filesort，根因为 LIMIT 500000, 20 深分页且缺 (tenant_id, status, created_at) 联合索引。改为 keyset 分页并补索引后，P99 回到 SLO。

-- 问题 SQL
SELECT * FROM orders
WHERE tenant_id = 1001 AND status = 'PAID'
ORDER BY created_at DESC
LIMIT 500000, 20;

-- 修复
SELECT id, total, created_at FROM orders
WHERE tenant_id = 1001 AND status = 'PAID'
  AND created_at < :lastCreatedAt
ORDER BY created_at DESC
LIMIT 20;

CREATE INDEX idx_orders_tenant_status_created
  ON orders (tenant_id, status, created_at DESC);

Long SQL 之 GuassDB

GaussDB 调优闭环：查到 Long SQL → EXPLAIN 分析 → 改写 / 下推 → 压测验证。以 long sql 视图 dv_long_sql 查看慢语句明细；视图中无数据时，须在控制台开启语句跟踪相关参数。

查找 Long SQL

-- 参数（控制台修改，以实例版本为准）
ALTER SYSTEM SET log_min_duration_statement = 200;  -- 毫秒，-1 关闭
ALTER SYSTEM SET enable_stmt_track = on;

-- 查询 long sql 表
SELECT * FROM dv_long_sql
ORDER BY elapsed_time DESC
LIMIT 100;

优先关注 elapsed_time 最大、重复出现的 SQL；分布式实例注意记录来自 CN 还是 DN。辅助：控制台「慢 SQL / DAS」、WDR 快照、Druid / APM。

针对性优化

执行 EXPLAIN (ANALYZE, VERBOSE)，分布式额外关注 Streaming（shuffle）、Remote query、是否下推到 DN。

EXPLAIN (ANALYZE, VERBOSE)
SELECT ...;
  • 下推：过滤与聚合尽量在 DN 完成；CN 侧大量 Streaming 时优先改写 SQL。
  • 统计信息：计划异常时低峰 ANALYZE 表名;。
  • 分区与汇总：大表按业务键分区；报表可物化汇总表。
  • 自诊断：关注「未下推」「数据倾斜」告警。

案例：报表 SQL 未下推导致 CN 瓶颈

分布式实例业务高峰，部门汇总接口 P99 超标。dv_long_sql 中某 GROUP BY 语句多次出现且 elapsed_time 最高。计划显示大量 CN 侧 Streaming、未下推。改写为先在 orders 过滤聚合再关联 dept，并 ANALYZE 两表，复压后 P99 达标。

-- 问题写法
SELECT d.dept_name, SUM(o.amount)
FROM orders o JOIN dept d ON o.dept_id = d.id
WHERE o.biz_date BETWEEN '2026-01-01' AND '2026-03-31'
GROUP BY d.dept_name;

-- 改写
SELECT d.dept_name, t.amt FROM dept d
JOIN (
  SELECT dept_id, SUM(amount) AS amt FROM orders
  WHERE biz_date >= DATE '2026-01-01' AND biz_date < DATE '2026-04-01'
  GROUP BY dept_id
) t ON d.id = t.dept_id;

ANALYZE orders;
ANALYZE dept;

缓存

缓存用可控的不一致换取更低延迟与更高吞吐，不能替代数据库的事务一致性。Java 后端最常用 Cache-Aside：读路径先查缓存，miss 再加载 DB 并回填；写路径先写 DB，再删除缓存（而不是同步更新缓存，避免并发写导致乱序）。架构层面的缓存分层见第 03 章数据架构。

三种典型故障模式

  • 击穿：热点 key 过期瞬间，大量请求同时打到 DB。应对：互斥锁、singleflight，或逻辑过期（旧值仍可返回，后台异步刷新）。
  • 穿透：查询不存在的数据，缓存反复 miss。应对：空值短 TTL，或布隆过滤器前置拦截。
  • 雪崩：大量 key 在同一时刻过期。应对：TTL 加随机 jitter、多级缓存错峰过期，必要时熔断降级。

二级缓存架构

读多写少场景可采用 Caffeine（进程内） + Redis（跨实例）：本地命中亚毫秒级，Redis 负责 Pod 间共享。写后删缓存时，需通过 MQ 或 Redis PubSub 广播失效事件，避免各实例本地缓存不一致。多租户系统 key 应带租户/版本前缀，防止串数据（见第 16 章）。

flowchart LR
    REQ[读请求] --> L1{Caffeine 命中?}
    L1 -->|是| RET[返回]
    L1 -->|否| L2{Redis 命中?}
    L2 -->|是| FILL[回填本地缓存]
    L2 -->|否| DB[(DB 加载)]
    DB --> W[写 Redis + 本地]
    W --> RET
    FILL --> RET

图：Cache-Aside 二级读路径

代码示例

@Cacheable(value = "orders", key = "#id", unless = "#result == null")
public Order getOrder(UUID id) {
    return repo.findById(id).orElse(null);
}

@CacheEvict(value = "orders", key = "#order.id")
public void updateOrder(Order order) {
    repo.save(order);
}

LoadingCache<String, User> localCache = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofMinutes(5))
    .build(this::loadUserFromRedisOrDb);

// 雪崩：TTL 基础值 + 随机偏移
int ttl = 300 + ThreadLocalRandom.current().nextInt(60);

落地要点

  • 写后删缓存通常优于写后更新；强一致场景可用延时双删，或订阅 binlog（如 Canal）驱动失效。
  • Redis 是 DB 的投影，不是唯一数据源；列表类数据避免整表大对象入缓存，可用 ID 集合 + 分批 mget。
  • 本地缓存必须设置 maximumSize 或权重驱逐，防止堆内存失控。
  • 压测前预热热点 key，并在报告中记录命中率与 P99 的对照关系（见本章压测）。

压力测试与性能指标

压测类型、工具、指标与完整流程

概要

压测类型（别混用术语）：基准测试（Benchmark）——单接口、固定并发，建立性能基线；负载测试（Load）——预期日常流量下验证 SLO；压力测试（Stress）——持续加压直到错误率上升或资源饱和，找系统拐点；稳定性/浸泡测试（Soak）——中等负载长时间运行，暴露内存泄漏、连接泄漏、GC 恶化；峰值测试（Spike）——短时流量尖刺，验证限流、熔断与队列缓冲。

工具选型：通用 JMeter（GUI + CLI，生态最大）、k6（JS 脚本、thresholds 内置）、Gatling（Scala DSL、高并发报告精美）、wrk/ab（快速 HTTP 探针）。Java 生态常用 Gatling 或 JMeter 对 Spring Boot REST 做场景化脚本；k6 适合 CI 门禁。压测机与 SUT 分离，避免压测端 CPU 成为瓶颈。

性能指标：吞吐统一按 QPS 表达（HTTP 场景下常与 RPS 近似等价，TPS 需按业务事务口径单独定义）；延迟 Avg、P50/P90/P95/P99、Max（对外承诺看 P95/P99，别只报 Avg）；错误率、并发用户数/VU；资源 CPU、内存、GC pause、线程池队列、DB 连接池、慢 SQL。与指标体系卡片衔接：SLI（可测，如 p99 延迟）→ SLO（目标，如 p99 < 200ms）→ 压测验收标准（预发/发布前必须通过）。

压测流程：① 目标定义（场景、SLO、数据规模）→ ② 脚本（混合读写、think time、参数化）→ ③ 环境隔离（独立预发、禁与其他任务争用）→ ④ 预热（JIT、缓存填热）→ ⑤ 阶梯加压 → ⑥ 报告与对照 SLO → ⑦ 未达标则回到证据链（Profiler/火焰图/堆 dump）定位瓶颈 → 调优 → 再压测闭环。

flowchart TD
    GOAL[目标与 SLO 定义] --> SCRIPT[场景脚本 JMeter/k6/Gatling]
    SCRIPT --> ENV[环境隔离 预发]
    ENV --> WARM[预热 JIT/缓存]
    WARM --> RAMP[阶梯加压]
    RAMP --> REPORT[报告: TPS/分位/错误率/资源]
    REPORT --> PASS{SLO 达标?}
    PASS -->|是| CAP[容量规划 1.5~2x 余量]
    PASS -->|否| EVID[证据链: Profile/火焰图/堆]
    EVID --> TUNE[调优 JVM/并发/SQL/缓存]
    TUNE --> RAMP

图：压力测试完整流程与证据链闭环

示例代码

// k6 — 阶梯加压 + SLO thresholds（适合 CI）
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '2m', target: 100 },
    { duration: '5m', target: 100 },
    { duration: '2m', target: 200 },
    { duration: '5m', target: 200 },
    { duration: '2m', target: 0 },
  ],
  thresholds: {
    http_req_duration: ['p(95)<150', 'p(99)<200'],
    http_req_failed: ['rate<0.01'],
  },
};

export default function () {
  const res = http.get('https://staging/api/v1/orders');
  check(res, { 'status 200': (r) => r.status === 200 });
  sleep(1); // think time
}

// Gatling Scala 简述（Spring Boot 下单接口）
class OrderSimulation extends Simulation {
  val httpProtocol = http.baseUrl("https://staging")
  val scn = scenario("Orders")
    .exec(http("list").get("/api/v1/orders").check(status.is(200)))
    .pause(1)
  setUp(scn.inject(rampUsers(200).during(5.minutes)).protocols(httpProtocol))
}

// JMeter CLI 非 GUI 压测
// jmeter -n -t order.jmx -l result.jtl -e -o report/

结果解读（示例表）

指标本次SLO结论
QPS1,240≥ 1,000通过
P99 延迟218 ms< 200 ms不通过 → 查 GC/慢 SQL
错误率0.3%< 1%通过
DB 连接池等待持续上升且伴随 P99 恶化—瓶颈信号 → 调池或 SQL

关键/技巧

  • 预发数据量、索引、缓存命中率接近生产；压测前固定 JVM、连接池、线程池并记录 baseline。
  • 场景混合读写 + think time，避免「只打 GET」高估容量；报告同时看吞吐与 P99，拐点常先于 Avg 恶化。
  • 生产容量 ≈ 实测峰值 QPS × 1.5~2 安全系数，并预留发布窗口内的流量突增。
  • Spring Boot 压测时同步抓 /actuator/prometheus 与 GC 日志，与 k6/Gatling 时间轴对齐。

易错点

  • 未预热直接加压——JIT 与缓存未稳定，P99 虚高。
  • 压测机与 SUT 同机或网络未隔离——测的是压测端瓶颈。
  • 只盯 Avg 延迟——长尾被平均掉，线上投诉来自 P99。
  • 生产直接全量压测——用预发/影子流量；CI 轻量 k6 门禁即可，见第 21 章 CI。

速记

「五类压测分清场景；工具 JMeter/k6/Gatling；看 P99 与错误率，SLO 不过就回证据链；容量留 1.5~2 倍。」

延伸阅读：Gatling 官方文档、k6 文档、Systems Performance（Brendan Gregg）

压测指标采集与验收

Micrometer 对齐、压测报告与容量规划

概要

压测期间的指标应与生产同一套导出方式：Micrometer → Prometheus scrape → Grafana 看板（详见第 21 章可观测性）。压测脚本 thresholds 与 Prometheus 告警规则使用相同 SLI 口径，避免「压测通过、上线告警」两套标准。

压测报告模板（发布评审附件）：场景说明、并发曲线、QPS/P50/P95/P99、错误率、资源峰值（CPU/堆/GC/连接池）、与 SLO 对照表、瓶颈与待办。未达标项必须链到调优工单，禁止仅凭「感觉更快」上线。

与容量规划：拐点 QPS × 安全系数 = 单机/集群目标；结合业务增长预测与多 AZ 冗余，反推实例数、DB 规格与缓存容量。压测是验证容量模型，不是替代监控。

示例：压测报告摘要（Markdown）

## 压测报告 — order-service v2.3（预发 2026-05-20）

| SLI | 目标 SLO | 200 VU | 400 VU | 结论 |
|-----|----------|--------|--------|------|
| QPS | ≥ 1000 | 1180 | 1210 | OK |
| P99 延迟 | < 200ms | 142ms | 218ms | 400 VU 超标 |
| 错误率 | < 1% | 0% | 0.4% | 边缘 |

瓶颈：400 VU 时 Hikari 等待 + Full GC 增多 → 调连接池 / SQL（见 Long SQL 之 Mysql）
决策：生产按 800 VU 峰值 × 1.5 部署 3 实例

关键/技巧

  • 压测窗口在 Grafana 建临时 Dashboard，变量绑定 application 与环境标签。
  • CI 可对预发跑 k6 thresholds 作门禁；全量浸泡测试放发布前人工触发。

易错点

  • 压测不看 Prometheus 只看工具自带报告——缺少 JVM/DB 关联，根因难定。
  • 报告无版本与配置快照——无法复现结论。

速记

「压测与生产同一套 Micrometer；报告对 SLO 表；拐点 × 1.5~2 = 容量。」

延伸阅读：Site Reliability Engineering（Google SRE）、Prometheus 官方文档

章末实战闭环

性能调优落地清单

输入

  • SLO 指标与用户体验阈值
  • 压测脚本与真实流量画像
  • APM/日志/指标历史数据
  • 容量预算与成本约束

输出

  • 性能瓶颈证据链与优先级
  • 调优方案（代码/SQL/缓存）
  • 容量规划与扩容触发条件

验收标准

  • P95/P99 指标达到目标区间
  • 调优收益有前后对比数据
  • 高峰流量下系统稳定可降级

失败信号

  • 凭直觉调优缺少指标依据
  • 压测场景与真实业务脱节
  • 仅提升吞吐忽略错误率
