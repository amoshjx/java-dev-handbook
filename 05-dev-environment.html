05 开发环境搭建 — Cursor · IDEA · VS Code

本章聚焦可落地的开发机初始化：按 安装步骤（Install）→ 验证命令（Verify）→ 故障排查（Troubleshooting） 三段式完成 Java 后端环境。默认以 Windows 11 + WSL2 为主线，同时覆盖 Linux 命令口径；目标是让新成员在 60 分钟内跑通 Java、Git、Maven、数据库与远程连接工具。

环境总览与目标版本矩阵

版本基线（Baseline）与安装顺序（Order）

讲解

建议安装顺序：Java 21 LTS → IDE → Git → Maven → Node.js LTS → Postman → WSL2 → WSL 内 Docker → WSL 内 minikube/kubectl → DBeaver → MobaXterm → 本地数据库。核心原则：先装运行时（Runtime），再装开发工具（Tools），最后装数据与远程协作组件，避免 PATH 冲突与依赖缺失。本地 K8s 在 WSL 中完成，见WSL 内 minikube，供第 13 章 K8s 部署使用。

目标版本矩阵（Windows 优先）

| 组件（Component） | 推荐版本 | Windows | WSL/Linux |
|---|---|---|---|
| Java JDK | 21 LTS | Temurin 21 | OpenJDK 21 |
| IDE | IDEA 2024+ / Cursor 1.x / VS Code 1.9x+ | 是 | 可选（Remote） |
| Git | 2.45+ | Git for Windows | git |
| Maven | 3.9+ | 二进制包 | apt/yum |
| Node.js | 22 LTS | 官方 MSI / nvm-windows | nvm / NodeSource |
| npm | 随 Node.js | 随 Node.js | 随 Node.js |
| Postman | 11.x+ | Desktop App | Web/可选 |
| WSL | WSL2 + Ubuntu 24.04 LTS | 必装 | N/A |
| Docker | 24+ / docker.io | Desktop 集成（可选） | WSL 内必装 |
| kubectl | 1.30+ | — | WSL 内安装 |
| minikube | 1.34+ | — | WSL · docker 驱动 |
| DBeaver | 24.x+ | 是 | 可选 |
| MobaXterm | 24.x+ | 是 | N/A |
| DB | MySQL 8.4 LTS（主）/PostgreSQL 16（备） | 是 | 是 |

阶段成果

  • 团队统一版本矩阵与下载源（官网下载页或内网镜像）。
  • 新人按顺序执行后，一次通过自检脚本。

Java 21 LTS 安装与 JAVA_HOME 配置

安装（Install）+ 验证（Verify）+ 排障（Troubleshooting）

安装步骤

  1. 下载并安装 Temurin 21（x64）：https://adoptium.net。
  2. 设置系统变量 JAVA_HOME 指向 JDK 根目录（例如 C:\Program Files\Eclipse Adoptium\jdk-21）。
  3. 在系统 Path 中添加 %JAVA_HOME%\bin，并确保旧 JDK 路径靠后或移除。

验证命令

# PowerShell
java -version
javac -version
echo $env:JAVA_HOME
where.exe java

# WSL/Linux
java -version
javac -version
echo $JAVA_HOME
which java

常见问题排查

  • 症状：java -version 仍显示旧版本。处理：检查 where.exe java 输出顺序，清理旧 JDK 的 bin 路径。
  • 症状：JAVA_HOME 指向 ...\bin。处理：改为 JDK 根目录。
  • 症状：IDE 与终端版本不一致。处理：IDE Project SDK 改为 JDK 21，并重启 IDE。

IDE 安装（IntelliJ IDEA + Cursor + VS Code）

IDEA 稳态开发 + Cursor AI 提效 + VS Code 轻量协作

安装步骤

  1. 安装 IntelliJ IDEA（Community 或 Ultimate），首次启动将 JDK 设为 21。
  2. 安装 Cursor（Windows 优先）：访问官网下载安装包，首次启动选择导入 VS Code 设置与扩展。
  3. 在 Cursor 扩展市场安装 Extension Pack for Java 与 Spring Boot Extension Pack，并确认 Java Language Server 已启用。
  4. 打开 Cursor 设置，校验 java.jdt.ls.java.home 指向 JDK 21，Maven 可执行路径与本机一致。
  5. 安装 VS Code（可选），用于纯轻量编辑或与团队统一插件调试，扩展组合与 Cursor 保持一致。

定位建议：Cursor 适合代码理解、批量重构、测试生成与文档补全；IDEA 适合大型 Java 工程的深度调试、复杂重构与性能分析。二者并行能兼顾效率与稳定性。

Java 开发必备配置与验证

# IDEA 验证
# File -> Project Structure -> Project SDK = 21

# Cursor 验证（与 VS Code 口径一致）
cursor --version
# Command Palette: Java: Configure Java Runtime
# Settings: editor.formatOnSave = true
# Settings: terminal.integrated.defaultProfile.windows = "PowerShell"
# AI 设置：启用项目索引并允许工作区上下文

# VS Code 验证（可选）
code --version
# Command Palette: Java: Configure Java Runtime

# 任意 IDE 验证（项目根目录）
mvn -v
mvn -q -DskipTests package

IDE 协同建议（何时用 Cursor / IDEA）

  • 优先用 Cursor：需求拆解、跨文件阅读、脚手架代码生成、单测草稿与注释补全。
  • 优先用 IDEA：复杂断点调试、线程/内存分析、全量重命名重构、数据库与 Spring 深度集成。
  • 协同方式：先在 Cursor 快速产出，再在 IDEA 做最终编译、调试与提交前检查。
  • 团队规范：格式化规则与 Maven/JDK 路径统一，避免“本机通过、同伴失败”。

常见问题排查（Cursor）

  • 索引慢/语义不完整：确保项目已完全打开，等待首次索引完成；大型仓库先关闭无关目录再重启窗口。
  • JDK 未识别：检查 java.jdt.ls.java.home 与系统 JAVA_HOME 是否一致，必要时执行 Java: Clean Java Language Server Workspace。
  • Maven 项目红线：确认 mvn -v 可用后，执行 Maven: Reload project 或重新导入工作区。
  • 终端路径错误：在设置中修正 terminal.integrated.cwd 或默认 Profile，Windows/WSL 混用时避免硬编码盘符路径。

Git 安装与基础配置（含凭证/SSH）

身份配置、凭证管理与 SSH 免密

安装步骤

  1. 安装 Git for Windows（建议启用 OpenSSH 与 Git Credential Manager）。
  2. 执行全局配置：用户名、邮箱、默认分支、换行策略。
  3. 生成 SSH 密钥并配置到代码托管平台（GitHub/GitLab/Gitea）。

命令示例（可直接执行）

git --version
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --global core.autocrlf false
git config --global credential.helper manager

# 生成 Ed25519 密钥对；-C 为备注邮箱（建议填代码托管平台账号邮箱）
ssh-keygen -t ed25519 -C "you@example.com"
# Windows PowerShell 下查看公钥内容，复制输出粘贴到 GitHub/GitLab SSH Keys
Get-Content $env:USERPROFILE\.ssh\id_ed25519.pub
# 测试与 GitHub 的 SSH 连接；成功时显示 "Hi username! You've successfully authenticated..."
ssh -T git@github.com

常见问题排查

  • 权限拒绝（Permission denied publickey）：确认公钥已上传，且 ssh-agent 已加载私钥。
  • 反复输入密码：确认启用了 credential.helper manager。
  • 换行符污染：仓库加 .gitattributes，统一 LF 策略。

Maven 安装与仓库配置（镜像、settings.xml）

本地 Maven 与私服镜像（Mirror）配置

安装步骤

  1. 下载 Apache Maven 3.9+，解压到固定目录（如 C:\tools\apache-maven-3.9.9）。
  2. 设置 MAVEN_HOME 并追加 %MAVEN_HOME%\bin 到 Path。
  3. 创建用户配置文件 %USERPROFILE%\.m2\settings.xml，写入 mirror 与私服账号。

settings.xml 片段与验证

<settings>
  <mirrors>
    <mirror>
      <id>aliyunmaven</id>
      <mirrorOf>central</mirrorOf>
      <name>Aliyun Maven Central</name>
      <url>https://maven.aliyun.com/repository/public</url>
    </mirror>
  </mirrors>
</settings>

mvn -v
mvn -U -q -DskipTests clean package
mvn help:effective-settings

常见问题排查

  • 依赖下载失败 401/403：检查 servers 凭证与私服权限。
  • 下载慢或超时：确认 mirror 可访问，必要时切换公司内网源。
  • 插件解析异常：避免 mirrorOf="*" 粗暴配置，优先 central。

Node.js 安装

安装（Install）+ 验证（Verify）+ 排障（Troubleshooting）

定位与适用场景

Node.js 是 Java 后端项目常见的配套运行时：前端工程（Vue/React）、RuoYi 管理端、OpenAPI 代码生成、ESLint/Prettier、Vite/Webpack 构建链均依赖 node 与 npm（或 pnpm）。团队建议统一 Node.js 22 LTS，与 Java 21 LTS 一样写入版本矩阵，避免「本机 18、同伴 20」导致 lockfile 与构建脚本不一致。

Windows 安装步骤

  1. 访问 https://nodejs.org，下载 22.x LTS Windows 安装包（x64）。
  2. 安装时勾选 Add to PATH；若需切换多版本，改用 nvm-windows 管理。
  3. （可选）启用 Corepack 以使用 pnpm：corepack enable。
  4. 配置 npm 镜像（内网或国内加速）：npm config set registry https://registry.npmmirror.com。

nvm-windows 简要流程：安装 nvm-windows → nvm install 22 → nvm use 22 → 新开终端验证。

WSL / Linux 安装步骤

  1. 进入 WSL（wsl -d Ubuntu-24.04），优先用 nvm 安装，便于与 Windows 侧版本对齐。
  2. 安装 nvm 后执行：nvm install 22、nvm alias default 22、nvm use 22。
  3. 若不用 nvm，可用 NodeSource 脚本安装 22.x，或 sudo apt install nodejs npm（需确认 apt 源版本 ≥ 22）。

验证命令

# PowerShell / Windows
node -v
npm -v
where.exe node
npm config get registry

# 可选：pnpm / corepack
corepack enable
pnpm -v

# WSL / Linux
node -v
npm -v
which node
npm config get registry

# 前端项目最小验证（在项目根目录）
npm install
npm run dev
# 或 npm run build

与 Java 项目协同建议

  • 前后端分离：后端 mvn spring-boot:run（8080），前端 npm run dev（常见 5173/3000），代理到后端 API。
  • 锁文件入库：提交 package-lock.json 或 pnpm-lock.yaml，CI 使用 npm ci 保证可重复安装。
  • 版本文件：可在仓库根目录增加 .nvmrc（内容如 22），便于 nvm 自动切换。
  • 不要全局装业务依赖：项目依赖写在 package.json，避免 npm install -g 污染团队环境。

常见问题排查

  • node 不是内部或外部命令：检查 Path 是否包含 Node 安装目录；nvm-windows 切换版本后需新开终端。
  • 版本与 lockfile 不匹配：对齐 Node 22 LTS，删除 node_modules 后重新 npm install。
  • npm EACCES / 权限错误（Linux）：勿用 sudo npm install；修正目录属主或使用 nvm 用户级安装。
  • 安装慢或超时：切换 registry 镜像；公司内网配置 .npmrc 指向私服。
  • Windows 与 WSL 各装一套 Node：前端在 WSL 内开发时，在 WSL 终端执行 npm；Windows IDE 终端注意当前是 PowerShell 还是 WSL Profile。

Postman 安装与接口联调配置

API 调试（Debug）+ 集合复用（Collection）+ 环境隔离（Environment）

定位与适用场景

Postman 是接口联调与接口资产管理工具，适合在后端开发阶段完成接口调试、请求集合沉淀、环境变量隔离。在团队协作中，推荐将请求按业务域组织到 Collection，并通过 Environment 管理 dev/test/staging 不同地址与令牌，减少“改 URL、改 Token”带来的人工错误。

Windows 安装步骤

  1. 访问 Postman 官网下载 Windows Desktop App（建议安装最新版 11.x+）。
  2. 运行安装包并首次启动，使用团队账号登录（便于 Workspace 共享）。
  3. 在设置中确认自动更新策略与代理策略符合公司网络规范。

若公司内网限制外网访问，优先使用 IT 提供的离线安装包或软件分发平台版本。

基础配置（Workspace / Environment / Collection / 变量）

  • Workspace：按团队或项目创建共享 Workspace（如 order-service-dev），避免个人空间散落资产。
  • Environment：为 dev、test、staging 创建环境，维护 baseUrl、token、tenantId 等变量。
  • Collection：按模块建立集合（用户、订单、支付），将接口请求、示例响应、测试脚本集中管理。
  • 变量管理：优先使用 Environment 变量；仅在少数跨环境场景使用 Collection 变量，避免同名覆盖导致请求错发。

与 Java/Spring Boot 最小联调流程

  1. 启动本地服务：mvn spring-boot:run（或 IDE 启动），确认接口基础地址如 http://localhost:8080。
  2. 在 Postman 新建 Environment：设置 baseUrl=http://localhost:8080。
  3. 新建 Collection（如 user-api），添加请求：GET {{baseUrl}}/api/users/health。
  4. 若接口需鉴权，先调用登录接口并在 Tests 中提取 token 写入环境变量：pm.environment.set("token", pm.response.json().token)。
  5. 后续请求统一带 Authorization: Bearer {{token}}，即可形成可复用联调链路。

常见问题排查

  • 证书报错（SSL Error）：内网自签证书场景先导入公司 CA，勿长期全局关闭 SSL 校验。
  • 代理导致请求失败：公司代理开启时，核对 Postman 代理配置与系统代理是否冲突。
  • 跨域误解：Postman 不受浏览器同源策略限制；前端跨域报错不代表后端接口不可达。
  • 环境变量覆盖：同名变量在多层级（Global/Collection/Environment）会覆盖，建议统一命名并减少 Global 变量。

WSL 安装与基础配置（含与 Windows 工具协同）

WSL2 + Ubuntu + Windows/WSL 协作原则

安装步骤

  1. 管理员 PowerShell 执行：wsl --install -d Ubuntu-24.04，重启后设置 Linux 用户。
  2. 执行更新：wsl --update，确认版本为 WSL2。
  3. 项目代码建议放在 Linux 文件系统（如 ~/workspace），通过 IDEA/Cursor/VS Code Remote 连接。

将 Ubuntu 迁移到非系统盘（释放 C 盘空间）

WSL 发行版默认安装在系统盘用户目录下，长期开发会占用大量 C 盘空间。建议在初始化完成后，将 Ubuntu 导出并重新导入到非系统盘（如 D:\wsl\Ubuntu-24.04）。以下命令在 PowerShell 中执行，迁移前先关闭所有 WSL 终端、IDE Remote 会话和 Docker Desktop。

# 1. 查看发行版名称，确认要迁移的 Name
wsl -l -v

# 示例输出：
#   NAME            STATE           VERSION
# * Ubuntu-24.04    Running         2

# 2. 停止 WSL
wsl --shutdown

# 3. 准备非系统盘目录
New-Item -ItemType Directory -Force D:\wsl\backup
New-Item -ItemType Directory -Force D:\wsl\Ubuntu-24.04

# 4. 导出当前 Ubuntu 到 tar 备份
wsl --export Ubuntu-24.04 D:\wsl\backup\Ubuntu-24.04.tar

# 5. 注销原系统盘发行版
# 注意：此操作会删除原发行版注册信息，务必确认第 4 步 tar 已成功生成
wsl --unregister Ubuntu-24.04

# 6. 从 tar 导入到非系统盘，并指定 WSL2
wsl --import Ubuntu-24.04 D:\wsl\Ubuntu-24.04 D:\wsl\backup\Ubuntu-24.04.tar --version 2

# 7. 启动验证
wsl -d Ubuntu-24.04
pwd
lsb_release -a
exit

# 8. 确认迁移后路径与版本
wsl -l -v

导入后的默认登录用户可能变成 root。如果原用户名是 amos，进入 WSL 后执行以下命令写入默认用户配置：

# 在 WSL 内执行
sudo tee /etc/wsl.conf << 'EOF'
[user]
default=amos
EOF

# 回到 PowerShell 后重启 WSL 生效
wsl --shutdown
wsl -d Ubuntu-24.04

确认迁移成功、项目和工具链可正常使用后，再删除备份包释放空间：

Remove-Item D:\wsl\backup\Ubuntu-24.04.tar

验证命令

wsl --status
wsl -l -v

# 进入 WSL
wsl
uname -a
lsb_release -a
git --version

协同建议

  • Windows 负责 GUI 工具（IDEA、DBeaver、MobaXterm），WSL 负责构建命令与脚本。
  • 跨系统路径避免硬编码，统一使用相对路径或环境变量。

WSL 内安装 minikube（Docker 驱动）

在 Ubuntu WSL 中搭建本地 Kubernetes 集群

定位与原则

所有 K8s 相关命令均在 WSL 终端执行（docker、kubectl、minikube），与 Windows 侧工具链分离，避免 PATH 与 kubeconfig 混用。minikube 使用 --driver=docker，在 WSL 的 Docker 引擎里启动节点容器，用于本地验证第 13 章部署。

前置：已完成 WSL2 + Ubuntu 24.04；建议在 Windows 用户目录创建 .wslconfig 为 WSL 分配足够内存（见下文）。

0. 为 WSL 分配资源（Windows 侧，可选但推荐）

在 C:\Users\<你的用户名>\.wslconfig 写入（修改后需 wsl --shutdown 再启动 WSL）：

[wsl2]
memory=8GB
processors=4
swap=4GB

1. 在 WSL 内安装 Docker

进入 WSL（wsl -d Ubuntu-24.04），任选一种方式。

方式 A（推荐）：Docker Desktop + WSL Integration

  1. Windows 安装并启动 Docker Desktop，勾选 WSL2 引擎。
  2. Settings → Resources → WSL Integration：为 Ubuntu-24.04 开启集成。
  3. 不要勾选 Docker Desktop 自带「Enable Kubernetes」，与 minikube 二选一。

方式 B：WSL 内原生安装 docker.io（不依赖 Desktop）

# 在 WSL 内执行
sudo apt update
sudo apt install -y docker.io
sudo usermod -aG docker $USER

# 注销并重新进入 WSL，使 docker 组生效
exit
wsl -d Ubuntu-24.04

# 验证
docker version
docker run --rm hello-world
sudo systemctl enable docker
sudo systemctl start docker

方式 B 若 systemctl 不可用，可在 /etc/wsl.conf 启用 systemd（Ubuntu 24.04 通常已支持）：

sudo tee /etc/wsl.conf << 'EOF'
[boot]
systemd=true
EOF
# PowerShell: wsl --shutdown 后重新进入 WSL

2. 在 WSL 内安装 kubectl 与 minikube

# 在 WSL 内执行
sudo apt update
sudo apt install -y curl conntrack

# kubectl（apt 版本即可；需固定版本时用官方 curl 脚本）
sudo apt install -y kubectl

# minikube 最新版
curl -LO https://storage.googleapis.com/minikube/releases/latest/minikube-linux-amd64
sudo install minikube-linux-amd64 /usr/local/bin/minikube
rm minikube-linux-amd64

kubectl version --client
minikube version

内网环境可从 GitHub Releases 下载二进制后 sudo install 到 /usr/local/bin/。

3. 启动 minikube 集群

# 在 WSL 内执行
minikube config set driver docker

# 首次启动（拉镜像较慢，请耐心等待）
minikube start --driver=docker

# 资源紧张时可显式限制
# minikube start --driver=docker --memory=4096 --cpus=2

kubectl config use-context minikube
kubectl cluster-info
kubectl get nodes

# 应看到 minikube 节点 STATUS 为 Ready
kubectl get nodes -o wide
docker ps | grep minikube

4. 常用运维命令（均在 WSL 内）

minikube status
minikube dashboard          # 在 WSL 中启动；浏览器从 Windows 访问提示的 URL

minikube service list
minikube service demo-service -n dev

minikube ssh
minikube image load demo-service:1.0.0   # 加载本机构建的镜像

minikube stop
minikube delete

# 指定 K8s 版本重建
minikube delete
minikube start --driver=docker --kubernetes-version=v1.30.0

与第 13 章联调提示

  • 项目代码放在 WSL 文件系统（如 ~/workspace），在 WSL 内执行 mvn package、docker build、kubectl apply，避免跨盘符性能问题。
  • 练习环境建议 kubectl create namespace dev，manifest 中 namespace 改为 dev 后再 kubectl apply -f k8s/ -n dev。
  • 私服镜像需 imagePullSecrets；本地快速验证优先 minikube image load。
  • LoadBalancer 类型 Service：在 WSL 另开终端执行 minikube tunnel（保持前台运行）。
  • Windows 浏览器访问 WSL 服务：NodePort 用 minikube service；或查 WSL IP（hostname -I）配合端口转发。

常见问题排查

  • permission denied while trying to connect to docker：sudo usermod -aG docker $USER 后重新登录 WSL；或暂时 sudo minikube start 验证（不建议长期使用 root）。
  • Cannot connect to the Docker daemon：方式 A 确认 Docker Desktop 已 Running 且 WSL Integration 已开启；方式 B 确认 sudo systemctl status docker 为 active。
  • DRV_DOCKER_NOT_RUNNING：在 WSL 内先执行 docker ps 成功，再 minikube start。
  • Preparing Kubernetes 长时间卡住：提高 .wslconfig 的 memory；或 minikube start --driver=docker --memory=4096；检查代理/镜像加速。
  • Windows 与 WSL 各装一套 kubectl 导致连错集群：第 13 章实操统一在 WSL 执行；Windows PowerShell 中可用 wsl kubectl get nodes 代查。
  • 拉镜像超时：为 Docker 配置 registry mirror；或 minikube start --driver=docker --image-mirror-country=cn（视版本支持）。
  • 端口已被占用：是否同时启用了 Docker Desktop 自带 K8s；执行 minikube delete 后重建。

DBeaver 安装与连接配置

数据库客户端（DB Client）标准化

  1. 下载安装 DBeaver Community 24.x+。
  2. 创建连接：选择 MySQL 或 PostgreSQL，填写主机、端口、库名、用户名、密码。

连接参数示例（MySQL）

常见问题排查

  • Connection refused：确认数据库服务已启动、端口未被占用。
  • Authentication failed：检查用户授权与认证插件配置。
  • 时区/编码异常：连接属性补充 serverTimezone=Asia/Shanghai 与 UTF-8 设置。

  2. 创建 SSH Session：填写 Host、Port、Username，并加载私钥。

本地数据库安装（MySQL 完整，PostgreSQL 选型）

MySQL 8.4 LTS 完整流程 + PostgreSQL 选型建议

MySQL 安装步骤（完整）

  1. 安装 MySQL Community Server 8.4 LTS，端口建议 3306。
  2. 初始化 root 密码，创建业务库与业务账号。
  3. 开启开机自启服务并确认监听端口。

MySQL 初始化命令

mysql --version
mysql -u root -p

CREATE DATABASE app_dev CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE USER 'app'@'%' IDENTIFIED BY 'StrongPassword!123';
GRANT ALL PRIVILEGES ON app_dev.* TO 'app'@'%';
FLUSH PRIVILEGES;

mysql -u app -p -h 127.0.0.1 -P 3306 -D app_dev -e "SELECT VERSION();"

PostgreSQL 选型说明（备选）

  • 当业务依赖 JSONB、复杂查询、扩展生态（如 PostGIS）时优先 PostgreSQL 16。
  • MySQL 更适合团队已有经验、运维脚本成熟、迁移成本低的场景。
  • PostgreSQL 最小验证：psql --version、psql -h 127.0.0.1 -U postgres -c "select version();"。

常见问题排查

  • 端口冲突：netstat -ano | findstr :3306，更换实例端口。
  • 字符集乱码：统一 UTF-8，JDBC URL 指定字符集参数。
  • 权限不足：避免业务直接使用 root，单独授予 app 用户权限。

高频故障闭环
