16 安全开发

面向 Spring Boot / Java 企业项目的安全原理、威胁模型与防护配置：Spring Security 架构、认证授权、密码与 Token、CSRF/CORS/Session 防护、OWASP 常见漏洞、密钥与 TLS、审计合规。业务侧 RBAC/SSO 落地见第 16 章 RBAC与第 16 章统一登录鉴权；本章侧重「为什么这样配、攻击面在哪、默认配置缺什么」。

Spring Security 架构与 Filter Chain

DelegatingFilterProxy → SecurityFilterChain → 认证/授权决策

概要

零信任架构（Never Trust, Always Verify）：默认不信任内网——每次请求都须认证授权，服务间 mTLS 或 Service Account Token，最小权限 RBAC。纵深防御分层：① 边界（WAF/API Gateway 鉴权、限流）；② 网络（VPC/安全组/egress 控制）；③ 应用（Filter 链 + 方法级授权，细节见第 16 章）；④ 数据（加密、脱敏、审计）。Spring Security 在此模型中负责应用层：多条 SecurityFilterChain 按路径分流——/api/** JWT Resource Server、/actuator/** 独立保护。401=未认证，403=已认证无权限。

flowchart TD
    REQ[HTTP Request] --> PROXY[DelegatingFilterProxy]
    PROXY --> CHAIN[SecurityFilterChain]
    CHAIN --> CTX[SecurityContextHolderFilter]
    CTX --> AUTH[Authentication Filter]
    AUTH --> AUTHZ[AuthorizationFilter]
    AUTHZ --> APP[Controller @PreAuthorize]

图：Spring Security Filter Chain 请求链路

示例代码

@Configuration
@EnableWebSecurity
public class SecurityConfig {

  @Bean
  @Order(1)
  SecurityFilterChain apiChain(HttpSecurity http) throws Exception {
    return http
        .securityMatcher("/api/**")
        .csrf(csrf -> csrf.disable()) // 纯 JWT 无 Cookie 时可关，见 csrf-cors-session 卡片
        .sessionManagement(s -> s.sessionCreationPolicy(STATELESS))
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/public/**").permitAll()
            .anyRequest().authenticated())
        .oauth2ResourceServer(oauth2 -> oauth2.jwt(Customizer.withDefaults()))
        .build();
  }

  @Bean
  @Order(2)
  SecurityFilterChain defaultChain(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/login", "/css/**").permitAll()
            .anyRequest().authenticated())
        .formLogin(Customizer.withDefaults())
        .build();
  }
}

关键/技巧

  • 开启 logging.level.org.springframework.security=DEBUG 看 Filter 匹配与决策路径。
  • 多链时用 securityMatcher 明确路径，避免一条链 anyRequest 吞掉全部规则。
  • 自定义 Filter 用 addFilterBefore/After 插入，勿直接改内部 Filter 列表。

易错点

  • 以为 @RestController 自动安全——未引入 Security 或 permitAll 时接口全开放。
  • 在 Filter 里写业务逻辑且不 chain.doFilter，导致后续鉴权被跳过。
  • Actuator 未单独链保护，/actuator/env 泄露配置。

速记

「请求进 Proxy，多链按路径分；Security 6：ContextHolder → 认证 → AuthorizationFilter。」

延伸阅读：Spring Security Reference — Servlet Architecture、Filter Chain

认证机制选型

表单 / HTTP Basic / JWT / OAuth2 Resource Server

概要

OAuth2 架构：Authorization Server（Keycloak / Spring Authorization Server）集中签发 Token；API Gateway 统一验签、限流、透传身份 Header；业务服务为 Resource Server，只验签不存 Session。BFF 持 Session + Cookie 时，Gateway 仍须校验下游 JWT/mTLS。选型：前后端分离 → JWT Bearer；企业 SSO → 授权码 + Refresh；内部服务 → Client Credentials / mTLS。与 Filter 细节分工：Gateway 做粗粒度鉴权与 WAF；Resource Server 做细粒度 @PreAuthorize（见第 16 章 SSO）。勿在 JWT 塞 PII；Access 短效 + Refresh 轮换。

sequenceDiagram
    participant U as 用户/客户端
    participant AS as Authorization Server
    participant APP as Resource Server
    U->>AS: 授权码/密码换 Token
    AS-->>U: Access Token + Refresh Token
    U->>APP: API + Bearer Token
    APP->>APP: JWK 验签 + 校验 exp/scope
    APP-->>U: 200 资源响应

图：OAuth2 授权码模式与 Resource Server 验签

OAuth2 组件职责表

| 组件                  | 职责                          |
|-----------------------|-------------------------------|
| Authorization Server  | 签发/刷新/撤销 Token          |
| API Gateway           | JWT 验签、限流、路由、mTLS    |
| Resource Server       | 细粒度授权、业务 API          |
| BFF（可选）           | 聚合 API、Session/Cookie 转换 |

示例代码

# application.yml — Resource Server
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://auth.example.com/realms/corp
          # 或 jwk-set-uri 直接指定 JWK 端点

// 自定义 JWT 转 Authentication（提取 roles）
@Bean
JwtAuthenticationConverter jwtAuthConverter() {
  var conv = new JwtAuthenticationConverter();
  conv.setJwtGrantedAuthoritiesConverter(jwt -> {
    var roles = jwt.getClaimAsStringList("roles");
    return roles.stream()
        .map(r -> new SimpleGrantedAuthority("ROLE_" + r))
        .collect(Collectors.toSet());
  });
  return conv;
}

// 统一 401 响应体（EntryPoint）
@Component
public class JsonAuthEntryPoint implements AuthenticationEntryPoint {
  public void commence(HttpServletRequest req, HttpServletResponse resp,
      AuthenticationException ex) throws IOException {
    resp.setStatus(401);
    resp.setContentType("application/json");
    resp.getWriter().write("{\"code\":401,\"message\":\"Unauthorized\"}");
  }
}

关键/技巧

  • Resource Server 优先 issuer-uri 自动发现 JWK，轮换密钥无感。
  • 登录失败返回泛化文案「用户名或密码错误」，防账号枚举。
  • 多端场景见第 16 章统一登录的 Refresh / 互踢实现。

易错点

  • JWT 只 Base64 解码不验签——任何人可伪造 payload。
  • Basic 认证若未启用 HTTPS 则等同明文传输，抓包即泄露。
  • 把 JWT 放 URL Query（?token=），Referer 日志泄露。

速记

「Session 配 CSRF，JWT 验签+短效，Basic 仅内网 HTTPS。」

授权：URL 级 vs 方法级

@PreAuthorize、RBAC 与分层授权策略

概要

URL 级：authorizeHttpRequests 按路径/HTTP 方法放行或要求角色，配置集中、适合粗粒度（/admin/** → ROLE_ADMIN）。方法级：@EnableMethodSecurity + @PreAuthorize("hasAuthority('order:export')")，细到接口动作，与第 16 章 RBAC 权限码对齐。RBAC：角色聚合权限，Spring 里 GrantedAuthority 可映射为权限码或 ROLE_*；SpEL 支持 @authzService.canEdit(#id) 做数据级判断（与第 16 章数据权限配合）。原则：URL 拦大类，方法拦细粒度；公开路径白名单最小化；默认 deny。

示例代码

@Configuration
@EnableMethodSecurity  // 替代旧 @EnableGlobalMethodSecurity
public class MethodSecurityConfig {}

@RestController
@RequestMapping("/api/orders")
public class OrderController {

  @PreAuthorize("hasAuthority('order:read')")
  @GetMapping("/{id}")
  public OrderDTO get(@PathVariable Long id) { /* ... */ }

  @PreAuthorize("@orderAuth.canDelete(authentication, #id)")
  @DeleteMapping("/{id}")
  public void delete(@PathVariable Long id) { /* ... */ }
}

@Service("orderAuth")
public class OrderAuthorizationService {
  public boolean canDelete(Authentication auth, Long orderId) {
    // 结合 owner / 部门 / 角色
    return /* ... */;
  }
}

关键/技巧

  • 权限码集中枚举，@PreAuthorize 引用常量，避免魔法字符串。
  • 集成测试用 @WithMockUser(authorities = "order:export") 覆盖鉴权分支。
  • 403 与 401 区分：未登录 401，已登录无权限 403，前端跳转逻辑不同。

易错点

  • 忘记 @EnableMethodSecurity，注解静默不生效。
  • 内部 @Scheduled / 自调用绕过代理，方法级注解失效。
  • 只配 URL 级，Service 被其他 Controller 复用时越权。

速记

「URL 粗拦，方法细拦；EnableMethodSecurity 不开等于裸奔。」

密码编码与策略

BCrypt、Argon2 与企业密码策略

概要

存储原则：永不明文、可逆加密（AES）存密码；只用单向哈希 + 盐。BCrypt：Spring 默认 BCryptPasswordEncoder，内置盐与 cost 因子（推荐 10–12），够用且生态成熟。Argon2：2015 密码哈希竞赛赢家，抗 GPU/ASIC，Spring Security 5.8+ 支持 Argon2PasswordEncoder，内存硬度高，适合高安全场景。密码策略：最小长度、复杂度、历史密码禁止重用；是否定期轮换按合规要求与泄露风险评估执行。登录失败锁定与 CAPTCHA 见 api-rate-limit 卡片。传输层必须 HTTPS；重置密码用一次性 Token + 短 TTL。

示例代码

@Bean
PasswordEncoder passwordEncoder() {
  // 默认 BCrypt strength=10
  return new BCryptPasswordEncoder(12);
  // 高安全：return Argon2PasswordEncoder.defaultsForSpringSecurity_v5_8();
}

// 注册 / 改密
user.setPassword(passwordEncoder.encode(rawPassword));

// 登录校验
if (!passwordEncoder.matches(rawPassword, user.getPassword())) {
  throw new BadCredentialsException("Invalid credentials");
}

// 禁止弱口令（示意）
if (!passwordPolicy.isStrong(rawPassword)) {
  throw new ValidationException("密码需 12 位含大小写数字符号");
}

关键/技巧

  • 升级 cost/算法时：matches 成功后若参数过旧则 encode 重写库。
  • 管理员重置密码强制首次登录改密，标记 mustChangePassword。
  • 日志与异常禁止打印明文密码或哈希。

易错点

  • 用 MD5/SHA1 无盐哈希——彩虹表秒破。
  • 前后端同时「加密」密码（如固定 AES）——密钥泄露等于明文。
  • 密码重置链接长期有效、可重复使用。

速记

「存哈希不存密，BCrypt 默认够，Argon2 更高配。」

CSRF / CORS / Session 固定攻击

浏览器侧经典攻击面与 Spring Security 对策

概要

CSRF：攻击者诱使已登录用户浏览器提交恶意请求；Session Cookie 自动携带导致越权操作。对策：同步器 Token（Spring 默认）、SameSite Cookie（Lax/Strict）、关键操作二次验证。纯 JWT Header 认证、无 Cookie 的 API 可关闭 CSRF，但若有 Cookie 混用仍要开。CORS：控制哪些源可跨域读响应；生产禁止 allowedOrigins("*") 且 allowCredentials(true)。前后端同域 Nginx 反代最优（见第 4 章）。Session 固定：攻击者固定 SessionId 诱用户登录后劫持；登录成功必须 sessionFixation().changeSessionId()（Spring 默认）或新建 Session。

示例代码

@Bean
SecurityFilterChain sessionApp(HttpSecurity http) throws Exception {
  return http
      .csrf(csrf -> csrf
          .csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse())
          .ignoringRequestMatchers("/api/webhook/**")) // 外部回调需签名替代 CSRF
      .sessionManagement(session -> session
          .sessionFixation().changeSessionId()
          .maximumSessions(1)
          .maxSessionsPreventsLogin(false)) // true=踢后者
      .cors(cors -> cors.configurationSource(corsSource()))
      .build();
}

@Bean
CorsConfigurationSource corsSource() {
  var config = new CorsConfiguration();
  config.setAllowedOrigins(List.of("https://admin.example.com"));
  config.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE"));
  config.setAllowCredentials(true);
  var source = new UrlBasedCorsConfigurationSource();
  source.registerCorsConfiguration("/api/**", config);
  return source;
}

关键/技巧

  • SPA + Session：前端从 Cookie 读 CSRF Token 放 Header X-XSRF-TOKEN。
  • Webhook 用 HMAC 签名 + 时间戳，而非关闭 CSRF 裸奔。
  • Cookie 设 Secure; HttpOnly; SameSite=Lax。

易错点

  • JWT API 关 CSRF 但登录仍用 Cookie Session——CSRF 窗口仍在。
  • CORS 只拦浏览器，Postman/curl 不受限——后端鉴权不能省。
  • 把 CSRF Token 放 localStorage 与 XSS 风险叠加。

速记

「Cookie 会话防 CSRF，CORS 白名单源，登录换 SessionId。」

SecurityContext 与多租户

ThreadLocal 上下文、异步传递与环境隔离

概要

SecurityContextHolder：默认 ThreadLocal 存 Authentication；Filter 入口写入，请求结束清理。异步：@Async、线程池、MQ 消费线程默认无上下文——需 DelegatingSecurityContextRunnable / SecurityContextHolder.MODE_INHERITABLETHREADLOCAL 或手动传播。多租户：租户 ID 从 JWT claim / Header 解析，写入 TenantContext（与第 16 章数据权限配合）；禁止信任前端传的 tenantId 参数。多环境：dev 禁止用生产密钥；Profile 隔离 application-prod.yml，Actuator 生产最小暴露。

示例代码

// 获取当前用户
Authentication auth = SecurityContextHolder.getContext().getAuthentication();
String userId = auth.getName();

// @Async 传播 SecurityContext
@Configuration
@EnableAsync
public class AsyncConfig implements AsyncConfigurer {
  @Override
  public Executor getAsyncExecutor() {
    ThreadPoolTaskExecutor ex = new ThreadPoolTaskExecutor();
    ex.initialize();
    return new DelegatingSecurityContextAsyncTaskExecutor(ex);
  }
}

// 租户解析 Filter（JWT 内 tenant_id）
@Component
public class TenantFilter extends OncePerRequestFilter {
  protected void doFilterInternal(HttpServletRequest req, ...) {
    String tenantId = resolveFromJwt(req);
    TenantContext.set(tenantId);
    try { chain.doFilter(req, resp); }
    finally { TenantContext.clear(); }
  }
}

关键/技巧

  • 封装 SecurityUtils.currentUserId() 统一取值，避免散落 getPrincipal() 强转。
  • 集成测试 @WithUserDetails 或 MockMvc JWT 测租户隔离。
  • 定时任务无用户上下文时显式设系统账号，审计日志标注 SYSTEM。

易错点

  • 线程池复用导致 ThreadLocal 泄漏或串租户——finally 必须 clear。
  • Reactive WebFlux 用 ThreadLocal 取用户——应换 ReactiveSecurityContextHolder。
  • 测试环境 permitAll 忘改回生产规则。

速记

「Context 跟线程走，异步要委托传；租户信 Token，不信前端参。」

注入、XSS 与 SSRF

OWASP Top 10 中的输入与出站请求

概要

SQL 注入：拼接 SQL 导致任意查询；对策——参数化查询（JPA/MyBatis #{}）、ORM 绑定、最小权限 DB 账号；动态排序白名单字段名。XSS：存储型/反射型脚本注入；后端 JSON 输出时前端转义，富文本用 OWASP Java HTML Sanitizer 白名单过滤；设置 Content-Security-Policy Header。SSRF：服务端根据用户 URL 发起请求（导入、预览、Webhook 校验），可打内网 169.254.169.254；对策——URL 协议/host 白名单、禁止私有 IP 段、禁用重定向跟随或限次数。

flowchart TB
    L1[网络层 WAF/防火墙] --> L2[传输层 TLS]
    L2 --> L3[应用层 Filter Chain]
    L3 --> L4[输入校验/参数化 SQL]
    L4 --> L5[输出编码防 XSS]
    L5 --> L6[授权与数据脱敏]
    L6 --> L7[审计日志与监控]

图：OWASP 纵深防护层次

示例代码

// ? MyBatis 参数化
@Select("SELECT * FROM user WHERE name = #{name}")
User findByName(String name);

// ? 禁止 ${name} 拼接用户输入

// 动态 ORDER BY 白名单
private static final Set<String> SORT_COLS = Set.of("created_at", "amount");
public String safeSort(String col) {
  if (!SORT_COLS.contains(col)) throw new BadRequestException("invalid sort");
  return col;
}

// SSRF 防护：校验 URL
public void fetchUserUrl(String urlStr) throws Exception {
  URI uri = URI.create(urlStr);
  if (!List.of("http", "https").contains(uri.getScheme())) throw forbidden();
  InetAddress addr = InetAddress.getByName(uri.getHost());
  if (addr.isAnyLocalAddress() || addr.isLoopbackAddress() || addr.isSiteLocalAddress())
    throw forbidden();
  // 使用 RestClient，限制 timeout、禁止自动 redirect
}

关键/技巧

  • 启用 SpotBugs/FindSecBugs、Sonar 规则扫描 SQL 拼接。
  • 导出 CSV 时对公式注入字段前缀 ' 防 Excel 宏执行。
  • SSRF 场景走独立 egress 代理，网络层再拦 RFC1918 私网地址段。

易错点

  • MyBatis ${} 用于动态表名时未白名单。
  • 认为 JSON API 无 XSS——前端 v-html 仍可利用存储型 payload。
  • PDF/图片「转 URL 抓取」功能成为 SSRF 入口。

速记

「SQL 用 #{}，XSS 白名单滤，SSRF 拦内网 IP。」

敏感数据与反序列化

日志脱敏、加密存储与不安全反序列化

概要

敏感数据泄露：日志打印手机号、身份证、Token、卡号；对策——Logback 自定义 Converter 脱敏（中间位 *）、结构化日志字段分级、生产关闭 SQL 参数明文。存储加密：PII 字段 AES-GCM 列级加密，密钥来自 KMS/Vault（见 secrets-config 卡片）；密码学分离——传输 TLS、存储加密、哈希分场景。不安全反序列化：Java 原生 ObjectInputStream、JSON 全局多态（如历史 enableDefaultTyping）可触发 RCE；对策——禁用原生反序列化、禁用全局 Default Typing，确需多态时用白名单 PolymorphicTypeValidator / @JsonTypeInfo 限定子类，并升级 Commons Collections 等历史 Gadget 依赖。

示例代码

// 日志脱敏（示意）
public static String maskPhone(String phone) {
  if (phone == null || phone.length() < 7) return "***";
  return phone.substring(0, 3) + "****" + phone.substring(phone.length() - 4);
}

// Jackson 安全：禁止 default typing
@Bean
ObjectMapper objectMapper() {
  ObjectMapper mapper = JsonMapper.builder()
      .build(); // 默认不启用全局 Default Typing
  // 历史代码若启用过 default typing，应显式调用 mapper.deactivateDefaultTyping();
  return mapper;
}

// JPA 属性转换器加密 PII
@Converter
public class EncryptedStringConverter implements AttributeConverter<String, String> {
  public String convertToDatabaseColumn(String attr) {
    return cryptoService.encrypt(attr);
  }
  public String convertToEntityAttribute(String db) {
    return cryptoService.decrypt(db);
  }
}

关键/技巧

  • 定义「禁止入日志字段」清单：password、token、idCard、bankCard。
  • Exception 全局处理返回对外泛化 message，细节只写 server log。
  • 依赖扫描（OWASP Dependency-Check、Snyk）纳入 CI，并结合 SBOM 做供应链治理。

易错点

  • 把 JWT Secret 打进日志或 Actuator /env。
  • Redis 存 Session 序列化对象可被污染链利用。
  • 错误配置 logging.level.org.hibernate.SQL=DEBUG 在生产泄露参数。

速记

「日志脱敏、PII 加密存、反序列化能不用就不用。」

文件上传与 API 限流

上传校验、防暴力破解与速率限制

概要

文件上传：校验扩展名 + MIME（Tika 嗅探）+ 大小限制；随机文件名存对象存储，禁止用户控制路径（路径遍历）；病毒扫描（ClamAV）与图片重编码去 EXIF。可执行类型（jsp、html、svg with script）禁止或隔离桶。API 限流：网关（Sentinel、Redis 滑动窗口）或 Bucket4j 按 IP/用户/API Key 限 QPS；登录、短信、验证码接口严限防暴力破解。账户锁定：连续失败 N 次锁定 M 分钟，Redis 计数；与 CAPTCHA 联动。业务模块上传细节见第 18 章文件上传卡片，本章强调威胁面。

示例代码

// Spring 上传限制
spring:
  servlet:
    multipart:
      max-file-size: 10MB
      max-request-size: 12MB

// Bucket4j 限流（示意）

关键/技巧

  • 下载接口 Content-Disposition: attachment，防浏览器嗅探执行。
  • 限流返回 429 + Retry-After Header。
  • 管理端上传与公网用户分桶、分权限。

易错点

  • 只校验客户端扩展名，双扩展名 evil.jsp.jpg 绕过。
  • 限流只限 IP，攻击者轮换代理；关键接口加账号维度。
  • Zip 炸弹未限制解压后总大小。

速记

「上传白名单+随机名，登录限流+锁定，429 要带 Retry-After。」

密钥、配置与 TLS

环境变量、Vault/K8s Secret 与 HTTPS

概要

密钥管理：09-Factor 配置与密钥分离；本地 .env 不入库，生产用环境变量、HashiCorp Vault、云 KMS 或 K8s Secret（配合 External Secrets 同步）。Spring ${DB_PASSWORD} 注入，禁止硬编码在 application.yml 提交 Git。HTTPS/TLS：全链路 TLS 1.2+，Nginx/Ingress 终止或 Boot 内置 SSL；HSTS Header 强制浏览器 HTTPS。证书 Pinning：移动端 App 可 Pin 服务端公钥防中间人，需规划证书轮换；Web 一般依赖系统 CA。详见第 22 章密钥与配置管理。

示例代码

# application-prod.yml — 占位符，值来自环境/K8s
spring:
  datasource:
    password: ${DB_PASSWORD}
  data:
    redis:
      password: ${REDIS_PASSWORD}

custom:
  jwt:
    private-key-location: ${JWT_PRIVATE_KEY_PATH}

# K8s Secret 挂载为文件
# env:
#   - name: DB_PASSWORD
#     valueFrom:
#       secretKeyRef:
#         name: app-db
#         key: password

# Nginx TLS 片段
# ssl_protocols TLSv1.2 TLSv1.3;
# add_header Strict-Transport-Security "max-age=31536000" always;

关键/技巧

  • 密钥轮换：双密钥并行验签窗口，再下线旧钥。
  • Git 提交前 gitleaks/trufflehog 扫描历史密钥。
  • Boot Actuator 生产只开 health、info，且需认证。

易错点

  • 把 AK/SK 写进前端或移动端包体。
  • K8s Secret Base64 非加密，etcd 权限不当仍泄露。
  • 内网 HTTP 「反正隔离」——横向移动后明文可嗅探。

速记

「密钥不进 Git，生产走 Vault/Env；全站 HTTPS，HSTS 要开。」

JWT 最佳实践

过期、刷新、黑名单与算法选择

概要

结构：Header.Payload.Signature；Payload 只放 sub、roles、tenant 等必要声明，禁止密码/PII。算法：Resource Server 应显式限制可信 iss/aud 与允许算法（如 RS256/ES256）；拒绝 alg:none 与 HS256 弱密钥（<256 bit）。生命周期：Access 15–30 min；Refresh 7–30 天存 HttpOnly Cookie 或 Redis，Refresh 轮换（用后作废旧 jti）。黑名单：登出/改密/踢人将 jti 入 Redis，TTL=剩余 exp；网关与服务双重校验更稳。

示例代码

// 签发（Authorization Server 或自建）
JwtEncoderParameters params = JwtEncoderParameters.from(
    JwtClaimsSet.builder()
        .issuer("https://auth.example.com")
        .subject(userId)
        .expiresAt(Instant.now().plus(30, ChronoUnit.MINUTES))
        .claim("jti", UUID.randomUUID().toString())
        .claim("roles", roles)
        .build());
String accessToken = jwtEncoder.encode(params).getTokenValue();

// 验签 + 黑名单
public void validate(String token) {
  Jwt jwt = jwtDecoder.decode(token);
  if (blacklist.exists(jwt.getId())) throw new JwtException("revoked");
}

// Resource Server：issuer 自动拉 JWK + 校验 aud/iss
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://auth.example.com
          audiences: order-service  # 防 Token 挪用到其他微服务

@Bean
JwtDecoder jwtDecoder(OAuth2ResourceServerProperties props) {
  NimbusJwtDecoder decoder = JwtDecoders.fromIssuerLocation(props.getJwt().getIssuerUri());
  OAuth2TokenValidator<Jwt> aud = new JwtClaimValidator<List<String>>(
      "aud", aud -> aud != null && aud.contains("order-service"));
  decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(JwtValidators.createDefault(), aud));
  return decoder;
}

关键/技巧

  • 时钟偏移容忍 clockSkew 30s，多节点 NTP 同步。
  • 短 Access + Refresh 优于长 Access——泄露窗口更小。
  • 网关统一验签，下游可信任内网 Header 但需 mTLS 防伪造。

易错点

  • JWT 当 Session 存大量状态——体积膨胀且无法服务端撤销（无黑名单时）。
  • HS256 密钥 < 256 bit 或硬编码在代码库。
  • 不校验 aud，Token 被挪用到其他服务。

速记

「Access 短、Refresh 轮换，jti 黑名单；RS256 优先，none 必拒。」

安全审计与合规

审计日志、等保与开发注意点

概要

安全审计日志：谁、何时、从何 IP、对何资源、何操作、结果（成功/失败）；登录/登出、权限变更、敏感数据导出、配置修改必记；日志防篡改（独立存储、WORM、SIEM 对接）。与第 18 章操作审计业务字段互补，本章强调不可抵赖与留存周期（常 ≥6 个月）。等保 2.0 / 合规（简要）：身份鉴别、访问控制、安全审计、通信完整性/保密性、恶意代码防范；开发侧对应——多因素认证（高危操作）、三权分立（系统/安全/审计管理员）、密码策略、漏洞修复 SLA、渗透测试。数据分类分级：公开/内部/敏感/机密，不同加密与脱敏策略。

示例代码

@Aspect
@Component
public class SecurityAuditAspect {
  @AfterReturning("@annotation(Audited)")
  public void logSuccess(JoinPoint jp) { writeAudit(jp, "SUCCESS"); }

  @AfterThrowing(value = "@annotation(Audited)", throwing = "ex")
  public void logFail(JoinPoint jp, Exception ex) { writeAudit(jp, "FAIL"); }

  void writeAudit(JoinPoint jp, String result) {
    auditLogger.info(AuditEvent.builder()
        .userId(SecurityUtils.userId())
        .ip(RequestContext.clientIp())
        .action(jp.getSignature().toShortString())
        .resource(extractResource(jp))
        .result(result)
        .timestamp(Instant.now())
        .build().toJson());
  }
}

// 等保：管理员操作二次验证（示意）
@PreAuthorize("hasRole('ADMIN')")
@PostMapping("/api/admin/users/{id}/role")
public void changeRole(@PathVariable Long id, @RequestBody RoleReq req,
    @RequestHeader("X-MFA-Token") String mfa) {
  mfaService.verify(SecurityUtils.userId(), mfa);
  userService.changeRole(id, req.role());
}

关键/技巧

  • 审计日志与用户业务日志分 Logger、分索引，防误删。
  • 定期导出权限矩阵与 API 鉴权清单做合规自查。
  • 上线前安全 checklist：依赖 CVE、渗透项、配置基线。

易错点

  • 只记成功操作，登录失败不记——暴力破解无迹可寻。
  • 审计日志含明文密码或 Token。
  • 等保测评临时改配置，测评后未固化。

速记

「审计记成败、记 IP；等保重鉴别、审计、加密；测评配置要常态化。」

延伸阅读：GB/T 22239 等保基本要求、OWASP ASVS、NIST SP 800-53

供应链安全（SBOM）

依赖漏洞扫描与 CVE 响应

概要

SBOM（Software Bill of Materials）列出应用全部依赖及版本。CI 集成 OWASP Dependency-Check、Snyk 或 GitHub Dependabot；blocker 级 CVE 阻断发布。响应流程：发现 → 评估可利用性 → 升级版本 / 临时缓解 → 验证 → 关闭。

Maven 插件示例

<plugin>
  <groupId>org.owasp</groupId>
  <artifactId>dependency-check-maven</artifactId>
  <executions>
    <execution><goals><goal>check</goal></goals></execution>
  </executions>
</plugin>
