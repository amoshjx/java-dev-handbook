24 Palantir AIP 级企业智能化架构设计与开发实现

在企业级 AI 落地中，「LLM 对话框」正被企业级 AI 微操作系统取代——类似 Palantir AIP：本体描述业务世界、护栏约束模型、Action 将决策幂等、可审计写回老系统。本章覆盖四层架构、Ontology/GraphRAG、护栏链与回写总线（Java 21 / Spring Boot 3.x）。与第 23 章（场景/Eval）、第 22 章（开发侧 AI）、第 17 章、第 11 章衔接。建议先读模块导览。

课程前言

从对话框到企业 AI 操作系统

讲解

核心矛盾：如何让「有幻觉、不可控」的 LLM，在「严谨、古板」的企业系统里安全打工？AIP 的答案不是无限调 Prompt，而是架构约束确定性：模型只能看见 Ontology 导出的上下文、只能调用白名单 Tool、写回必须经护栏与（可选）人工审批。

三种形态对比

| 维度           | Chatbot 套壳     | 独立 RAG 平台    | AIP 级系统              |
|----------------|------------------|------------------|-------------------------|
| 数据视图       | 文档片段         | 向量 Chunk       | 业务对象 + 关系图       |
| 权限           | 粗粒度 API Key   | 检索 metadata    | 细胞级密级 + 数据边界   |
| 写回能力       | 无或人工复制     | 少见             | 强类型 Tool + 幂等总线  |
| 审计           | 对话日志         | ingest 版本      | Prompt/Tool/Action 全链 |
| 适用           | 内部 FAQ         | 制度/手册问答    | 跨系统决策与闭环操作    |

成熟度阶梯（自评用）

  • L1：单应用 + 直连 LLM API，无统一鉴权。
  • L2：独立 RAG，检索带 tenant 过滤（见第 23 章 RAG）。
  • L3：Ontology + Guardrails，只读问答，无写回。
  • L4：Tool + 异步审批回写 + 全链路审计（本章目标）。
  • L5：多 Agent Saga、跨域补偿、生产 Eval 门禁与模型路由。

速记

「Chatbot 会说话，RAG 会查资料，AIP 会办事且办得可追溯。」

第一部分：AIP 系统总体架构设计

1.1 四层架构职责划分

讲解

AIP 采用四层隔离架构，每层职责单一、可独立演进与审计：

  1. 统一网关与安全透传层（AIP Gateway & Auth）：拦截所有用户请求，OAuth2 / OIDC 认证；核心职责是透传 SecurityContext（角色、部门、密级标签如 L5_SECRET）至下游微服务。
  2. 数据本体与语义上下文层（Ontology Engine）：拒绝 LLM 直连原始库表；将关系表、NoSQL、文档转为统一业务对象（Objects）与关系（Relations），结合 Pgvector / Milvus 做动态 RAG，为 LLM 绘制企业「数字孪生」地图。
  3. 安全合规护栏层（AIP Guardrails & Policy）：Prompt 前置审计（越权提问、敏感词）；LLM 响应后、Action 执行前后置审计（意图越权、参数异常）。
  4. 智能体编排与行动回写层（Agent & Write-back Bus）：Tool Calling 分发；经 Kafka 等事件总线与双向适配器，将 AI 决策幂等、可审计写回 ERP / CRM / MES。
flowchart LR
    USER[用户/应用] --> GW[Gateway + Auth]
    GW --> ONT[Ontology + RAG]
    ONT --> PRE[preHandlePrompt]
    PRE --> LLM[LLM]
    LLM --> POST[postHandleResponse]
    POST --> TOOL[Tool / Action]
    TOOL --> KAFKA[Kafka Write-back]
    KAFKA --> ADAPTER[老系统 Adapter]

图：请求在各层间的典型流转

关键/技巧

  • 网关层只做身份与上下文，不把业务规则堆在 BFF。
  • LLM 永远只看到 Ontology 导出的上下文，而非裸 SQL 结果集。
  • 与第 03 章架构设计的 ADR、质量属性权衡一并归档四层边界。

阶段成果

  • AIP 上下文图（C4 L2）：四层边界、外部系统、数据流
  • 质量属性表：安全、可审计、可用性、延迟预算（见下表口径）

质量属性与架构对策（摘录）

| 质量属性   | 目标口径              | 架构对策                          |
|------------|-----------------------|-----------------------------------|
| 安全       | 零信任、最小权限      | Gateway 透传 + Guardrails 双检    |
| 可审计     | Action 100% 可追溯    | 审计表 + Kafka 事件 + traceId     |
| 可用性     | LLM 降级仍可只读问答  | 缓存 Ontology 子图、规则兜底话术  |
| 性能       | P95 问答 < 8s（含检索）| 子图深度≤2、向量 Top-K≤8、流式输出 |

1.2 推荐微服务拆分与职责

讲解

不必一开始拆得过细，但逻辑边界须清晰，便于独立扩缩容与合规审计：

  • aip-gateway：OAuth2 终结、限流、Aip-Nonce-Key 签发、SecurityContext 序列化透传。
  • aip-ontology-service：实体/关系 CRUD、子图遍历、向量索引、ingest 任务（无 LLM）。
  • aip-agent-orchestrator：对话状态机、Prompt 组装、调用 LLM、调度 Tool（不直连老库）。
  • aip-guardrails-service（可内嵌 orchestrator）：拦截器链、策略配置、审计写入。
  • aip-action-service：ActionTask 状态机、审批 API、Kafka 生产。
  • aip-adapter-*：按域拆分（order-adapter、mes-adapter），消费写回主题、幂等执行、回调 Ontology 刷新。

  • 在 orchestrator 内嵌 MyBatis 直连业务库——破坏 Ontology 单一数据视图。

1.3 SecurityContext 透传（Gateway → 下游）

讲解

下游服务禁止再次解析用户自然语言来推断权限；只信任 Gateway 注入的上下文。推荐 JWT Custom Claims 或内部 X-AIP-Context（mTLS 内网 + 签名防篡改）。与第 17 章 Resource Server 配置一致。

JWT Claims 与 Filter 还原

// Gateway 签发时写入（示意）
{
  "sub": "u10086",
  "roles": ["ROLE_MANAGER"],
  "permissions": ["MODIFY_ORDER", "QUERY_ONTOLOGY"],
  "deptId": "D-SH-01",
  "maxClassification": "L3_INTERNAL",
  "traceId": "8f3c..."
}

// 下游 aip-agent-orchestrator
@Component
public class AipSecurityContextFilter extends OncePerRequestFilter {
  @Override
  protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
      throws ServletException, IOException {
    Jwt jwt = (Jwt) SecurityContextHolder.getContext().getAuthentication().getPrincipal();
    AipUserContext ctx = AipUserContext.fromJwt(jwt);
    AipContextHolder.set(ctx);
    try { chain.doFilter(req, res); } finally { AipContextHolder.clear(); }
  }
}

关键/技巧

  • permissions 与 Tool 名称一一映射，避免模型自创 action 名。
  • maxClassification 用于 Ontology 检索前过滤，见下文密级矩阵。

第二部分：数据本体（Ontology）模块开发实现

2.1 关系表模拟图结构的数据库设计

讲解

兼顾关系库严谨性与图结构灵活性，PostgreSQL 推荐 EAV 扩展 + 拓扑关系表：实体类型元数据、实例 JSONB 动态属性、显式边表表达 CONTAINS / REQUIRED_BY 等关系。每条实例带 security_classification，供检索前按用户密级过滤（细胞级权限）。亿级边、深度路径分析场景可另选专用图库，存储分工见第 03 章图数据库选型。

DDL 示例

-- 1. 实体类型定义表（元数据）
CREATE TABLE aip_entity_type (
    type_key VARCHAR(50) PRIMARY KEY,
    display_name VARCHAR(100) NOT NULL,
    description TEXT
);

-- 2. 实体实例表（JSONB 动态属性）
CREATE TABLE aip_entity_instance (
    instance_id VARCHAR(64) PRIMARY KEY,
    type_key VARCHAR(50) REFERENCES aip_entity_type(type_key),
    display_name VARCHAR(200),
    properties JSONB NOT NULL,
    security_classification VARCHAR(50),
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 3. 关系拓扑表
CREATE TABLE aip_relation (
    relation_id BIGSERIAL PRIMARY KEY,
    source_id VARCHAR(64) REFERENCES aip_entity_instance(instance_id),
    target_id VARCHAR(64) REFERENCES aip_entity_instance(instance_id),
    relation_type VARCHAR(50) NOT NULL,
    description TEXT
);

-- 4. 索引建议
CREATE INDEX idx_entity_type ON aip_entity_instance(type_key);
CREATE INDEX idx_entity_props ON aip_entity_instance USING GIN (properties);
CREATE INDEX idx_relation_src ON aip_relation(source_id);
CREATE INDEX idx_relation_tgt ON aip_relation(target_id);

-- 5. 可选：实体描述向量（GraphRAG 语义入口）
-- embedding vector(1536) 存 Pgvector，对 display_name + description 做嵌入

密级与可见性矩阵（示例）

| 用户 maxClassification | 可见实体 security_classification |
|------------------------|--------------------------------------|
| L1_PUBLIC              | L1_PUBLIC                            |
| L3_INTERNAL            | L1_PUBLIC, L2_TEAM, L3_INTERNAL      |
| L5_SECRET              | 全部（含 L5_SECRET，需 ROLE 额外校验）|

检索 SQL 片段: WHERE security_classification <= :userMaxLevel

易错点

  • JSONB 无 schema 约束导致 LLM 上下文字段漂移——应对高频属性做 generated column 或校验触发器。
  • 二度以上图遍历未设深度上限，Prompt 爆炸。

2.2 拓扑图检索与 LLM 语义转换（Java）

讲解

用户针对某实体提问时，引擎执行一度或二度邻居动态图遍历，组装为 LLM 易读的结构化 Markdown 上下文，降低幻觉。实现上可用递归 CTE 或应用层 BFS；输出前再次按 security_classification 过滤节点。

OntologySubGraph → LLM Context

@Data
public class OntologySubGraph {
    private Map<String, EntityInstance> entities = new HashMap<>();
    private List<RelationEdge> edges = new ArrayList<>();

    public String toLlmContext() {
        StringBuilder sb = new StringBuilder("=== 发现的相关业务实体 (Ontology Context) ===\n");
        entities.values().forEach(e -> {
            sb.append(String.format("- [%s](类型: %s): 属性=%s\n",
                e.getInstanceId(), e.getTypeKey(), e.getProperties().toString()));
        });
        sb.append("\n=== 实体之间的关联拓扑关系 ===\n");
        edges.forEach(edge -> {
            sb.append(String.format("- 实体 [%s] 通过关系 {%s} 连接到 实体 [%s]\n",
                edge.getSourceId(), edge.getRelationType(), edge.getTargetId()));
        });
        return sb.toString();
    }
}

关键/技巧

  • 上下文模板版本化，便于 Eval 对比幻觉率。
  • 向量检索命中实体后，再以 instance_id 为种子做子图扩展（GraphRAG 常见模式）。
  • 子图 Token 预算：实体数 ≤ 30、边数 ≤ 50，超出则按关系权重截断。

2.3 老系统 → Ontology 同步（Ingest）

讲解

Ontology 不是一次性 ETL，而是持续对齐企业真相源：CDC（Debezium）、定时批同步、或领域事件（订单已支付 → 更新 Order 实例）。每条 ingest 记录 source_system、source_pk、sync_version，便于对账与 LLM 引用「数据截至时间」。

映射配置（YAML 示意）

ontology:
  types:
    - typeKey: Order
      source: erp.order_header
      idMapping: "ORD-{order_id}"
      properties:
        status: status_code
        amount: total_amount
      classification: "L3_INTERNAL"
  relations:
    - type: CONTAINS
      from: Order
      to: OrderLine
      join: order_id

阶段成果

  • Ingest 映射表：源表 → typeKey / 属性 / 关系
  • 同步 SLA：延迟上限、失败重试与死信队列策略

2.4 二度邻居图遍历（SQL + Service）

讲解

PostgreSQL 用递归 CTE做有界深度遍历；应用层须传入 maxDepth（建议 2）与密级过滤，避免全图扫库。

递归 CTE（深度 ≤ 2）

WITH RECURSIVE graph AS (
  SELECT source_id, target_id, relation_type, 1 AS depth
  FROM aip_relation WHERE source_id = :seedId
  UNION ALL
  SELECT r.source_id, r.target_id, r.relation_type, g.depth + 1
  FROM aip_relation r
  JOIN graph g ON r.source_id = g.target_id
  WHERE g.depth < :maxDepth
)
SELECT DISTINCT e.* FROM aip_entity_instance e
WHERE e.instance_id IN (
  SELECT source_id FROM graph UNION SELECT target_id FROM graph UNION SELECT :seedId
)
AND e.security_classification <= :userMaxLevel;

OntologyQueryService（Java 示意）

@Service
@RequiredArgsConstructor
public class OntologyQueryService {
  private final OntologySubGraphMapper mapper;

  public OntologySubGraph loadSubGraph(String seedId, int maxDepth, String userMaxLevel) {
    List<EntityInstance> entities = mapper.selectSubGraphEntities(seedId, maxDepth, userMaxLevel);
    List<RelationEdge> edges = mapper.selectEdgesAmong(
        entities.stream().map(EntityInstance::getInstanceId).toList());
    OntologySubGraph graph = new OntologySubGraph();
    entities.forEach(e -> graph.getEntities().put(e.getInstanceId(), e));
    graph.getEdges().addAll(edges);
    return graph;
  }
}

2.5 GraphRAG：向量入口 + 子图扩展

讲解

纯向量 RAG 易丢失结构关系（「该订单下的延期组件」）。GraphRAG 标准路径：① 用户问题 Embedding；② 在 Ontology 实体描述向量上 Top-K；③ 以命中 instance_id 为种子拉子图；④ toLlmContext() 与可选文档 Chunk 合并进 Prompt。与第 23 章 RAG互补——本章强调结构化对象而非仅文档。

flowchart LR
    Q[用户问题] --> EMB[Query Embedding]
    EMB --> VEC[Ontology 向量 Top-K]
    VEC --> SEED[种子 instance_id]
    SEED --> SUB[子图遍历 depth≤2]
    SUB --> CTX[Markdown Context]
    DOC[可选文档 RAG] --> CTX
    CTX --> LLM[LLM]

图：GraphRAG 与文档 RAG 组合

Spring AI 组合顾问（概念示意）

String ontologyCtx = ontologyQueryService
    .loadSubGraph(seedId, 2, ctx.getMaxClassification())
    .toLlmContext();

ChatResponse response = chatClient.prompt()
    .system("仅依据 ONTOLOGY_CONTEXT 与 DOC_CONTEXT 回答，禁止编造实体 ID。")
    .user("ONTOLOGY_CONTEXT:\n" + ontologyCtx + "\n\n问题: " + question)
    .advisors(new QuestionAnswerAdvisor(docVectorStore)) // 可选文档层
    .call()
    .chatResponse();

第三部分：安全护栏（Guardrails）安全拦截机制

3.1 拦截器管道（Interceptor Pipeline）设计

讲解

类比 Spring MVC HandlerInterceptor，在「大模型推理前」与「工具执行前」架设两道防火墙。所有拦截器实现统一接口，可链式组合（敏感词、密级、租户、自定义策略）。

接口契约

public interface AipGuardrailInterceptor {
    boolean preHandlePrompt(String prompt, SecurityContext userAuth);
    boolean postHandleResponse(LLMResponse response, SecurityContext userAuth);
}

责任链注册（Spring）

@Configuration
public class GuardrailConfig {
  @Bean
  AipGuardrailChain guardrailChain(List<AipGuardrailInterceptor> interceptors) {
    return new AipGuardrailChain(interceptors); // 按 @Order 排序
  }
}

public class AipGuardrailChain {
  private final List<AipGuardrailInterceptor> chain;
  public void preHandle(String prompt, SecurityContext ctx) {
    for (var i : chain) {
      if (!i.preHandlePrompt(prompt, ctx)) {
        throw new GuardrailBlockedException("preHandle blocked");
      }
    }
  }
  public boolean postHandle(LLMResponse resp, SecurityContext ctx) {
    for (var i : chain) {
      if (!i.postHandleResponse(resp, ctx)) return false;
    }
    return true;
  }
}

推荐拦截器清单

  • ClassificationInterceptor：Prompt 是否触及超密级关键词。
  • PiiRedactionInterceptor：身份证/手机号进 LLM 前掩码（日志同理）。
  • PromptInjectionHeuristicInterceptor：「忽略上文规则」类模式评分。
  • SecurityGuardrailInterceptor：Tool 垂直/水平越权（见下节）。
  • RateBudgetInterceptor：单用户 Token/Action 日配额。

3.2 后置「意图审计」核心实现

讲解

防御 Prompt Injection 与模型缺陷导致的越权写回：垂直越权检查用户是否具备 Action 权限；水平越权检查目标资源（如 orderId）是否落在用户数据边界内。审计失败应阻断 Tool 执行并留痕，不可静默降级为「仅返回文本」。

SecurityGuardrailInterceptor

@Component
@Slf4j
public class SecurityGuardrailInterceptor implements AipGuardrailInterceptor {

    @Override
    public boolean preHandlePrompt(String prompt, SecurityContext userAuth) {
        if (prompt.contains("SECRET_PROJECT")
                && !userAuth.getRoles().contains("ROLE_DIRECTOR")) {
            throw new SecurityException("AIP 安全拦截：您无权向大模型探听核心机密项目。");
        }
        return true;
    }

    @Override
    public boolean postHandleResponse(LLMResponse response, SecurityContext userAuth) {
        if (response.isToolCall()) {
            String targetAction = response.getToolName();
            Map<String, Object> params = response.getToolArguments();

            if (!userAuth.getPermissions().contains(targetAction)) {
                log.error("安全警报！AI Agent 试图代表用户 {} 执行未授权动作: {}",
                    userAuth.getUserId(), targetAction);
                return false;
            }

            String targetOrderId = (String) params.get("orderId");
            if (!checkDataBoundary(userAuth.getUserId(), targetOrderId)) {
                log.error("安全警报！用户 {} 试图通过 AI 修改越权数据: {}",
                    userAuth.getUserId(), targetOrderId);
                return false;
            }
        }
        return true;
    }

    private boolean checkDataBoundary(String userId, String orderId) {
        return true; // 查库核验订单是否属于用户管辖区域/部门
    }
}

易错点

  • 仅校验 Tool 名称，不校验参数中的资源 ID。
  • 权限列表来自 LLM 上下文而非登录态，可被注入伪造。
  • postHandle 返回 false 仍执行 Tool——须在编排层硬阻断，不能仅打日志。

编排层硬阻断（示意）

LLMResponse resp = llmClient.complete(prompt, tools);
if (resp.isToolCall() && !guardrailChain.postHandle(resp, userCtx)) {
  auditService.logBlocked(userCtx, resp);
  return AgentReply.blocked("该操作未通过安全审计，已拒绝执行。");
}
return toolExecutor.execute(resp); // 仅审计通过后

3.3 全链路审计留痕

讲解

合规与事故复盘要求：谁、何时、问了什么、模型回了什么、试图执行哪条 Action、是否审批、老系统最终状态。审计记录只追加、不更新；敏感字段脱敏存储；保留期按等保/行业规范配置。

审计表 DDL（摘录）

CREATE TABLE aip_audit_event (
    event_id        BIGSERIAL PRIMARY KEY,
    trace_id        VARCHAR(64) NOT NULL,
    user_id         VARCHAR(64) NOT NULL,
    event_type      VARCHAR(32) NOT NULL,  -- PROMPT / LLM_RESPONSE / TOOL_BLOCKED / ACTION_APPROVED
    payload_json    JSONB,
    created_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX idx_audit_trace ON aip_audit_event(trace_id);
CREATE INDEX idx_audit_user_time ON aip_audit_event(user_id, created_at DESC);

关键/技巧

  • traceId 从 Gateway 贯穿 Kafka、Adapter，对齐第 20 章链路追踪。
  • Prompt 原文可 hash 存证 + 加密对象存储，库内只存摘要。

第四部分：智能体行动与数据回写（Action Write-back）

4.1 强类型契约与反向上下文注入

讲解

禁止大模型自由生成 SQL 改库。通过 LangChain4j @Tool 或 Spring AI 注解向模型声明有限参数、强类型方法。LLM 常只有语义（「给张三延期」），缺少老系统需要的 operatorId、客户端 IP 等——由代理层从 SecurityContext反向注入，绝不信任模型传入的操作人字段。

关键/技巧

  • Tool 定义遵循 JSON Schema，保持模型无感知（Model Agnostic），可切换不同 LLM 供应商。
  • 高危 Action 默认走审批流，见下一节。
  • 参数校验用 Jakarta Validation（@NotBlank、枚举），拒绝模型传入非法状态码。

Spring AI @Tool + 反向注入

@Configuration
class OrderTools {
  @Bean
  @Description("修改订单状态，需主管审批")
  Function<ModifyOrderRequest, String> modifyOrder(AipActionWorkflowEngine engine) {
    return req -> {
      AipUserContext ctx = AipContextHolder.get(); // 来自 Filter，非 LLM
      return engine.modifyOrderStatus(
          req.orderId(), req.newStatus(), req.reason(), ctx);
    };
  }
}

public record ModifyOrderRequest(
    @NotBlank String orderId,
    @Pattern(regexp = "DELAYED|SHIPPED|CANCELLED") String newStatus,
    @Size(max = 500) String reason) {}

易错点

  • 在 Tool 方法签名暴露 operatorId 参数——必须由框架注入。
  • Tool 内部写 JDBC 绕过 Adapter——破坏幂等与审计统一出口。

4.2 老系统 Adapter 与幂等消费

讲解

Adapter 是唯一允许调用 ERP/MES 写接口的进程。消费 Kafka 时用 taskId 作幂等键：先查 aip_idempotency_record，已 SUCCESS 则 ack 跳过；执行成功再写 SUCCESS；失败进 DLQ 并告警。禁止 LLM 或 orchestrator 直连 SOAP/遗留 RPC。

Kafka 消费者（摘录）

@KafkaListener(topics = "aip-writeback-topic")
public void onMessage(ConsumerRecord<String, String> record) {
  String taskId = record.key();
  if (idempotencyStore.exists(taskId)) return;

  ActionTask task = parse(record.value());
  try {
    legacyOrderClient.updateStatus(
        task.getPayload().get("orderId"),
        task.getPayload().get("status"),
        task.getOperatorId());
    idempotencyStore.markSuccess(taskId);
    ontologySyncService.refreshEntity("Order", task.getPayload().get("orderId"));
  } catch (Exception ex) {
    idempotencyStore.markFailed(taskId, ex.getMessage());
    throw ex; // 触发重试 / DLQ 策略
  }
}

4.3 异步回写（Human-in-the-Loop）架构

讲解

高危变更采用状态机 + Kafka + 人工审批：Tool 调用只创建 PENDING_APPROVAL 任务并挂起 Agent；主管批准后以 taskId 为幂等键投递写回主题，由老系统 Adapter 消费执行。

stateDiagram-v2
    [*] --> PENDING_APPROVAL: "LLM Tool 调用"
    PENDING_APPROVAL --> APPROVED: "主管审批"
    PENDING_APPROVAL --> REJECTED: "驳回"
    APPROVED --> PUBLISHED: "Kafka 投递"
    PUBLISHED --> [*]: "Adapter 幂等执行"

图：Action 任务状态机

AipActionWorkflowEngine

@Service
public class AipActionWorkflowEngine {

    @Autowired private KafkaTemplate<String, String> kafkaTemplate;
    @Autowired private ActionTaskRepository taskRepository;

    @Tool("修改指定订单的状态，并记录延期原因")
    public String modifyOrderStatus(String orderId, String newStatus, String reason,
            @ObjectContext SecurityContext auth) {

        ActionTask task = new ActionTask();
        task.setTaskId(UUID.randomUUID().toString());
        task.setActionType("MODIFY_ORDER");
        task.setOperatorId(auth.getUserId());
        task.setPayload(Map.of("orderId", orderId, "status", newStatus, "reason", reason));
        task.setStatus("PENDING_APPROVAL");
        taskRepository.save(task);

        return "Action 已挂起，审批单 [" + task.getTaskId()
            + "]，请等待主管确认（Human-in-the-loop）。";
    }

    public void onApprovalSuccess(String taskId) {
        ActionTask task = taskRepository.findById(taskId).orElseThrow();
        task.setStatus("APPROVED");
        taskRepository.save(task);
        kafkaTemplate.send("aip-writeback-topic", task.getTaskId(),
            JacksonUtil.toJson(task));
    }
}

4.4 多步骤回写与 Saga 补偿

讲解

Agent 编排「扣 MES 库存 → 改 ERP 订单金额」时，第二步失败必须触发已定义好的补偿 Tool（恢复库存、冲正凭证），由 Java 状态机驱动，而非让 LLM「想办法撤销」。

sequenceDiagram
    participant AG as Agent
    participant MES as MES Adapter
    participant ERP as ERP Adapter
    AG->>MES: Step1 扣库存
    MES-->>AG: OK
    AG->>ERP: Step2 改账
    ERP-->>AG: FAIL
    AG->>MES: Compensate 回滚库存

图：失败后的补偿路径

补偿 Action 注册（示意）

@Tool("回滚 MES 库存扣减")
public String compensateMesStock(String mesTxnId, @ObjectContext AipUserContext ctx) {
  return mesAdapter.reverse(mesTxnId, ctx.getUserId());
}

// Saga 状态: RUNNING -> COMPENSATING -> COMPLETED / FAILED
// 每步落库 aip_saga_step，幂等键 = sagaId + stepIndex

易错点

  • 补偿本身非幂等——须用 mesTxnId 唯一键。
  • LLM 自行决定调用补偿 Tool 的顺序——应由编排引擎按状态机触发。

结语

工业级躯壳，而非无限调参

讲解

构建 Palantir AIP 级别系统的本质，是用工业级分布式架构和严密元数据管控，为大模型打造安全、稳定、高确定性的运行环境。上线前自检：

  • LLM 是否从未直连业务库？
  • 每次 Tool 调用是否有 pre/post 护栏与审计 traceId？
  • 写回是否全部经 Adapter + 幂等键？
  • 是否已规划 Eval 与发布门禁（见第 23 章）？

后续结合Eval 门禁、CI/CD、测试策略将 AIP 纳入标准发布。与第 23 章分工不变：23 定业务场景与 RAG 产品规格，本章定平台级工程实现。
