24 Palantir AIP 实战教程：从 Ontology 到 Agentic Workflow

Palantir AIP 不是一个普通聊天机器人，也不是把 RAG 接到企业数据库上这么简单。它的核心是把企业的数据、逻辑、行动与安全统一到 Ontology，再让 LLM、人员、应用和自动化流程在同一个业务语义层上协作。本章按真实 AIP 的产品与架构重新组织：先理解 Ontology，再理解 AIP Logic、Chatbot Studio、Action Types、OSDK、MCP、AIP Evals 与 Agentic Runtime，最后落到 Java 团队如何接入和交付。

flowchart TB
    DATA[Foundry 数据资产] --> ONT[Ontology: 对象/属性/链接/动作/函数]
    LOGIC[AIP Logic / Functions] --> ONT
    ONT --> APP[Workshop / 自定义应用 / OSDK]
    ONT --> BOT[AIP Chatbot Studio]
    ONT --> AUTO[Automate / Agentic Runtime]
    BOT --> ACT[Action Types 写回 Ontology]
    AUTO --> ACT
    ACT --> WB[(Writeback Dataset / 运营系统)]
    SEC[安全: 角色/用途/标记/血缘/发布治理] --> ONT
    SEC --> BOT
    SEC --> AUTO
    EVAL[AIP Evals] --> LOGIC
    EVAL --> BOT

图：Palantir AIP 的真实中心不是 Prompt，而是可读、可写、可治理的 Ontology。

学习地图

这章要解决什么问题

讲解

大多数企业 AI 项目失败，不是因为模型不够强，而是因为模型无法安全理解企业上下文，也无法把建议变成可靠行动。Palantir AIP 的设计重点是“把 AI 接到企业决策系统上”：让 AI 只在授权的数据、逻辑、动作和应用边界内工作，并把每一次读、写、审批和反馈纳入平台治理。

阅读顺序

  1. 先理解 AIP 定位：AIP 与 ChatGPT、BI、传统 RPA、普通 RAG 的差异。
  2. 再掌握 Ontology：对象、属性、链接、对象集、函数与动作类型。
  3. 理解 AIP 工具链：AIP Logic、Chatbot Studio、Evals、Threads、OSDK、MCP。
  4. 学习 Agentic Workflow：如何从问答走向可审批、可执行、可回滚的行动。
  5. 最后做治理：权限、用途、安全标记、血缘、发布门禁和运行监控。

速记

普通 AI 系统让模型“回答问题”；AIP 让模型、人员和应用在同一个业务操作层上“共同做决定并执行”。

第一部分：Palantir AIP 到底是什么

1.1 AIP 的产品定位

讲解

AIP，全称 Artificial Intelligence Platform，是 Palantir 在 Foundry 和 Gotham 等平台能力之上构建的企业 AI 平台。它让组织可以用 LLM 构建工作流、Agent、应用和自动化，并让这些能力直接使用 Palantir 平台中的 Ontology 数据、逻辑和动作。

与“给数据库加一个聊天入口”不同，AIP 的关键价值是把 AI 放进受控的运营体系：模型看到的是经过权限过滤的对象集，调用的是被平台注册和验证过的工具，执行的是被 Action Type 定义过的业务动作，生产上线前还要通过 Evals、审批和发布治理。

四类系统对比

形态 核心能力 主要短板 AIP 的不同点
ChatGPT 企业版 通用问答、文档总结、代码辅助 难以稳定连接企业动作与审批 AIP 把 LLM 放在 Ontology、Action 和治理体系内
传统 BI 指标、报表、仪表盘 偏分析，离实际操作还有距离 AIP 面向决策与行动，不只展示数据
RAG 知识库 检索文档并回答问题 缺少对象关系、写回和业务动作 AIP 同时理解对象、链接、函数和动作
RPA 模拟人工点击和固定流程 脆弱，语义理解弱 AIP 用 Ontology 和 Action Type 表达业务语义

1.2 AIP 的核心思想：Decision-Centric Architecture

讲解

Palantir 反复强调 Ontology 不是抽象数据模型，而是面向企业决策的语义系统。传统数据平台通常把数据、算法、应用、审批和执行系统分散在不同地方，AI 很难知道“这个数据意味着什么、谁能看、能做什么、做了以后会影响哪里”。

AIP 的做法是把这些关键要素合并进一个可治理的业务层：

  • Data：来自数据库、数据集、文档、模型输出和运营系统的真实数据。
  • Logic：计算规则、业务函数、预测模型、优化逻辑和提示词逻辑。
  • Action：可以改变对象、属性、链接或触发副作用的标准动作。
  • Security：角色、用途、数据标记、对象级权限、血缘和发布治理。

架构师视角

如果一个 AI 项目不能回答“AI 依据哪些业务对象做判断、能执行哪些动作、动作如何被审批和追踪、错误如何回滚”，它就还不是 AIP 级系统，只是一个模型入口。

第二部分：Ontology 是 AIP 的操作系统内核

2.1 Ontology 的基本概念

讲解

Foundry Ontology 是组织世界的数字孪生。它把底层数据资产和模型映射成业务语言中的对象、属性、链接和动作。对业务人员来说，它像“企业的业务地图”；对开发者来说，它像“可查询、可写回、带权限的业务 API”；对 AI Agent 来说，它是可安全推理和行动的上下文边界。

核心术语

术语 含义 制造业示例
Object Type 业务对象类型，代表实体或事件 订单、工单、设备、供应商、批次
Object 某个对象类型的具体实例 订单 ORD-10086、设备 CNC-07
Property 对象的业务属性 订单状态、交付日期、库存数量、故障等级
Link Type 对象之间的关系定义 订单包含订单行、工单使用设备、供应商供应物料
Object Set 按权限、条件或应用上下文过滤后的一组对象 华东区域本周延迟风险订单
Function 可复用的代码逻辑，可读取对象和对象集并返回结果 计算延迟风险、推荐替代供应商、生成排产方案
Action Type 定义用户或 AI 可以提交的业务变更 调整订单优先级、重新分配员工、创建补货任务

2.2 从数据库表到 Ontology 的建模方法

讲解

不要把每张表机械映射成一个 Object Type。Ontology 建模要从业务决策反推：用户和 Agent 需要围绕什么对象做判断？哪些属性影响判断？哪些关系决定上下文？哪些动作会改变业务状态？

建模步骤

  1. 识别决策对象：例如“是否要加急某订单”涉及订单、客户、物料、库存、生产线、供应商。
  2. 定义对象类型：把稳定的业务概念建成 Object Type，而不是把临时查询结果建成对象。
  3. 挑选关键属性：只暴露决策需要的属性，避免把底层表字段无差别暴露给应用和模型。
  4. 建立链接关系：用 Link Type 表达业务上下文，例如订单到客户、订单到物料、物料到供应商。
  5. 注册函数逻辑：把风险评分、约束检查、推荐算法做成可复用 Function。
  6. 设计动作类型：把可写回的业务变更定义为 Action Type，并配置参数、验证和副作用。
  7. 附加安全语义：对象、属性、链接和动作都要有访问策略，而不是只在前端隐藏按钮。

    ERP[(ERP 订单表)] --> OT1[Order Object Type]
    MES[(MES 工单表)] --> OT2[WorkOrder Object Type]
    WMS[(WMS 库存表)] --> OT3[Inventory Object Type]
    OT1 --> L1[hasWorkOrder]
    OT2 --> L2[requiresMaterial]
    OT3 --> L2
    OT1 --> F1[delayRisk Function]
    OT1 --> A1[expediteOrder Action Type]

2.3 Action Type：把 AI 建议变成平台内的正式变更

讲解

Action Type 是 AIP 与普通问答系统的分水岭。它定义一组对对象、属性和链接的变更，也可以包含通知、验证、审批或写回等副作用。用户或 AI 提交动作后，变更会写入 Ontology，并反映到所有基于该 Ontology 的应用中。

示例：订单加急 Action Type

动作名称 Expedite Order
输入参数 orderId、priority、reason、requestedShipDate
验证规则 订单必须属于用户可见区域；priority 只能从标准枚举选择；加急原因不能为空
对象变更 更新 Order.priority、Order.requestedShipDate，创建 OrderEvent
副作用 通知生产计划员；触发排产重算；必要时进入主管审批
写回结果 提交到对象类型的 writeback dataset，并同步给相关应用

易错点

  • 让 LLM 直接生成 SQL 或调用底层 ERP API，而不是通过 Action Type。
  • 只在聊天界面执行操作，没有把变更写回 Ontology，导致其他应用看不到同一事实。
  • Action 缺少参数验证和提交条件，导致 Agent 可以构造业务上非法的变更。

第三部分：AIP 产品能力与工具链

3.1 AIP 应用全景

讲解

AIP 不是单个应用，而是一组围绕 LLM 工作流的构建能力。不同角色会使用不同入口：业务人员可能从 AIP Threads 和 Workshop 进入，低代码构建者使用 AIP Logic 和 Chatbot Studio，工程师则通过 OSDK、Functions、Code Workspaces、MCP 和平台 API 构建更复杂的应用。

主要能力

能力 用途 适合谁用
AIP Assist 在平台内提供上下文感知的自然语言帮助 平台使用者、分析师、开发者
AIP Logic 无代码创建、测试和部署 AI-powered functions 业务专家、运营团队、低代码构建者
AIP Chatbot Studio 创建可使用 Ontology、文档和工具的交互式 Chatbot 产品团队、业务构建者、AI 应用开发者
AIP Evals 测试提示词和 LLM 工作流，比较模型与运行结果稳定性 AI 工程师、平台团队、质量团队
AIP Threads 无需复杂配置地与文档和 Chatbot 进行临时分析 业务用户、管理层、分析师
Ontology SDK 用 Python、Java、TypeScript 基于 Ontology 构建应用 软件工程师、平台开发者
Palantir MCP 让外部 AI IDE 和 Agent 获取 Ontology、Foundry 工具和文档上下文 AI 开发者、自动化团队

3.2 AIP Logic：把 LLM 能力封装成可复用业务函数

讲解

AIP Logic 可以理解为面向业务构建者的 AI 函数开发环境。它支持围绕 Ontology 数据、结构化输入、非结构化文本和提示词逻辑构建函数，并进行测试、部署和自动化集成。适合做“可解释、可复用、可评估”的 AI 逻辑，而不是一次性聊天。

典型用法

  • 对客户投诉文本进行分类，并关联 Customer、Order、Case 对象。
  • 读取一个 Object Set，输出风险摘要、行动建议和置信度。
  • 把优化或调度问题包装成业务函数，供应用、自动化和 Agent 调用。
  • 和 Automate 结合，在条件满足时自动生成建议动作或进入人工审批。

3.3 AIP Chatbot Studio：可带工具和企业上下文的 Chatbot

讲解

AIP Chatbot Studio 原名 AIP Agent Studio。它允许构建交互式助手，并把助手部署到平台内部、Workshop 应用、外部应用或通过 OSDK/API 集成。Chatbot 可以使用 LLM、Ontology、文档和自定义工具，完成上下文问答、工作流辅助、Ontology 编辑和任务自动化。

设计 Chatbot 的关键问题

  • 它服务哪个业务角色？例如计划员、维修主管、销售经理还是供应链调度员。
  • 它能访问哪些 Object Set？是否来自当前应用变量、用户选择或预设过滤条件。
  • 它能调用哪些工具？这些工具是只读函数、AIP Logic 函数，还是可写 Action Type。
  • 它的失败边界是什么？哪些问题必须拒答，哪些动作必须转人工审批。
  • 它如何被评估？测试集、期望答案、动作准确率、幻觉率和安全阻断率是否明确。

3.4 AIP Evals：生产级 AI 的发布门禁

讲解

AIP Evals 用于测试和评估 LLM 函数、提示词和 Agent 工作流。它的价值不只是“看模型答得好不好”，而是把 AI 能力纳入工程发布体系：每次改提示词、换模型、改工具或调整上下文，都可以用同一批测试用例比较稳定性、准确率、风险和方差。

建议评估维度

维度 评估问题 示例指标
正确性 回答是否基于 Ontology 中真实对象与属性 事实准确率、实体引用准确率
行动准确性 是否选择了正确 Action Type 和参数 工具选择准确率、参数合法率
安全 是否拒绝越权数据和高风险动作 越权阻断率、敏感信息泄露率
稳定性 多次运行是否输出一致结论 方差、重跑一致率
业务价值 是否减少人工步骤或缩短决策时间 节省工时、处理时长、人工采纳率

第四部分：从 Chatbot 到 Agentic Workflow

4.1 Agentic Workflow 的基本闭环

讲解

AIP 的 Agent 不是“模型自由发挥”。更准确地说，它是一个受平台治理的控制循环：观察 Ontology 上下文，调用逻辑和工具，提出或提交 Action，等待审批或自动执行，然后把结果写回平台并进入下一轮学习。

sequenceDiagram
    participant U as 用户/应用
    participant B as AIP Chatbot
    participant O as Ontology
    participant L as AIP Logic/Function
    participant A as Action Type
    participant G as 审批与治理
    U->>B: 提问或请求执行任务
    B->>O: 读取授权 Object Set
    B->>L: 调用风险计算/推荐函数
    L-->>B: 返回结构化结果
    B->>A: 生成候选动作及参数
    A->>G: 校验权限、提交条件和审批策略
    G-->>A: 通过/拒绝/转人工
    A->>O: 写回对象、属性、链接或事件
    O-->>U: 应用中看到最新状态

图：Agentic Workflow 的关键在于“观察、推理、行动、治理、反馈”闭环。

4.2 实战案例：供应链延迟风险处置助手

业务场景

计划员每天要处理大量延迟风险订单。传统流程需要打开 ERP、MES、WMS、邮件和 Excel，手工判断风险原因，再联系采购、生产或销售。AIP 的做法是把相关对象统一到 Ontology，并让 Chatbot 在应用上下文中读取当前计划员可见的订单集合。

Ontology 设计

  • Object Types：Order、OrderLine、Customer、Material、Inventory、Supplier、WorkOrder、Shipment。
  • Link Types：Order has OrderLine，OrderLine requires Material，Material suppliedBy Supplier，WorkOrder produces OrderLine。
  • Functions：delayRiskScore、findAlternativeSupplier、estimateRecoveryDate、explainDelayRootCause。
  • Action Types：expediteOrder、switchSupplier、createPurchaseRequest、notifyCustomer、rescheduleWorkOrder。

用户体验

  1. 计划员在 Workshop 应用中筛选“未来 7 天交付且风险较高的订单”。
  2. AIP Chatbot 接收这个 Object Set 作为上下文，而不是全库自由搜索。
  3. Chatbot 调用 delayRiskScore 和 explainDelayRootCause，生成延迟原因和证据链。
  4. Chatbot 建议“将 ORD-10086 切换到供应商 S-200，并创建加急采购请求”。
  5. 计划员确认后提交 switchSupplier 和 createPurchaseRequest Action。
  6. 平台检查权限、提交条件、审批策略，并把结果写回 Ontology。

4.3 自动化程度分级

从增强到自动化

级别 人机分工 适合场景
L1 辅助分析 AI 只总结和解释，人来判断 风险分析、根因解释、会议摘要
L2 建议动作 AI 推荐 Action，人选择是否提交 加急订单、客户通知、工单分派
L3 人审执行 AI 生成并提交待审批动作，主管批准后执行 高金额采购、价格调整、供应商切换
L4 条件自动化 满足明确规则时由 Automate 或 Agentic Runtime 自动执行 低风险重复流程、告警响应、标准补货
L5 闭环优化 系统持续采集反馈，改进策略和模型 动态调度、库存优化、复杂运营决策

第五部分：安全、治理与生产运行

5.1 AIP 安全不是简单 RBAC

讲解

生产级 Agent 的风险来自两方面：它能读到什么，以及它能做什么。AIP 的安全模型不应只理解为角色权限，还要包括数据标记、用途约束、对象级权限、动作权限、动态血缘、审批流、变更管理和运行审计。

治理清单

  • 数据可见性：Object Set 必须按用户、角色、区域、项目、用途和数据标记过滤。
  • 工具可调用性：Chatbot 或 Agent 只能使用被授权的 Function、Action 和外部工具。
  • 参数合法性：Action 参数要有枚举、范围、必填项和业务规则校验。
  • 人工审批：高风险动作进入人审流程，低风险动作才允许自动执行。
  • 动态血缘：记录回答和动作依据了哪些对象、文档、函数和模型输出。
  • 发布治理：提示词、函数、动作类型和 Chatbot 配置都要走版本管理与发布审批。
  • 运行审计：保留输入、上下文引用、模型输出、工具调用、审批和写回结果。

5.2 Agentic Runtime 的工程要求

讲解

当 Agent 从“人在聊天框里点一下”走向“按事件、计划或外部触发自动运行”，运行时要求会显著提高。平台必须处理并发编排、失败重试、降级策略、审批超时、状态恢复、密钥隔离和可观测性。

生产设计要点

能力 为什么重要 设计建议
触发机制 Agent 可能由对象变化、定时任务或外部事件触发 明确触发条件、去重规则和暂停机制
失败策略 LLM、工具或下游系统都可能失败 区分可重试错误、不可重试错误和需人工介入错误
回退效果 自动化失败不能静默消失 封装错误信息，通知负责人，必要时创建人工任务
幂等性 重试可能造成重复写回 每个 Action 提交使用稳定幂等键和状态机
可观测性 需要解释 Agent 为什么做某个决定 记录 traceId、上下文对象、函数版本、动作版本和审批记录

5.3 Prompt Injection 与工具滥用防护

讲解

在 AIP 里，Prompt Injection 的风险不只是“回答错了”，而是模型可能被诱导调用错误工具或泄露受限对象。防护原则是：不把权限写在 Prompt 里，不让模型决定自己的权限，不让模型自由拼接动作，不让模型绕过 Action Type。

红线

  • 不要把“你有权限访问所有订单”这类规则放进系统提示词后就信任模型。
  • 不要让 Chatbot 访问比当前用户更宽的 Object Set。
  • 不要把 Action 的操作者、审批人、租户、区域等安全字段交给模型填写。
  • 不要把文档内容中的指令当成系统指令执行。
  • 不要跳过 Evals 直接把 Agent 接入写回动作。

第六部分：Java 团队如何接入 AIP

6.1 OSDK：把 Ontology 当成业务 SDK 使用

讲解

Ontology SDK 的价值在于：开发者不是直接面对一堆底层表、临时 API 和文档约定，而是使用由 Ontology 生成或暴露的业务语言。一个“订单 SDK”应该让代码表达 Order、Customer、Shipment、Action 和 Function，而不是表达 erp_order_header、mes_job_detail 这类底层结构。

Java 应用中的分层建议

controller
  -> application service       // 编排用例：查询风险订单、提交加急动作
  -> aip ontology client       // 封装 OSDK / API 调用
  -> domain policy             // 本地业务策略和异常处理
  -> audit adapter             // 对接企业已有审计/工单/消息系统

工程原则

  • 让 Spring Boot 服务调用 Ontology 层的对象、函数和动作，不直接绕回源系统改库。
  • 把 AIP 侧对象模型看成外部边界，使用防腐层转换成本地 DTO 或领域对象。
  • 把用户身份、租户、用途和 traceId 从入口一直传到 AIP 调用层。
  • 对 Action 提交做幂等封装，避免网络重试造成重复业务动作。

6.2 与现有 Java 系统的三种集成模式

模式对比

模式 适合场景 优点 注意点
AIP 作为前台智能应用 业务用户主要在 Palantir Workshop 或 AIP Chatbot 中工作 上线快，治理集中 要把关键业务对象建好，避免只做文档问答
Java 系统调用 OSDK/API 已有门户、ERP 扩展或客户系统需要嵌入 AI 能力 保留现有用户体验，复用 Ontology 和 Action 需要统一身份、权限映射和审计链路
Java 系统作为外部工具或数据源 已有系统掌握独有业务能力，需要被 Agent 调用 保护遗留投资，逐步迁移 工具接口必须强类型、幂等、可观测、可限流

6.3 Spring Boot 防腐层示意

讲解

即使使用 OSDK，也建议在企业 Java 服务里保留防腐层。防腐层负责身份透传、异常转换、幂等、重试、审计和模型演进隔离。这样 Ontology 调整字段或 Action Type 升级时，不会把变更扩散到所有业务代码。

代码骨架

@Service
public class AipOrderFacade {
    private final AipOntologyClient ontologyClient;
    private final AuditPublisher auditPublisher;

    public DelayRiskReport analyzeDelayRisk(String orderId, UserContext user) {
        AipRequestContext ctx = AipRequestContext.from(user);
        OrderObject order = ontologyClient.orders().getById(orderId, ctx);
        RiskResult risk = ontologyClient.functions().delayRiskScore(order, ctx);
        auditPublisher.recordRead(user, "Order", orderId);
        return DelayRiskReport.from(order, risk);
    }

    public ActionSubmission submitExpedite(String orderId, ExpediteCommand command, UserContext user) {
        AipRequestContext ctx = AipRequestContext.from(user);
        String idempotencyKey = command.requestId();
        ActionSubmission result = ontologyClient.actions()
            .expediteOrder(orderId, command.priority(), command.reason(), idempotencyKey, ctx);
        auditPublisher.recordAction(user, "expediteOrder", result.actionId());
        return result;
    }
}

不要这样做

  • 不要在 Java 服务中复制一份 Ontology 权限规则，规则源应尽量收敛到平台侧。
  • 不要因为 SDK 调用方便，就绕过企业审计、限流和工单体系。
  • 不要把 AIP 的对象 ID 和内部数据库主键混用，边界处要显式转换。

第七部分：AIP 项目落地路线图

7.1 不要从“做一个企业大脑”开始

讲解

AIP 项目最好的切入点不是宏大的“全公司智能化平台”，而是一个高频、高价值、数据可得、动作明确、风险可控的运营流程。Palantir Bootcamp/AgentCamp 这类打法强调快速把人带到键盘前，用真实业务流程证明价值，再扩大 Ontology 和自动化范围。

选题标准

  • 每天或每周高频发生，人工处理步骤多。
  • 涉及多个系统，信息碎片化明显。
  • 有明确业务动作，例如创建任务、调整计划、通知客户、审批采购。
  • 数据质量足以支撑第一版，不需要先做一年数据治理。
  • 风险可以分级，第一阶段可采用建议加人工确认。
  • 能用业务指标衡量，例如处理时长、误判率、延误减少、库存周转改善。

7.2 四周交付计划

从试点到可运行版本

阶段 目标 产出物
第 1 周：业务切片 锁定一个运营流程和 3 到 5 个关键决策 用户旅程、决策清单、对象草图、成功指标
第 2 周：Ontology MVP 接入关键数据，建出对象、属性、链接和 Object Set Object Type、Link Type、权限策略、样例数据
第 3 周：AI 能力 构建 AIP Logic、Chatbot、Action Type 和 Evals 提示词版本、函数、动作、测试集、评估报告
第 4 周：试运行 接入真实用户，跑人审流程和运营指标 试运行看板、审计日志、改进清单、扩展计划

7.3 上线前检查清单

必须回答的问题

  • Chatbot 或 Agent 使用的 Object Set 是否与当前用户权限一致？
  • 每个 Action Type 是否有参数定义、提交条件、权限校验和必要审批？
  • AIP Logic 和提示词是否有版本、测试集和 Evals 结果？
  • 模型输出是否能追溯到对象、文档、函数和工具版本？
  • 失败重试是否幂等？重复提交是否会造成重复业务动作？
  • 人工审批、拒绝、超时和回退路径是否设计清楚？
  • 业务指标是否比“回答满意度”更具体，例如缩短处理时长或减少库存缺口？

结语

AIP 的本质是企业行动层，不是模型包装层

总结

学习 Palantir AIP，最重要的是把注意力从“模型能不能回答”转移到“企业能不能安全行动”。Ontology 提供共享业务语义，AIP Logic 和 Functions 提供可复用逻辑，Chatbot Studio 和 Agentic Runtime 提供交互与自动化，Action Types 提供受控写回，Evals 和治理体系保证生产可靠性。

对 Java 团队来说，最现实的路线不是重造一个 Palantir，而是学会这种架构思路：把企业数据建成业务对象，把 AI 能力封装成可评估函数，把写回动作收敛成强类型契约，把权限、审计、审批和发布治理前置。这样做出来的 AI 系统，才可能从演示走向运营现场。
