03 架构设计

在已冻结的原型（第 02 章）与澄清需求基础上，把方案画清楚、可追溯：先建立架构愿景与 DDD 边界，再完成模式选型、关键决策方法、质量属性权衡、数据架构落位、ADR 与评审。

架构设计模块导览

从“愿景”到“可交付架构包”的阅读路径

讲解

本章按决策顺序组织，而非按技术名词堆叠：先定义边界，再选架构，再落地治理。建议按下列模块顺序阅读，确保每一步都有可评审产物。

模块划分

  • 模块 A（愿景与边界）：架构愿景与交付边界、DDD领域驱动设计、功能模块设计
  • 模块 B（模式与风格）：架构模式选型、事件驱动架构、微服务架构
  • 模块 C（关键决策方法）：决策框架与评估方法、API 与集成设计
  • 模块 D（质量属性权衡）：性能·一致性·安全·成本权衡、FinOps 与云成本估算
  • 模块 E（数据与落地）：数据架构与存储选型、表结构设计、ADR 与架构评审、需求→架构追溯、章末实战闭环

关键/技巧

  • 每个模块都应产出“图 + 文档 + 可验证检查单”三件套。
  • 跨服务协作默认先考虑异步事件，强一致场景再评估同步方案。

关键决策方法

把“经验判断”变成“可评审决策”

讲解

架构决策建议采用统一方法链：决策前置清单（目标、约束、风险）→ 候选方案矩阵（收益/成本/复杂度）→ 轻量 ATAM 场景评估（质量属性冲突）→ ADR 固化。避免“先定技术、后补理由”。

阶段成果

  • 决策问题清单：每个问题明确决策 owner、截止时间、影响范围
  • 方案对比表：至少包含可用性、性能、一致性、成本、团队能力五维
  • 证据链接：压测、PoC、故障演练、历史事故复盘

决策矩阵示例（节选）

| 决策问题             | 方案A（同步） | 方案B（事件驱动） | 结论 |
|----------------------|---------------|-------------------|------|
| 订单-库存一致性      | 一致性高，耦合高 | 最终一致，弹性高  | B    |
| 搜索索引更新链路      | 实现快，双写风险 | Outbox/CDC 更稳   | B    |
| 多端 API 编排         | 前端聚合复杂     | BFF 统一编排      | B    |

质量属性权衡

性能、可用性、一致性、安全与成本的平衡

讲解

架构不是“最优解”，而是“约束下可持续解”。建议将每项关键质量属性量化为 SLO，并显式记录冲突取舍：例如强一致 vs 高可用、低时延 vs 成本、快速发布 vs 变更风险。权衡结果必须映射到实现策略与监控指标。

阶段成果

  • 质量属性场景表：场景、刺激、响应、可测指标、验收门槛
  • 冲突处理策略：例如峰值降级、一致性补偿、限流与熔断策略
  • 验证计划：压测、故障注入、安全基线扫描、容量演练

云成本估算与 FinOps

架构阶段的 TCO 模型：计算 · 存储 · 流量 · MQ · AI

讲解

成本是质量属性之一，须在 ADR / 架构评审 中与性能、可用性并列量化。TCO = 固定成本 + 可变成本 × 流量系数。MVP 用数量级估算 + 上限预算；规模化后接云厂商 Cost Explorer / Cost Tag 分账。AI 成本（Token + 向量库）是 TCO 子项，详细治理见第 22 章 AI 成本 SLO。

架构愿景与交付边界

从需求到架构

讲解

架构设计将已澄清的需求转化为结构化的技术方案：模块边界、通信方式、数据流、质量属性如何落地。好的架构让变更局部化、团队并行化。输出架构愿景（一句话 + 关键原则）与ADR（Architecture Decision Record）记录重要决策及权衡。

阶段成果

  • 架构愿景：目标架构一句话、设计原则（如「Domain 零框架依赖」）
  • ADR 模板：标题、状态、背景、决策、后果、备选方案

ADR 模板示例

DDD领域驱动设计

从战略到战术的 DDD 方法论

DDD（Domain-Driven Design，领域驱动设计） 是一种应对复杂软件系统的设计思想和方法论，核心思想是：让软件的设计紧密围绕业务领域（Domain）的现实模型展开。

核心概念：两大支柱 —— DDD 的方法论主要分为战略设计（宏观上划分解耦）和战术设计（微观上落地实现）。

1. 战略设计 (Strategic Design) —— 划分边界

战略设计是高层建筑，负责把复杂的业务大系统拆分成小系统。

  • 领域 (Domain) 与子域 (Subdomain)：业务的范围。比如一个电商系统（领域），可以拆分为商品子域、订单子域、支付子域、物流子域等。
  • 通用语言 (Ubiquitous Language)：团队（开发、产品、测试、业务专家）必须使用统一的业务术语。代码里的类名、方法名要和业务术语完全一致，消除沟通鸿沟。
  • 限界上下文 (Bounded Context)：业务概念的边界。在同一个边界内，词汇的含义是唯一的。例如，「商品」在「仓储上下文」中代表的是「库存货物」，而在「销售上下文」中代表的是「上架商品」。

2. 战术设计 (Tactical Design) —— 代码落地

战术设计是一套模式，指导我们在限界上下文内部如何组织代码和业务逻辑。

  • 实体 (Entity)：具有唯一标识（ID）的对象。它的状态会发生变化，但只要 ID 不变，它就是同一个东西（例如：用户 User、订单 Order）。
  • 值对象 (Value Object)：没有唯一标识、只由其属性定义的对象。它是不可变的（Immutable），通常用来描述实体的属性（例如：地址 Address、金额 Money）。
  • 聚合与聚合根 (Aggregate & Aggregate Root)：聚合是一组相关对象的集合（比如「订单」和「订单明细」），它们作为一个整体进行数据修改，保证业务内聚。聚合根是这个集合的外部唯一入口，外部只能通过聚合根来修改内部的数据。
  • 领域服务 (Domain Service)：当某个业务逻辑不属于任何一个具体的实体或值对象时，就把它提炼成一个领域服务（例如：转账操作，涉及两个账户实体）。
  • 仓储 (Repository)：负责聚合根的持久化（保存和读取），它将底层的数据库操作（MySQL、MongoDB 等）屏蔽掉，让领域层只关注业务。

DDD 的经典分层架构

传统的 MVC 架构通常是三层（Controller → Service → DAO），而 DDD 推荐使用四层架构（或六边形架构 / 整洁架构），其核心是将业务逻辑（Domain）保护在最内层，不依赖任何外部框架和数据库。

  • 用户接口层 (User Interface)：处理外部请求，进行参数校验和转换（DTO 转换）。
  • 应用层 (Application Layer)：很薄的一层，负责编排业务流程、事务控制、安全检查。它不包含核心业务逻辑，而是协调领域层工作。
  • 领域层 (Domain Layer)：系统的核心！包含所有的实体、值对象、聚合、领域服务和业务规则。它不依赖其他任何层。
  • 基础设施层 (Infrastructure Layer)：提供通用的技术能力，比如数据库持久化（Repository 的具体实现）、缓存、消息队列、第三方 API 调用等。

为什么需要 DDD？（解决什么痛点）

  • 防止系统变成「大泥潭」：随着业务发展，传统架构的代码会变得臃肿，修改一处引发无数 Bug。DDD 通过边界划分，让系统高内聚、低耦合。
  • 告别贫血模型：传统 Service 包含所有逻辑，Entity 只有 getter/setter（被称为贫血模型）。DDD 提倡充血模型，让实体自己拥有行为和业务规则，代码更符合面向对象思想。
  • 精准应对微服务划分：限界上下文（Bounded Context）是微服务拆分的天然边界。没有经过 DDD 战略设计的微服务，很容易拆成一摊互相强耦合的分布式垃圾。

小结：DDD 不是一种具体的框架，而是一套思维方式。对于简单的 CRUD 系统，用 DDD 反而会增加复杂度；但对于业务逻辑错综复杂的大型企业级应用，DDD 是理清头绪、保证软件长治久安的利器。

限界上下文划分检查单

□ 同一上下文内术语是否一致？（订单 vs 单据）
□ 是否同一团队负责演进？（Conway 定律）
□ 跨上下文是否只需 ID 引用，而非对象导航？
□ 集成是否需 ACL 防外部模型污染？
□ 上下文边界是否与事务边界对齐？（单聚合强一致）

易错点

  • 聚合过大（订单 + 用户 + 库存同一聚合）导致锁竞争。
  • 贫血模型：逻辑全在 Service，实体只有 getter/setter。
  • 简单 CRUD 系统过度套用 DDD，引入不必要的抽象与复杂度。
  • 未经战略设计就拆微服务，限界上下文边界不清，形成强耦合的分布式系统。

延伸阅读：Domain-Driven Design（Eric Evans）、Implementing Domain-Driven Design（Vaughn Vernon）

功能模块设计

从业务能力到可演进模块的工程化设计

讲解

功能模块设计（Functional Module Design）的目标不是“把代码分目录”，而是建立稳定边界 + 清晰职责 + 可替换协作。实践中先按业务能力划分模块边界（Bounded Context / Module Boundary），再定义依赖方向与契约，最后落到分层结构与发布边界。若边界划分稳定，系统可随着团队扩张从模块化单体平滑演进到微服务。

模块边界划分（Bounded Context / Module Boundary）

  • 以业务能力和变更频率作为第一划分轴：如订单、库存、支付、履约。
  • 以数据所有权和团队归属作为第二划分轴：同一模块内数据与代码共同演进。
  • 边界描述至少包含：输入/输出、核心规则、外部依赖、故障影响半径。
  • 跨模块协作默认通过契约，不直接共享内部对象或数据库表。

模块职责与依赖方向（High Cohesion, Low Coupling）

  • 高内聚：同一模块聚焦单一业务能力，规则与状态聚在一起。
  • 低耦合：依赖从上游业务流程指向下游能力，不允许“反向依赖”。
  • 跨模块引用优先 ID 和 DTO，不透传领域内部结构。
  • 在设计评审中显式标注“允许依赖”与“禁止依赖”矩阵，减少隐式耦合。

接口与契约（Synchronous / Asynchronous）

同步契约（Sync Contract）
- 场景：查询、强时效校验、短链路编排
- 载体：REST/gRPC + OpenAPI/Proto
- 约束：超时、限流、幂等、错误码标准化

异步契约（Async Contract）
- 场景：跨模块状态传播、副作用解耦、削峰
- 载体：事件总线 + AsyncAPI/Schema Registry
- 约束：事件版本、幂等消费、重试与死信策略

设计准则：同步处理“当前事务”，异步传播“业务事实”。

模块分层（Controller / Application / Domain / Infrastructure）

建议采用稳定的四层结构：Controller 负责协议适配与输入输出；Application 负责编排用例与事务边界；Domain 承载业务规则与模型；Infrastructure 负责数据库、消息、中间件适配。依赖必须由外向内，Domain 不反向依赖框架细节。

典型反模式（Anti-patterns）

  • 大泥球（Big Ball of Mud）：业务逻辑散落在 Controller/Service，模块边界名存实亡。
  • 循环依赖（Cyclic Dependency）：A 依赖 B，B 又依赖 A，导致改动无法局部化。
  • 共享数据库耦合（Shared Database Coupling）：模块直接读写他方表结构，演进受阻。
  • 万能公共模块：将业务逻辑堆入 common，最终形成隐式单体。

落地 Checklist

  • □ 每个模块是否有清晰 owner、边界描述、输入输出契约？
  • □ 是否定义了允许依赖方向，并通过架构测试/静态扫描守护？
  • □ 同步接口是否具备超时、重试预算、幂等策略？
  • □ 异步事件是否有版本策略、消费幂等、死信治理？
  • □ 分层是否落地为目录与包约束，Domain 是否零框架依赖？
  • □ 是否已对照第 16 章常见功能模块完成模块职责对齐？

架构模式选型与演进策略

分层、六边形与微服务

讲解

分层架构：Interface → Application → Domain ← Infrastructure，依赖由外向内，Domain 不依赖 Spring/JPA。六边形/整洁架构强调端口适配器，基础设施可替换。微服务按限界上下文拆分，非按技术层；先模块化单体（Maven 多模块），验证边界后再拆。跨上下文一致性在业务架构层选型（与第 11 章本地事务分工）：单库/单服务内 → 本地 ACID；跨服务需协调 → Outbox + 事件（默认推荐）、Saga（长流程补偿）、2PC/TCC（一致性强但实现复杂，需谨慎评估）。演进：MVP 模块化单体 → 流量/团队触发再拆服务。

何时拆微服务 vs 保持模块化单体

| 信号                     | 保持模块化单体     | 拆微服务           |
|--------------------------|--------------------|--------------------|
| 团队规模                 | ≤2 个小队          | 多团队并行         |
| 部署频率                 | 统一发版可接受     | 需独立发布         |
| 上下文耦合               | 强事务、频繁 JOIN  | 边界清晰、事件协作 |
| 运维成熟度               | 无 K8s/可观测      | 有 SRE 体系        |
| 反模式                   | —                  | 分布式单体（拆而未 decouple）

  • Strangler Fig：新功能新服务，旧功能逐步迁移。
  • 服务间异步事件优于同步编排；API Gateway + BFF 适配不同客户端。
  • 跨服务读聚合用 BFF 编排，避免Chatty API（N+1 远程调用）。

易错点

  • 分布式单体：拆了微服务但共享 DB、同步链式调用——复杂度翻倍无收益。
  • 过度微服务：CRUD 也独立部署，运维成本 > 业务收益。
  • 跨服务用 2PC 解决一切——优先 Outbox/Saga，2PC 仅极少数强一致场景。

速记

「先模块化，后微服务；按上下文拆，别按表拆；Outbox 默认，2PC 慎用。」

Servlet + 虚拟线程 vs WebFlux

同步 vs 响应式选型决策树

讲解

大多数 B 端 CRUD 后台：Spring MVC + Servlet + 虚拟线程（Boot 3.2+ spring.threads.virtual.enabled=true）即可应对高并发阻塞 IO，团队认知成本最低。WebFlux 适合全链路非阻塞（网关聚合、SSE 流式、高 fan-out 代理），但调试难、与 JPA/阻塞库混用易「阻塞 EventLoop」。

决策树（简化）：
1) 是否 90%+ 阻塞 IO（DB/HTTP/RPC）？ → MVC + 虚拟线程
2) 是否全链路 reactive 且团队有 Rx 经验？ → WebFlux
3) 是否仅个别 SSE/流式接口？ → MVC + async/SseEmitter 或独立 reactive 服务

详见第 09 章并发、第 10 章 Netty/WebFlux。

事件驱动架构

定义、模式与工程化落地

定义与适用场景

事件驱动架构（EDA）以“状态变化事件”为系统协作主通道：生产者发布事件、消费者按订阅处理。适用于跨上下文协同、异步解耦、高吞吐、弹性扩缩、审计追踪等场景，典型如订单-库存-支付-履约链路。

不建议为纯 CRUD、强同步交互、低复杂单体系统强行引入 EDA，避免不必要的分布式复杂度。

核心概念与常见模式

  • 事件：事实（Fact）而非命令（Command），具备事件名、版本、业务主键、发生时间、追踪 ID。
  • 主题/分区：按业务键分区保证同键有序；吞吐靠分区扩展。
  • 模式：Event Notification、Event-Carried State Transfer、Event Sourcing、CQRS、Outbox、Saga。
  • 契约：Schema Registry + 兼容策略（向后兼容优先），禁止无版本裸 JSON 漫游。

事件契约示例

{
  "eventId": "01J2...",
  "eventType": "OrderCreated",
  "eventVersion": 2,
  "aggregateId": "ORD-20260521-001",
  "occurredAt": "2026-05-22T11:20:30Z",
  "traceId": "9f0d...",
  "payload": {
    "customerId": "C1001",
    "items": [{"sku":"SKU-1","qty":2}],
    "totalAmount": 19900
  }
}

优缺点

  • 优点：服务解耦、峰值削峰、扩展性好、天然审计链。
  • 缺点：一致性变复杂、调试链路长、事件治理成本高。
  • 判定标准：业务收益（并行协作/吞吐/自治）应显著大于复杂度成本。

一致性与幂等

EDA 默认追求最终一致。跨服务事务优先 Outbox + 消费者幂等，避免把分布式事务当默认路径。幂等策略组合：业务唯一键、去重表、幂等窗口 TTL、状态机防重入。

可靠性与重试

可靠性关注“至少一次投递”后的副作用控制：消费失败需指数退避重试，超过阈值进入 DLQ；重放前先校验消费者版本与依赖状态。关键业务建议配置“重试预算 + 告警 + 人工补偿 Runbook”。

事件建模建议

命名：{BoundedContext}.{Aggregate}.{PastTenseVerb}
示例：Order.Order.Created / Inventory.Reservation.Released

建模原则：
1) 一个事件只表达一个已发生事实
2) payload 携带“消费者最小可用信息”
3) 必带业务主键、追踪字段、schema 版本
4) 禁止在事件里泄露内部表结构字段

与微服务关系

EDA 不是微服务前提，但在微服务中常用于降低同步耦合。推荐策略：同步 API 处理查询与强一致写，事件流处理跨上下文传播与异步副作用。避免“全异步化”导致业务时效不可控。

落地实践建议

  • 先从单一高价值流程试点（如订单创建后异步履约），避免一次性全局改造。
  • 建立事件目录（Event Catalog）：owner、schema、SLO、下游消费者、回滚策略。
  • 接入可观测：发布/消费延迟、积压、重试率、DLQ 深度、端到端业务时延。
  • 将事件契约评审纳入 DoR/DoD，与 ADR、OpenAPI 同级治理。

常见陷阱

  • 把“命令”当“事件”发布，导致语义混乱与重复处理。
  • 无版本演进策略，消费者升级时发生批量兼容性故障。
  • 仅依赖 MQ 重试而不做业务幂等，造成资金/库存重复扣减。
  • 忽略事件所有权，多个服务同时定义同名异义事件。
  • 缺少对账机制，最终一致长期漂移无人发现。

微服务架构

从服务边界到治理体系

定义与适用场景

微服务架构将系统拆为一组可独立开发、部署、扩缩与演进的自治服务，每个服务围绕明确业务能力与数据所有权建设。适用于多团队并行交付、业务域复杂、发布频繁、容量差异大、需要局部弹性扩容的场景。若团队规模小、业务耦合强、运维能力不足，优先模块化单体，避免过早分布式化。

拆分原则与服务边界（业务能力 / DDD 上下文）

  • 按业务能力拆分：围绕“下单、库存预留、支付、履约”等完整能力切分，而非按 Controller/DAO 技术层切分。
  • 按限界上下文拆分：服务边界优先对齐 DDD Bounded Context，保证模型语义一致与团队自治。
  • 一服务一数据主权：服务拥有私有存储与写入权，跨服务通过 API/事件集成，避免共享数据库。
  • 高内聚低耦合：同变更频率、同责任团队、同发布节奏的能力优先归于同一服务。

服务间通信（同步 / 异步）

同步通信（HTTP/gRPC）适合查询、短链路编排、强时效反馈；异步通信（MQ/事件总线）适合跨上下文广播、削峰填谷、解耦副作用。实践上采用“同步处理当前事务，异步传播业务事实”的组合：写路径中同步最小化，后续扩展动作通过事件分发。

数据管理（数据库拆分、一致性、事务策略）

数据库拆分遵循“按服务数据域垂直拆分 + 必要时分库分表”。一致性分层处理：服务内本地事务保障 ACID，跨服务采用最终一致（Outbox + 幂等消费 + 对账）；长事务流程采用 Saga 补偿。2PC/TCC 仅用于强一致且收益显著高于复杂度的少量核心场景，并必须有降级与回滚预案。

服务治理（注册发现、配置、限流熔断、容错）

  • 注册与发现：通过注册中心维护实例健康状态，实现弹性扩缩容后的透明寻址。
  • 配置中心：集中管理环境配置，支持灰度配置与版本回滚，禁止配置漂移。
  • 流量治理：入口限流、并发隔离、超时控制、重试预算、防雪崩熔断。
  • 容错机制：降级策略、舱壁隔离、失败快速返回、人工兜底 Runbook。

可观测性（日志、指标、追踪）

  • 日志：结构化日志统一字段（traceId、spanId、bizKey、service、env），支持跨服务检索。
  • 指标：RED/USE 指标体系覆盖请求率、错误率、延迟、资源饱和度与队列积压。
  • 追踪：全链路追踪打通入口网关、服务调用、消息消费与数据库操作。
  • SLO 驱动：以 SLI/SLO 建立告警门槛与错误预算，支撑发布决策与容量规划。

部署与交付（容器化、灰度/金丝雀、回滚）

微服务交付建议标准化为“容器镜像 + 不可变制品 + 环境无关配置”。发布采用蓝绿/灰度/金丝雀逐步放量，结合自动化健康检查与指标门禁。回滚策略需前置设计：应用版本回退、配置回退、数据变更兼容与紧急止损开关应作为同一发布单元评审。

安全（鉴权、零信任、密钥与证书）

服务间默认零信任：每次调用都身份校验与授权，不因内网而豁免。统一令牌签发与细粒度权限控制（RBAC/ABAC），机器身份建议采用 mTLS 双向证书。密钥与证书通过集中密钥管理系统托管并定期轮换，严禁硬编码至仓库或镜像。

优缺点与常见陷阱

  • 优点：团队自治、独立发布、弹性扩缩容、故障隔离能力更强。
  • 缺点：分布式复杂度高，运维、排障、治理与组织协同成本显著增加。
  • 陷阱 1：共享数据库或跨服务直连表，最终演变为“分布式单体”。
  • 陷阱 2：同步调用链过长，放大尾延迟与级联故障。
  • 陷阱 3：缺乏契约治理与版本策略，导致服务升级互相阻塞。

与事件驱动架构的关系和组合实践

关系定位：
- 微服务回答“系统怎么拆、怎么自治”
- 事件驱动回答“服务之间如何低耦合协作”

组合实践（推荐）：
1) 命令/查询走同步 API（校验、权限、快速反馈）
2) 状态变化发布领域事件（跨上下文传播）
3) 事务策略采用 Outbox + 幂等消费 + 对账
4) 长流程编排采用 Saga（可观测 + 补偿）
5) 关键链路保留人工降级与应急回滚开关

参见：事件驱动架构、ADR 与架构评审

API 与集成设计

模块定位：API 在架构中的角色（契约 · 边界 · 演进）

讲解

API（Application Programming Interface，应用编程接口）是系统对外的稳定契约，也是服务之间的显式边界。在DDD 限界上下文层面，API 是上下文集成的“开放主机服务”（OHS）；在微服务架构层面，API 是服务自治与组合的基本单元；在产品形态层面，API 是构建生态（开放平台、SaaS）的资产。

架构师必须把 API 当作长期资产而非短期产物：契约一旦发布即承担向后兼容义务，演进遵循“加法兼容、减法弃用、破坏性升 major”三原则。API 设计的好坏直接决定团队耦合度、上线节奏与故障爆炸半径。

阶段成果

  • API 资产清单：所有对外/对内 API 的 owner、版本、状态（Draft/Active/Deprecated/Sunset）、SLO
  • 集成上下文图：本系统与外部系统的同步/异步集成点、协议、依赖方向
  • API 设计基线：风格、版本、错误、鉴权、限流、可观测的统一约定（团队 API Style Guide）

关键/技巧

  • API 设计的“客户”是调用方开发者，不是服务自身——以 DX（Developer Experience）为评审目标。
  • 每条对外 API 都必须有明确的 owner 团队与SLA/SLO，否则视为“无主接口”。
  • 对内 RPC 与对外 REST 通常拆分：内部 gRPC 追求性能与强类型，外部 REST 追求兼容性与可观测。

API 风格选型矩阵：REST / GraphQL / gRPC / WebSocket / Webhook / 事件

讲解

没有“最优风格”，只有“最匹配场景的风格”。选型应从调用语义、网络条件、客户端类型、演进策略、团队能力五维出发，避免技术品味驱动。同一系统内允许多风格并存（典型组合：外部 REST + 内部 gRPC + 推送 WebSocket + 跨系统 Webhook/事件）。

风格对比矩阵

| 风格        | 语义           | 典型协议        | 优势                       | 劣势/边界                 | 适用场景                       |
|-------------|----------------|-----------------|----------------------------|---------------------------|--------------------------------|
| REST        | 资源/请求-响应 | HTTP/1.1+JSON   | 通用、缓存友好、生态成熟   | 强类型弱、过度获取/欠获取 | 公开 API、CRUD、Web/移动端     |
| GraphQL     | 字段查询       | HTTP+JSON       | 客户端按需取字段、聚合多源 | 缓存复杂、N+1、权限粒度细 | BFF 聚合、多端字段差异大       |
| gRPC        | RPC/流         | HTTP/2+Protobuf | 强类型、高性能、双向流     | 浏览器需 gRPC-Web、调试难 | 内部服务间、低延迟、强契约     |
| WebSocket   | 全双工长连接   | TCP+ws/wss      | 实时推送、低开销           | 连接状态、负载均衡复杂    | 实时消息、行情、协同编辑       |
| SSE         | 服务器推送     | HTTP+text/event | 简单、走 HTTP 基础设施     | 单向、不支持二进制        | 通知流、日志流、AI Token 流    |
| Webhook     | 反向回调       | HTTP POST       | 解耦、按需推送             | 重试/签名/IP 白名单复杂   | 第三方集成、SaaS 事件外发      |
| 消息/事件   | 异步发布订阅   | Kafka/MQ        | 高吞吐、解耦、可重放       | 最终一致、运维成本高      | 跨上下文协作、削峰、审计       |

选型决策清单

  • 调用方：浏览器/移动端 → REST/GraphQL；内部服务 → gRPC；第三方 → REST + Webhook。
  • 实时性：被动查询 → REST；服务端推送 → SSE/WebSocket；事件传播 → Kafka/MQ。
  • 字段差异:多端字段差异大、聚合多源 → GraphQL/BFF；字段稳定 → REST。
  • 性能/类型：低延迟+强类型 → gRPC；通用兼容 → REST。
  • 跨域集成：同步请求-响应 → REST；事实通知 → Webhook；最终一致协作 → 事件总线，详见事件驱动架构。

易错点

  • 统一“一切皆 REST”：把高频实时推送场景硬塞为轮询 REST，导致网关压力与延迟。
  • 统一“一切皆 GraphQL”：忽略缓存、权限、N+1 复杂度，最终 BFF 成为新单点。
  • 对外暴露 gRPC：浏览器/合作伙伴接入门槛骤增，应在边缘转 REST。

REST API 设计规范：资源、URI、方法、状态码、版本、分页

讲解

REST 设计的核心是“用资源建模业务”：先识别资源（Resource）与子资源，再把动作映射到 HTTP 方法语义，最后用状态码表达结果。优秀的 REST 设计应满足可预测（Predictable）、可演进（Evolvable）、可观测（Observable）三性。HATEOAS（Hypermedia as the Engine of Application State）适合开放平台与高自描述需求，业务系统可选用 Richardson 成熟度等级 L2 即可。

资源建模与 URI

  • 资源名词、复数：/orders、/orders/{id}、/orders/{id}/items。
  • 动词作动作（少用）：极少数无法资源化的操作用 POST /orders/{id}:cancel 或 /orders/{id}/cancellations，避免 /getOrder 这类 RPC 风格。
  • 层级表达从属：/customers/{cid}/orders 表示从属关系，跨聚合根用查询参数：/orders?customerId=...。
  • kebab-case：/shipping-addresses，避免大小写混用。

HTTP 方法语义与状态码

| 方法    | 语义       | 幂等 | 安全 | 典型状态码                              |
|---------|------------|------|------|-----------------------------------------|
| GET     | 读取       | ?    | ?    | 200, 304, 404                            |
| POST    | 创建/动作  | ?    | ?    | 201(+Location), 202, 400, 409, 422       |
| PUT     | 整体替换   | ?    | ?    | 200, 204, 404, 409, 412(If-Match)        |
| PATCH   | 部分更新   | △    | ?    | 200, 204, 400, 409                       |
| DELETE  | 删除       | ?    | ?    | 204, 404, 409                            |
| HEAD    | 元信息     | ?    | ?    | 200, 304                                 |
| OPTIONS | 能力发现   | ?    | ?    | 200, 204                                 |

状态码使用约定：
- 2xx 仅在业务成功时返回；业务失败但 HTTP 正常 → 4xx（不要 200 + code=ERR）
- 401 未认证 / 403 已认证但无权限（明确区分）
- 409 资源冲突 / 422 语义错误（如校验失败）
- 429 限流 / 503 服务降级（带 Retry-After）

分页 · 过滤 · 排序 · 字段选择

# 分页：cursor/keyset 优先（稳定、可水平扩展），offset 仅用于小数据
GET /api/v1/orders?cursor=eyJpZCI6MTAwfQ&limit=20

# 过滤：使用查询参数，复杂筛选用 RSQL/FIQL 或专用 :search 子资源
GET /api/v1/orders?status=PAID&createdAfter=2026-05-01

# 排序：sort=field,(asc|desc)；多字段逗号分隔
GET /api/v1/orders?sort=createdAt,desc&sort=amount,asc

# 字段选择：稀疏字段集，降低带宽
GET /api/v1/orders?fields=id,status,totalAmount

# 响应统一信封（可选）
{
  "data": [...],
  "page": { "nextCursor": "eyJ...", "size": 20, "hasMore": true }
}

版本策略对比

| 策略           | 示例                                  | 优点                  | 缺点                          |
|----------------|---------------------------------------|-----------------------|-------------------------------|
| URI 版本       | /api/v1/orders                        | 直观、易缓存、易路由   | URI 不"纯粹"、迁移成本高       |
| Header 版本    | Accept: application/vnd.acme.v2+json  | URI 稳定              | 调试不直观、网关需特殊处理     |
| Query 版本     | /api/orders?version=2                 | 简单                  | 不规范、易被忽略               |
| 字段版本演化   | 字段加法/弃用标记                     | 不破坏调用方           | 适合演进期，无法替代 major     |

实践建议：对外公开 API 推荐 URI 版本（v1/v2），内部服务用 Header 版本配合契约测试。
破坏性变更（删字段、改语义、变必填）必须升 major；新增字段、放宽校验属于加法兼容。

关键/技巧

  • 列表接口分页详细规范同步参考第 16 章分页模块，统一 cursor 编码规则。
  • 枚举值用大写常量（PAID）而非魔法数字（1），避免跨语言反序列化歧义。
  • 时间字段统一 ISO 8601 + UTC，金额用分而非小数，避免浮点误差。

错误处理与响应规范：Problem Details（RFC 7807/9457）

讲解

错误响应是 API 最被忽视也最影响 DX 的部分。统一采用 RFC 7807 / RFC 9457 Problem Details for HTTP APIs：标准化字段 type / title / status / detail / instance，并以扩展字段承载业务错误码与可观测信息（code、traceId、errors[]）。

错误码体系采用分层命名：{domain}.{category}.{reason}，例如 order.stock.insufficient、auth.token.expired。HTTP 状态码表达协议层结果，业务码表达业务层语义，二者互补不替代。第 12 章 Spring Framework 异常映射给出 @RestControllerAdvice 落地实现。

HTTP/1.1 409 Conflict
Content-Type: application/problem+json

  "title": "Insufficient Stock",
  "status": 409,
  "detail": "SKU-001 available=0, requested=2",
  "instance": "/api/v1/orders",
  "code": "order.stock.insufficient",
  "traceId": "9f0d2a1c4b8e",
  "timestamp": "2026-05-22T08:30:12Z",

错误码字典（节选）：
| code                           | http | message_zh           | message_en               | 是否可重试 |
|--------------------------------|------|----------------------|--------------------------|------------|
| common.request.invalid         | 400  | 请求参数非法         | Invalid request          | 否         |

易错点

  • 反模式：HTTP 200 + body.code=ERR——破坏 HTTP 语义、网关与缓存无法识别错误率。
  • 用 500 当兜底状态码，掩盖 400/404/409 等业务可识别错误，影响告警与重试策略。
  • 错误 detail 直接回显敏感信息（SQL、堆栈、内网 IP），违反第 17 章敏感数据规范。

鉴权 · 安全 · 限流 · 防重放

讲解

API 安全是多层防御组合，不存在“单一令牌包打天下”。常见层次：传输安全（TLS/mTLS）→ 身份认证（OAuth 2.1 / OIDC / mTLS / API Key）→ 授权（RBAC/ABAC、Scope）→ 防滥用（限流 / 配额 / 防重放 / 签名）→ 审计。详细实现见第 17 章认证、授权与JWT 最佳实践。

鉴权方案矩阵

  • OAuth 2.1 + OIDC：用户态对外 API 首选，authorization_code + PKCE 覆盖 Web/移动/SPA，client_credentials 用于服务间。
  • JWT（access token）：短 TTL（15 分钟）+ 长 refresh token；必须校验 iss/aud/exp/nbf，禁用 alg=none。
  • mTLS：内网服务间或高安全合作伙伴双向证书认证，零信任默认。
  • API Key：低风险、机器到机器的开放 API；需配额、IP 白名单、可撤销与轮换。
  • HMAC 签名：Webhook 出站与高完整性要求接口，签名时间窗 + nonce 防重放。

限流 · 配额 · 防重放

# 限流响应（统一回 429）
HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1747895412

{
  "type": "https://api.example.com/errors/common/rate-limit",
  "title": "Rate limit exceeded",
  "status": 429,
  "code": "common.rate_limit.exceeded",
  "detail": "tenant=acme exceeded 100 req/min"
}

# 防重放：HMAC + 时间戳 + nonce（用于 Webhook/开放平台）
X-Signature: hmac-sha256=base64(HMAC(secret, ts + nonce + body))
X-Timestamp: 1747895400          # 服务端拒绝偏移 > 5min
X-Nonce: 8f1c-...                 # 服务端 5min 内去重

限流策略选型

| 策略           | 适用                          | 维度                | 风险                       |
|----------------|-------------------------------|---------------------|----------------------------|
| 固定窗口计数   | 简单粗略                      | IP/Key              | 边界突刺                   |
| 滑动窗口       | 通用                          | IP/Key/User/Tenant  | 实现略复杂                 |
| 令牌桶         | 允许突发                      | 用户/租户           | 需令牌生成速率合理         |
| 漏桶           | 平滑输出                      | 网关入口            | 难处理突发                 |
| 并发数（信号量）| 后端保护                     | 服务/接口           | 与 QPS 限流互补使用        |
| 分布式限流     | 多实例                        | Redis/Sentinel      | 一致性 vs 性能权衡         |

易错点

  • JWT 当 Session 用，登出无法实时失效——需引入吊销列表或缩短 TTL。
  • 限流只在网关做，绕过网关的内网调用未限流，故障时无保护。
  • Webhook 出站不签名/不重放保护，调用方被伪造请求攻击。
  • API Key 长期不轮换、写在代码或日志中，违反密钥治理。

幂等性 · 一致性 · 重试策略

讲解

分布式调用的默认假设是“至少一次”：网络抖动、超时、网关重试都可能让同一请求被处理多次。幂等性是 API 的第一可靠性原则：相同输入多次执行结果一致、副作用一次。GET/PUT/DELETE 天然幂等；POST 通过 Idempotency-Key Header 实现幂等（Stripe 风格事实标准）。

一致性策略与微服务数据管理对齐：服务内 ACID，跨服务最终一致（Outbox + 幂等消费 + 对账），长流程 Saga 补偿，2PC/TCC 仅用于强一致核心场景。

Idempotency-Key 实现要点

POST /api/v1/orders
Idempotency-Key: 7f3a8c2e-9d1b-4e5a-8c2f-1b6d4a9e3f7c
Content-Type: application/json

# 服务端处理：
# 1) 以 (route + Idempotency-Key + tenant) 为去重键，TTL 24h
# 2) 首次请求：执行业务 + 写入幂等记录(键, 请求摘要, 响应状态/体)
# 3) 重复请求：
#    - 同摘要 → 直接返回已存响应（含原 HTTP 状态码）
#    - 不同摘要 → 422 idempotency.conflict（同 Key 不同 body）
# 4) 处理中并发：用分布式锁/数据库唯一索引兜底
@PostMapping("/orders")
public ResponseEntity<Order> create(
    @RequestHeader("Idempotency-Key") UUID idemKey,
    @RequestBody @Valid CreateOrderReq req) {
  return idempotency.execute(idemKey, req, () -> orderApp.create(req));
}

客户端重试策略

# 仅对幂等方法 + 可重试错误（5xx、429、网络超时）重试
# 指数退避 + 抖动（Full Jitter）防雪崩
sleep = random(0, min(cap, base * 2^attempt))   # base=200ms, cap=10s
max_attempts = 3 ~ 5
budget = 10% 总请求量                            # 重试预算，避免放大故障

# Server 提供退避建议
Retry-After: 30                                  # 秒，429/503 必带

# 反模式：
- 对 POST 无幂等键就重试 → 重复扣款
- 固定间隔重试 → 同步雪崩
- 无上限重试 → 故障放大

关键/技巧

  • 幂等键存储优先选Redis + 数据库双写：Redis 抗并发、数据库做持久化与对账。
  • 幂等记录与业务事务同一事务提交，避免“业务成功 + 幂等记录丢失”导致重复执行。
  • 事件消费者必须幂等：用业务唯一键 + 去重表，与事件驱动架构幂等策略一致。

性能与可伸缩：缓存 · 压缩 · 批量 · 流式 · Backpressure

讲解

API 性能从“响应时间 + 吞吐 + 稳态弹性”三轴度量。设计层可控的杠杆：HTTP 缓存（ETag/Cache-Control）、传输压缩（gzip/br）、批量接口减少往返、流式接口处理长响应、Backpressure 控制客户端速率。优化必须以SLO 与压测数据驱动，而非凭直觉。

HTTP 缓存与条件请求

# 强缓存：Cache-Control（适合静态/不变资源）
Cache-Control: public, max-age=300, stale-while-revalidate=60

# 协商缓存：ETag + If-None-Match（适合可变资源）
GET /api/v1/products/SKU-1
→ 200 OK
  ETag: "v42-9f0d"
  Cache-Control: private, max-age=0, must-revalidate
  ...body...

GET /api/v1/products/SKU-1
  If-None-Match: "v42-9f0d"
→ 304 Not Modified   # 无 body，节省带宽

# 乐观锁（写）：If-Match + ETag
PUT /api/v1/products/SKU-1
  If-Match: "v42-9f0d"
→ 412 Precondition Failed   # 版本冲突，避免覆盖

批量 · 流式 · Backpressure

  • 批量接口：POST /orders:batchGet 或 ?ids=1,2,3，减少 N+1 与连接开销；批量大小硬上限（如 100），并返回逐项结果与错误。
  • 流式响应：大列表/导出/AI 推理用 SSE（text/event-stream）或 HTTP 分块传输，避免一次性内存膨胀。
  • Backpressure：服务端用 429 + Retry-After 或 RateLimit-* 头反压；流式接口可用 WebSocket/gRPC 流的流控窗口。
  • 响应压缩：开启 Accept-Encoding: gzip, br，小响应（< 1KB）跳过压缩避免 CPU 浪费。
  • 稀疏字段集：?fields=... 减少带宽；GraphQL 天然支持按需取字段。

关键/技巧

  • 缓存策略要写进 OpenAPI 的 responses.headers，让 CDN/网关也能识别。
  • 批量接口的错误响应用“多状态”模式：HTTP 200 + items[].status/error 标识逐项结果。
  • 性能问题先用第 20 章性能调优方法论压测定位，再在 API 层裁剪。

讲解

关键组件职责

  • API Gateway：统一入口、TLS 终止、鉴权、限流、路由、灰度、可观测；不承载业务逻辑。
  • BFF（Backend for Frontend）：按端聚合（Web/iOS/Android/小程序），适配字段与编排，避免后端被前端字段差异污染。
  • Service Mesh：服务间通信治理下沉到 Sidecar（mTLS、重试、熔断、可观测），应用代码零侵入；适合多语言、多团队。
  • Webhook：反向回调，需签名 + 重试（指数退避）+ DLQ + 客户端可重放；事件元数据携带 eventId/traceId/timestamp。
  • 消息总线：跨上下文事实传播，详见事件驱动架构。

Webhook 出站设计要点

POST https://partner.example.com/webhooks/orders
Content-Type: application/json
X-Event-Id: 01J2HZ3K...                # 幂等键，消费方去重
X-Event-Type: order.created            # 事件类型
X-Event-Version: 2                      # schema 版本
X-Timestamp: 1747895400                 # 防重放
X-Signature: hmac-sha256=...            # HMAC(secret, ts + nonce + body)
X-Delivery-Attempt: 3                   # 第 N 次投递

发送策略：
- 重试：指数退避 + 抖动，max 6 次，总窗口 24h，失败入 DLQ
- 仅对 2xx 视为成功，3xx/4xx/5xx 触发重试（除非 410 Gone → 主动停投）
- 提供后台“重放最近 X 条”能力，便于合作伙伴恢复

关键/技巧

  • “同步处理当前事务，异步传播业务事实”：写路径最小化同步依赖，副作用走事件。
  • BFF 不沉淀业务逻辑，只做聚合与适配；业务规则归属后端领域服务。
  • 对外开放 API 与对内服务 API 严格分层：外层走网关 + 公网域名 + 公开契约，内层走 Mesh + 私有域名 + 内部契约。

易错点

  • BFF 成“胖中间层”：业务规则沉淀于 BFF，违反 DDD 边界。
  • Gateway 写业务逻辑（Lua/JS 脚本里塞规则），运维与排障极其困难。
  • Webhook 不带签名/不重试，对方故障时全量丢失。

    Deprecated --> Sunset: "兼容期到期"
    Sunset --> [*]: "下线"
    Active --> Active: "加法兼容演进"
    Active --> Deprecated: "破坏性变更升 major"

变更分类与策略

  • 加法兼容（Additive）：新增可选字段、新增端点、放宽校验、新增状态码。不升 major，记入 changelog。
  • 变更（Modifying）：字段语义微调、默认值变化。升 minor，文档高亮，给调用方 review 期。
  • 破坏（Breaking）：删字段、改类型、改必填、删端点、改状态码语义。必须升 major，旧版本进入 Deprecated，公告兼容期（典型 6~12 个月）。

  ...body...

弃用流程：
1) ADR 立项：动机、影响范围、迁移成本、兼容期长度
2) 标记 OpenAPI: deprecated: true + x-sunset
3) 响应头 Deprecation/Sunset，调用方监控可识别
4) 开发者门户、邮件、客户经理三通道通知
5) 兼容期内每月通报存量调用方与剩余流量
6) Sunset 到期：返回 410 Gone + 迁移指引

  • 建立组织级 API 目录（Developer Portal）：搜索、订阅、试用、changelog、SDK、状态页。

API 可观测性：指标 · 日志 · 追踪

讲解

API 的可观测性遵循RED + USE方法：Rate（QPS）、Errors（错误率）、Duration（延迟分位）+ 资源饱和度。所有 API 指标必须按(service, route, method, status, tenant)多维切片，保证排障可下钻。链路追踪贯穿网关→服务→数据库→消息，traceId 同时回灌错误响应与日志。详见第 21 章可观测体系。

核心指标与 SLO 模板

# RED 指标（OpenTelemetry 语义约定）
http.server.request.duration{route="/api/v1/orders", method="POST", status="2xx"}
http.server.request.count{...}
http.server.errors{route, code="order.stock.insufficient"}

# 典型 SLO（按端点设定）
- 可用性：成功率 (2xx+客户端错误)/总数 ≥ 99.9%（30天滚动）
- 延迟：p95 ≤ 200ms，p99 ≤ 500ms
- 错误预算：0.1% / 月 ≈ 43 分钟，超支则冻结发布

  "env": "prod",

落地清单

  • 统一中间件：网关/Spring Boot Filter 自动注入 traceId，错误响应回灌 traceId。
  • 采样策略：错误 100% 采、慢请求 100% 采、正常请求按比例（1%~10%）采。
  • 关联 ID：X-Request-Id（边缘生成）+ traceId（链路）+ bizKey（业务主键，如 orderId）三联。
  • 告警：错误率突增、延迟劣化、错误预算消耗速率、限流命中率均设阈值。

常见反模式与陷阱

反模式速查

  • HTTP 200 + body.code=ERR：破坏 HTTP 语义、网关/缓存/告警全部失灵。
  • RPC over REST：POST /getUserById、POST /doSomething，丧失资源语义与可缓存性。
  • 万能 DTO：所有接口共用一个超大 Schema，字段大部分场景为 null，文档失去意义。
  • Chatty API：客户端为渲染一屏发 N 次请求，应在 BFF 聚合或提供批量端点。
  • 无版本演进：所有变更直接改 v1，下游故障频发；或反过来 v1/v2/v3 并行无下线计划，运维成本爆炸。
  • 错误码混乱：HTTP 状态码、业务码、消息文案三套体系互相矛盾。
  • 幂等键缺失：所有 POST 重试都可能重复扣款/扣库存。
  • 分布式单体：服务拆了，但同步链路嵌套 5 层，任何一环抖动级联放大。
  • 无契约的事件：MQ 里漂裸 JSON，消费方升级时全网兼容性故障。
  • API 即数据库视图：API 字段与数据库列 1:1 暴露，数据库重构即破坏 API。
  • 无主接口：上线后 owner 离职、文档失修，调用方故障无人响应。

数据架构回答三件事：数据如何正确（Correctness）、如何扩展（Scalability）、如何控本与治理（Cost & Governance）。设计应先定义数据所有权（Data Ownership）、一致性边界（Consistency Boundary）与保留策略（Retention Policy），再决定存储组合，而不是先选技术栈。

目标与原则（Goals & Principles）

  • 正确性（Correctness）：关键账务链路以 ACID + 幂等（Idempotency）保障，避免“写丢/重放”
  • 可扩展（Scalability）：按读写模式拆分 OLTP/OLAP，热点隔离、弹性扩缩容
  • 成本最优（Cost Efficiency）：冷热分层、对象存储归档、按价值分配算力与 IOPS
  • 治理合规（Governance & Compliance）：分类分级、脱敏、审计留痕、可追溯删除

业务数据分层与模型（OLTP / OLAP）

| 层次 | 全称 | 主要职责 | 数据特征 | 常见技术 |
|------|------|----------|----------|----------|
| OLTP | Online Transaction Processing | 在线交易与状态变更 | 强一致、低延迟、小事务 | MySQL / PostgreSQL |
| ODS  | Operational Data Store        | 业务变更汇聚与标准化 | 近实时、可追溯、保留原貌 | Kafka + 湖仓/列存 |
| DWD  | Data Warehouse Detail         | 明细主题建模 | 可复用明细、口径统一 | Hive / Iceberg / ClickHouse |
| ADS  | Application Data Service      | 应用层指标与报表服务 | 面向消费、聚合结果 | ClickHouse / StarRocks / ES |

存储选型矩阵（Technology Decision Matrix）

| 技术 | 典型场景 | 优势 | 代价/风险 | 选型信号 |
|------|----------|------|-----------|----------|
| MySQL / PostgreSQL | 核心交易、主数据 | ACID、生态成熟、事务语义清晰 | 跨库扩展复杂、热点写入瓶颈 | 需要强一致与复杂关系约束 |
| Redis | 热点缓存、分布式锁、会话 | 亚毫秒读写、结构灵活 | 内存成本高、误用易丢一致性 | 读多写少、可容忍短暂不一致 |
| Elasticsearch | 全文检索、日志检索 | 倒排索引、检索能力强 | 写放大、映射治理成本高 | 关键词检索/聚合查询重 |
| Kafka / Pulsar | 事件总线、异步解耦、CDC 扩散 | 高吞吐、可回放、削峰填谷 | 运维复杂、消息语义需治理 | 跨系统事件驱动与重放需求 |
| 对象存储 Object Storage | 附件、归档、数据湖 | 低成本、高耐久、海量扩展 | 低延迟随机读写能力弱 | 冷数据、文件型与归档场景 |
| 时序库 Time-series DB | 指标监控、设备遥测 | 时间窗口聚合高效、压缩比高 | 高基数标签易爆炸 | 以时间维度聚合为主 |
| ClickHouse / StarRocks | 实时分析、看板查询 | 列式压缩、聚合快 | 更新语义受限、建模要求高 | 秒级分析与多维聚合 |

一致性与事务策略（Consistency & Transaction）

  • 本地事务（Local Transaction）：单库内使用 ACID，优先保证核心写路径正确性。
  • 最终一致（Eventual Consistency）：跨服务通过事件驱动 + 补偿，避免分布式 2PC 成为系统瓶颈。
  • Outbox Pattern：业务变更与事件写入同库同事务，异步投递消息，防止“业务成功但事件丢失”。
  • Saga Pattern：长事务拆分为本地事务链，失败时按补偿动作回滚业务语义。
-- Outbox 简化示例：业务表与 outbox 同事务提交
BEGIN;
  UPDATE orders SET status = 'PAID' WHERE order_id = :orderId;
  INSERT INTO outbox(event_id, aggregate_id, event_type, payload, status)
  VALUES (:eventId, :orderId, 'OrderPaid', :payload, 'NEW');
COMMIT;

扩展策略：读写分离、分片与热点治理

  • 读写分离（Read/Write Split）：读流量导向只读副本，主库保留写入与一致性校验。
  • 分库分表（Sharding）：先垂直拆分（按域），再水平拆分（按租户/用户/时间）。
  • 分区分片（Partitioning/Sharding）：时间分区 + 哈希分片组合，兼顾归档与并行查询。
  • 热点治理（Hotspot Mitigation）：键打散、局部缓存、异步化、限流与排队。
  • 迁移策略：双写校验 + 灰度切流 + 回滚开关，避免一次性大切换。

索引与查询优化原则（Index & Query Optimization）

  • 索引围绕高频查询路径设计：先过滤、再排序、再回表最少化。
  • 避免“为每列建索引”，关注写放大与维护成本。
  • 分页优先 Keyset Pagination，避免深分页 OFFSET 扫描。
  • 在发布前固定执行计划（Explain Baseline）并压测回归。
-- 组合索引示例（订单列表：按租户 + 状态 + 时间倒序）
CREATE INDEX idx_orders_tenant_status_created
ON orders(tenant_id, status, created_at DESC);

-- 查询示例：匹配索引前缀 + 限制返回列
SELECT order_id, amount, created_at
FROM orders
WHERE tenant_id = ? AND status = 'PAID' AND created_at > ?
ORDER BY created_at DESC
LIMIT 100;

生命周期、合规与容灾（Lifecycle / Compliance / DR）

  • 数据生命周期（Data Lifecycle）：在线层（7-30 天）→ 近线层（3-12 月）→ 归档层（对象存储）。
  • 合规控制（Compliance）：敏感字段脱敏（Masking）、静态加密（Encryption at Rest）、传输加密（TLS）、审计日志不可篡改。
  • 备份恢复（Backup & Restore）：明确 RPO（可接受数据丢失窗口）与 RTO（可接受恢复时长），并进行季度演练。
  • 同城双活/异地灾备（DR）：按业务等级定义主备策略，核心账务链路优先跨 AZ/Region 冗余。
  • 可观测与容量规划（Observability & Capacity）：统一跟踪 QPS、P95/P99、命中率、慢查询率、磁盘增长率与单分片倾斜度。

表结构设计

从数据模型到可扩展 DDL 的实战方法

讲解

表结构设计（Table Schema Design）是把业务语义转成可长期演进的数据骨架。推荐路径为概念模型（Conceptual Model）→ 逻辑模型（Logical Model）→ 物理模型（Physical Model）：先定义实体关系与业务约束，再映射键、索引和字段类型，最后结合存储引擎、分区策略与运维约束落地。

本节与数据架构与存储选型配套：前者回答“数据放哪里”，本节回答“表怎么建才可持续”。跨服务事务边界与一致性策略可结合第 11 章持久化一起评审。

主键策略与索引设计（Primary Key & Index Design）

  • 自增主键（AUTO_INCREMENT）：单库简单高效，但跨库合并与全局唯一治理成本高。
  • 雪花 ID（Snowflake）：全局唯一且趋势递增，适合分布式高并发写入。
  • UUID：去中心化生成方便，但随机写放大明显，通常建议用有序 UUID 变体。
  • 索引设计遵循“高频查询驱动”：先过滤列、再排序列、最后回表列，避免冗余索引。
  • 上线前固定 explain 基线，避免发布后执行计划漂移。

规范化与反规范化（Normalization vs Denormalization）

  • 规范化降低冗余、提升一致性，适合核心交易写路径。
  • 反规范化提升查询性能，适合高频读取与报表场景。
  • 做反规范化前先明确：更新触发点、回填策略、对账机制、数据时效 SLO。
  • 架构评审中必须记录“为什么冗余”与“如何修复漂移”。

审计与治理字段（Audit / Soft Delete / Tenant / Version）

推荐基础字段（按业务可裁剪）
- created_at / created_by：创建时间与创建人
- updated_at / updated_by：更新时间与更新人
- deleted_at / is_deleted：软删除标记
- tenant_id：多租户隔离键
- version：乐观锁版本号（Optimistic Lock）

典型约束：
1) 所有业务表默认包含 created_at 与 updated_at
2) 软删除表的唯一索引要考虑 is_deleted 维度
3) 多租户系统索引前缀优先 tenant_id
4) 更新语句必须携带 version 条件，防止并发覆盖

分库分表与冷热分层前置点

分库分表不是“容量不够再说”，而是建模阶段就要预留：分片键（tenant_id/user_id/order_id）、时间分区字段、全局 ID 方案、跨分片查询策略。冷热分层同理：高频近线数据留在 OLTP，历史数据归档到对象存储/分析引擎，避免主库被历史查询拖垮。

常见 SQL/DDL 规范与反模式

  • DDL 规范：命名统一（表/索引/约束）、字段非空策略明确、默认值语义可解释。
  • SQL 规范：禁止 SELECT *、禁止无条件全表更新/删除、分页避免深 OFFSET。
  • 反模式 1：把 JSON 大字段当万能扩展，导致查询与索引不可控。
  • 反模式 2：缺失唯一约束，仅靠应用层防重，产生脏数据。
  • 反模式 3：表结构直接暴露为 API 契约，数据库重构时引发连锁破坏。

落地 Checklist

  • □ 概念/逻辑/物理模型是否完整，实体关系与约束是否可追溯到需求？
  • □ 主键策略是否匹配部署形态（单库/分库/多租户）？
  • □ 高频查询是否有对应索引，写放大风险是否评估？
  • □ 审计字段、软删除、租户字段、版本字段是否按规范落地？
  • □ 是否预留了分片键、分区键、归档策略与迁移方案？
  • □ SQL/DDL 规范是否纳入 CI（lint + review gate），并建立反模式巡检？

ADR 与架构评审

决策记录与评审检查单

讲解

ADR 轻量记录架构决策：背景、选项、决策、后果，版本化管理（Proposed → Accepted → Superseded → Deprecated）。每条 ADR 须可评审：有量化权衡（如「选 Kafka 因吞吐 10 万/s，接受运维复杂度」）、有回滚/替代方案。架构评审（ATAM 轻量变体）在里程碑前进行：对照 NFR 矩阵、走查质量属性冲突（性能 vs 安全 vs 成本），检查单逐项过。评审结论写入 ADR 状态或评审纪要，PR 引用 ADR 编号，避免「会议口头通过、文档无留痕」。

阶段成果

  • ADR 文档集：编号、状态、日期、关联 NFR/RTM；存 docs/adr/
  • 架构评审纪要：参与人、结论（Go/Go-with-conditions/No-Go）、待办与截止日期
  • 架构评审检查单（签字版）：NFR、一致性、安全、可观测、容量、回滚

评审检查单（节选）

□ NFR 指标可度量，每条有验证计划与负责人
□ 单点故障、降级、熔断策略已定义
□ 跨服务一致性：Outbox/Saga/2PC 选型有 ADR
□ 密钥/配置管理（见第 17 章）
□ 日志、指标、链路追踪接入点（见第 21 章）
□ 数据库迁移与回滚方案
□ 反模式检查：分布式单体 / Chatty API / 缓存作 SoT

关键/技巧

  • ADR 存于 docs/adr/ 或 Wiki，PR 引用 ADR 编号。
  • 重大决策邀请运维/安全/DBA 列席，减少上线 surprises。
