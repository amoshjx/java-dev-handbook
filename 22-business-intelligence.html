LLM 业务引入总览

何时引入 LLM、与规则引擎/传统 ML 的边界

讲解

LLM 适合：开放域语言理解/生成、非结构化文档问答、多步推理编排、自然语言接口（NL→API）。规则引擎（Drools、Easy Rules）适合确定性业务规则、可审计的 if-then、监管口径固定场景——成本低、可解释。传统 ML（分类、排序、风控模型）适合标注数据充足、指标可量化、延迟/成本需可控的预测任务。决策原则：① 能否用 SQL + 规则 + 检索解决？能则不上 LLM；② 错误代价是否可接受（客服草稿 vs 自动放款）？③ 是否有 Golden Set 可 Eval？无则先 PoC。架构师在需求基线后输出AI 可行性评估，避免“为 AI 而 AI”。

flowchart TD
    NEED[业务需求] --> Q1{规则可穷举?}
    Q1 -->|是| RULE[规则引擎/工作流]
    Q1 -->|否| Q2{有标注数据+固定指标?}
    Q2 -->|是| ML[传统 ML 模型]
    Q2 -->|否| Q3{开放语言+可容忍幻觉?}
    Q3 -->|是| LLM[LLM + RAG/Agent]
    Q3 -->|否| HYBRID[混合: 规则兜底 + LLM 辅助]

图：LLM vs 规则 vs ML 选型决策

阶段成果

  • AI 可行性评估：场景、风险等级、是否 Human-in-the-loop、替代方案对比
  • 场景清单：编号、业务域、输入输出、成功指标、数据敏感度

关键/技巧

  • 用「红队思维」问：LLM 说错话/泄露数据/被注入时业务会怎样？
  • 高合规场景默认「LLM 只产草稿，人确认后落库」。

易错点

  • 把 LLM 当搜索引擎——无 grounding 时幻觉率不可控。
  • 用 ChatGPT 演示效果直接写进 SLA，未做离线 Eval。

速记

「规则定边界，ML 算分数，LLM 补语言；先 Eval 再承诺。」

典型业务用例矩阵

客服、RAG、文档问答、抽取、Agent 工作流

讲解

常见模式：智能客服（意图识别 + 知识库 RAG + 工单升级）；企业文档问答（制度/手册/合同）；代码/运维助手（内部 Wiki + 日志，开发侧见第 20 章）；结构化抽取（发票/简历/合同字段 → JSON Schema）；Agent 工作流（查库存 → 算价 → 生成报价 → 发邮件）。用价值 × 可行性 × 风险三维排优先级：MVP 选 1–2 个闭环场景，ROI 可度量（节省人力小时、转化率、首响时间）。

阶段成果

  • 用例矩阵：场景 × 用户 × 输入 × 输出 × 依赖数据 × 优先级 P0/P1/P2
  • 优先级路线图：PoC → 试点部门 → 全量

用例矩阵片段

UC-01 售后 FAQ | P0 | 输入: 用户问题 | 输出: 答案+引用片段 | RAG | 客服主管
UC-02 合同条款抽取 | P1 | PDF | JSON{parties,amount,date} | Function+Schema | 法务
UC-03 运维 Runbook 问答 | P2 | 告警描述 | 处置步骤 | RAG+Tool(查监控) | SRE

易错点

  • 一次立项 10+ 场景，资源分散、Eval 集建不起来。
  • 未定义「答不上来」时的降级路径（转人工、固定话术）。

RAG 架构设计

知识库、Embedding、向量库、检索与生成

讲解

RAG 链路：文档 ingest → 分块 → Embedding → 向量库 → 检索（+ rerank）→ Prompt Context → LLM 生成并强制引用来源。架构上 RAG 应作为独立能力层（RAG Platform / Knowledge Service），与业务域服务解耦：业务服务只调「问答 API」，不内嵌向量库逻辑。边界：ingest/索引归 RAG 平台；权限过滤在检索前按 tenant/role 过滤 metadata；生成层不直连业务 DB。Java 生态：Spring AI（VectorStore、DocumentReader、ChatClient）；LangChain4j。存储选型见第 03 章存储选型；与第 15 章 RBAC联动做知识库 ACL。

flowchart LR
    DOC[文档源] --> PARSE[解析分块]
    PARSE --> EMB[Embedding]
    EMB --> VDB[(向量库)]
    Q[用户问题] --> QEMB[Query Embedding]
    QEMB --> RET[Top-K 检索]
    VDB --> RET
    RET --> RERANK[可选 Rerank]
    RERANK --> CTX[Prompt Context]
    CTX --> LLM[LLM 生成]
    LLM --> ANS[答案+引用]

图：RAG 端到端链路

阶段成果

  • RAG 架构图：ingest/索引/检索/生成四层边界与数据流
  • 向量库选型 ADR：数据量、QPS、混合检索、运维成本对比
  • Chunk 策略说明：大小、重叠、metadata 规范、版本化 ingest 流程

Spring AI 示意

// 概念示意 — 检索增强问答
ChatResponse response = chatClient.prompt()
    .user(question)
    .advisors(new QuestionAnswerAdvisor(vectorStore, SearchRequest.defaults()))
    .call()
    .chatResponse();
// 返回答案时应附带 Document id / 片段供前端展示引用

关键/技巧

  • Hybrid 检索：向量 + BM25 关键词，提高专有名词命中率。
  • Chunk 带标题路径 metadata（如「财务制度/报销/第3节」）便于引用。

易错点

  • Chunk 过大塞满 Context，过小丢失语义——需 A/B chunk 策略。
  • 未做 ingest 版本化，文档更新后答案仍引用旧 chunk。

速记

「切好块、嵌好向量、检准了、答必带出处。」

业务 Prompt 设计

System Prompt、Few-shot、输出 Schema

讲解

业务 Prompt 是产品规格的可执行版：System 层定义角色、边界（「仅依据提供的 Context 回答，不知道则说不知道」）、语气与合规禁则；User 层传业务变量；Few-shot 示例对齐输出格式与拒答行为。结构化输出用 JSON Mode / Response Schema（OpenAI structured outputs、Spring AI BeanOutputConverter）约束字段，便于 Java 反序列化进 DTO 落库。Prompt 版本化存 Git 或配置中心，与 Eval 集绑定——改 Prompt 必跑回归。开发侧 Prompt 技巧见第 21 章，本章强调业务语义与验收口径。

阶段成果

  • 业务 Prompt 规格：System/User 模板、Few-shot、拒答示例、版本号
  • 输出 Schema：JSON 字段定义与 Java DTO 映射表

JSON Schema 输出示例

System: 你是企业报销助手。仅根据 CONTEXT 回答。禁止编造政策条款。
输出 JSON: {"answer":"...","citations":["docId:chunkId"],"confidence":"high|medium|low","needHuman":boolean}

User CONTEXT:
{{retrieved_chunks}}
问题: {{user_question}}

关键/技巧

  • 拒答示例写进 Few-shot，减少「一本正经胡说」。
  • 长 System Prompt 拆「政策层 + 任务层」，便于 A/B 只改任务层。

易错点

  • Prompt 里写死今日促销——应参数化或由 Tool 查实时数据。
  • 未校验 JSON Schema，模型多字段/少字段导致解析异常。

Function Calling 与 Tool 设计

与 Java 业务 API 对接、MCP 概念

讲解

Function Calling：模型输出结构化 tool call，应用层执行 Java 方法/API 后回传结果。架构边界：Tool 层是业务 API 的受控门面——粒度=业务原子操作，执行前鉴权与 RBAC（见第 15 章 RBAC）；Agent 编排层不绕过 Tool 直连 Repository。MCP：Model Context Protocol（模型上下文协议），可标准化工具暴露与调用，企业内可封装「订单 MCP Server」供多 Agent 发现。与业务模块集成：AI 能力应嵌入现有 BFF/领域服务，避免孤立「AI 微服务」缺统一鉴权。防注入：Tool 参数不信任模型自由文本拼 SQL。

sequenceDiagram
    participant U as 用户
    participant A as Java Agent 编排
    participant L as LLM
    participant T as 业务 Tool/API
    U->>A: 自然语言请求
    A->>L: Prompt + tools schema
    L->>A: tool_call getOrder(id)
    A->>T: 鉴权后调用 OrderService
    T-->>A: 订单 JSON
    A->>L: tool_result
    L-->>A: 自然语言答复
    A-->>U: 响应

图：Function Calling 时序

Tool 定义片段

@Tool("查询订单状态，需要 orderId")
public OrderSummary getOrderStatus(
    @P("订单号") String orderId,
    @ToolMemoryId String userId) {
  authzService.assertCanViewOrder(userId, orderId);
  return orderService.getSummary(orderId);
}

易错点

  • Tool 内无幂等——模型重复调用导致重复下单。
  • 把 admin 级 Tool 暴露给普通用户会话。

Agent 与工作流设计

单 Agent、多 Agent、Human-in-the-loop

讲解

单 Agent + ReAct：适合工具数 <10 的垂直场景。多 Agent：Planner 分派专员 Agent，跨域但增延迟——架构上仅在上下文边界清晰时采用。Human-in-the-loop：高风险动作（退款、权限变更）插入审批节点，与工作流引擎（Flowable/Camunda，见第 15 章工作流）结合：LLM 填表单 → 人审 → 执行 Tool。决策：能单不双，能审不自动；状态机记录每步 I/O 便于审计与 Eval。

stateDiagram-v2
    [*] --> Understand
    Understand --> Retrieve: "需知识"
    Retrieve --> Plan
    Plan --> Act: "自动 Tool"
    Plan --> Approve: "高风险"
    Approve --> Act: "人通过"
    Approve --> Reject: "人驳回"
    Act --> Respond
    Respond --> [*]
    Reject --> [*]

图：Agent 状态与人工审批

阶段成果

  • Agent 工作流需求说明：状态机、人工审批节点、最大步数/超时
  • Human-in-the-loop 清单：高风险动作与审批 SLA

关键/技巧

  • 最大步数/超时硬限制，防 Agent 死循环烧 Token。
  • 高风险 Tool 默认 dryRun=true 先展示计划。

速记

「能单不双，能审不自动，状态可回放。」

AI 数据治理

隐私、脱敏、出境与训练/推理边界

讲解

数据分级：公开 / 内部 / 敏感 / 机密——决定是否可进 Prompt、是否需脱敏（手机号、身份证、薪资）。推理 vs 训练：企业 API 默认关闭「用对话改进模型」；私有化部署数据不出 VPC。出境：调用境外 API 需法务评估（个人信息保护法、行业监管）。日志：记录 Prompt/Response 摘要时脱敏，全量仅存加密审计库、短 TTL。与第 16 章安全开发联动：Prompt Injection 防护、输出过滤、租户隔离。RAG 知识库 ACL 与业务 RBAC 一致。

阶段成果

  • 数据流图：哪些字段进 LLM、留存多久、谁可访问
  • 合规检查清单：出境、PII、审计、用户告知与同意

易错点

  • 把生产全量 DB 导出做 Embedding，未做字段级过滤。
  • 在 Prompt 中粘贴客户完整合同未做权限校验。

成本、延迟与 SLO

Token 预算、缓存、流式与降级

讲解

成本治理：Token 预算是第 03 章 FinOps TCO的子项，架构评审须纳入总成本表。按场景估算 QPS × 平均 Token × 单价；设 dev/staging/prod 配额与告警阈值（90% 预警、100% 熔断非 P0）。优化：意图路由（简单走 mini 模型）、Prompt 压缩、Embedding/语义缓存。延迟 SLO：流式 SSE 改善首 token 体验；同步 API 设 p99 上限。降级：模型超时 → 模板/转人工；向量库不可用 → BM25 兜底；预算熔断 → 限流。监控对接第 20 章可观测性。演进：PoC 不限预算 → 试点设软上限 → 生产硬配额 + FinOps 月报。

阶段成果

  • SLO 文档：p50/p99 延迟、可用性、首 token 时间、错误率
  • Token 预算表：场景 × 环境 × 月配额 × 告警阈值 × 负责人
  • 降级决策表：故障类型 → 降级动作 → 恢复条件（可演练）

成本治理决策表

| 场景           | 模型路由        | 预算动作              |
|----------------|-----------------|-----------------------|
| FAQ 简单意图   | mini 模型       | 占总额 ≤30%           |
| 合同抽取       | 标准模型+Schema | 按单计费，超 500/天告警|
| Agent 多步     | 标准+步数上限   | maxSteps=8 硬限制     |
| 月预算 100%    | —               | 非 P0 拒绝，P0 人工审批|

降级策略表

LLM 5xx/超时 → 重试1次 → 仍失败 → 固定话术 + 创建人工工单
向量检索空 → 扩大 K + BM25 → 仍空 → 「未找到相关规定，请联系 XX」
月 Token 达 90% 预算 → 告警；100% → 非 P0 场景拒绝服务

速记

「算清 Token 账，流式减焦虑，降级有预案。」

Prompt 与模型版本治理

Prompt Registry · A/B · 回滚

讲解

Prompt 与模型版本应与代码同等治理：Prompt Registry（Git 或专用库）版本化、变更审计、CI 跑 Eval 门禁。生产变更有 A/B 分桶与一键回滚；禁止「改 Prompt 无记录」。与Eval 章节、第 21 章衔接。

AI 效果评估

离线 Eval、Golden Set、幻觉检测、A/B

讲解

Eval 体系是 AI 能力的质量门禁，架构上与 CI/CD 同级： Golden Set（50–200 条）+ 离线指标（Faithfulness、Citation 命中率）+ 业务 KPI（转人工率）构成三层评估。 架构产出：Eval 平台/流水线（Prompt 版本 tag → 自动跑分 → 门禁阈值 → 阻断发布）；与第 21 章 Harness Engineering衔接。无 Golden Set 不上生产；模型/Prompt/检索策略变更必跑回归。A/B 分桶看业务 KPI，非仅 ROUGE/BLEU。

阶段成果

  • Golden Set：问答对 + 期望要点 + 必含引用 + 拒答 case，版本化管理
  • Eval 门禁配置：Faithfulness ≥ 阈值、Citation 命中率、幻觉 case 零容忍
  • Eval 报告模板：版本对比、回归 diff、Go/No-Go 结论

关键/技巧

  • 从生产「转人工」会话挖掘 hard case 补进 Golden Set。
  • Eval 与 Prompt 同版本 tag，便于回滚对比。

易错点

  • 只用 BLEU/ROUGE 评 RAG——与业务正确性相关性弱。
  • Eval 集过拟合 demo 问题，上线后效果骤降。

Java 后端 LLM 集成

Spring AI、Ollama/OpenAI、异步与幂等

讲解

Spring AI：统一 ChatModel、EmbeddingModel、VectorStore，配置 spring.ai.openai / spring.ai.ollama 切换供应商。Ollama：本地 dev/test；生产多选云 API 或私有化 vLLM。异步：长生成走 MQ（用户提交 → jobId → WebSocket/SSE 推送），避免阻塞 Tomcat 线程。幂等：同一 conversationId + messageId 重试返回缓存结果；写操作 Tool 带 idempotencyKey。超时、重试、熔断用 Resilience4j；密钥走第 20 章配置管理。

阶段成果

  • LLM 集成需求说明：同步/异步模式、幂等键、超时重试策略
  • 供应商选型约束：dev 本地 / prod 云 API、密钥管理要求

异步任务示意

@PostMapping("/chat")
public ResponseEntity<JobAccepted> submit(@RequestBody ChatRequest req) {
  String jobId = UUID.randomUUID().toString();
  chatQueue.send(new ChatJob(jobId, req, userId()));
  return ResponseEntity.accepted().body(new JobAccepted(jobId));
}
// Consumer 调 ChatClient，结果写 Redis + 通知 SSE

易错点

  • 同步调用 LLM 占满线程池，高峰全站卡顿。
  • API Key 写在 application.yml 提交 Git。

AI 与常见业务模块结合

RBAC、审计、日志、工作流

讲解

AI 能力嵌入企业横切模块层，非孤岛：RBAC——Tool 与知识库按角色过滤；审计——model、prompt 版本、docId、tool 参数（脱敏）；日志——traceId 串联（见第 15 章日志体系）；工作流——AI 节点 + 人工节点；通知——完成发站内信。架构原则：优先在现有 BFF/领域服务加 AI Advisor，避免单独「AI 微服务」缺统一鉴权与数据权限。

AI 与业务模块集成架构（示意）

[前端] → [BFF/Gateway 鉴权]
              → [领域服务 + AI Advisor]
                   ├─ RBAC 过滤 Tool/知识库
                   ├─ 审计 AOP（model, tokenUsage）
                   ├─ 工作流（高风险 → 审批）
                   └─ 通知（完成 → 站内信）
              → [RAG Platform] / [LLM API]

关键/技巧

讲解

阶段 0 PoC（2–4 周）：单场景 + 小 Golden Set + 人工全审，验证技术可行。阶段 1 试点：部门灰度，Human-in-the-loop 抽检 20%。阶段 2 生产：自动化 Eval 门禁、预算告警、on-call runbook。阶段 3 扩展：复用 RAG 平台、Tool 目录、Prompt 仓库。每阶段明确 Go/No-Go：Faithfulness ≥ 阈值、转人工率下降、无 P0 合规事件。与第 03 章追溯对齐——AI 场景挂需求 ID。
