10 IO·NIO·网络

文件读写、多路复用、HTTP 出站调用与序列化——Java 后端与操作系统、上下游服务打交道的主战场。与第 09 章并发、第 19 章性能调优衔接。

IO 模型总览

Java IO 演进可概括为三种心智模型，选型取决于并发连接数与线程成本，而非「NIO 一定比 BIO 快」。

  • BIO（Blocking IO）：一连接一线程，读写阻塞直到内核返回。实现简单，适合连接数少、逻辑重的内部批处理或管理端。
  • NIO（Non-blocking IO + 多路复用）：Channel 非阻塞注册到 Selector，单线程（或少量线程）监听大量连接的就绪事件。Netty、Tomcat NIO、Redis 客户端底层均基于此。
  • AIO（异步 IO）：JDK 自带 AIO 在 Linux 上长期不成熟，生产几乎不用；业务侧「异步」多指线程池 + 回调/Future 或 Reactor 响应式（WebFlux），而非严格意义的内核 AIO。

图：BIO 与 NIO 并发模型对比

Spring Boot 默认嵌入式 Tomcat 对 HTTP 入站已用 NIO；业务代码里你更多面对的是文件 IO与HTTP 出站（调下游）。原则：阻塞 IO 不要占满 Tomcat 工作线程；出站调用必须设超时；高 fan-out 下游用连接池 + 熔断（见下文）。

经典 IO 与文件操作

Java 传统 IO 分字节流与字符流两条线，现代项目更推荐 java.nio.file 高层 API，仅在操作网络二进制协议或老库集成时直接接触 Stream。

字节流与字符流

InputStream / OutputStream 按字节处理，适合图片、压缩包、加密流。Reader / Writer 在字节之上做字符解码，必须显式指定 Charset（统一 StandardCharsets.UTF_8），否则 Windows 与 Linux 默认编码不一致会导致配置文件、日志乱码。

包装 BufferedInputStream / BufferedReader 可减少系统调用次数；但不要无限增大缓冲区，几 KB 到几十 KB 通常足够。

NIO.2 文件 API（日常首选）

Java 7 引入的 Path、Files 支持读写字符串、行流、目录遍历、原子移动，语义比旧 File 更清晰，且与 WatchService 等配合可做配置热加载。

Path path = Path.of("config", "application.yml");

// 读全文
String content = Files.readString(path, StandardCharsets.UTF_8);

// 按行处理大文本（避免一次性 readString 撑爆堆）
try (Stream<String> lines = Files.lines(path, StandardCharsets.UTF_8)) {
    lines.filter(l -> !l.isBlank()).forEach(this::parseLine);
}

// 写 JSON / 二进制
try (OutputStream out = Files.newOutputStream(path,
        StandardOpenOption.CREATE, StandardOpenOption.TRUNCATE_EXISTING)) {
    mapper.writeValue(out, config);
}

// 复制 / 移动
Files.copy(source, target, StandardCopyOption.REPLACE_EXISTING);
Files.move(oldPath, newPath, StandardCopyOption.ATOMIC_MOVE);

资源关闭与异常路径

Java 7+ 的 try-with-resources 会在块结束或异常时自动调用 close()，优于手写 finally。任何实现 AutoCloseable 的对象（流、Channel、部分 HTTP 包装）都应使用。

try (InputStream in = Files.newInputStream(path);
     OutputStream out = Files.newOutputStream(outPath)) {
    in.transferTo(out);
}

易错点：未指定编码；在循环中反复 new FileInputStream 却不关闭导致句柄泄漏；把数百 MB 文件一次性 readAllBytes 进堆——大文件应分块读或走 FileChannel.transferTo。

NIO：Buffer、Channel 与 Selector

NIO 核心抽象是面向缓冲区的 Channel，数据先进入 ByteBuffer，再与 Channel 交互。理解 Buffer 状态机是读懂 Netty 与各种网络框架的基础。

ByteBuffer 状态机

三个关键属性：capacity（容量）、position（当前读写位置）、limit（可读/写边界）。

  • 写入阶段：put 推进 position，limit 通常等于 capacity。
  • flip()：写完后切换为读模式——limit = position，position = 0。
  • clear()：清空准备下一轮写；compact()：保留未读字节并移到头部，适合「读了一部分还要继续读」的协议解析。

堆内存 Buffer（ByteBuffer.allocate）分配快，但数据拷到内核 socket 缓冲区时多一次拷贝。直接内存 Buffer（allocateDirect）分配在堆外，适合高吞吐网络 IO，需关注 -XX:MaxDirectMemorySize 与泄漏（见第 08 章 JVM直接内存）。

FileChannel 与零拷贝

FileChannel.transferTo / transferFrom 在 Linux 等平台上可走 sendfile 类路径，减少用户态与内核态之间的拷贝，适合大文件分发、网关静态资源、日志归档。

try (FileChannel in = FileChannel.open(src, StandardOpenOption.READ);
     FileChannel out = FileChannel.open(dst,
         StandardOpenOption.CREATE, StandardOpenOption.WRITE)) {
    long transferred = 0;
    long size = in.size();
    while (transferred < size) {
        transferred += in.transferTo(transferred, size - transferred, out);
    }
}

Selector 事件循环

非阻塞 SocketChannel 注册到 Selector，线程调用 select() 阻塞直到有 OP_READ / OP_WRITE / OP_CONNECT 就绪，再批量处理。这是「单线程管万连接」的根基；Netty 的 EventLoop 在此基础上封装了 Pipeline 与内存池。

flowchart LR
    REG[Channel 注册 Selector] --> SEL[select 等待就绪]
    SEL --> R[OP_READ 读 Buffer]
    SEL --> W[OP_WRITE 写 Buffer]
    R --> FLIP[flip 切换读模式]
    FLIP --> BIZ[业务处理]
    BIZ --> CLEAR[clear 下一轮]

图：NIO Selector 典型处理循环

手写 Selector 服务端在业务项目里极少见；知道原理即可，实际用 Netty 或 Spring WebFlux。日常文件场景用 Files，不必手写 Buffer 循环。

HTTP 客户端与出站调用

微服务架构下，每个服务除处理入站请求外，大量时间花在调用下游 REST/gRPC。JDK 11 起标准库提供 java.net.http.HttpClient，Spring 6 推荐 RestClient（同步）与 WebClient（响应式异步）。

HttpClient 基本用法

HttpClient 应作为单例 Bean 复用连接池；每次 newBuilder().build() 会丢失连接复用。支持 HTTP/2、同步 send 与异步 sendAsync。

@Configuration
public class HttpClientConfig {
    @Bean
    public HttpClient httpClient() {
        return HttpClient.newBuilder()
            .connectTimeout(Duration.ofSeconds(3))
            .version(HttpClient.Version.HTTP_2)
            .followRedirects(HttpClient.Redirect.NORMAL)
            .build();
    }
}

// 同步调用
HttpRequest req = HttpRequest.newBuilder()
    .uri(URI.create("https://api.example.com/orders/" + id))
    .timeout(Duration.ofSeconds(5))   // 请求级超时，含读写
    .header("Accept", "application/json")
    .header("X-Request-Id", requestId)
    .GET()
    .build();

HttpResponse<String> resp = client.send(req, HttpResponse.BodyHandlers.ofString());
if (resp.statusCode() >= 400) {
    throw new DownstreamException(resp.statusCode(), resp.body());
}

超时、连接与线程

  • connectTimeout：TCP 建连上限，防止下游宕机时长时间卡在 SYN。
  • request timeout：单次请求总时限，应小于 Tomcat/网关的上游超时，留出级联余量。
  • 同步 send 占用调用方线程（如 Tomcat worker）；高并发 fan-out 可考虑 sendAsync + CompletableFuture，或 WebClient 非阻塞。
  • 出站 QPS 高时配合连接池上限与舱壁隔离（Bulkhead），避免拖垮本服务线程（Resilience4j）。

Spring RestClient / WebClient

Spring Boot 3 中 RestClient 基于 HttpClient 或 Apache HttpClient 5，声明式风格接近旧 RestTemplate 但 API 更清晰。WebClient 基于 Reactor Netty，适合流式与大量并发出站，需团队熟悉响应式调试。选型：普通 CRUD 集成用 RestClient；全链路异步或 SSE 用 WebClient。

序列化与协议

数据跨越进程边界必须约定格式、编码、版本兼容。Java 后端主流组合如下。

JSON（REST 默认）

Spring Boot 默认 Jackson。领域对象与 API 契约分离：对外用 record / DTO，勿直接暴露 JPA 实体。日期时间用 Instant / OffsetDateTime，关闭时间戳数字序列化，统一 ISO-8601。

@JsonInclude(JsonInclude.Include.NON_NULL)
public record OrderDto(
    @JsonSerialize(using = ToStringSerializer.class)  // 防前端 Long 精度丢失
    Long id,
    Instant createdAt,
    BigDecimal total
) {}

ObjectMapper mapper = JsonMapper.builder()
    .disable(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS)
    .addModule(new JavaTimeModule())
    .build();

版本演进：只增字段、不改语义；废弃字段保留并标 @Deprecated；Breaking 变更走新 API 版本（第 03 章 API 设计）。

Protobuf 与 gRPC

内部高性能 RPC、流式场景常用 Protobuf 二进制 + gRPC。优点：体积小、IDL 强类型、多语言；缺点：调试不如 JSON 直观，需生成代码与兼容策略。REST 对外、gRPC 对内是常见分层。

避免 Java 原生序列化

ObjectOutputStream 存在安全漏洞历史与版本脆弱性，Redis Session、MQ 等应换 JSON/Kryo 等并评估白名单。切勿把不可信字节流直接 readObject。

下游容错：超时、重试与熔断

网络调用失败是常态：超时、连接拒绝、5xx、慢响应。裸 HttpClient 只解决「能发请求」，生产必须叠加超时 + 有限重试 + 熔断 + 可选限流。第 12 章 Resilience4j 提供 Spring Boot 3 集成。

设计原则

  • 超时：每层都设——客户端、网关、服务线程，且下游 < 上游。
  • 重试：仅对幂等读请求或带幂等键的写（第 03 章）；指数退避 + 抖动，限制最大次数。
  • 熔断：失败率/慢调用率超阈值则快速失败，给下游恢复时间，半开探测恢复。
  • 舱壁：不同下游用独立线程池或信号量，防止一个慢服务占满所有 Tomcat 线程。

编程式组合示例

CircuitBreaker cb = CircuitBreaker.of("payment-api",
    CircuitBreakerConfig.custom()
        .slidingWindowSize(20)
        .failureRateThreshold(50f)
        .waitDurationInOpenState(Duration.ofSeconds(30))
        .build());

Retry retry = Retry.of("payment-api",
    RetryConfig.custom()
        .maxAttempts(3)
        .waitDuration(Duration.ofMillis(200))
        .retryExceptions(IOException.class, TimeoutException.class)
        .build());

Supplier<HttpResponse<String>> call = () -> client.send(req, BodyHandlers.ofString());

HttpResponse<String> resp = Decorators.ofSupplier(call)
    .withCircuitBreaker(cb)
    .withRetry(retry)
    .withTimeout(Duration.ofSeconds(5))
    .get();

易错点：对创建订单等 POST 无脑重试导致重复扣款；熔断参数未按压测校准，短暂抖动就长时间拒流。应对：幂等键 + 业务去重表；熔断指标接入 Prometheus 告警。

Netty 与 Reactor 模型

Netty 是 Java 领域事实上的高性能 NIO 框架：Tomcat 可选、Spring WebFlux、Dubbo、gRPC-Java、Lettuce（Redis）、RocketMQ 客户端等均基于或可选 Netty。业务开发很少手写 Bootstrap，但必须遵守其线程模型。

线程模型

典型服务端：Boss EventLoop 线程只负责 accept 新连接；Worker EventLoop 负责已连接 Channel 的 IO 读写。每个 EventLoop 绑定一个单线程队列，保证同一 Channel 上的事件顺序处理，无锁化设计。

flowchart LR
    BOSS[Boss EventLoop accept] --> WORK[Worker EventLoop]
    WORK --> PIPE[ChannelPipeline]
    PIPE --> DEC[入站：解码]
    DEC --> BIZ[业务 Handler]
    BIZ --> ENC[出站：编码]

图：Netty Boss/Worker 与 Pipeline

ChannelPipeline

入站（Inbound）事件从 head 向 tail 传播：字节 → HTTP 帧 → 完整请求 → 业务。出站（Outbound）从 tail 向 head：业务响应 → 编码 → 字节。Handler 分为解码器、编码器、业务逻辑；添加顺序影响协议解析正确性。

铁律：勿在 EventLoop 上阻塞

JDBC、阻塞 HTTP、Thread.sleep、重 CPU 计算放在 EventLoop 上会阻塞该 Loop 上所有连接，造成级联超时。正确做法：提交到业务线程池，完成后再 ctx.executor().execute(() -> ctx.writeAndFlush(msg)) 写回。

// 反模式
protected void channelRead0(ChannelHandlerContext ctx, FullHttpRequest req) {
    Order o = jdbcTemplate.query(...);  // 阻塞 EventLoop
    writeJson(ctx, o);
}

// 正模式
protected void channelRead0(ChannelHandlerContext ctx, FullHttpRequest req) {
    businessExecutor.execute(() -> {
        Order o = orderService.find(...);
        ctx.executor().execute(() -> writeJson(ctx, o));
    });
}

若全栈 Spring MVC + JDBC，由 Tomcat 线程池承担阻塞，与 Netty 无感；一旦引入 WebFlux 或自研 Netty 网关，必须审计阻塞点。

章末实战闭环

上线前用下列清单自检 IO 与网络边界，避免「功能正确但高峰超时雪崩」。

输入

  • 文件读写量级（单次大小、QPS）与是否走磁盘/对象存储
  • 出站依赖列表：协议、SLA、是否幂等
  • 峰值并发连接数与线程池规格

输出

  • IO 模型说明（BIO 文件 + NIO 入站 + HttpClient 出站）
  • HttpClient 单例、connect/request 超时、重试与熔断参数表
  • JSON/Protobuf 版本兼容与 Long-as-String 等约定

验收标准

  • 核心下游调用在压测下 P99 可解释，无连接泄漏（句柄/ESTABLISHED 平稳）
  • 下游故障时本服务快速失败或降级，不无限阻塞 Tomcat 线程
  • 大文件上传下载有大小限制与流式处理，无 OOM

失败信号

  • 高并发路径使用阻塞 IO 且无舱壁隔离
  • 每次请求 new HttpClient、未设超时
  • 非幂等写自动重试、熔断阈值未校准
  • Netty/WebFlux 链路上执行阻塞 JDBC
