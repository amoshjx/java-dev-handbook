12 Spring Framework

以 Java 21、Spring Framework 6 与 Jakarta EE 9+ 为基线，从 IoC/DI、AOP、MVC、数据访问、事务、配置、事件与分层实践理解企业级应用开发。

Spring Framework 是什么

企业 Java 应用开发的基础框架

概要

Spring Framework 是企业级 Java 应用的基础框架，核心目标是把对象创建、依赖组装、横切能力、事务、Web 请求处理和数据访问统一到可测试、可替换、可演进的应用模型中。它不是某个单一 Web 框架，而是一组围绕 IoC Container（控制反转容器） 的开发能力。

应用开发时要把 Spring 理解为“业务对象运行的容器”：容器管理 Bean，DI（Dependency Injection，依赖注入）连接对象，AOP（Aspect-Oriented Programming，面向切面编程）承载日志、审计、权限、事务等横切逻辑，Spring MVC处理 HTTP，Data Access Abstraction（数据访问抽象）统一 JDBC、事务与 ORM 集成。

上图是典型的 Maven 多模块 Spring 项目：父 pom 管聚合与版本，子 pom 管各自依赖与打包。父模块没有 src/，只负责把 common、service、web 三个子模块串成一次构建；依赖方向是 web → service → common，与图中箭头一致。

父 pom（spring-multi-module-demo/pom.xml） 的 packaging 必须是 pom，核心内容如下：

  • <modules>：声明子模块目录名 common、service、web，执行 mvn install 时按顺序递归构建。
  • <dependencyManagement>：统一 Spring Boot BOM、MyBatis、Flyway 等第三方版本，以及内部模块 common / service 的版本（通常写 ${project.version}）。
  • <pluginManagement>：统一 maven-compiler-plugin、spring-boot-maven-plugin 等插件版本与配置，子模块引用时不必重复写版本号。
  • <properties>：如 java.version、编码、Spring 版本等全局属性，供子模块和插件继承。
<project>
    <groupId>com.example</groupId>
    <artifactId>spring-multi-module-demo</artifactId>
    <version>1.0.0</version>
    <packaging>pom</packaging>

    <modules>
        <module>common</module>
        <module>service</module>
        <module>web</module>
    </modules>

    <dependencyManagement>
        <dependencies>
            <dependency>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-dependencies</artifactId>
                <version>3.4.0</version>
                <type>pom</type>
                <scope>import</scope>
            </dependency>
            <dependency>
                <groupId>com.example</groupId>
                <artifactId>common</artifactId>
                <version>${project.version}</version>
            </dependency>
            <dependency>
                <groupId>com.example</groupId>
                <artifactId>service</artifactId>
                <version>${project.version}</version>
            </dependency>
        </dependencies>
    </dependencyManagement>
</project>

子 pom 都要通过 <parent> 指向父模块，继承 groupId、version 和 dependencyManagement；各自 packaging 为 jar，只声明本模块真正用到的依赖：

  • common/pom.xml：放 Result、PageRequest、Constants 等通用类，依赖尽量轻（如 validation、commons），不依赖其他内部模块，也不引入 Web 或数据库 starter。
  • service/pom.xml：承载 Controller / Service / Repository 与 MyBatis、Flyway 配置，声明对 common 的依赖，并引入 spring-boot-starter-jdbc、MyBatis、数据库驱动、Flyway 等。
  • web/pom.xml：启动模块，含 DemoApplication.java；依赖 service（会传递引入 common）和 spring-boot-starter-web；在 <build> 里配置 spring-boot-maven-plugin 打出可执行 fat jar。

子模块写依赖时通常只写 groupId + artifactId，版本由父 pom 的 dependencyManagement 统一管理；在根目录执行 mvn clean install 即可一次构建全部模块。更完整的多模块构建命令见第 13 章 · 多模块项目。

关键/技巧

  • IoC Container 解决对象创建和依赖装配，不让业务代码到处 new 基础设施对象。
  • ApplicationContext 在 BeanFactory 之上提供事件、资源、国际化、环境和生命周期管理。
  • 声明式能力 的本质通常是代理，例如 @Transactional、@Cacheable、@Async。

速记

Spring Framework 管对象、管边界、管横切；业务代码专注用例和领域规则。

IoC / DI 应用

Bean 定义、组件扫描、构造器注入与生命周期

概要

Bean 是由 Spring 容器创建和管理的对象。业务类通常用 @Component、@Service、@Repository、@Controller 通过 Component Scan（组件扫描）注册；第三方客户端、连接工厂、策略对象更适合通过 @Configuration + @Bean 显式定义。

依赖注入优先使用构造器注入：依赖可见、字段可 final、测试可直接 new。默认 Scope（作用域） 是 singleton，每个 ApplicationContext 一个实例；prototype 每次获取新实例；Web 场景还有 request、session。生命周期从 BeanDefinition 加载、实例化、属性填充、Aware 回调、BeanPostProcessor、初始化，到容器关闭时销毁。

示例代码

@Service
public class OrderApplicationService {
    private final OrderRepository orderRepository;
    private final PaymentGateway paymentGateway;

    public OrderApplicationService(OrderRepository orderRepository,
                                   PaymentGateway paymentGateway) {
        this.orderRepository = orderRepository;
        this.paymentGateway = paymentGateway;
    }

    public OrderId placeOrder(PlaceOrderCommand command) {
        Order order = Order.create(command.customerId(), command.lines());
        paymentGateway.authorize(order.totalAmount());
        orderRepository.save(order);
        return order.id();
    }
}

@Configuration
class PaymentConfig {
    @Bean
    PaymentGateway paymentGateway(PaymentProperties props) {
        return new StripePaymentGateway(props.endpoint(), props.apiKey());
    }
}
<!-- XML 仍可用于历史系统兼容，新项目优先 Java Config -->
<bean id="paymentGateway" class="com.acme.pay.StripePaymentGateway">
  <constructor-arg value="${payment.endpoint}" />
</bean>

易错点

  • 字段注入隐藏依赖，单元测试困难；优先构造器注入。
  • 多个实现未使用 @Qualifier 或 @Primary，会导致 NoUniqueBeanDefinitionException。
  • singleton 注入 prototype 不会每次自动刷新，必要时用 ObjectProvider<T>。
  • 循环依赖通常是职责边界问题，应拆服务、抽端口或改用事件。

AOP 应用

日志、审计、权限与事务背后的代理机制

概要

AOP 用于把横切逻辑从业务方法中抽离。典型场景包括接口访问日志、操作审计、权限校验、幂等、限流、缓存和声明式事务。Spring AOP 默认基于代理：目标类有接口时可用 JDK Dynamic Proxy（JDK 动态代理），无接口时常用 CGLIB 创建子类代理。

理解代理是排障关键：调用方必须通过 Spring 代理对象进入方法，通知才会执行；同类 this.method() 自调用、private 方法、final 方法、非 Spring Bean 方法都容易让切面和事务失效。切面顺序用 @Order 控制，权限、事务、审计的先后要有明确策略。

flowchart LR
    CALLER["调用方"] --> PROXY["Spring Proxy
JDK / CGLIB"]
    PROXY --> ADVICE["Advice
日志 · 权限 · 事务"]
    ADVICE --> TARGET["Target Bean
业务方法"]
    TARGET --> ADVICE
    ADVICE --> CALLER

示例代码

@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Audited {
    String action();
}

@Aspect
@Component
class AuditAspect {
    @Around("@annotation(audited)")
    Object audit(ProceedingJoinPoint pjp, Audited audited) throws Throwable {
        long start = System.nanoTime();
        try {
            Object result = pjp.proceed();
            // 记录操作者、动作、业务主键、耗时和 traceId，不记录敏感字段。
            return result;
        } catch (Throwable ex) {
            // 审计失败结果，但不能吞异常。
            throw ex;
        }
    }
}

Web MVC 应用

DispatcherServlet、Controller、绑定、校验与异常处理

概要

Spring MVC 的入口是 DispatcherServlet（前端控制器）。请求进入后依次经过 FilterChain、HandlerMapping、HandlerAdapter、Controller、参数绑定、校验、业务调用、返回值处理和 HttpMessageConverter。Controller 应保持薄：完成协议适配、入参校验、调用 Application Service、返回 DTO。

Filter（过滤器） 位于 Servlet 层，适合 TraceId、编码、认证入口、CORS；HandlerInterceptor（拦截器） 位于 MVC 层，适合审计、幂等、灰度标签。异常处理集中到 @RestControllerAdvice，把领域异常、校验异常和系统异常映射为稳定错误码与 ProblemDetail。

示例代码

@RestController
@RequestMapping("/api/v1/orders")
class OrderController {
    private final CreateOrderUseCase createOrder;

    OrderController(CreateOrderUseCase createOrder) {
        this.createOrder = createOrder;
    }

    @PostMapping
    ResponseEntity<OrderResponse> create(@Valid @RequestBody CreateOrderRequest request) {
        OrderView order = createOrder.execute(request.toCommand());
        URI location = URI.create("/api/v1/orders/" + order.id());
        return ResponseEntity.created(location).body(OrderResponse.from(order));
    }
}

@RestControllerAdvice
class ApiExceptionHandler {
    @ExceptionHandler(MethodArgumentNotValidException.class)
    ResponseEntity<ProblemDetail> validation(MethodArgumentNotValidException ex) {
        ProblemDetail body = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
        body.setProperty("errorCode", "REQUEST_INVALID");
        body.setProperty("errors", ex.getBindingResult().getFieldErrors().stream()
            .collect(Collectors.toMap(FieldError::getField, FieldError::getDefaultMessage)));
        return ResponseEntity.badRequest().body(body);
    }
}

异常映射要点

  • 业务异常映射 4xx，系统异常映射 500，日志包含 traceId。
  • 对外错误体给稳定业务码，不泄露 SQL、堆栈、类名和敏感数据。
  • 参数绑定失败通常来自字段名不一致、日期格式、枚举值、Content-Type 或嵌套对象未加 @Valid。

数据访问抽象

JdbcTemplate、事务管理与 MyBatis / JPA 集成位置

概要

Spring 的数据访问抽象把连接获取、资源释放、异常转换和事务同步统一起来。JdbcTemplate 适合显式 SQL、批处理和性能敏感路径；MyBatis 适合 SQL 可控、复杂报表和已有 SQL 资产；JPA 适合领域模型清晰、对象关系映射收益高的系统。它们都应位于 Repository / Infrastructure 层，由 Application Service 定义事务边界。

PlatformTransactionManager 是事务管理抽象：JDBC 使用 DataSourceTransactionManager，JPA 使用 JpaTransactionManager。Spring 还提供 DataAccessException 统一异常层，避免业务层直接依赖不同驱动的 SQLException。

示例代码

@Repository
class JdbcOrderRepository implements OrderRepository {
    private final JdbcTemplate jdbcTemplate;

    JdbcOrderRepository(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    @Override
    public void save(Order order) {
        jdbcTemplate.update("""
            insert into orders(id, customer_id, status, total_amount)
            values (?, ?, ?, ?)
            """, order.id(), order.customerId(), order.status().name(), order.totalAmount());
    }
}

@Mapper
interface OrderMapper {
    List<OrderRow> selectByCustomerId(String customerId);
}

public interface JpaOrderRepository extends JpaRepository<OrderEntity, UUID> {
    @Query("select o from OrderEntity o join fetch o.lines where o.id = :id")
    Optional<OrderEntity> findWithLines(UUID id);
}

关键/技巧

  • 复杂写操作优先把事务放在应用服务层，而不是 Repository 内部。
  • 批量写入使用 JDBC batch 或数据库原生能力，避免循环单条 ORM save。
  • JPA Entity 不直接作为 REST DTO 返回，避免懒加载、循环引用和字段泄漏。

声明式事务

@Transactional 的传播、隔离、回滚规则与失效场景

概要

@Transactional 通过 AOP 代理在方法前后开启、提交或回滚事务。常用 Propagation（传播行为）：REQUIRED 加入当前事务或新建；REQUIRES_NEW 挂起当前事务新开事务；NESTED 使用保存点；SUPPORTS 有事务则加入。常用 Isolation（隔离级别） 包括 READ_COMMITTED、REPEATABLE_READ、SERIALIZABLE，默认通常交给数据库。

默认只对 RuntimeException 和 Error 回滚，checked 异常需要 rollbackFor。事务边界应尽量短，不要把慢 HTTP、MQ 等外部调用长时间包在数据库事务里；跨服务一致性优先使用 Outbox、消息最终一致或 Saga，而不是分布式大事务。

示例代码

@Service
class PlaceOrderService {
    private final OrderRepository orders;
    private final DomainEventPublisher events;

    @Transactional(rollbackFor = BusinessException.class)
    public OrderId place(PlaceOrderCommand command) throws BusinessException {
        Order order = Order.create(command.customerId(), command.lines());
        orders.save(order);
        events.publish(new OrderPlacedEvent(order.id()));
        return order.id();
    }

    @Transactional(readOnly = true, isolation = Isolation.READ_COMMITTED)
    public OrderView get(OrderId id) {
        return orders.findView(id).orElseThrow(OrderNotFoundException::new);
    }
}

失效场景

  • 同类自调用没有经过代理：this.inner() 不会触发事务。
  • 方法不是 public、类或方法 final、对象不是 Spring Bean。
  • 异常被 catch 后吞掉，或 checked 异常未配置 rollbackFor。
  • @Async 新线程、手写线程池不会自动继承当前事务。

配置与环境

Environment、Profile、PropertySource 与外部化配置

概要

Environment（环境抽象） 统一读取系统属性、环境变量、配置文件、命令行参数和自定义 PropertySource（属性源）。Profile 用于按环境启用 Bean 或配置，例如 dev、test、prod。应用代码应读取类型安全配置对象，而不是散落字符串 key。

新项目优先使用 Java Config 和外部化配置：本地使用 YAML / properties，生产由环境变量、Secret、配置中心或部署平台注入。Profile 管环境差异，不应承载复杂业务分支。

示例代码

@Configuration
@Profile("prod")
class ProdDataSourceConfig {
    @Bean
    DataSource dataSource(DatabaseProperties props) {
        return DataSourceBuilder.create()
            .url(props.url())
            .username(props.username())
            .password(props.password())
            .build();
    }
}

事件机制

ApplicationEvent、监听器与同步 / 异步事件

概要

ApplicationEvent（应用事件） 适合在同一应用内解耦模块，例如订单创建后发送站内信、记录审计、触发缓存刷新。默认事件是同步发布，监听器异常会影响发布方；启用 @Async 后可异步执行，但事务上下文、异常处理和重试策略需要单独设计。

事件不是消息队列替代品。进程内事件适合同一 JVM 内的模块解耦；跨服务、可靠投递和削峰应使用 MQ，并配合 Outbox 或事务消息。

示例代码

public record OrderPlacedEvent(UUID orderId, Instant occurredAt) {}

@Service
class OrderService {
    private final ApplicationEventPublisher publisher;

    @Transactional
    public UUID place(PlaceOrderCommand command) {
        UUID orderId = saveOrder(command);
        publisher.publishEvent(new OrderPlacedEvent(orderId, Instant.now()));
        return orderId;
    }
}

@Component
class OrderEventListener {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    void afterCommit(OrderPlacedEvent event) {
        // 事务提交后再发通知，避免回滚后外部已感知。
    }

    @Async
    @EventListener
    void buildReadModel(OrderPlacedEvent event) {
        // 异步监听器需要独立异常日志、重试和线程池配置。
    }
}

Bean Validation

JSR 380 / Jakarta Validation 在入参与业务模型中的使用

概要

Spring Framework 6 使用 Jakarta EE 9+ 命名空间，因此校验注解来自 jakarta.validation。Web 入参使用 @Valid 触发对象图校验，Service 方法级校验可用 @Validated。校验适合表达格式、长度、必填、范围、集合元素等规则；涉及库存、额度、状态流转的业务规则应放在领域对象或应用服务中。

示例代码

public record CreateOrderRequest(
    @NotBlank String customerId,
    @NotEmpty List<@Valid LineRequest> lines
) {}

public record LineRequest(
    @NotBlank String sku,
    @Positive int quantity
) {}

@Service
@Validated
class CustomerService {
    public CustomerView get(@NotNull UUID customerId) {
        return findCustomer(customerId);
    }
}

易错点

  • 嵌套对象或集合元素忘记加 @Valid，内层约束不会执行。
  • 把业务规则全写成注解，导致规则难测试、难组合、错误信息难表达。
  • Spring 6 / Boot 3 项目误用 javax.validation 包。

应用分层实践

Controller / Application Service / Domain / Repository / Infrastructure

概要

Spring 应用不是把所有类放进 service 包就结束。推荐按业务上下文组织包，再在上下文内分层：Controller 负责 HTTP 适配；Application Service 编排用例和事务；Domain 承载实体、值对象、领域服务和规则；Repository 表达持久化端口；Infrastructure 实现数据库、MQ、第三方客户端等技术细节。

物理目录遵循 Maven/Gradle 标准布局（src/main/java、src/main/resources、src/test/java），源码包内再按业务上下文与分层职责划分；启动类与全局 @Configuration 通常放在根包，便于组件扫描覆盖全部业务模块。

与 Spring Boot 的关系

Boot 是基于 Spring 的工程化快速启动层

概要

Spring Boot 不是 Spring Framework 的替代品，而是基于 Spring 的工程化快速启动层。Boot 提供 Starter 依赖组合、Auto Configuration（自动配置）、内嵌 Web Server、配置绑定、Actuator、测试切片与打包部署约定，让团队更快创建可运行应用。

本章主角是 Spring Framework 的应用开发模型。Boot 在真实项目中通常作为脚手架和运行时约定使用：它减少样板配置，但底层仍是 IoC、AOP、MVC、事务、数据访问、Environment 与事件机制。高级开发者需要能解释 Boot 默认 Bean 从哪里来、如何覆盖和如何排障，但设计业务边界时仍以 Spring Framework 能力和分层原则为核心。

示例代码

@SpringBootApplication
public class ShopApplication {
    public static void main(String[] args) {
        SpringApplication.run(ShopApplication.class, args);
    }
}

// @SpringBootApplication 组合了 @Configuration、@ComponentScan 和 Boot 自动配置入口。
// 业务类仍由 Spring IoC 管理，事务和 MVC 仍来自 Spring Framework。

Spring Boot 工程化

Actuator · 健康探针 · 优雅停机

概要

生产环境 Spring Boot 应用须与 K8s 探针、发布策略对齐。Actuator 暴露运维端点；Liveness 判断进程是否存活（失败则重启 Pod）；Readiness 判断能否接流量（失败则从 Service 摘除）。Graceful Shutdown 在 SIGTERM 后停止接收新请求、等待在途请求完成再退出，避免发布时 502。

安全：生产仅暴露 health、info、prometheus（若用），且须认证或网络隔离——详见第 17 章安全开发。

配置示例

# application-prod.yml
server:
  shutdown: graceful
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s
  threads:
    virtual:
      enabled: true   # IO 密集可选，见第 09 章
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
  endpoint:
    health:
      probes:
        enabled: true   # /actuator/health/liveness & /readiness
  health:
    livenessstate:
      enabled: true
    readinessstate:
      enabled: true

# K8s Deployment 片段
# livenessProbe:  httpGet /actuator/health/liveness  initialDelaySeconds: 60
# readinessProbe: httpGet /actuator/health/readiness initialDelaySeconds: 30
# preStop: exec sleep 5  # 给 Endpoint 摘除留窗口

关键/技巧

  • Readiness 可绑定 DB/Redis 连通性；启动慢的服务调大 initialDelaySeconds。
  • 优雅停机 + MQ 消费者：停止 poll 前完成当前 batch ack。
  • 与第 21 章 CI/CD蓝绿/金丝雀发布配合验证无 502 尖刺。

速记

「Liveness 重启，Readiness 摘流；graceful 等完，preStop 缓冲。」

DTO 映射（MapStruct）

Entity / DTO / VO 转换规范

概要

分层边界要求：Controller 只暴露 DTO/VO，不泄漏 JPA Entity 或懒加载关联。MapStruct 在编译期生成映射代码，性能优于反射，类型安全。复杂映射（枚举翻译、嵌套聚合）在 @Mapper 中声明 @Mapping 或 default 方法。

示例代码

@Mapper(componentModel = "spring")
public interface OrderMapper {
  OrderResponse toResponse(Order entity);
  @Mapping(target = "id", ignore = true)
  @Mapping(target = "status", constant = "PENDING")
  Order toEntity(CreateOrderRequest dto);
}

@Service
@RequiredArgsConstructor
public class OrderQueryService {
  private final OrderRepository repo;
  private final OrderMapper mapper;
  public OrderResponse get(UUID id) {
    return repo.findById(id).map(mapper::toResponse).orElseThrow(...);
  }
}

关键/技巧

  • 写操作 Command 与读模型 Response 分离，避免同一 DTO 双向映射歧义。
  • MapStruct + Lombok 需配置 lombok-mapstruct-binding 注解处理器顺序。

异步边界

@Async · 事件 · 虚拟线程与上下文传播

概要

@Async 将方法提交到线程池执行，适合非阻塞通知、审计落库。虚拟线程（spring.threads.virtual.enabled=true）适合高并发阻塞 IO，见第 09 章。异步线程默认无 SecurityContext / MDC / Locale——需 DelegatingSecurityContextAsyncTaskExecutor 或手动传播（见第 17 章）。领域事件：事务提交后再发布（@TransactionalEventListener(phase = AFTER_COMMIT)）。

示例代码

@Configuration
@EnableAsync
class AsyncConfig {
  @Bean
  Executor taskExecutor() {
    return new DelegatingSecurityContextAsyncTaskExecutor(
        Executors.newVirtualThreadPerTaskExecutor());
  }
}

@Service
class OrderAppService {
  @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
  void onOrderPlaced(OrderPlacedEvent e) {
    notificationService.sendAsync(e.orderId());
  }
}

Resilience4j 容错

超时 · 重试 · 熔断 · 舱壁 · 限流

概要

Resilience4j 为 Spring Boot 3 推荐的轻量容错库，替代 Hystrix。与第 03 章 API 幂等/重试对齐：仅对幂等请求重试；熔断打开后快速失败，避免级联故障。网关层限流（Sentinel/Gateway）与应用层 Resilience4j 互补。

配置示例

# application.yml
resilience4j:
  circuitbreaker:
    instances:
      payment:
        slidingWindowSize: 20
        failureRateThreshold: 50
        waitDurationInOpenState: 30s
  retry:
    instances:
      payment:
        maxAttempts: 3
        waitDuration: 200ms
  timelimiter:
    instances:
      payment:
        timeoutDuration: 3s

@Service
class PaymentClient {
  @CircuitBreaker(name = "payment", fallbackMethod = "chargeFallback")
  @Retry(name = "payment")
  @TimeLimiter(name = "payment")
  public CompletableFuture<Receipt> charge(Money amount) { ... }
}

速记

「超时先定，幂等才重试；熔断防雪崩，舱壁隔离慢依赖。」

统一异常与错误码

业务异常 · Problem Details · @ControllerAdvice

概要

异常分层：业务异常（可预期，4xx，稳定 error code）vs 系统异常（5xx，日志告警）。对外响应遵循 RFC 9457 Problem Details，与第 03 章错误规范一致。错误码用英文常量（如 order.not_found），用户可见文案走 MessageSource（见第 16 章 i18n）。

示例代码

public class BusinessException extends RuntimeException {
  private final String code;
  private final HttpStatus status;
}

@RestControllerAdvice
class GlobalExceptionHandler {
  @ExceptionHandler(BusinessException.class)
  ProblemDetail handle(BusinessException ex) {
    return ProblemDetail.forStatusAndDetail(ex.getStatus(), ex.getCode())
        .setProperty("code", ex.getCode());
  }
  @ExceptionHandler(Exception.class)
  ProblemDetail handleSystem(Exception ex) {
    log.error("unexpected", ex);
    return ProblemDetail.forStatus(HttpStatus.INTERNAL_SERVER_ERROR)
        .setDetail("internal.error");
  }
}

常见问题与排障

从 Bean、代理、事务、绑定到 Web 行为

排障清单

  • Bean 找不到：检查包扫描根路径、Profile、条件 Bean、模块依赖、Bean 名称和测试切片加载范围。
  • 循环依赖：优先拆职责、抽端口、改事件；不要把允许循环依赖作为长期方案。
  • 代理失效：排查自调用、final/private 方法、对象未交给 Spring、切点表达式过窄或代理类型不匹配。
  • 事务不生效：检查异常是否被吞、checked 异常回滚规则、事务管理器、方法可见性和异步线程。
  • 参数绑定失败：检查 JSON 字段名、Content-Type、日期格式、枚举值、嵌套 @Valid 和构造器。
  • 跨域 CORS：区分浏览器预检与服务端错误，统一在 MVC 或 Security 层配置。
  • JSON 序列化：避免 Entity 直出，处理懒加载、循环引用、时间格式、BigDecimal 精度和枚举兼容。

诊断入口

  • 启动日志、Bean 创建异常栈和条件装配报告能定位大多数容器问题。
  • MVC 问题优先看请求日志、异常映射、MockMvc 回归测试和浏览器 Network 面板。
  • 事务问题用集成测试验证提交/回滚结果，不只看日志是否打印。

生产开发 Checklist

上线前必须确认的应用工程项

代码与分层

  • Controller 薄，Application Service 定义用例和事务边界，Domain 不依赖 Web / ORM 细节。
  • Bean 使用构造器注入，无隐藏字段注入、无无意义循环依赖、无静态可变状态。
  • DTO、Command、Entity 边界清晰，外部接口不直接暴露持久化模型。
  • AOP 切点明确，审计、权限、事务、缓存顺序可解释。

配置与数据

  • Profile、PropertySource 和外部化配置来源清晰，密钥不入 Git。
  • JdbcTemplate / MyBatis / JPA 选型与模块位置明确，SQL 和迁移脚本可追踪。
  • @Transactional 的传播、隔离、回滚规则经过集成测试覆盖。
  • 事件监听器区分同步、异步和事务后发布，失败策略明确。

接口与质量

  • 入参校验、异常响应、错误码、CORS、JSON 序列化和安全入口有回归测试。
  • 核心用例有单元测试，Repository 有真实数据库方言测试，Web 层有 MockMvc 或等价测试。
  • 日志包含 traceId，关键业务操作有审计，生产排障不依赖临时改代码。
  • 使用 Boot 时能说明自动配置覆盖点、Actuator 暴露范围和运行时配置来源。
