20 工程化·DevOps·CI/CD

本章聚焦持续集成与持续交付（CI/CD）——把「提交代码 → 构建测试 → 打镜像 → 部署上线」整条链路自动化。跟着实操走完一遍，你的 Java 后端项目就能在每次 Push 后自动跑流水线，并可控地发布到测试与生产环境。

默认示例项目：fdc-webservice（Java 21 · Spring Boot 3.x · Maven 3.9+）。Maven 打包、Dockerfile、K8s 清单见第 13 章；单元测试与质量门禁见第 17 章、第 18 章。

本章概览

建议按顺序实操：

  1. 理解工程化、DevOps 与 CI/CD 的关系
  2. 设计 Java 后端流水线阶段与质量门禁
  3. 选定 CI 平台（本章以自建 GitLab 为主）
  4. 部署 GitLab 与 Runner
  5. 编写并调试 .gitlab-ci.yml
  6. 配置分支策略与 Merge Request 门禁
  7. 多环境发布与人工审批
  8. 缓存、并行与安全扫描优化
  9. 排障与运维清单

预设环境：Docker 24+ · 一台 8 GB+ 内存 Linux 服务器（GitLab + Runner）· 可访问的镜像仓库（GitLab 内置 Registry 或 Harbor）。

一、三个概念，一条链路

很多人把「工程化」「DevOps」「CI/CD」混为一谈。实操前先分清职责——后面写流水线时才知道每一步在解决什么问题。

概念是什么本章中的体现
工程化 用标准化、自动化、可度量的方式开发软件——把「手艺活」变成「可重复的工业流程」 统一分支规范、Commit 格式、构建命令、测试覆盖率阈值
DevOps 开发（Dev）与运维（Ops）协作的文化与工具链，目标是高质量、高频率交付 开发者自己维护 .gitlab-ci.yml，运维提供 Runner 与 K8s 集群，共同定义发布流程
CI/CD DevOps 落地的核心引擎——代码一提交就自动构建、测试、部署 .gitlab-ci.yml 定义的 Pipeline，本章实操主体

DevOps 生命周期与 CI/CD 的对应

DevOps 的「∞」循环中，CI/CD 流水线负责中间段（Build → Test → Release → Deploy）；Plan/Code 在开发阶段完成，Operate/Monitor 在上线后由可观测性体系统筹（见第 19 章）。

二、CI/CD 流水线设计

1. CI 与两种 CD 的区别

缩写全称触发时机产出
CI Continuous Integration
持续集成		 每次 Push / MR 编译通过 + 自动化测试通过 → 尽早发现集成问题
CD Continuous Delivery
持续交付		 合并到主干后 可部署的制品（JAR / 镜像）+ 自动部署到类生产环境，生产发布需人工审批
CD Continuous Deployment
持续部署		 测试全部通过后 自动推到生产环境，无需人工点击（适合高频迭代、强自动化测试的团队）

大多数企业 Java 后端采用 CI + Continuous Delivery：SIT/UAT 自动部署，生产环境 when: manual 或走变更审批。

2. Java 后端标准阶段

与第 13 章 CI/CD 图对齐，推荐阶段划分如下：

flowchart TD
    PUSH[Push / MR] --> LINT[静态检查]
    LINT --> BUILD[compile]
    BUILD --> TEST[unit test + 覆盖率]
    TEST --> PKG[mvn package]
    PKG --> SCAN[安全/依赖扫描]
    SCAN --> IMG[docker build]
    IMG --> REG[push registry]
    REG --> DEPLOY_SIT[deploy sit]
    DEPLOY_SIT --> APPROVE[人工审批]
    APPROVE --> DEPLOY_PROD[deploy prod]

3. 质量门禁（Quality Gate）

流水线不只是「跑完就行」——在关键阶段设硬门槛，不合格则 Pipeline 失败、禁止合并：

阶段门禁条件工具示例
静态检查无 Blocker 级告警Checkstyle、SpotBugs、SonarQube
单元测试全部通过，覆盖率 ≥ 阈值（如 60%）JUnit 5 + JaCoCo
依赖扫描无 Critical CVEOWASP Dependency-Check、Trivy
镜像扫描无高危漏洞Trivy、Grype
合并 MRPipeline 绿 + 至少 1 人 ReviewGitLab Protected Branch

三、CI 平台选型

平台适用场景优势局限
自建 GitLab CE 内网交付、代码不出域、需 MR + CI + Registry 一体化 私有仓库无限、CI/CD 与代码同源、权限精细 需自行运维服务器与备份
GitHub Actions 开源项目、已用 GitHub 托管 生态最好、Marketplace 插件丰富 私有仓库 CI 分钟数有限；国内访问不稳定
Jenkins 已有 Jenkins 基建、插件需求复杂 插件生态最老最全、流水线 DSL 灵活 需单独维护 Master/Agent；配置分散在 Job 与 Jenkinsfile
Gitee Go / 云效 国内中小企业、Gitee 托管 国内访问快、与 Gitee 集成 高级功能与企业合规需额外评估

本章选型：对有隐私或内网要求的团队，自建 GitLab 最常见——代码、流水线、镜像仓库在一个平台闭环，不必再对接 Jenkins + 独立 Git 托管 + Harbor。

四、实战：部署 GitLab

服务器建议：最低 4 GB 内存可跑，推荐 8 GB+（Sidekiq、Puma、PostgreSQL 同机运行较吃资源）。

1. Docker Compose 一键启动

# docker-compose.yml
version: '3.8'

services:
  gitlab:
    image: gitlab/gitlab-ce:latest
    container_name: gitlab
    restart: always
    hostname: 'gitlab.example.com'
    environment:
      GITLAB_OMNIBUS_CONFIG: |
        external_url 'http://gitlab.example.com'
        gitlab_rails['gitlab_shell_ssh_port'] = 2222
        # 启用 Container Registry（CI 推镜像用）
        registry_external_url 'http://gitlab.example.com:5050'
    ports:
      - '80:80'
      - '443:443'
      - '2222:22'
      - '5050:5050'
    volumes:
      - './gitlab/config:/etc/gitlab'
      - './gitlab/logs:/var/log/gitlab'
      - './gitlab/data:/var/opt/gitlab'
    shm_size: '256m'
# 启动并等待就绪（首次约 5–10 分钟）
docker compose up -d
docker logs -f gitlab

# 获取 root 初始密码（24 小时内有效，过期需重置）
docker exec -it gitlab grep 'Password:' /etc/gitlab/initial_root_password

2. 初始安全配置

  1. Admin Area → Settings → Sign-up restrictions → 关闭公开注册
  2. Admin Area → Settings → Visibility → 默认仓库设为 Private
  3. 创建 Group（如 fdc）与 Project（如 fdc-webservice）
  4. 成员配置 SSH Key：User Settings → SSH Keys；克隆地址用 git@gitlab.example.com:2222

3. 部署 GitLab Runner

Runner 是执行 CI Job 的代理。可与 GitLab 同机，但生产环境建议单独一台，避免构建任务与 GitLab 争抢 CPU/内存。

# Docker 方式安装 Runner
docker run -d --name gitlab-runner --restart always \
  -v /var/run/docker.sock:/var/run/docker.sock \
  -v gitlab-runner-config:/etc/gitlab-runner \
  gitlab/gitlab-runner:latest

在 GitLab → Admin Area → CI/CD → Runners 复制注册 Token，然后注册：

docker exec -it gitlab-runner gitlab-runner register

# 交互示例：
# GitLab URL: http://gitlab.example.com
# Registration token: [粘贴 Token]
# Description: java-docker-runner
# Tags: docker,maven,java
# Executor: docker
# Default image: maven:3.9-eclipse-temurin-21

若 Job 内需要 docker build，在 Runner 的 config.toml 中挂载 Docker 套接字并开启 privileged（或改用 Kaniko 等免特权方案）：

# 编辑 config.toml（路径因安装方式而异）
[runners.docker]
  image = "maven:3.9-eclipse-temurin-21"
  privileged = true
  volumes = ["/cache", "/var/run/docker.sock:/var/run/docker.sock"]

注册完成后，在 GitLab → CI/CD → Runners 页面确认 Runner 状态为 绿色在线。

五、实战：Java 项目 CI/CD 配置

.gitlab-ci.yml 放在仓库根目录；每次 Push 或 Merge Request 会按 stages 顺序触发 Job。以下配置覆盖编译、测试、打 JAR、构建并推送 Docker 镜像。

1. 流水线阶段一览

flowchart LR
    MR[MR / Push] --> BUILD[build]
    BUILD --> TEST[test]
    TEST --> PACKAGE[package]
    PACKAGE --> IMAGE[build-image]
    IMAGE --> SIT[deploy-sit]
    SIT --> PROD[deploy-prod
manual]

图：fdc-webservice GitLab 流水线

2. 完整 .gitlab-ci.yml

# .gitlab-ci.yml
stages:
  - build
  - test
  - package
  - deploy

variables:
  MAVEN_OPTS: "-Dmaven.repo.local=.m2/repository"
  DOCKER_TLS_CERTDIR: ""
  # 镜像名由 GitLab 内置变量提供，无需手写

cache:
  key: "${CI_COMMIT_REF_SLUG}"
  paths:
    - .m2/repository/

# ---------- 编译 ----------
build:
  stage: build
  image: maven:3.9-eclipse-temurin-21
  tags: [docker, maven, java]
  script:
    - mvn -B compile -DskipTests
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == "main" || $CI_COMMIT_BRANCH == "develop"

# ---------- 单元测试 ----------
test:
  stage: test
  image: maven:3.9-eclipse-temurin-21
  tags: [docker, maven, java]
  script:
    - mvn -B test
    # 可选：JaCoCo 覆盖率门禁
    # - mvn -B verify -DskipTests  # 若 pom 配了 jacoco:check
  artifacts:
    when: always
    reports:
      junit:
        - target/surefire-reports/TEST-*.xml
    paths:
      - target/site/jacoco/   # 若启用 JaCoCo 报告
    expire_in: 1 week
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == "main" || $CI_COMMIT_BRANCH == "develop"

# ---------- 打 JAR ----------
package:
  stage: package
  image: maven:3.9-eclipse-temurin-21
  tags: [docker, maven, java]
  script:
    - mvn -B package -DskipTests
  artifacts:
    paths:
      - target/*.jar
    expire_in: 1 week
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

# ---------- 构建并推送镜像 ----------
build-image:
  stage: deploy
  image: docker:24
  services:
    - docker:24-dind
  tags: [docker]
  before_script:
    - docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" "$CI_REGISTRY"
  script:
    - docker build -t "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA" .
    - docker build -t "$CI_REGISTRY_IMAGE:latest" .
    - docker push "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA"
    - docker push "$CI_REGISTRY_IMAGE:latest"
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
  needs: [package]

# ---------- 部署 SIT（自动） ----------
deploy-sit:
  stage: deploy
  image: bitnami/kubectl:latest
  tags: [docker]
  variables:
    KUBE_NAMESPACE: fdc-sit
  script:
    - kubectl set image deployment/fdc-webservice \
        fdc-webservice="$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA" \
        -n "$KUBE_NAMESPACE"
    - kubectl rollout status deployment/fdc-webservice -n "$KUBE_NAMESPACE" --timeout=120s
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
  needs: [build-image]
  environment:
    name: sit
    url: https://sit.example.com

# ---------- 部署 PROD（人工审批） ----------
deploy-prod:
  stage: deploy
  image: bitnami/kubectl:latest
  tags: [docker]
  variables:
    KUBE_NAMESPACE: fdc-prod
  script:
    - kubectl set image deployment/fdc-webservice \
        fdc-webservice="$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA" \
        -n "$KUBE_NAMESPACE"
    - kubectl rollout status deployment/fdc-webservice -n "$KUBE_NAMESPACE" --timeout=180s
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
  when: manual          # 必须人工点击才执行
  needs: [build-image]
  environment:
    name: production
    url: https://api.example.com

3. 配置要点说明

配置项作用实操提示
cache.paths 缓存 Maven 本地仓库 第二次 Pipeline 可快 50%+；key 按分支隔离避免污染
rules 控制何时触发 Job MR 只跑 build+test；main 才打镜像与部署
artifacts.reports.junit 测试报告可视化 GitLab MR 页面直接展示通过/失败用例数
CI_REGISTRY_* GitLab 内置镜像仓库变量 无需手写仓库地址；Project → Deploy → Container Registry 可查看
needs Job 依赖，跳过不必要等待 build-image 不必等 test 所在 stage 全部完成（同 stage 内仍并行）
when: manual 人工审批门禁 生产部署必设；SIT 可自动以加快反馈
environment 环境追踪与部署历史 GitLab → Deploy → Environments 可查看每次部署记录与回滚

4. 挂载 Maven 私服 / 镜像加速

CI 内 Maven 下载慢时，在项目中添加 .mvn/settings-ci.xml 并在 Job 中引用：

# Job script 中加一行
- mvn -B test -s .mvn/settings-ci.xml
<!-- .mvn/settings-ci.xml 片段：阿里云 mirror -->
<settings>
  <mirrors>
    <mirror>
      <id>aliyun</id>
      <mirrorOf>central</mirrorOf>
      <url>https://maven.aliyun.com/repository/public</url>
    </mirror>
  </mirrors>
</settings>

K8s 部署清单与 Dockerfile 写法见第 13 章 Docker 节与K8s 节；CI 中的 kubectl Job 需在 Runner 上配置 KUBECONFIG 或使用 GitLab Kubernetes Agent。

六、分支策略与 Merge Request

流水线与分支模型必须配套——否则开发者直接 Push 到 main，CI 门禁形同虚设。

1. 推荐分支模型（Git Flow 简化版）

gitGraph
    commit id: "init"
    branch develop
    checkout develop
    commit id: "feat-a"
    branch feature/login
    checkout feature/login
    commit id: "login-api"
    checkout develop
    merge feature/login
    checkout main
    merge develop tag: "v1.0.0"

图：main / develop / feature 三分支模型

分支用途CI 行为
feature/*功能开发MR → develop 时跑 build + test
develop集成测试分支Push 时跑 build + test
main生产就绪代码Push 时跑完整流水线（含打镜像、部署）

2. 保护 main 分支

Settings → Repository → Protected branches：

  • Allowed to merge：Maintainers
  • Allowed to push：No one（禁止直接 push）
  • Require approval：至少 1 人 Code Review
  • Pipelines must succeed：Pipeline 必须通过才能合并

3. MR 描述模板

在 .gitlab/merge_request_templates/default.md 中固定审查清单：

## 变更类型
- [ ] 新功能  - [ ] Bug 修复  - [ ] 重构  - [ ] 文档

## 测试说明
- [ ] 单元测试已补充/更新
- [ ] 本地 `mvn test` 通过

## Checklist
- [ ] 无硬编码密钥/密码
- [ ] 数据库变更有对应 migration 脚本
- [ ] 接口变更有 Swagger/文档更新

七、多环境发布策略

典型 Java 后端至少有三个环境；CI/CD 负责按规则自动推进，而非每次手工 SSH 传 JAR。

环境用途部署方式数据来源
DEV开发者自测本地 docker compose 或 SkaffoldMock / 本地 DB
SIT系统集成测试CI 自动部署（main 合并后）测试库快照
UAT业务验收CI 手动触发或定时脱敏生产数据
PROD生产CI when: manual + 变更审批生产库

环境变量与配置分离

同一镜像、不同配置——通过 K8s ConfigMap/Secret 或 Spring Profile 注入，不要把环境差异写进镜像：

# K8s Deployment 片段
env:
  - name: SPRING_PROFILES_ACTIVE
    value: "sit"
  - name: SPRING_DATASOURCE_URL
    valueFrom:
      secretKeyRef:
        name: fdc-db-sit
        key: url

回滚

部署失败时，用 GitLab Environment 或 kubectl 快速回滚到上一版本：

# 回滚到上一版本 Deployment
kubectl rollout undo deployment/fdc-webservice -n fdc-prod

# 或指定镜像 tag（推荐保留每次发布的 SHA tag）
kubectl set image deployment/fdc-webservice \
  fdc-webservice=registry.example.com/fdc/fdc-webservice:abc1234 -n fdc-prod

八、流水线优化与安全左移

1. 加速构建

  • Maven 缓存：cache.paths: [.m2/repository/]，配合私服 mirror
  • 并行 Job：静态检查与单元测试可放同一 stage 并行跑
  • Docker 分层：Spring Boot layers + 多阶段 Dockerfile，仅依赖变更时才重推大层（见第 13 章）
  • 按需触发：rules:changes 仅在 pom.xml 或 src/** 变更时跑完整流水线

2. 安全扫描接入 Pipeline

# 依赖漏洞扫描（OWASP Dependency-Check 示例）
dependency-check:
  stage: test
  image: maven:3.9-eclipse-temurin-21
  script:
    - mvn -B org.owasp:dependency-check-maven:check
  artifacts:
    paths: [target/dependency-check-report.html]
  allow_failure: true   # 初期可先告警不阻断，稳定后改为 false

# 镜像漏洞扫描（Trivy 示例）
trivy-scan:
  stage: deploy
  image: aquasec/trivy:latest
  script:
    - trivy image --severity HIGH,CRITICAL --exit-code 1 "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA"
  needs: [build-image]
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

安全扫描细节与 OWASP 实践见第 16 章。

3. 通知与可观测

  • Pipeline 失败 → 企业微信/钉钉 Webhook（GitLab → Settings → Integrations）
  • 部署成功 → Environment 页面记录版本与部署人
  • 上线后 → Actuator + Prometheus 监控（见第 19 章）

九、备选：GitHub Actions 简要示例

若项目托管在 GitHub，可用 .github/workflows/ci.yml 达到类似效果：

# .github/workflows/ci.yml
name: Java CI/CD

on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main, develop]

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          java-version: '21'
          distribution: 'temurin'
          cache: maven
      - run: mvn -B test

  docker-push:
    needs: build-and-test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: mvn -B package -DskipTests
      - uses: docker/build-push-action@v5
        with:
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}

概念与阶段设计与 GitLab 完全一致，仅语法不同。

十、故障排查与运维清单

常见问题

现象常见原因处理
GitLab 502启动未完成或内存不足docker logs gitlab；扩容至 8 GB+ 或调低 Sidekiq/Puma 并发
Pipeline 一直 pending无可用 Runner 或 tag 不匹配检查 Runner 在线状态与 Job 的 tags 是否一致
mvn 极慢未命中 cache / 未配 mirror确认 cache.paths；挂载 settings-ci.xml
docker build 失败Runner 未挂载 docker.sock调整 config.toml 的 volumes 与 privileged，或改用 Kaniko
MR 无法合并Pipeline 红 / 缺少 Review修测试或代码；请同事 Approve
部署后 Pod CrashLoop镜像 tag 错 / 配置缺失kubectl logs；对照第 13 章排障表

# 手动备份（数据无价，至少每日一次并异地同步）

0 3 * * * docker exec -t gitlab gitlab-backup create CRON=1

上线前 CI/CD 自检清单

  • main 分支已保护，禁止直接 Push
  • MR 必须 Pipeline 绿 + 至少 1 人 Review
  • 生产部署 Job 设为 when: manual
  • Maven 缓存与 mirror 已配置，Pipeline 耗时在可接受范围
  • 镜像使用 $CI_COMMIT_SHA tag，便于回滚
  • GitLab 备份 cron 已配置并验证恢复流程
  • 远程开发者通过 VPN 访问内网 GitLab，避免裸露公网

更多参考：GitLab CI/CD 官方文档。

十一、总结

本章的核心不是「了解 DevOps 文化」，而是亲手搭出一条能跑的 CI/CD 流水线：

  • 工程化提供规范与度量；DevOps让开发与运维同频；CI/CD把这一切自动化。
  • Java 后端流水线标准路径：编译 → 测试 → 打 JAR → 构建镜像 → 推仓库 → 部署 →（人工）上生产。
  • 质量门禁、分支保护、人工审批是「又快又稳」的三道保险——缺一不可。

把脏活累活交给流水线，团队才能把精力放在业务逻辑上。Maven/Docker/K8s 的构建与部署细节继续深入第 13 章。
