20 工程化·DevOps·CI/CD

把「提交 → 构建测试 → 打镜像 → 部署上线」自动化——流水线是工程化的落地引擎，不是运维文档里的装饰。

示例项目 fdc-webservice（Java 21 · Spring Boot 3.x · Maven 3.9+）。构建与 K8s 清单见第 13 章；测试门禁见第 17 章、第 18 章。

概念与链路

工程化 · DevOps · CI/CD

讲解

工程化：标准化、可度量的开发流程（分支规范、Commit 格式、覆盖率阈值）。DevOps：开发与运维协作，目标是高质量、高频率交付——开发者维护流水线配置，运维提供 Runner 与集群。CI/CD：DevOps 的核心引擎，代码提交后自动构建、测试、部署。DevOps 生命周期中，CI/CD 覆盖 Build → Deploy 段；Operate/Monitor 由可观测性体系统筹（见第 19 章）。

flowchart LR
    ENG[工程化
规范与度量] --> DEVOPS[DevOps
协作文化]
    DEVOPS --> CICD[CI/CD
自动化流水线]
    CICD --> VALUE[持续交付业务价值]

图：三者关系——CI/CD 是最终落地的自动化手段

速记

「工程化定规矩，DevOps 破部门墙，CI/CD 把规矩跑起来。」

流水线设计

CI 与两种 CD

讲解

CI（持续集成）：每次 Push/MR 触发，产出编译通过 + 测试通过。Continuous Delivery（持续交付）：合并主干后产出可部署制品，类生产环境自动部署，生产需人工审批——大多数 Java 后端采用此模式。Continuous Deployment（持续部署）：测试全过后自动上生产，适合测试覆盖极厚、发布频率极高的团队。Java 后端推荐阶段：静态检查 → compile → unit test → package → 安全扫描 → docker build → push registry → deploy SIT → 人工审批 → deploy PROD。

flowchart TD
    PUSH[Push / MR] --> LINT[静态检查]
    LINT --> BUILD[compile]
    BUILD --> TEST[unit test + 覆盖率]
    TEST --> PKG[mvn package]
    PKG --> SCAN[安全/依赖扫描]
    SCAN --> IMG[docker build]
    IMG --> REG[push registry]
    REG --> DEPLOY_SIT[deploy sit]
    DEPLOY_SIT --> APPROVE[人工审批]
    APPROVE --> DEPLOY_PROD[deploy prod]

图：Java 后端 CI/CD 推荐阶段

质量门禁

讲解

关键阶段设硬门槛，不合格则 Pipeline 失败、禁止合并 MR：静态检查无 Blocker（Checkstyle、SonarQube）；单元测试全通过且覆盖率 ≥ 阈值（JUnit 5 + JaCoCo）；依赖扫描无 Critical CVE（OWASP Dependency-Check）；镜像扫描无高危漏洞（Trivy）；MR 需 Pipeline 绿 + 至少 1 人 Review（Protected Branch）。

速记

「门禁不是拖慢发布，是用机器挡掉不该合并的代码。」

平台选型

GitLab / GitHub Actions / Jenkins

讲解

自建 GitLab CE：内网交付、代码不出域，CI + Registry + MR 一体化，本章主示例。GitHub Actions：开源项目首选，Marketplace 生态丰富，国内访问与私有仓库分钟数需评估。Jenkins：插件最全、DSL 灵活，但需单独维护 Master/Agent，配置分散。Gitee Go / 云效：国内中小企业、Gitee 托管场景。选型原则：代码托管与 CI 尽量同源，减少 Token 与权限对接成本。

GitLab CI/CD 实战

Runner 与 .gitlab-ci.yml

讲解

GitLab 可用 Docker Compose 部署（推荐 8 GB+ 内存），启用 Container Registry 供 CI 推镜像。Runner 是执行 Job 的代理，生产建议与 GitLab 分机；注册时选 docker executor，默认镜像 maven:3.9-eclipse-temurin-21，需 docker build 时挂载 docker.sock 或改用 Kaniko。.gitlab-ci.yml 放仓库根目录，用 stages 定义阶段，rules 控制触发（MR 只跑 build+test，main 才打镜像部署），cache.paths 缓存 .m2/repository/，when: manual 控制生产审批。

flowchart LR
    MR[MR / Push] --> BUILD[build]
    BUILD --> TEST[test]
    TEST --> PACKAGE[package]
    PACKAGE --> IMAGE[build-image]
    IMAGE --> SIT[deploy-sit]
    SIT --> PROD[deploy-prod
manual]

图：fdc-webservice GitLab 流水线

示例配置

# .gitlab-ci.yml（核心片段）
stages: [build, test, package, deploy]

variables:
  MAVEN_OPTS: "-Dmaven.repo.local=.m2/repository"

cache:
  key: "${CI_COMMIT_REF_SLUG}"
  paths: [.m2/repository/]

build:
  stage: build
  image: maven:3.9-eclipse-temurin-21
  script: [mvn -B compile -DskipTests]
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == "main" || $CI_COMMIT_BRANCH == "develop"

test:
  stage: test
  image: maven:3.9-eclipse-temurin-21
  script: [mvn -B test]
  artifacts:
    when: always
    reports:
      junit: [target/surefire-reports/TEST-*.xml]

package:
  stage: package
  image: maven:3.9-eclipse-temurin-21
  script: [mvn -B package -DskipTests]
  artifacts:
    paths: [target/*.jar]
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

build-image:
  stage: deploy
  image: docker:24
  services: [docker:24-dind]
  before_script:
    - docker login -u "$CI_REGISTRY_USER" -p "$CI_REGISTRY_PASSWORD" "$CI_REGISTRY"
  script:
    - docker build -t "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA" .
    - docker push "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA"
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
  needs: [package]

deploy-prod:
  stage: deploy
  image: bitnami/kubectl:latest
  script:
    - kubectl set image deployment/fdc-webservice \
        fdc-webservice="$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA" -n fdc-prod
    - kubectl rollout status deployment/fdc-webservice -n fdc-prod --timeout=180s
  when: manual
  needs: [build-image]
  environment:
    name: production

速记

「MR 跑验证，main 出制品；镜像打 SHA tag，生产必 manual。」

分支与环境

分支保护 · 多环境发布

讲解

推荐简化 Git Flow：feature/* → MR 到 develop（跑 build+test）；develop 集成测试；main 生产就绪（完整流水线）。main 设 Protected Branch：禁止直接 Push、Pipeline 必须绿、至少 1 人 Review。环境分层：DEV 本地自测 → SIT 系统集成（CI 自动） → UAT 业务验收（手动/定时） → PROD（when: manual + 变更审批）。同一镜像、不同配置——通过 K8s ConfigMap/Secret 或 Spring Profile 注入，不要把环境差异写进镜像。回滚用 kubectl rollout undo 或指定 SHA tag。

优化与安全左移

加速 · 扫描 · 通知

讲解

加速：Maven cache + 私服 mirror；静态检查与单测同 stage 并行；Spring Boot layers + 多阶段 Dockerfile；rules:changes 按需触发。安全左移：Pipeline 中接入 OWASP Dependency-Check（依赖 CVE）与 Trivy（镜像漏洞），初期可 allow_failure: true，稳定后改为阻断。细节见第 16 章。通知：Pipeline 失败 Webhook 到企微/钉钉；部署记录 GitLab Environments；上线后 Actuator + Prometheus 监控。

安全扫描 Job 示例

trivy-scan:
  stage: deploy
  image: aquasec/trivy:latest
  script:
    - trivy image --severity HIGH,CRITICAL --exit-code 1 "$CI_REGISTRY_IMAGE:$CI_COMMIT_SHA"
  needs: [build-image]
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

GitHub Actions 备选

讲解

项目托管 GitHub 时，阶段设计与 GitLab 一致，仅语法不同：.github/workflows/ci.yml 用 jobs + steps，actions/setup-java 自带 Maven cache，docker/build-push-action 推 GHCR。

示例

# .github/workflows/ci.yml（核心片段）
on:
  push: { branches: [main, develop] }
  pull_request: { branches: [main, develop] }

jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { java-version: '21', distribution: 'temurin', cache: maven }
      - run: mvn -B test

  docker-push:
    needs: build-and-test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: mvn -B package -DskipTests
      - uses: docker/build-push-action@v5
        with:
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
