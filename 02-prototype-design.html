02 原型设计 — 线框 · 交互 · Mock · 评审

需求基线（第 01 章用户故事与 AC）之后、第 03 章架构设计之前，用可感知、可点击、可 Mock的原型把「做什么」翻译成「长什么样、如何交互、调用什么接口」。本章聚焦 UI/交互/API Mock 与评审冻结；前后端契约见第 03 章 API 设计，排期见第 04 章。

原型设计总览

为何在需求与架构之间做原型

讲解

文字需求与Given-When-Then验收标准回答「对不对」，但干系人往往对界面与流程没有共同画面。原型设计在不写生产代码的前提下，低成本验证：信息架构是否合理、关键路径是否顺畅、异常态是否被看见、前后端边界是否清晰。对 Java 后端团队尤其重要——API Mock 原型让前端/移动端/联调方并行，架构师从原型反推聚合边界与 OpenAPI 草案。原型不是「美工稿」，而是需求澄清的第三媒介（文字 + 故事 + 可感知界面）。

阶段成果

  • 原型范围说明：覆盖的用户旅程、页面/模块清单、In/Out Scope（含不做的高保真页面）
  • 干系人确认纪要：参与角色、确认日期、未决项列表

关键/技巧

  • 按用户旅程而非按「系统菜单」组织原型，与故事地图对齐。
  • MVP 先覆盖主路径 + 3 个高频异常（空态、权限不足、提交失败）。
  • 原型阶段即标注「需后端字段/API」占位，避免架构阶段才发现缺口。

易错点

  • 跳过原型直接画架构图——集成接口与页面字段后期大面积返工。
  • 原型范围与需求基线不一致，评审时才发现漏 Story。

速记

「需求说 WHAT，原型显 HOW IT LOOKS，架构定 HOW TO BUILD。」

原型类型选型

线框 / 高保真 / 可点击 / API Mock / 技术 Spike

讲解

低保真线框：灰盒布局，验证 IA 与流程，1–2 天可出全站骨架。高保真视觉稿：品牌/组件规范，适合对外演示或设计系统沉淀。可点击原型（Figma Prototype / Axure）：模拟跳转与状态，用于 UAT 预演。API Mock 原型：REST 场景以 OpenAPI 为契约，GraphQL 场景以 Schema/SDL 为契约，再配合 Mock Server 实现前后端并行（见 #api-mock-prototype）。技术 Spike：throwaway 代码验证性能/第三方 SDK，不是 UI 原型，但可并行——结论写入 ADR 而非进主干。

flowchart TB
    Q{目标?}
    Q -->|对齐流程| WF[低保真线框]
    Q -->|品牌/组件| HI[高保真]
    Q -->|演示/UAT| CL[可点击原型]
    Q -->|前后端并行| API[API Mock]
    Q -->|技术风险| SP[Spike 代码]
    WF --> REV[评审冻结]
    CL --> REV
    API --> REV

图：按目标选择原型形态

阶段成果

  • 原型类型决策表：模块 × 类型 × 工具 × 负责人 × 截止日期
  • Spike 结论摘要（若有）：可行/不可行、推荐方案、预估工作量

关键/技巧

  • 内部 B 端后台：线框 + 可点击往往足够；C 端营销页才需高保真。
  • Mock 与线框同步：页面上每个「提交」按钮对应一条 API 路径草稿。

易错点

  • 一上来全站高保真——改需求时成本爆炸。
  • Spike 代码未标注 throwaway，被误合并进生产仓库。

速记

「线框定结构，Mock 定契约，Spike 证可行，高保真最后上。」

UI 原型工具与实践

Figma · Axure · 墨刀与交付规范

讲解

Figma：组件化 + Dev Mode，适合与设计系统、第 03 章 API 设计（Vue/React）协作；Prototype 链接触达移动端预览。Axure：复杂条件交互、动态面板，传统企业/政务常见。墨刀：国内协作与中文模板，中小团队上手快。无论工具，交付须含：页面清单（编号、路由、关联 Story ID）、交互说明（触发、校验、跳转、空态/错误态）、设计规范摘要（色板、字号、间距、组件命名与前端组件库映射）。

阶段成果

  • 页面清单表：P-001 登录页 → US-012；含 Web/移动端变体
  • 交互说明文档：按页面附状态机或流程备注
  • 设计规范 v0：Token/组件与 Element Plus、Ant Design 等映射表

页面清单片段

P-003 | 订单列表 | /orders | US-045, US-046
交互：筛选区折叠；空态引导创建；行内「取消」二次确认
API 占位：GET /api/v1/orders, POST .../cancel

关键/技巧

  • 组件命名与前端一致（如 OrderStatusTag），减少翻译损耗。
  • 异常态每页至少一帧：加载中、无数据、无权限、网络错误。

易错点

  • 只有 happy path 原型，测试验收时补异常 UI 导致延期。
  • 设计稿分辨率与目标端不一致（PC 稿硬套小程序）。

速记

「清单连 Story，交互写状态，规范对组件。」

AI 生成原型页面 — Prompt · 工具 · 落地流程

v0 · Bolt · Cursor Canvas · Figma AI · 落地工作流

讲解

在已有用户故事与验收标准（AC）基线上，用生成式 AI 从文字需求快速产出可感知页面——线框级布局、Landing 营销页、后台 CRUD 列表/表单、Dashboard 骨架。适用场景：需求评审前「先看见」、MVP 范围对齐、前端尚未到位时后端/产品自证流程。AI 原型不替代 Figma 高保真与设计系统沉淀，而是与传统原型工具分工：AI 出速度，Figma/墨刀出规范与组件一致性。

常用工具：v0.dev（Vercel，React/shadcn 输出）、Bolt.new（全栈沙箱，可运行预览）、Cursor + Canvas（在仓库内快速产出 HTML/React 原型稿）、Figma AI / Galileo AI（设计稿生成）、国内 即时设计 AI、MasterGo AI 等（中文模板与协作）。选型看：是否需可运行代码、是否对接现有组件库、团队是否以设计稿为单一事实源。

Prompt 要点：① 角色（B 端产品经理 + 前端架构师）；② 页面类型（列表+筛选+分页 / 分步表单 / Landing）；③ 组件库（Ant Design / Element Plus / shadcn）；④ 交互说明（提交校验、空态、权限不足、加载中）；⑤ 响应式（≥1280 桌面 / 375 移动）；⑥ 输出格式（纯 HTML、React TSX、Vue SFC）。附 Story ID 与字段清单，减少幻觉字段。

工作流：需求/Story → AI 生成初稿 → 人工评审（产品/设计/前端/后端）→ 导入 Figma 精修或保留为开发参考 → 标注 API 占位 → 与 API Mock 对齐 → 评审冻结。与第 22 章 AI 辅助开发分工：本章 = 业务原型（What it looks like）；第 22 章 = 写生产代码、测试、Review（How to implement）。

Java 团队视角：AI 页面作前端布局与字段参考，接口契约仍由后端 Tech Lead 主导——REST 使用 OpenAPI、GraphQL 使用 Schema；从页面操作反推资源与数据结构，Mock 与 SpringDoc/OpenAPI 文档对齐，避免「AI 臆造接口」直接进实现。生成物标注 throwaway，不进生产主干。

风险与治理：幻觉布局/字段、无障碍（a11y）缺失、与设计系统 Token 不一致、训练数据版权争议。必须坚持 Human-in-the-loop（人工在环）：每条 Story 至少一人签字确认界面与 AC 一致后方可冻结。

flowchart LR
    STORY[01 用户故事 + AC] --> PROMPT[Prompt 工程]
    PROMPT --> AI[v0 / Bolt / Cursor]
    AI --> DRAFT[AI 原型初稿]
    DRAFT --> REV{人工评审}
    REV -->|通过| FIG[Figma 精修 或 开发参考]
    REV -->|驳回| PROMPT
    FIG --> MOCK[API Mock 对齐]
    MOCK --> FREEZE[评审冻结 v1.0]

图：AI 原型生成 → 人工评审 → Mock → 冻结

阶段成果

  • AI 原型包：页面链接/源码、关联 Story ID、Prompt 存档（可复现）
  • Prompt 记录：可复用模板 + 本次约束（组件库、断点、输出格式）
  • 评审差异清单：AI 稿 vs 确认稿（布局/字段/交互）
  • API 占位表：每按钮/表单域 → 拟议 REST 路径（纳入 Mock 章节）

Prompt 片段示例

角色：资深 B 端产品经理 + Vue3 前端
页面：订单管理 CRUD 列表（US-045, US-046）
组件库：Element Plus；桌面端 1280px
功能：顶部筛选（状态/日期/关键词）；表格列：订单号、客户、金额、状态 Tag、操作（详情/取消）
交互：取消需二次确认；空态引导「创建订单」；加载 Skeleton
异常：无权限显示 403 占位；提交失败 Toast
输出：Vue 3 SFC + 假数据，不调用真实 API
字段仅使用：orderNo, customerName, amount, status(enum: PENDING/PAID/CANCELLED)

关键/技巧

  • 一次生成单页或单流程，比「整站」可控；多页用相同 Prompt 前缀保持风格一致。
  • Prompt 中白名单字段（仅允许列出的 JSON 键），显著降低幻觉列。
  • 生成后立即截屏 + 链入 RTM，与 GWT 场景并排，评审效率高于纯链接。
  • 需要可点击演示：Bolt/v0 预览 → 录屏 30s 走主路径，供远程干系人确认。

易错点

  • 把 AI 生成代码直接合并进生产仓库——缺少鉴权、i18n、错误边界与测试。
  • 未评审即冻结，开发按 AI 臆造字段写 DTO，与真实领域模型冲突。
  • 忽略 a11y 与键盘导航，后期合规/政务项目返工。
  • 混用多套 AI 工具且未统一组件库，视觉与交互碎片化。

速记

「Story 进 Prompt，AI 出草稿，人审再 Mock，契约后端定。」

API Mock 原型

Apifox · Postman · SpringDoc + WireMock

讲解

契约先行：由原型页面字段与操作反推资源模型。REST 场景在 Apifox/Postman 维护 OpenAPI 3.x，GraphQL 场景维护 Schema/SDL，并开启 Mock Server 返回示例 JSON。Java 侧：SpringDoc 从 Controller 生成 OpenAPI 文档，或先用 YAML 契约 + WireMock/Spring Cloud Contract 提供 Stub；前端通过环境变量切换 Mock Base URL 与真实 Spring Framework 应用服务。Mock 数据应覆盖分页、错误码（4xx/5xx）、幂等冲突等场景，而非永远 200。

sequenceDiagram
    participant UI as 前端原型
    participant Mock as Apifox/WireMock
    participant API as Spring Boot
    UI->>Mock: 开发期请求
    Mock-->>UI: 契约示例 JSON
    Note over Mock,API: 契约文档为单一事实源
    API->>Mock: 契约测试/对齐
    UI->>API: 联调期切换 Base URL

图：契约先行的 Mock → 实装切换

阶段成果

  • OpenAPI v0 草案：路径、Schema、错误模型、鉴权占位
  • Mock 环境说明：Base URL、场景切换、示例 curl
  • 契约变更日志：版本、Breaking 标记、影响页面清单

关键/技巧

  • 错误体统一结构（code/message/traceId），前端一次封装 Toast。
  • Mock 用例与 GWT 场景一一对应，便于后期自动化契约测试。

易错点

  • Mock 返回「过于完美」的数据，联调才发现字段 nullable、枚举不全。
  • 前后端各维护一份 API 文档，原型冻结后双份漂移。

速记

「OpenAPI 单源，Mock 带异常，联调只换 URL。」

原型评审与冻结

评审流程 · 签字冻结 · GWT 映射

讲解

原型评审参与方：产品、设计、前端、后端（Java）、测试、业务代表。议程：走主路径 → 过异常态 → 核对 API 清单 → 标记未决项。通过后签字冻结（版本号 + 日期），变更走 CR 与排期评估。每条GWT 验收场景应映射到：页面/交互帧 + Mock 用例 ID，写入 RTM 扩展列，供第 03 章架构与第 18–19 章测试追溯。

flowchart LR
    STORY[User Story + GWT] --> PAGE[原型页面 P-xxx]
    PAGE --> MOCK[Mock 用例 M-xxx]
    STORY --> RTM[RTM 追溯]
    PAGE --> RTM
    MOCK --> RTM
    RTM --> SIGN[签字冻结 v1.0]

图：Story → 原型 → Mock → RTM 映射

阶段成果

  • 原型评审纪要：结论、未决项、Action Owner
  • 冻结声明：版本、范围、变更流程
  • GWT–原型映射表：Story ID ? 页面 ? Mock ID

关键/技巧

  • 评审用「可点击链接 + 投影」，避免只发静态 PDF 无人点开。
  • 测试早期介入：按 GWT 在原型上标记「需自动化/需人工」。

易错点

  • 口头「差不多」未签字，开发中途需求仍当 bug 改。
  • GWT 与原型脱节，UAT 时才发现场景无对应界面。

速记

「评审走场景，冻结靠签字，GWT 三线对齐。」

原型结论回写架构

OpenAPI · ADR · 架构输入

讲解

原型冻结后，后端 Tech Lead 将结论回写至第 03 章 API 与集成设计：OpenAPI 升版、聚合边界调整（页面过度聚合提示拆分 Bounded Context）、异步/批量操作写 ADR。前端组件选型与第 03 章 API 设计对齐；复杂交互若影响性能（大列表、实时推送）在架构阶段提前标注 NFR。原型发现的集成点（支付、短信、OSS 上传）进入架构集成视图。

阶段成果

  • OpenAPI v1（自 v0 升级）：经架构评审的契约
  • 原型→架构差异清单：需 ADR 的决策项
  • 更新后的 RTM：Story → 原型 → API/模块

关键/技巧

  • 页面「跨模块」跳转往往是限界上下文集成信号，优先画在上下文图上。
  • Mock 已验证的枚举/分页参数直接进 Schema，减少架构会扯皮。

易错点

  • 原型冻结后不升 OpenAPI，开发各自理解字段含义。
  • 为凑页面把多个聚合塞进一个「万能 DTO」，破坏 DDD 边界。

速记

「原型出界面，架构出边界，OpenAPI 连两端。」

原型里程碑与变更控制

排期嵌入与 CR 流程

讲解

在第 04 章项目排期中，原型通常占 M1 需求冻结 与 M2 架构评审 之间的窗口：线框 3–5 天 → 可点击 + Mock 5–10 天 → 评审 1 天 → 冻结。WBS 单列「原型设计」工作包，含设计、前端、后端契约、评审。冻结后变更：提交 CR → 影响评估（页面/API/测试）→ 产品签字 → 更新版本号与 RTM；重大变更可触发「再评审」，避免静默改稿。

阶段成果

  • 原型里程碑：线框完成日、Mock 就绪日、评审日、冻结日
  • 变更记录：CR 编号、原型版本 diff、排期影响人日

关键/技巧

  • 与 M2 架构 Gate 绑定：无冻结原型，架构评审 No-Go。
  • 缓冲 20% 给「评审后小改」——集中在文案与布局，不动 API 语义。

易错点

  • 原型与开发并行且无冻结点，编码期持续改交互。
  • CR 只改文档不更新 Mock，前端与后端看到不同契约。

速记

「里程碑卡 Gate，变更走 CR，Mock 随版走。」

原型反模式

无限改稿 · 原型当交付 · 无验收标准

讲解

无限改稿：无冻结、无 CR，设计/产品持续微调像素，开发永远等「最终版」。原型当交付：把 Figma 链接当上线标准，缺少 API、权限、性能与可访问性验收。无验收标准：原型精美但与GWT无关，测试无法写用例。其他反模式：Mock 与实现长期双轨；Spike 代码进主干；跳过业务代表评审。

阶段成果

  • 反模式检查单：评审前自检，命中则不允许冻结
  • 健康度指标：冻结后 CR 次数、原型–实现差异 Bug 数

关键/技巧

  • 设「改稿预算」：冻结后仅允许 P0 缺陷级交互修正。
  • Definition of Done 含「与冻结原型 vX 一致或 CR 已批准」。

易错点

  • 用原型演示签单，合同验收却按需求文档——交付争议。
  • 追求动效细节，忽略 API 与权限模型——后端返工更大。

速记

「能冻结、能验收、能追溯——否则只是画图。」

无障碍（a11y）原型 Checklist

WCAG 基线与 B 端后台可访问性

讲解

政务/金融/出海项目常要求 WCAG 2.1 AA。原型评审须覆盖：对比度（文本/背景 ≥4.5:1）、键盘导航（Tab 顺序、焦点可见）、屏幕阅读器（表单 label、aria-label）、错误提示不仅靠颜色。B 端后台同样适用——运营人员也可能依赖辅助技术。

评审 Checklist

  • □ 所有表单控件有可见 label 或 aria-labelledby
  • □ 主按钮与背景对比度达标
  • □ 模态框可 Esc 关闭、焦点 trap
  • □ 状态不仅用红绿色区分（配图标/文案）
