15 项目代码生成器

面向自有 Spring Boot 多模块工程，概要如何设计与实现一套「表结构 → 分层代码 → 业务子模块」的项目级代码生成器。对照 RuoYi、JeecgBoot 等开源实现提炼可复用模式，而非仅使用现成菜单。建议先读第 12 章 Spring Framework（多模块结构）、第 11 章持久化、第 14 章 RuoYi（内置生成器能力概览）。

本章导读

企业后台大量模块是「一张表 + 标准 CRUD + 列表页」。手写重复代码成本高、风格易漂移。成熟脚手架（RuoYi、JeecgBoot）都内置元数据驱动 + 模板渲染的生成器；当团队需要统一包名、分层、注解、前端框架，或生成结果要直接落入自有 Maven 子模块时，应在项目内自建生成器模块。

阅读路径：

  1. 为何自建 → 开源对照 → 总体架构
  2. Maven 多模块落位 → 元数据采集 → 配置模型
  3. 模板引擎 → 模板设计 → 输出目录
  4. 生成服务 → RuoYi 实现要点 → JeecgBoot 差异
  5. 安全与治理 → 落地路线 → 实战清单

为什么要自建代码生成器

开箱即用的 RuoYi/Jeecg 生成器能快速出活，但常与固定目录、固定前端、固定基类绑定。以下场景更适合自建：

  • 已有模块化单体或 DDD 分层（domain / application / adapter），生成物须符合团队包结构与命名规范。
  • 多产品线共用父工程，需生成到 order-service、inventory-service 等不同子模块。
  • 要生成 MapStruct、Record DTO、Problem Details 异常、OpenAPI 注解等脚手架未覆盖的内容。
  • 生成逻辑需纳入 CI（仅允许生成到 generated/ 目录或 PR 审查门禁）。

自建目标不是「替代程序员」，而是固化 80% 重复结构，让人力集中在 20% 业务规则、事务与集成测试上。生成代码默认视为草稿，必须 Review 后合入主干。

RuoYi 将生成器独立为 ruoyi-generator 模块，与 ruoyi-system、ruoyi-admin 解耦——这是 Spring 多模块项目中值得直接借鉴的结构。

总体架构：四层流水线

无论界面是 Web 还是 CLI，内核都可拆为四层：

  1. 元数据层（Metadata）：从数据库或已保存配置读取表、列、主键、索引、注释。
  2. 领域模型层（Gen Model）：转换为 Java 类型、字段名（驼峰）、是否插入/编辑/列表展示、字典引用等。
  3. 模板层（Template）：按「单表 / 树表 / 主子表」选择模板集，填充上下文后渲染文本。
  4. 输出层（Writer）：写入磁盘或 ZIP；支持预览、差异对比、跳过已存在文件。

核心接口可定义为：TableMetadataLoader、CodegenConfigRepository、TemplateRenderer、GeneratedFilePublisher。便于单测时用内存元数据 + 固定模板验证输出快照。

Maven 多模块：生成器作为独立子模块

参考第 12 章父工程聚合方式，推荐在与业务平级增加 tools/codegen 或 xxx-generator 子模块，不要把生成器打进生产 Fat JAR（或仅在 dev Profile 引入）。

corp-platform/                    # 父 pom, packaging=pom
├── pom.xml
├── platform-common/              # 工具类、统一响应
├── platform-system/              # 系统域（用户、角色）
├── biz-order/                      # 业务域：订单（生成目标之一）
│   ├── order-api/
│   ├── order-service/
│   └── order-web/
├── platform-admin/               # 启动模块（聚合 web）
└── platform-generator/           # 代码生成器（仅 dev/test 依赖）
    ├── pom.xml
    └── src/main/
        ├── java/.../generator/
        └── resources/vm/         # Velocity 模板

父 pom 要点：

  • dependencyManagement 锁定 velocity-engine-core、mybatis-plus-generator（若复用）版本。
  • 生成器模块依赖 platform-common 以复用常量、基类信息；业务模块不反向依赖生成器。
  • 可用 maven-invoker-plugin 或独立 main 类在本地执行生成；CI 中通过 profile 触发。

生成到业务子模块时，在配置里写清绝对或基于仓库根的路径，例如：

# codegen.yml（示例）
output:
  moduleRoot: ${repoRoot}/biz-order/order-service
  javaDir: src/main/java
  packageBase: com.corp.order
  overwrite: false          # 默认不覆盖已存在文件
  paths:
    entity: domain/model
    mapper: infrastructure/persistence/mapper
    service: application/service
    controller: adapter/web

包路径与架构分层一致，避免生成器写死 com.ruoyi.system 式目录。

元数据采集

从数据库读取

常用两种方式：

  • JDBC DatabaseMetaData：getTables / getColumns，与数据库无关性好；注意 MySQL 的 REMARKS、PostgreSQL 的 comment 需额外 SQL。
  • 查询 information_schema：列注释、字符集、是否自增更直观；可过滤 table_schema 与表前缀（如 biz_%）。
// 列元数据示意（Java 21 record）
public record ColumnMeta(
    String columnName,
    String dataType,
    int columnSize,
    boolean nullable,
    boolean primaryKey,
    String comment,
    String javaType,
    String javaField
) {}

public List<ColumnMeta> loadColumns(DataSource ds, String table) throws SQLException {
  try (Connection c = ds.getConnection()) {
    DatabaseMetaData md = c.getMetaData();
    // 主键
    Set<String> pks = new HashSet<>();
    try (ResultSet pk = md.getPrimaryKeys(null, null, table)) {
      while (pk.next()) pks.add(pk.getString("COLUMN_NAME"));
    }
    List<ColumnMeta> list = new ArrayList<>();
    try (ResultSet rs = md.getColumns(null, null, table, null)) {
      while (rs.next()) {
        String col = rs.getString("COLUMN_NAME");
        list.add(new ColumnMeta(
            col,
            rs.getString("TYPE_NAME"),
            rs.getInt("COLUMN_SIZE"),
            rs.getInt("NULLABLE") == DatabaseMetaData.columnNullable,
            pks.contains(col),
            rs.getString("REMARKS"),
            mapJdbcToJava(rs.getString("TYPE_NAME")),
            toCamelCase(col)
        ));
      }
    }
    return list;
  }
}

类型映射

维护一张 jdbcType → javaType 映射表（BIGINT → Long、DECIMAL → BigDecimal、DATETIME → Instant 或 LocalDateTime）。团队统一时间类型，避免生成代码混用 Date 与 LocalDateTime。

配置模型与持久化（对标 RuoYi gen_table）

RuoYi 使用 gen_table、gen_table_column 保存「生成策略」：类名、模块名、作者、模板类型、是否树表、前端类型等。列级配置包括：是否在列表/表单/查询、显示类型（input/select）、字典类型。

自建时建议同样将「表级 + 列级」配置持久化，而不是每次从库表裸生成——否则无法表达「密码列不展示」「状态列用字典」等业务 UI 规则。

-- 表级（简化示例）
CREATE TABLE gen_table (
  table_id      BIGINT PRIMARY KEY,
  table_name    VARCHAR(200) NOT NULL,
  table_comment VARCHAR(500),
  class_name    VARCHAR(100),   -- Order
  module_name   VARCHAR(50),    -- order → 对应 biz-order
  package_name  VARCHAR(200),
  template_type VARCHAR(20),      -- crud / tree / sub
  gen_path      VARCHAR(500),   -- 输出根路径
  options       JSON            -- 扩展：是否生成前端、是否 Lombok
);

-- 列级
CREATE TABLE gen_table_column (
  column_id     BIGINT PRIMARY KEY,
  table_id      BIGINT NOT NULL,
  column_name   VARCHAR(200),
  java_field    VARCHAR(100),
  java_type     VARCHAR(50),
  is_pk         CHAR(1),
  is_insert     CHAR(1),
  is_edit       CHAR(1),
  is_list       CHAR(1),
  is_query      CHAR(1),
  query_type    VARCHAR(20),    -- EQ / LIKE / BETWEEN
  html_type     VARCHAR(20)     -- input / select / datetime
);

同步流程：用户选择物理表 → 导入列 → 在管理界面调整 → 保存配置 → 触发生成。与 RuoYi「导入表结构」菜单一致。

模板引擎选型

  • Apache Velocity：RuoYi 默认；语法 #if #foreach，学习成本低；Spring 生态示例多。
  • FreeMarker：Jeecg 常用；对空值、宏、国际化更友好；严格语法减少静默错误。
  • Mustache / Handlebars：逻辑更少，适合极简模板；复杂条件会吃力。

团队选定一种后，所有模板统一引擎。渲染时构造统一上下文对象 GenTableContext（含 table、columns、author、datetime、packagePrefix），避免在 Java 里拼接字符串。

// Velocity 渲染示意
Properties p = new Properties();
p.setProperty("resource.loader.file.class",
    "org.apache.velocity.runtime.resource.loader.ClasspathResourceLoader");
VelocityEngine engine = new VelocityEngine(p);
engine.init();

VelocityContext ctx = new VelocityContext();
ctx.put("table", genTable);
ctx.put("columns", columns);
ctx.put("importList", importList);

StringWriter sw = new StringWriter();
engine.getTemplate("vm/java/entity.java.vm", "UTF-8").merge(ctx, sw);
return sw.toString();

模板设计与变量约定

按产物类型拆分模板文件，而不是一个巨大模板：

  • entity.java.vm — 实体（JPA 或 MyBatis 注解）
  • mapper.java.vm / mapper.xml.vm
  • service.java.vm / serviceImpl.java.vm
  • controller.java.vm — REST + 校验 + 权限占位
  • api.ts.vm / index.vue.vm — 若团队使用 Vue

约定示例（表级变量）：

  • ${table.className} — Order
  • ${table.businessName} — 订单（注释）
  • ${table.moduleName} — order，用于 URL 前缀 /order
  • ${packageName} — com.corp.order.application

列级在 #foreach($column in $columns) 中判断 $column.isPk、$column.isList 生成字段与查询条件。权限注解可预留 @PreAuthorize("hasAuthority('${module}:${business}:list')")，与第 16 章 RBAC权限码对齐。

模板内避免复杂业务逻辑；超过三层的 #if 应上移到 Java 预计算（如 listColumns、formColumns 两个 List）。

输出到 Spring 业务子模块

典型一次生成会产出如下文件（以单表 CRUD、MyBatis-Plus 为例）：

biz-order/order-service/src/main/java/com/corp/order/
├── domain/model/Order.java
├── infrastructure/persistence/mapper/OrderMapper.java
├── infrastructure/persistence/mapper/OrderMapper.xml
├── application/service/OrderService.java
├── application/service/impl/OrderServiceImpl.java
└── adapter/web/OrderController.java

biz-order/order-web/src/main/frontend/src/views/order/
├── index.vue
└── api/order.js

Writer 策略：

  • overwrite=false：跳过已存在文件，并记录 skipped 列表（RuoYi 默认谨慎覆盖）。
  • overwrite=true：仅对标记为 @generated 的文件覆盖，或限定子目录 src/main/java/.../generated，人工代码与生成代码分离。
  • 提供 ZIP 下载 与 直接写盘 两种模式：生产环境禁用写盘，仅允许下载后在开发机合并。

生成后执行 mvn -pl biz-order/order-service compile 验证；Mapper XML 路径须与 mybatis.mapper-locations 一致。

生成服务与管理 API

若需要 Web 界面（对标 RuoYi 系统工具 → 代码生成），在 platform-admin 或独立 platform-generator 中暴露 REST：

  • GET /tool/gen/db/list — 可选物理表
  • POST /tool/gen/import — 导入到 gen_table
  • PUT /tool/gen/table — 保存列配置
  • GET /tool/gen/preview/{tableId} — 预览各模板渲染结果
  • POST /tool/gen/code/{tableId} — 写盘或返回 ZIP

权限：仅 ROLE_ADMIN 或 tool:gen:code；生产环境建议关闭写盘接口，或通过网络策略限制仅内网可达。操作记入审计日志（见第 16 章）。

CLI 形态适合 CI：java -jar platform-generator.jar --table=order --module=biz-order，参数与 DB 配置一致，便于流水线批量初始化新域模块骨架。

RuoYi 实现要点（可借鉴）

RuoYi-Vue 后端 ruoyi-generator 模块核心类与职责：

  • GenTableServiceImpl — 同步表结构、保存配置、调用生成。
  • GenUtils — 初始化 Velocity、组装 VelocityContext。
  • GenController — 管理端 API；生成结果打包 ByteArrayOutputStream 下载。
  • 模板目录 resources/vm/java、vm/xml、vm/vue。

生成流程：读取 GenTable + 列 → VelocityUtils.prepareContext → 遍历模板列表 → 每个模板 merge → 按包路径拼接目标文件名 → 写入或 ZIP。树表、主子表通过 tplCategory 切换不同模板子集。

若团队已用 RuoYi，可先 fork ruoyi-generator，只改模板与 GenUtils 中的路径解析，把输出根目录改为自家 biz-* 模块，再逐步剥离对 RuoYi 基类的依赖。深入使用见第 14 章代码生成；本章侧重脱离脚手架的通用实现。

JeecgBoot 差异说明

JeecgBoot 在「代码生成」之外强调在线表单、报表、流程，生成物常与低代码元数据绑定。其思路值得借鉴之处：

  • 表单配置与代码生成共用一份元数据，减少「页面改了、代码没同步」。
  • 支持一对多、ERP 风格主子表代码一次性生成。
  • 与 AutoPoi、Jimureport 等集成时，模板变量更丰富。

若项目不需要低代码平台，不必引入整套 Jeecg；可只参考其元数据表设计与FreeMarker 模板组织。标准 CRUD 后台以 RuoYi 式轻量生成器往往更易维护。

安全与工程治理

  • SQL 注入：元数据查询使用绑定参数；禁止把用户输入的表名直接拼进 SQL（白名单校验表名）。
  • 路径穿越：写盘前规范化路径，确保落在 moduleRoot 之下。
  • 密钥：生成器连接库账号只读即可同步结构；写盘服务用最小权限。
  • 代码审查：生成 PR 必须人工 Review；禁止生成代码直接进 release 分支无 diff。
  • 许可证：若基于 RuoYi/Jeecg 模板修改，保留其版权头或遵守对应开源协议。
  • 测试：对模板做快照测试（golden file），改模板时 CI 自动对比差异。

与第 18 章 TDD结合：生成 Service 后补领域规则单测，不依赖生成器自带的空测试壳。

渐进式落地路线

  1. 第 1 周：确定包结构与 1 张试点表；用 Velocity 生成 Entity + Mapper + XML，手工补 Service/Controller。
  2. 第 2–3 周：引入 gen_table 配置表与管理 API；支持预览与 ZIP 下载。
  3. 第 4 周：对接团队前端模板（Vue3 + Element Plus 等）；统一权限码与字典占位。
  4. 持续：按业务反馈增加模板变体（树表、只读审计表）；模板版本化（vm/v2/）。

与第 13 章构建部署衔接：新子模块 biz-xxx 可先由生成器初始化，再由 Maven 聚合进父 pom。

实战清单

  • □ 父工程已新增 platform-generator 模块，且生产包不依赖该模块。
  • □ 输出路径映射到目标 biz-* 子模块，包名符合架构规范。
  • □ JDBC 类型映射表与团队时间/金额类型一致。
  • □ gen_table / gen_column 可保存列级 UI 与查询策略。
  • □ 默认不覆盖已存在文件；生成操作有权限与审计。
  • □ 模板变更具备快照或回归测试。
  • □ 生成后 mvn compile 与基础接口冒烟通过，再提交 PR。
