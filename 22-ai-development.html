21 AI 辅助开发

AI 是杠杆，不是替身——高级开发者用 AI 放大判断力，而非替代判断。本章聚焦开发者如何用 AI 写代码（Prompt、Cursor、Harness、本地模型）；产品/架构如何在业务中融入 LLM 见第 22 章业务智能化。

Prompt 工程

结构化 Prompt 与角色设定

讲解

有效 Prompt 包含：角色、上下文、任务、约束、输出格式、验收标准。避免模糊动词（「优化一下」）；给出输入输出示例（few-shot）。复杂任务拆步：先设计接口签名，再实现，再补测试。引用具体文件路径与现有约定，减少幻觉。

flowchart TD
    ROLE[角色设定] --> CTX[上下文/文件引用]
    CTX --> TASK[明确任务]
    TASK --> CONSTRAINT[约束条件]
    CONSTRAINT --> FORMAT[输出格式]
    FORMAT --> ACCEPT[验收标准]
    ACCEPT --> LLM[LLM 生成]
    LLM --> REVIEW[人工审查]

图：结构化 Prompt 工程流程

示例 Prompt 模板

你是资深 Java 架构师，熟悉 Spring Boot 3 与本项目分层规范。

任务：为 OrderService.pay() 添加幂等保护。
约束：
- 使用现有 IdempotencyStore 接口，不引入新依赖
- 构造器注入，@Transactional 在 application 层
- 补充 JUnit5 + Mockito 单测

输出：
1. 变更文件列表
2. 完整代码（可编译）
3. 边界 case 说明

关键/技巧

  • 让 AI 「先列出计划，确认后再写代码」降低返工。
  • 指定「最小 diff，不改无关文件」控制范围。

AI 代码审查（AI Code Review）

让 AI 当第一轮 Reviewer

讲解

提交 PR 前先用 AI 审查 diff：并发安全、事务边界、N+1、空指针、日志敏感信息、测试覆盖缺口。要求 AI 按严重级别分级（blocker/suggestion/nit）并引用行号。人工审查聚焦架构与业务语义，AI 主要用于提前暴露低级缺陷。

示例 Prompt

Review 以下 git diff，关注：
1. 并发与事务正确性
2. SQL/JPA 性能（N+1、缺失索引提示）
3. 安全（注入、鉴权、PII 日志）
4. 测试是否覆盖新分支

格式：
| 级别 | 文件:行 | 问题 | 建议 |
仅输出有实质问题的项，不要泛泛 praise。

易错点

  • 盲信 AI 审查，不验证就合并——AI 会漏业务语义与领域约束错误。
  • 把整个 codebase 塞给 AI，噪音淹没 signal——优先提供 diff + 相关文件。

测试生成

从行为规格到测试用例

讲解

把 Given-When-Then 验收标准直接喂给 AI 生成 JUnit5 + AssertJ + Mockito 测试。指定命名规范、fixture 位置、禁止真实 DB。生成后人工审查：断言是否测行为而非实现、mock 是否过度。

示例代码

// AI 生成的测试骨架（需人工审查）
@ExtendWith(MockitoExtension.class)
class PayOrderUseCaseTest {
    @Test
    void shouldBeIdempotentWhenSameIdempotencyKey() {
        var cmd = new PayOrderCommand(orderId, "key-1", proof);
        when(store.tryAcquire("key-1")).thenReturn(true, false);

        handler.execute(cmd);
        handler.execute(cmd); // 第二次

        verify(gateway, times(1)).charge(any());
    }
}

关键/技巧

  • 先让 AI 列「应测场景清单」，确认后再批量生成。
  • Mutation test（PIT）验证测试有效性，非仅覆盖率数字。

安全边界

数据隐私与供应链风险

讲解

禁止将生产密钥、用户 PII、未脱敏日志粘贴给外部模型。企业环境应使用隐私模式（privacy mode）或本地模型处理敏感代码。AI 建议引入的依赖需人工审计（如 typosquatting 风险）。许可证合规同样需要人工把关：AI 输出可能混入受限许可证代码片段。可通过 Cursor Rules 与 .cursorignore 排除 secrets 目录。

示例配置

# .cursorignore
.env
*.pem
**/secrets/**
**/application-prod.yml

# .gitignore 同样排除，双重保险

易错点

  • 为 debug 把完整 JWT/DB 连接串贴进 chat。
  • AI 建议 curl | bash 或不明 Maven 依赖未验证就引入。

速记

「秘密不出库，依赖要 audit，输出当草稿必人工验。」

Cursor Agent 工作流

Agent 模式最佳实践

讲解

Cursor Agent 可跨文件读写、执行终端命令并调用 MCP。有效工作流：明确目标 → 限定范围（文件/模块）→ 分步验收 → 每步执行 git diff 人工审查。大重构先在 Plan 模式对齐方案，再进入 Agent 模式实施。用 Rules 固化项目约定（包结构、命名、测试风格）。

示例工作流

1. @codebase 搜索现有 IdempotencyStore 实现
2. Agent 任务：
   「在 pay-order 用例接入幂等，仅改 application 层和测试」
3. 验收：
   - ./mvnw test -pl order-application
   - 人工看 diff 事务边界
4. 小步 commit（或 PR 一个 logical change）

关键/技巧

  • 复杂任务拆多个 Agent session，每 session 单一目标。
  • 用 @file 精确引用，减少 AI 猜路径。
  • CI 红时把失败日志贴给 Agent，比描述现象高效。

Hermes：会自我进化的 AI Agent

概述

在 AI 领域，Hermes（现通常指 Nous Research 在 2026 年推出的 Hermes-Agent）是一个标志性的开源 AI 智能体系统。它之所以引发轰动，是因为它打破了传统 Agent「只能执行、无法成长」的局限。

1. 核心特点：闭环学习（Learning Loop）

传统的 AI Agent（如早期的 AutoGPT）每次启动都是「失忆」的，做完任务就结束了。而 Hermes 拥有一个内置的自我改进闭环：

  • 经验转化为技能（Skills）：当 Hermes 独立完成一项复杂的任务后，它会自动把这次的成功经验沉淀、重构为一段「技能代码」（Skill）。
  • 越用越聪明：在后续的任务中，它会直接调用自己之前创造的技能，并在使用过程中不断优化这些技能。
  • 长期记忆与用户建模：它能跨会话检索自己过去的对话和行为，随着时间推移，它会越来越理解宿主（用户）的工作习惯。
flowchart LR
    T[复杂任务完成] --> S[沉淀为 Skill]
    S --> R[后续任务复用]
    R --> O[持续优化 Skill]
    M[跨会话记忆] --> U[用户习惯建模]

图：Hermes 闭环学习（Learning Loop）

2. 极低的运行门槛与泛用性

Hermes 可以在价格极低的云服务器（VPS）上全天候自主运行。它不依赖单一的大模型，你可以随意把底座切换为 OpenAI、Anthropic、或开源的各家模型，而它通过 Telegram、Discord 或命令行就能与人类保持连接。

快速上手实战：下命令、攒技能、挂后台、防拆家

快速上手并用好 Hermes Agent，可以将其核心实战流程简要概括为「下命令、攒技能、挂后台、防拆家」四个要点：

1. 极简安装与配置

  • 安装：终端运行官方一键脚本：
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash
  • 大脑配置：输入 hermes setup，绑定大模型 API Key（推荐支持提示词缓存的 Claude 3.5 Sonnet，或使用本地 Ollama 开源模型）。

2. 闭环学习：边用边「长脑子」

  • 下达复杂指令：直接让它处理涉及网页爬取、数据分析或代码编写的复杂长流程任务。
  • 技能自动沉淀：任务成功后，Hermes 会触发 Learning Loop，自动将成功经验抽象、重构并保存在本地，转化为一个可复用的永久技能（Skill）。
  • 下次直接调用：之后处理类似任务时，它会跳过摸索阶段，像熟练工一样直接调用该技能。

3. 多平台「挂机」当数字雇员

  • 配置网关：运行 hermes gateway setup，绑定你的 Telegram、Discord 或 Slack。
  • 后台全天候运行：启动后，你无需盯着电脑终端。随时随地在手机 Telegram 上给它发任务，它在后台做完后会自动向你汇报。它还支持定时任务（Cron），可以变成你的每日早报或自动化备份管家。

4. 筑好沙盒防火墙（防拆家）

  • 沙盒隔离：由于 Hermes 具备直接在终端执行代码和 Bash 命令的强力权限，部署时务必将其运行环境挂载在 Docker 或 Modal 等隔离沙盒中。
  • 权限管控：开启命令审批（ACP），高危操作（如修改系统文件）必须在手机上得到你的点击确认，确保 Agent 永远在「马具（Harness）」的约束下安全行驶。详见本章 Harness Engineering。

速记

「下命令、攒技能、挂后台、防拆家 —— Hermes = 任务经验沉淀为 Skill + 跨会话记忆；低门槛 VPS 常驻，模型与通道可换，沙盒 + ACP 必开。」

Harness Engineering — AI 执行约束与评估框架

为 Agent 构建可控、可测、可复现的执行 Harness

讲解

Harness（执行约束框架）指包裹 LLM/Agent 的执行环境：不仅是一次性 Prompt，而是工具边界 + 上下文策略 + 输出契约 + 评估回路 + 人工审批的组合。裸 Prompt 容易让模型无约束扩写；Harness 让行为可预测、可审计、可回归。

Java 团队尤其需要 Harness：编译/测试/静态分析是硬 gate；金融/政务要求变更可追溯；多模块 monorepo 里 Agent 误改 pom.xml、事务边界或密钥文件代价极高。Harness 把「AI 当实习生」变成「AI 在受控流水线里干活」。

核心组件（可分层落地）：

  • 工具白名单：允许读写的路径 glob、禁止 git push --force / 改 .git/config、Shell 仅 mvnw test 等安全子集；MCP 按 server 开关（如只允许 cursor-ide-browser 读、禁止未授权云 API）。
  • 上下文策略：repo map / @file 精准引用、.cursorignore 排除 secrets；按 token 预算裁剪（当前 task 相关模块优先，而非整库 dump）。
  • 输出约束：最小 diff、禁止无关文件、生成代码必须附带测试、Schema 化输出（JSON 变更清单）便于机器校验。
  • 评测与回归（Eval）：维护 golden prompt 集（固定输入 → 期望 diff 模式或测试通过）；快照对比 Agent 输出；CI 跑「AI 辅助检查」脚本（可配置为非阻断或分级阻断）。
  • Human-in-the-loop：危险操作（删库迁移、改生产配置）需显式确认；PR 必须人工批准；Agent 不得自行合并。

与 Cursor Agent 工作流、Prompt 工程 的关系：Prompt 定义单次意图，Agent 提供多步执行能力，Harness 定义允许做什么、如何验收、失败如何停。详见下文 Java 实践，安全与密钥边界交叉引用本章 安全边界。

flowchart TB
    AGENT[AI Agent] --> HAR[Harness 约束层]
    HAR --> TOOLS[工具白名单 MCP/Shell]
    HAR --> CTX[上下文/输出 Schema]
    HAR --> EVAL[Eval 回归集]
    EVAL --> GATE{通过?}
    GATE -->|否| HITL[Human-in-the-loop]
    GATE -->|是| MERGE[允许合并/发布]

图：Agent Harness 执行约束与评估框架

示例：Cursor Rules 作为 Harness 配置

# .cursor/rules/java-agent-harness.mdc
---
description: Java 服务 Agent 执行约束
globs: ["**/*.java", "**/pom.xml"]
---

## 工具与变更范围
- 仅修改任务列出的模块；禁止改 .git/config、CI 密钥、application-prod.yml
- 不执行 git push、git reset --hard；commit 仅当用户明确要求

## 输出契约
- 先列变更文件清单，再写代码
- 必须运行 ./mvnw -pl <module> test 并通过后再声称完成
- 构造器注入；@Transactional 在 application 层（与项目 ADR 一致）

## 失败处理
- 测试失败：贴完整 surefire 日志，最多重试修复 2 轮后停止并汇报

示例：pre-commit + CI Gate（伪流程）

# .pre-commit-config.yaml（片段）
repos:
  - repo: local
    hooks:
      - id: mvn-compile-test
        name: compile and unit test
        entry: ./mvnw -q -DskipITs test
        language: system
        pass_filenames: false
      - id: spotbugs
        entry: ./mvnw -q spotbugs:check
        language: system
        pass_filenames: false

# .github/workflows/ai-assisted-pr.yml（伪流程）
on: pull_request
jobs:
  java-gates:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: ./mvnw -B verify
      - run: ./mvnw -q spotbugs:check
  # 可选：对 PR diff 调本地 Review 服务，结果 comment 到 PR（失败不 merge 阻断，由 label 控制）
  ai-review-hint:
    if: contains(github.event.pull_request.labels.*.name, 'ai-generated')
    steps:
      - run: curl -s localhost:11434/v1/chat/completions ... # 见 gemma-local-deploy
      - run: echo "AI review 仅供参考，blocker 须人工确认"

示例：AGENTS.md 与 golden prompt 回归思路

# AGENTS.md（仓库根，给 Cursor / SDK Agent 读）
## 构建
./mvnw test -pl order-application

## Harness
- 幂等改造见 docs/adr/005-idempotency.md
- 禁止引入新 Maven 依赖未经架构组 label

# evals/golden/idempotency-pay.prompt   （固定输入）
# evals/expected/                       （期望：测试绿 + 无 gateway 双调）
# 定期脚本：对 golden prompt 跑 Agent/SDK，diff 与期望目录对比或只断言 mvn test

关键/技巧

  • 把重复约束写进 Rules/AGENTS.md，把单次任务留在 chat Prompt——避免每轮重复长篇规范。
  • Harness 分层：IDE Rules（软）→ pre-commit（本地硬）→ CI verify（团队硬）→ 人工 Review（最终）。
  • 为高频 Agent 任务维护 5–10 条 golden prompt，发版前跑一轮防回归。
  • 危险 Shell 用「建议命令 + 用户确认」而非 Agent 静默执行。

易错点

  • 只有 Prompt 没有 gate——AI 生成「能编译但破坏事务/幂等」的代码照样 merge。
  • Harness 过严（禁止一切 Shell）导致 Agent 无法跑测试，人又懒得代跑——形同虚设。
  • 把 eval 当绝对真理——golden 过期未更新会导致误杀合理重构。
  • 本地模型 Review 阻断 merge 却无人看 false positive——应分级为 suggestion。

速记

「白名单工具、精准上下文、diff+测试契约、golden 回归、人审危险操作；Rules 配置，CI 兜底。」

延伸阅读：Anthropic《Building effective agents》、Promptfoo / Braintrust 的评测实践、Accelerate 中「质量门禁」思想

本地开源大模型选用

Gemma / Llama / Qwen / DeepSeek 选型与部署方式概览

讲解

当代码含业务逻辑、未脱敏日志或内网架构时，本地开源模型比公有云 API 更可控（见本章「安全边界」）。主流家族简要对比：

  • Gemma（Google）：采用 Gemma 专用许可条款（非 Apache License）；英文与代码能力强，9B/27B 适合审查与补全；Gemma 3 支持更长上下文与多模态（图像理解）。
  • Llama（Meta）：生态最大，Ollama/HuggingFace 模型最全；Llama 3.x 推理与工具调用成熟，许可需遵守 Acceptable Use Policy。
  • Qwen（阿里）：中文与 Java/Spring 语境表现突出，Coder 系列专精代码；企业内中文文档、注释、PR 描述场景首选之一。
  • DeepSeek：代码与数学推理性价比高，R1 系列偏深度推理；许可相对宽松，适合离线 Code Review 辅助。

选型维度（Java 开发场景）：

  • 参数量 vs 显存：7B–9B Q4 量化约需 6–8 GB VRAM；27B 约 16–20 GB；无独显可用 CPU + 大内存（慢但可离线）。
  • 中文能力：中文需求高选 Qwen；纯英文代码库 Gemma/Llama 足够。
  • 许可证：商用前阅读 Gemma Terms、Llama License 与模型卡（Model Card）；不同家族对再分发、品牌使用与可接受用途（AUP）限制不同，需逐项核对。
  • 场景映射：代码补全 → 7B–9B Coder；PR 审查 → 9B–27B + 长上下文；私有数据问答 → 本地 RAG + 任意 7B+。

部署方式概览：

  • Ollama（推荐入门）：一键 pull/run，自带 OpenAI 兼容 API，Windows/macOS/Linux。
  • llama.cpp：极致 CPU/边缘推理，无守护进程，适合嵌入式或脚本化。
  • vLLM：生产级 GPU 吞吐，多并发 REST，适合团队内共享推理服务。
  • LM Studio：Windows/macOS GUI，适合非 CLI 用户试模型与调参。

显存粗算（Q4 量化）

模型参数量    约需 VRAM（推理）    典型用途
─────────────────────────────────────────────
2B–4B         2–4 GB              轻量补全、笔记本 CPU 可跑
7B–9B         6–8 GB              日常 Code Review / Agent
12B–14B       10–12 GB            平衡质量与速度
27B+          16–24 GB            复杂重构、长 diff 分析

关键/技巧

  • 先在小模型（7B–9B）验证 Prompt 与流程，满意后再换大模型——避免调 Prompt 烧显存。
  • Java 项目优先选代码专精权重（如 qwen2.5-coder、deepseek-coder、gemma2）。
  • 团队统一用 Ollama + 同一 tag，避免「我本地 9B 你本地 70B」输出不一致。

易错点

  • 只看 benchmark 分数不看实际上手——Java 泛型、Spring 注解等需实测。
  • 把 70B 全精度塞进 8 GB 显卡——OOM 或极慢；务必用量化（Q4_K_M 等）。
  • 本地模型≠绝对安全——仍可能幻觉；敏感逻辑必须人工审查（交叉引用本章「AI 代码审查」）。

速记

「中文 Qwen，代码 Gemma/DeepSeek，生态 Llama；Ollama 入门，vLLM 上生产。」

延伸阅读：Ollama 官方文档、Hugging Face Model Cards、Google Gemma 技术报告

Gemma 本地部署

Ollama 部署 Gemma 2/3 与 Java / Cursor 集成

讲解

Gemma 是 Google 发布的开源权重模型系列，当前主流：Gemma 2（2B / 9B / 27B，代码与推理较均衡）与 Gemma 3（1B / 4B / 12B / 27B，长上下文与多模态输入能力更强）。Java 开发场景可从 gemma2:9b 或 gemma3:12b 起步，再按延迟和质量逐步调参。

硬件要求：NVIDIA GPU 8 GB+ 体验更稳定；16 GB 系统内存可 CPU 推理（tokens/s 会明显下降）。Apple Silicon 可通过 Ollama 原生加速。无 GPU 时建议选 2B–4B 或高量化版本，并接受更高延迟。

隐私与离线优势：权重与推理可全部在本地执行，源码/配置/日志无需外发；适合金融、政务、内网 Maven 私服场景。即便如此，仍需用 .cursorignore 排除密钥文件并做好主机侧访问控制——本地部署不等于自动合规。

示例：Ollama 安装与拉取（Windows / Linux）

# Windows（PowerShell）— 官网安装包或 winget
winget install Ollama.Ollama
# 安装后托盘启动服务，默认监听 http://localhost:11434

# Linux
curl -fsSL https://ollama.com/install.sh | sh

# 拉取并交互测试
ollama pull gemma2:9b
ollama run gemma2:9b
# 或 Gemma 3（需 Ollama 已收录对应 tag）
ollama pull gemma3:12b

# 列出本地模型
ollama list

示例：Docker 运行 Ollama（可选，Linux 服务器）

# 需 NVIDIA Container Toolkit（GPU 版）
docker run -d --gpus=all -v ollama:/root/.ollama -p 11434:11434 \
  --name ollama ollama/ollama

docker exec -it ollama ollama pull gemma2:9b

# Windows Docker Desktop：去掉 --gpus 则走 CPU（慢）
docker run -d -v ollama:/root/.ollama -p 11434:11434 --name ollama ollama/ollama

示例：REST API 与 OpenAI 兼容端点

# 原生 Ollama API（PowerShell / curl）
curl http://localhost:11434/api/generate -d "{
  \"model\": \"gemma2:9b\",
  \"prompt\": \"Review 这段 Java 代码的 N+1 风险：@Transactional public void save(Order o) {...}\",
  \"stream\": false
}"

# OpenAI 兼容（/v1）— Cursor / Spring AI 均可用
curl http://localhost:11434/v1/chat/completions ^
  -H "Content-Type: application/json" ^
  -d "{\"model\":\"gemma2:9b\",\"messages\":[{\"role\":\"user\",\"content\":\"解释 Spring @Transactional 传播行为\"}]}"

# Linux/macOS 将 ^ 换为 \

示例：Java 调用（WebClient + Spring AI）

// 方式 1 — WebClient 直连 Ollama OpenAI 兼容端点
@Configuration
public class LocalLlmConfig {
  @Bean
  WebClient ollamaClient() {
    return WebClient.builder()
        .baseUrl("http://localhost:11434/v1")
        .defaultHeader(HttpHeaders.CONTENT_TYPE, MediaType.APPLICATION_JSON_VALUE)
        .build();
  }
}

@Service
public class CodeReviewAssistant {
  private final WebClient ollama;

  public CodeReviewAssistant(WebClient ollamaClient) { this.ollama = ollamaClient; }

  public String reviewDiff(String diff) {
    var body = Map.of(
        "model", "gemma2:9b",
        "messages", List.of(Map.of(
            "role", "user",
            "content", "你是 Java Reviewer，仅输出 blocker 级问题：\n" + diff)));
    return ollama.post()
        .uri("/chat/completions")
        .bodyValue(body)
        .retrieve()
        .bodyToMono(JsonNode.class)
        .map(json -> json.path("choices").get(0).path("message").path("content").asText())
        .block();
  }
}

关键/技巧

  • OLLAMA_HOST=0.0.0.0:11434 可让局域网同事共用——务必防火墙限制，勿暴露公网。
  • 长 diff Review 用 Gemma 3 长上下文；单次 Prompt 仍控制在关键文件，避免噪音。
  • ollama ps 查看加载模型；闲置后自动卸载可省 VRAM。
  • 与 CI 集成：MR 阶段调用本地 HTTP 服务做 lint 级 Review，失败不阻断 merge，仅注释建议。

易错点

  • Cursor Base URL 漏写 /v1 或模型名与 ollama list 不一致——报 404 / model not found。
  • Windows 防火墙拦截 11434——本机 curl 通但 IDE 不通，检查规则。
  • Docker 未挂载 GPU 却拉 27B——容器内 CPU 推理极慢，误以为「模型坏了」。
  • 把 Gemma 当最终 Authority merge——幻觉与漏检仍存在，人工 Review 不可省。

速记

「ollama pull gemma2:9b，API 走 localhost:11434/v1，Cursor 改 Base URL，Java 用 WebClient 或 Spring AI。」

上下文管理

Token 预算与知识沉淀

讲解

上下文窗口有限：优先给当前任务相关文件，而非整个 monorepo。重复性知识写入 Cursor Rules / Skills / ADR，而非每次会话重复粘贴。长会话后期 AI 容易遗忘早期约束——关键约束应写入 Rule 或每轮简要 recap。

关键/技巧

  • 项目级 Rule：「Spring 服务用构造器注入」「事务在 application 层」。
  • 模块 README 给 Agent 当 local context，@ 引用即可。
  • 新 feature 开新 chat，避免历史噪音。

速记

「Rule 存惯例，@ 给精准上下文，大任务拆 session。」

章末实战闭环

AI辅助开发落地清单

输入

  • 开发任务边界与安全约束
  • 代码规范、Rule、Harness 配置
  • 可用模型能力与成本预算
  • 人工评审与责任归属机制

输出

  • 可复用 Prompt/Agent 工作流模板
  • AI 生成代码审查与测试报告
  • 模型效果评估与风险清单

验收标准

  • AI 输出均经过人工审查签字
  • 关键改动有自动化测试兜底
  • 敏感数据不外流并可审计

失败信号

  • 将 AI 输出直接视为真理
  • 缺少 Harness 导致行为失控
  • 模型切换后无回归评估
